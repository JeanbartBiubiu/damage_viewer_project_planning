# WASM 护盾机制与跨游戏规则概要设计（V1 草案）

## 1. 目标

本文补充 WASM 在“护盾实例、护盾吸收、护盾过期、跨游戏护盾规则切换”上的统一设计，解决以下场景：

- 技能或装备可给单位施加通用护盾、物理护盾、魔法护盾等不同护盾。
- 同一单位可同时持有多个护盾，存在刷新、叠加、独立实例、优先级消耗等差异。
- 不同游戏对“真伤 / 纯粹伤害是否穿盾、不同伤害类型是否命中特定护盾”的规则不同。
- 护盾可能被伤害打破、自然过期、被主动移除，且三者触发事件不同。

设计目标：

- 不把护盾写死为 LoL 特判，而是通过“护盾定义 + 交互矩阵”驱动。
- 不把护盾当作一个普通属性值，而是建模为独立运行时实例。
- 与既有 `damage / heal / modifier / shield` 四通道方案对齐。
- 在 1v1 纯伤害模拟范围内，优先解决“护盾定义”“伤害穿盾规则”“生命周期事件”问题。

---

## 2. 结论先行

### 2.1 本文设计结论

- 护盾不应只建模成 `combatant.stats.shield` 这类单一数值。
- 推荐新增 `shield_profiles`，定义“这个护盾是什么”。
- 推荐在 `combat_rule_profiles` 中新增 `shieldInteraction`，定义“伤害如何与护盾交互”。
- 引擎运行时要新增 `ShieldInstance` 与 `DamagePacket`。
- `mechanics_config` 要补：
  - `apply_shield`
  - `remove_shield`
  - `on_shield_gain`
  - `on_shield_break`
  - `on_shield_expire`

### 2.2 为什么不只靠技能 JSON 临时写

如果只在技能配置里临时写护盾参数，会很快遇到这些问题：

- 同一种护盾在不同技能里重复定义，难以复用。
- 护盾的吸收规则实际是“全局战斗规则”，不属于单个技能。
- 当切换到第二款游戏时，最容易变化的是“穿盾规则”，不是护盾数值本身。

因此建议拆成两层：

- `shield_profiles`：护盾定义层
- `combat_rule_profiles.shieldInteraction`：护盾交互规则层

## 3. 设计原则

### 3.1 护盾是“运行时实例”，不是“一个属性值”

护盾和攻击力、生命值不同：

- 它会被伤害逐步消耗。
- 它可能被打破，也可能自然过期。
- 同一单位可以同时持有多层护盾。
- 不同护盾之间存在消耗顺序。

因此更适合建模为若干 `ShieldInstance`，而不是一个 `shieldValue` 数字。

### 3.2 护盾不是状态，但可以由状态或技能产生

护盾与 `status` 的区别在于：

- `status` 更适合描述“持续语义”和“动作约束”。
- `shield` 更适合描述“可被伤害消耗的资源实例”。

两者可以关联，但不应混为一种模型：

- 一个状态可以在 `on_gain` 时生成护盾。
- 一个技能也可以直接 `apply_shield`。
- 护盾本体仍应由 `ShieldInstance` 管理。

### 3.3 护盾定义与护盾交互规则分离

“这个护盾是什么”和“伤害如何打这个护盾”是两件事：

- `shield_profiles` 回答：
  - 护盾 scope 是什么
  - 护盾如何叠加
  - 默认持续时间是多少
  - 默认优先级是多少
- `combat_rule_profiles.shieldInteraction` 回答：
  - 物理伤害是否打魔法盾
  - 真伤是否打通用盾
  - 多层护盾如何排序消耗

### 3.4 护盾吸收只处理“减伤后的伤害”

护盾吸收必须发生在：

1. 公式计算之后
2. 增减伤修正之后
3. 穿透 / 抗性结算之后
4. HP 扣减之前

否则会重复计算减伤或出现跨游戏规则冲突。

### 3.5 免伤 / 无敌检查在护盾之前

若目标存在 `invulnerable / stasis` 等效果：

- 伤害应先被拦截
- 护盾不应被错误消耗

因此护盾吸收不是伤害管线的第一道检查，而是“目标可受伤”前提成立后的步骤。

### 3.6 跨游戏差异放在规则层，不放在核心引擎代码里

示例：

- LoL：物理伤害不打魔法盾，魔法伤害不打物理盾，真伤通常只打通用盾
- Dota 风格：Pure 伤害可无视护盾
- 王者风格：真实伤害可直接穿盾

这些都应通过规则矩阵切换，而不是改引擎代码。

## 4. 运行时模型补充

## 4.1 `RuntimeState` 新增护盾容器

推荐把护盾挂在单位运行时对象上：

```ts
type CombatantRuntime = {
  attrs: Record<string, number>
  hp: number
  resource?: number
  shields: ShieldInstance[]
}
```

说明：

- 护盾天然属于持有者，因此挂在 `combatants[id]` 下更直观。
- `shields` 应保持稳定顺序，避免同输入下结果抖动。

### 4.1.1 `ShieldInstance`

```ts
type ShieldInstance = {
  instanceId: string
  shieldId?: string
  shieldKey: string
  sourceId: string
  ownerId: string
  amount: number
  maxAmount: number
  scope: ShieldScope
  priority: number
  createdAtMs: number
  expireAtMs: number | null
  tags: string[]
  stackCount?: number
}
```

字段语义：

- `shieldId`：来源于 `shield_profiles` 的模板 ID，可选
- `shieldKey`：运行时归并 key，用于刷新 / 叠加 / 覆盖判断
- `scope`：这个护盾能吸收什么伤害
- `priority`：多层护盾的消耗顺序

### 4.1.2 `DamagePacket`

```ts
type DamagePacket = {
  packetId: string
  sourceId: string
  targetId: string
  damageType: string
  rawAmount: number
  postMitigationAmount: number
  tags: string[]
  flags?: {
    ignoreShield?: boolean
    ignoreArmor?: boolean
    ignoreResist?: boolean
  }
}
```

用途：

- 表示 damage 通道内部流转的标准伤害包
- 护盾吸收只读取 `postMitigationAmount`

## 5. 护盾定义层：`shield_profiles`

## 5.1 作用

`shield_profiles` 定义“这个护盾是什么”，类似于状态机制中的 `status_profiles`。

它适合承载：

- 护盾吸收范围
- 护盾叠加策略
- 默认持续时间
- 默认优先级
- 标签与移除策略

## 5.2 推荐字段

```ts
type ShieldProfile = {
  shieldId: string
  name?: string
  scope: ShieldScope
  tags?: string[]
  stacking?: {
    mode: "refresh" | "stack" | "independent"
    maxAmount?: number
  }
  durationPolicy?: {
    defaultDurationMs?: number
  }
  consumePolicy?: {
    priority?: number
  }
  removalPolicy?: {
    removable?: boolean
    removeTags?: string[]
  }
}

type ShieldScope =
  | "all"
  | "physical"
  | "magic"
  | { custom: string }
```

示例：

- `shield_generic_basic`
  - `scope = "all"`
  - `stacking.mode = "refresh"`
- `shield_magic_basic`
  - `scope = "magic"`
- `shield_physical_basic`
  - `scope = "physical"`
- `shield_damage_block_custom`
  - `scope = { custom: "damage_block" }`

## 5.3 为什么建议单独建表

如果护盾只存在于技能 JSON 内联参数里：

- 同一款游戏中大量“标准通用盾”无法复用
- 校验层无法统一约束 `scope / stacking / priority`
- 设计审查时很难看清“版本究竟改的是护盾定义，还是伤害交互规则”

因此建议新增：

```sql
CREATE TABLE public.shield_profiles (
    game_id varchar(64) NOT NULL,
    shield_id varchar(64) NOT NULL,
    start_version_id bigint NOT NULL,
    end_version_id bigint NOT NULL,
    shield_config jsonb NOT NULL DEFAULT '{}',
    description varchar(255),
    updated_at timestamp NOT NULL DEFAULT NOW(),
    CONSTRAINT pk_shield_profiles PRIMARY KEY (game_id, shield_id)
) PARTITION BY LIST (game_id);
```

## 6. 规则层：`combat_rule_profiles.shieldInteraction`

## 6.1 作用

规则层不定义某个护盾模板本身，而定义：

- 不同伤害类型如何命中不同护盾
- 护盾默认消耗顺序
- 未匹配时的默认行为

## 6.2 推荐数据结构

```ts
type ShieldInteractionMatrix = {
  rules: ShieldInteractionRule[]
  defaultBehavior: "consume" | "bypass"
  consumeOrder?: "priority_desc_created_asc"
}

type ShieldInteractionRule = {
  damageType: string | "*"
  damageTags?: string[]
  shieldScope: string | "*"
  shieldTags?: string[]
  behavior: "consume" | "bypass" | "partial"
  partialRate?: number
  priority?: number
}
```

## 6.3 LoL 示例

```json
{
  "defaultBehavior": "consume",
  "consumeOrder": "priority_desc_created_asc",
  "rules": [
    { "damageType": "physical", "shieldScope": "magic", "behavior": "bypass", "priority": 10 },
    { "damageType": "magic", "shieldScope": "physical", "behavior": "bypass", "priority": 10 },
    { "damageType": "true", "shieldScope": "physical", "behavior": "bypass", "priority": 10 },
    { "damageType": "true", "shieldScope": "magic", "behavior": "bypass", "priority": 10 },
    { "damageType": "physical", "shieldScope": "all", "behavior": "consume", "priority": 5 },
    { "damageType": "physical", "shieldScope": "physical", "behavior": "consume", "priority": 5 },
    { "damageType": "magic", "shieldScope": "all", "behavior": "consume", "priority": 5 },
    { "damageType": "magic", "shieldScope": "magic", "behavior": "consume", "priority": 5 },
    { "damageType": "true", "shieldScope": "all", "behavior": "consume", "priority": 5 }
  ]
}
```

## 6.4 其他游戏示例

**Dota 风格：**

```json
{
  "defaultBehavior": "bypass",
  "rules": [
    { "damageType": "physical", "shieldScope": "all", "behavior": "consume" },
    { "damageType": "magic", "shieldScope": "all", "behavior": "consume" },
    { "damageType": "pure", "shieldScope": "*", "behavior": "bypass" }
  ]
}
```

**王者风格：**

```json
{
  "defaultBehavior": "consume",
  "rules": [
    { "damageType": "*", "shieldScope": "all", "behavior": "consume" },
    { "damageType": "true", "shieldScope": "*", "behavior": "bypass" }
  ]
}
```

结论：

- 跨游戏变化最大的不是 `ShieldProfile`
- 而是 `ShieldInteractionMatrix`

## 7. `mechanics_config` 扩展建议

## 7.1 新增动作

```ts
type ActionNode =
  | { type: "apply_shield"; shield: ShieldApplySpec }
  | { type: "remove_shield"; shieldRef: ShieldRemoveSpec }
```

推荐规格：

```ts
type ShieldApplySpec = {
  shieldProfileId?: string
  shieldKey: string
  source: "self" | "owner"
  target: "self" | "enemy"
  amount: ExprNode
  scope?: ShieldScope
  durationMs?: ExprNode | number
  priority?: number
  stacking?: "refresh" | "stack" | "independent"
  tags?: string[]
}

type ShieldRemoveSpec = {
  target: "self" | "enemy"
  shieldKey?: string
  shieldProfileId?: string
  scope?: ShieldScope
}
```

说明：

- 若配置了 `shieldProfileId`，则优先读取模板，再用动作内字段做 override
- 若未配置 `shieldProfileId`，则允许纯内联定义，方便 MVP 快速落地

## 7.2 新增触发事件

```ts
type TriggerEvent =
  | { type: "on_shield_gain" }
  | { type: "on_shield_break" }
  | { type: "on_shield_expire" }
```

补充说明：

- `on_shield_break` 只在护盾因伤害归零时触发
- `remove_shield` 和 `shield_expire` 不应误触发 `on_shield_break`

## 8. 结算流程建议

## 8.1 护盾创建

1. 执行 `apply_shield`
2. 若存在 `shieldProfileId`，解析 `ShieldProfile`
3. 根据 `shieldKey + ownerId` 查找现有实例
4. 按 `stacking` 处理：
   - `refresh`
   - `stack`
   - `independent`
5. 若有 `durationMs`，入队 `shield_expire`
6. 触发 `on_shield_gain`

## 8.2 伤害结算中的护盾吸收

```text
damage 结算顺序：
1. 公式计算 rawAmount
2. 增减伤修正
3. 穿透 / 抗性计算 -> postMitigationAmount
4. 检查 damage immunity / invulnerable / stasis
5. 检查 ignoreShield
6. 读取目标 shields[]
7. 按 consumeOrder 遍历 ShieldInstance
8. 查 ShieldInteractionMatrix：
   - consume
   - bypass
   - partial
9. 扣减 shield.amount，汇总 absorbed
10. remaining 扣到 HP
11. 触发 on_damage_taken / on_damage_dealt
12. 若某护盾归零，触发 on_shield_break
```

关键约束：

- 护盾吸收输入必须是 `postMitigationAmount`
- 护盾阶段不得再次计算护甲 / 魔抗 / 穿透
- 若目标免伤，则本次伤害不应消耗护盾

## 8.3 护盾过期

1. `shield_expire` 到时
2. 移除对应 `ShieldInstance`
3. 触发 `on_shield_expire`

## 8.4 护盾主动移除

1. 执行 `remove_shield`
2. 按 `shieldKey / shieldProfileId / scope` 筛选
3. 移除匹配实例
4. 不触发 `on_shield_break`

## 9. 与状态机制的关系

- 护盾不是 `status_profiles` 的子集
- 但状态可以生产护盾
- `stasis / invulnerable` 等状态会影响护盾是否参与伤害吸收
- 因此两份设计文档应当并行存在：
  - [概要设计-控制与打断状态机制.md](/c:/project/damage_viewer_project_planning/wasm/概要设计-控制与打断状态机制.md)
  - 本文

建议的职责边界：

- `status_profiles`：动作权限、强制行为、免控、解控
- `shield_profiles`：护盾模板
- `combat_rule_profiles`：护盾交互矩阵 + 其他全局战斗规则

## 11. MVP 范围建议

首批建议先支持这些 `ShieldScope`：

- `all`
- `physical`
- `magic`

首批建议先支持这些叠加策略：

- `refresh`
- `stack`
- `independent`

首批建议先支持这些交互行为：

- `consume`
- `bypass`

首批建议先支持这些事件：

- `on_shield_gain`
- `on_shield_break`
- `on_shield_expire`

首批建议先支持这些伤害类型：

- `physical`
- `magic`
- `true`

可后置的能力：

- `partial` 吸收
- `custom scope`
- 更复杂的伤害格挡 / 分段吸收 / 护盾转化
