# WASM 护盾、生命值管理、乘区系数与跨游戏规则概要设计（V1 草案）

## 1. 目标

本文补充 WASM 在“护盾实例、生命值结算、乘区系数、护盾吸收、护盾过期、跨游戏规则切换”上的统一设计，解决以下场景：

- 技能或装备可给单位施加通用护盾、物理护盾、魔法护盾等不同护盾。
- 同一单位可同时持有多个护盾，存在刷新、叠加、独立实例、优先级消耗等差异。
- 不同游戏对“真伤 / 纯粹伤害是否穿盾、不同伤害类型是否命中特定护盾”的规则不同。
- 护盾可能被伤害打破、自然过期、被主动移除，且三者触发事件不同。
- 生命值不是普通面板属性，最终 HP 增减需要经过公式、系数、减免、护盾、上限/下限等多层结算。
- 除了 `hp`，移动速度、攻击速度、治疗率等其他基础属性也可能存在“同组相加、异组相乘”的乘区问题。

设计目标：

- 不把护盾写死为 LoL 特判，而是通过“护盾定义 + 交互矩阵”驱动。
- 不把乘区关系散落到技能局部 JSON 中，而是通过“系数桶注册表 + 局部引用”管理。
- 不把 `hp` 当作普通属性修正项，而是定义独立的生命值结算管线。
- 不把护盾当作一个普通属性值，而是建模为独立运行时实例。
- 与既有 `damage / heal / modifier / shield` 四通道方案对齐。
- 在 1v1 纯伤害模拟范围内，优先解决“生命值最终扣/加值”“护盾定义”“伤害穿盾规则”“生命周期事件”问题。

## 2. 结论先行

### 2.1 本文设计结论

- 推荐新增 `coefficient_buckets`，作为“乘区系数桶注册表”，供 `hp` 与普通属性共同复用。
- 推荐把“桶定义”和“桶贡献值”分离：
  - `coefficient_buckets` 负责定义桶本身
  - 技能 / 状态 / 装备 / 全局规则只引用 `bucketKey`，并给出本次贡献值
- `hp` 当前值应是引擎内建运行时资源，不应与攻击力、护甲这类普通属性走完全相同的增减逻辑。
- 推荐新增统一的 `HpChangePacket`，把伤害与治疗在真正改写 HP 之前归一化到同一结算模型。
- 推荐在 `combat_rule_profiles` 中新增 `hpResolution`，定义：
  - 不同 damage/heal type 的公式与减免规则
  - 系数分组如何“组内相加、组间相乘”
  - 护盾介入时机
  - 最终 HP clamp 规则
- 护盾不应只建模成 `combatant.stats.shield` 这类单一数值。
- 推荐新增 `shield_profiles`，定义“这个护盾是什么”。
- 推荐在 `combat_rule_profiles` 中新增 `shieldInteraction`，定义“伤害如何与护盾交互”。
- 引擎运行时要新增 `ShieldInstance` 与 `DamagePacket`。
- `mechanics_config` 要补：
  - `apply_shield`
  - `remove_shield`
  - `on_shield_gain`
  - `on_shield_break`
  - `on_shield_expire`

### 2.2 为什么不只靠技能 JSON 临时写

如果只在技能配置里临时写护盾参数，会很快遇到这些问题：

- 同一种护盾在不同技能里重复定义，难以复用。
- 护盾的吸收规则实际是“全局战斗规则”，不属于单个技能。
- 当切换到第二款游戏时，最容易变化的是“穿盾规则”，不是护盾数值本身。

因此建议拆成两层：

- `coefficient_buckets`：通用乘区桶定义层
- `combat_rule_profiles.hpResolution`：生命值结算规则层
- `shield_profiles`：护盾定义层
- `combat_rule_profiles.shieldInteraction`：护盾交互规则层

## 3. 设计原则

### 3.1 护盾是“运行时实例”，不是“一个属性值”

护盾和攻击力、生命值不同：

- 它会被伤害逐步消耗。
- 它可能被打破，也可能自然过期。
- 同一单位可以同时持有多层护盾。
- 不同护盾之间存在消耗顺序。

因此更适合建模为若干 `ShieldInstance`，而不是一个 `shieldValue` 数字。

### 3.2 护盾不是状态，但可以由状态或技能产生

护盾与 `status` 的区别在于：

- `status` 更适合描述“持续语义”和“动作约束”。
- `shield` 更适合描述“可被伤害消耗的资源实例”。

两者可以关联，但不应混为一种模型：

- 一个状态可以在 `on_gain` 时生成护盾。
- 一个技能也可以直接 `apply_shield`。
- 护盾本体仍应由 `ShieldInstance` 管理。

### 3.3 护盾定义与护盾交互规则分离

“这个护盾是什么”和“伤害如何打这个护盾”是两件事：

- `shield_profiles` 回答：
  - 护盾 scope 是什么
  - 护盾如何叠加
  - 默认持续时间是多少
  - 默认优先级是多少
- `combat_rule_profiles.shieldInteraction` 回答：
  - 物理伤害是否打魔法盾
  - 真伤是否打通用盾
  - 多层护盾如何排序消耗

### 3.4 护盾吸收只处理“减伤后的伤害”

护盾吸收必须发生在：

1. 公式计算之后
2. 增减伤修正之后
3. 穿透 / 抗性结算之后
4. HP 扣减之前

否则会重复计算减伤或出现跨游戏规则冲突。

### 3.5 免伤 / 无敌检查在护盾之前

若目标存在 `invulnerable / stasis` 等效果：

- 伤害应先被拦截
- 护盾不应被错误消耗

因此护盾吸收不是伤害管线的第一道检查，而是“目标可受伤”前提成立后的步骤。

### 3.6 跨游戏差异放在规则层，不放在核心引擎代码里

示例：

- LoL：物理伤害不打魔法盾，魔法伤害不打物理盾，真伤通常只打通用盾
- Dota 风格：Pure 伤害可无视护盾
- 王者风格：真实伤害可直接穿盾

这些都应通过规则矩阵切换，而不是改引擎代码。

### 3.7 乘区系数（Modifier Buckets）是全局基础机制，不只服务 `hp`

“同组相加、异组相乘”不是 `hp` 独有需求，而是整个引擎的通用基础能力。

适用对象至少包括：

- `hp` 伤害/治疗结算
- 移动速度
- 攻击速度
- 吸血 / 治疗率
- 某些带 cap / clamp 的特殊基础属性

因此推荐把它抽成统一机制：

- `Modifier Buckets`：负责定义“这个系数属于哪个桶”
- `bucketKey`：技能/状态/装备只引用桶，不自己发明乘区关系

关键原则：

- 桶的数量不预先写死为 `a1 / a2 / a3`
- 每个游戏可按实测逐步增加 bucket
- 未确认关系的系数，先放入临时桶 `provisional bucket`
- 测试确认后，再把多个临时桶合并为正式桶

这样做的好处是：

- 引擎实现不需要知道“到底有几个乘区”
- 前端编辑器可以给用户一个“从注册表里选桶”的稳定体验
- 游戏平衡或实测纠偏时，不需要全量重写技能公式

### 3.8 `hp` 是引擎内建资源，不是普通属性

`hp` 与攻击力、法强、双抗这类“面板属性”有根本区别：

- 面板属性通常只参与公式输入或简单修正
- `hp` 是最终承接伤害、治疗、护盾吸收结果的落点
- `hp` 变化会进一步影响斩杀、缺失生命值、治疗上限、死亡判定等后续流程

因此推荐明确区分：

- `attrs`：普通数值属性，供公式读取
- `hp`：当前生命值，属于运行时核心资源
- `maxHp`：生命上限，可来自属性系统，但进入运行时后应有独立字段

也就是说：

- `maxHp` 可以由属性公式驱动
- `hp` 当前值的最终增减必须走生命值结算管线

### 3.9 生命值最终变动必须走统一管线

无论来源是：

- 普攻/技能伤害
- DoT
- 治疗/HoT
- 吸血/回复
- 护盾吸收后的剩余伤害

在真正写入 `hp` 之前，都应归一化为统一的“生命值变动包”。

这样才能统一处理：

- 公式结果
- 来源方增伤/增疗
- 目标方减伤/受疗修正
- 不同伤害类型的减免公式
- 护盾吸收
- 生命上限/下限截断

### 3.10 系数不是一条链，而是“组内相加、组间相乘”

满足跨游戏规则的关键点，不是只有“支持多个系数”，而是显式定义它们怎么组合。

推荐统一约定：

- 同一 `combineGroup` 内的系数先相加
- 不同 `combineGroup` 之间再相乘
- 每个 group 的中性值是 `1`
- 因此：
  - `+20%` 记为 `+0.2`
  - `-35%` 记为 `-0.35`
  - 组结果为 `1 + sum(terms)`

示例：

- 来源方技能增伤 `+20%`
- 来源方装备增伤 `+10%`
- 目标方脆弱 `+15%`
- 目标方减伤 `-30%`

若分组为：

- `source_outgoing_add = [0.2, 0.1]`
- `target_vulnerability_add = [0.15]`
- `target_reduction_add = [-0.3]`

则总倍率为：

```text
(1 + 0.2 + 0.1) * (1 + 0.15) * (1 - 0.3)
= 1.3 * 1.15 * 0.7
```

这满足：

- 系数可大于 1，也可小于 1
- 有些系数在组内相加
- 不同语义组之间相乘

### 3.11 不同伤害类型要走不同减免公式

同一个 `baseAmount`，因为 `damageType` 不同，后续减免公式也应不同：

- `physical`：通常走护甲公式
- `magic`：通常走魔抗公式
- `true`：通常跳过抗性公式
- `pure`：某些游戏中既可能跳过抗性，也可能跳过护盾

因此不能只做一个统一的“damage multiplier”。

更合理的是：

- 先统一得到 `baseAmount`
- 再按 `hpChangeType` 进入对应的 type-specific pipeline

### 3.12 护盾是 `hp` 变动管线中的一个阶段，不是独立替代品

护盾不应该绕开生命值管理，而应该作为 damage pipeline 中的一个明确步骤：

1. 公式求值
2. 系数修正
3. 类型化减免
4. 免伤检查
5. 护盾吸收
6. 剩余伤害才真正扣到 `hp`

治疗则不经过护盾，但仍需要经过：

1. 公式求值
2. 来源与目标的治疗系数
3. 最大生命值截断
4. 再真正加到 `hp`

## 4. 运行时模型补充

## 4.1 `RuntimeState` 新增护盾容器

推荐把护盾挂在单位运行时对象上：

```ts
type CombatantRuntime = {
  attrs: Record<string, number>
  hp: number
  maxHp: number
  resource?: number
  shields: ShieldInstance[]
}
```

说明：

- 护盾天然属于持有者，因此挂在 `combatants[id]` 下更直观。
- `shields` 应保持稳定顺序，避免同输入下结果抖动。
- `hp / maxHp` 在运行时应是独立字段，不建议完全依赖 `attrs["hp"]` 临时读取。

### 4.1.1 `ShieldInstance`

```ts
type ShieldInstance = {
  instanceId: string
  shieldId?: string
  shieldKey: string
  sourceId: string
  ownerId: string
  amount: number
  maxAmount: number
  scope: ShieldScope
  priority: number
  createdAtMs: number
  expireAtMs: number | null
  tags: string[]
  stackCount?: number
}
```

字段语义：

- `shieldId`：来源于 `shield_profiles` 的模板 ID，可选
- `shieldKey`：运行时归并 key，用于刷新 / 叠加 / 覆盖判断
- `scope`：这个护盾能吸收什么伤害
- `priority`：多层护盾的消耗顺序

### 4.1.2 `DamagePacket`

```ts
type DamagePacket = {
  packetId: string
  sourceId: string
  targetId: string
  damageType: string
  rawAmount: number
  postMitigationAmount: number
  tags: string[]
  flags?: {
    ignoreShield?: boolean
    ignoreArmor?: boolean
    ignoreResist?: boolean
  }
}
```

用途：

- 表示 damage 通道内部流转的标准伤害包
- 护盾吸收只读取 `postMitigationAmount`

### 4.1.3 `HealPacket`

```ts
type HealPacket = {
  packetId: string
  sourceId: string
  targetId: string
  healType: string
  rawAmount: number
  tags: string[]
}
```

用途：

- 表示 heal 通道内部流转的标准治疗包
- 真正加到 `hp` 前仍要走治疗系数与上限截断

### 4.1.4 `HpChangePacket`

建议在真正落到 `hp` 之前，把 `DamagePacket / HealPacket` 统一归一化：

```ts
type HpChangePacket = {
  packetId: string
  kind: "damage" | "heal"
  hpChangeType: string
  sourceId: string
  targetId: string
  baseAmount: number
  tags: string[]

  flags?: {
    ignoreShield?: boolean
    ignoreMitigation?: boolean
    allowOverheal?: boolean
  }

  trace?: {
    sourceScaledAmount?: number
    targetScaledAmount?: number
    postMitigationAmount?: number
    shieldAbsorbedAmount?: number
    finalHpDelta?: number
  }
}
```

字段语义：

- `kind`：本次是扣血还是加血
- `hpChangeType`：用于选择物理/魔法/真实/纯粹/普通治疗等不同管线
- `baseAmount`：公式计算得到的原始值
- `trace`：保留每个阶段的中间值，方便日志、回放与调试

### 4.1.5 `CoefficientBucket`

推荐把“乘区关系”本身单独建模成注册表对象：

```ts
type CoefficientBucket = {
  bucketKey: string
  name?: string
  resolutionDomain: "attribute" | "hp_change"
  stageKey: string
  targetAttrKey?: string
  aggregationMode: "add" | "multiply" | "pick_max" | "set_final"
  provisional?: boolean
  description?: string
  editorHint?: {
    groupLabel?: string
    note?: string
    examples?: string[]
  }
}
```

字段语义：

- `bucketKey`：全局唯一桶标识，例如 `lol.hp.source.damage_amp`
- `resolutionDomain`：
  - `attribute`：服务普通属性计算
  - `hp_change`：服务伤害/治疗最终落到 `hp`
- `stageKey`：该桶属于哪个阶段
- `targetAttrKey`：仅普通属性桶使用，表示这个桶服务哪个属性
- `aggregationMode`：该桶采用什么聚合模式；这是移动速度能否落地的关键
- `provisional`：是否是临时桶；用于“先拆开记录，后续再合并”

### 4.1.6 `CoefficientContribution`

技能 / 状态 / 装备 / 全局规则本身不直接定义“乘区关系”，而是只贡献数值：

```ts
type CoefficientContribution = {
  bucketKey: string
  source: "skill" | "status" | "item" | "global"
  value: number
  priority?: number
}
```

解释：

- “桶定义”在 `CoefficientBucket`
- “某个效果给这个桶加多少值”在 `CoefficientContribution`
- 同一 `bucketKey` 的 contribution 相加
- 不同 `bucketKey` 的组结果再相乘

例如：

```text
baseAmount
  * bucket(lol.hp.source.damage_amp)
  * bucket(lol.hp.target.vulnerability)
  * bucket(lol.hp.target.reduction)
```

这样就能统一表达：

- 来源增伤
- 目标易伤
- 目标减伤
- 治疗加成
- 受疗降低（如重伤）
- 普通属性的乘区修正

### 4.1.7 `AttributeResolutionRules`

除了 `hp`，普通基础属性也应能复用同一套桶机制：

```ts
type AttributeResolutionRules = {
  attrKeys: Record<string, AttributeResolutionRule>
}

type AttributeResolutionRule = {
  coefficientStages: string[]
  stageAggregationModes?: Record<string, "add" | "multiply" | "pick_max" | "set_final">
  clampPolicy?: "none" | "min_zero" | "custom"
  minValue?: number
  maxValue?: number
}
```

示意：

- `move_speed`
  - 可能有 `base`, `flat_bonus`, `percent_bonus`, `final`
- `attack_speed`
  - 可能有 `base`, `ratio_bonus`, `final`

重点不是所有游戏都统一一套 stage 名，而是：

- 引擎知道“按桶聚合”
- 每个游戏通过规则层声明该属性用了哪些 stage
- 某个 stage 是 `add/multiply/pick_max/set_final`，由 bucket 或 stage rule 明确给出

## 4.2 生命值管理规则：`combat_rule_profiles.hpResolution`

### 4.2.1 作用

`hpResolution` 负责定义“某个 `HpChangePacket` 最终如何变成实际 HP 增减值”。

它不是独立于桶系统的另一套规则，而是：

- 读取 `coefficient_buckets`
- 按 `hp_change` 域筛选 bucket
- 再把各 effect 的 `CoefficientContribution` 聚合进来

它要回答的问题包括：

1. 这个 `hpChangeType` 用哪种减免公式
2. 哪些系数阶段参与结算
3. 护盾是否介入
4. 生命值最终如何截断

### 4.2.2 推荐数据结构

```ts
type HpResolutionRules = {
  coefficientStages: Array<
    "source_outgoing" |
    "target_incoming" |
    "post_mitigation" |
    "final"
  >
  damageTypes: Record<string, DamageResolutionRule>
  healTypes: Record<string, HealResolutionRule>
}

type DamageResolutionRule = {
  mitigation:
    | { kind: "attribute_formula"; formulaId: string; attrKeys: string[] }
    | { kind: "direct" }
  enableStages?: Array<
    "source_outgoing" |
    "target_incoming" |
    "post_mitigation" |
    "final"
  >
  shieldPolicy?: "normal" | "bypass"
  lowerBound?: number
}

type HealResolutionRule = {
  enableStages?: Array<
    "source_outgoing" |
    "target_incoming" |
    "final"
  >
  clampPolicy?: "target_max_hp" | "allow_overheal"
  lowerBound?: number
}
```

说明：

- `damageTypes` 决定物理/魔法/真实/纯粹等伤害分别怎么结算
- `healTypes` 决定普通治疗、回复、吸血等治疗分别怎么结算
- `formulaId` 复用现有公式体系，而不是在生命值文档里再发明一套 DSL
- `attribute` 域的普通属性则走 `AttributeResolutionRules`，与这里共享同一套 bucket 注册表

### 4.2.3 物理/魔法/真实伤害示意

```json
{
  "coefficientStages": [
    "source_outgoing",
    "target_incoming",
    "post_mitigation",
    "final"
  ],
  "damageTypes": {
    "physical": {
      "mitigation": {
        "kind": "attribute_formula",
        "formulaId": "armor_damage_taken_ratio",
        "attrKeys": ["armor"]
      },
      "shieldPolicy": "normal",
      "lowerBound": 0
    },
    "magic": {
      "mitigation": {
        "kind": "attribute_formula",
        "formulaId": "magic_resist_damage_taken_ratio",
        "attrKeys": ["magic_resist"]
      },
      "shieldPolicy": "normal",
      "lowerBound": 0
    },
    "true": {
      "mitigation": { "kind": "direct" },
      "shieldPolicy": "normal",
      "lowerBound": 0
    }
  },
  "healTypes": {
    "normal_heal": {
      "clampPolicy": "target_max_hp",
      "lowerBound": 0
    }
  }
}
```

这样满足：

- 不同伤害类型可以接不同减免公式
- 不同类型可以决定是否穿盾
- 治疗也能有单独的管线

## 5. 乘区系数注册表：`coefficient_buckets`

## 5.1 作用

`coefficient_buckets` 定义“这个乘区桶是什么”，供普通属性和 `hp` 结算共同复用。

它适合承载：

- `bucketKey`
- 这个桶属于 `attribute` 还是 `hp_change`
- 所属阶段 `stageKey`
- 对于普通属性，服务哪个 `attrKey`
- 是否为临时桶 `provisional`
- 编辑器提示信息

注意：

- 第一版建议只把“桶定义”落表
- 具体数值贡献仍保留在技能 / 状态 / 装备 / 全局效果配置里
- 这些配置只引用 `bucketKey`，不再自己发明乘区名称

## 5.2 推荐字段

```ts
type CoefficientBucketProfile = {
  bucketKey: string
  name?: string
  resolutionDomain: "attribute" | "hp_change"
  stageKey: string
  targetAttrKey?: string
  aggregationMode: "add" | "multiply" | "pick_max" | "set_final"
  provisional?: boolean
  editorHint?: {
    groupLabel?: string
    note?: string
    examples?: string[]
  }
  description?: string
}
```

示例：

- `lol.hp.source.damage_amp`
  - `resolutionDomain = "hp_change"`
  - `stageKey = "source_outgoing"`
  - `aggregationMode = "add"`
- `lol.hp.target.vulnerability`
  - `resolutionDomain = "hp_change"`
  - `stageKey = "target_incoming"`
  - `aggregationMode = "add"`
- `lol.move_speed.percent_bonus`
  - `resolutionDomain = "attribute"`
  - `stageKey = "percent_bonus"`
  - `targetAttrKey = "move_speed"`
  - `aggregationMode = "add"`
- `lol.move_speed.multiplicative_bonus`
  - `resolutionDomain = "attribute"`
  - `stageKey = "multiplicative_bonus"`
  - `targetAttrKey = "move_speed"`
  - `aggregationMode = "multiply"`
- `lol.move_speed.highest_slow`
  - `resolutionDomain = "attribute"`
  - `stageKey = "slow_select"`
  - `targetAttrKey = "move_speed"`
  - `aggregationMode = "pick_max"`
- `lol.move_speed.fixed_override`
  - `resolutionDomain = "attribute"`
  - `stageKey = "override"`
  - `targetAttrKey = "move_speed"`
  - `aggregationMode = "set_final"`

## 5.3 为什么建议单独建表

如果乘区桶只存在于技能 JSON 内部：

- 前端编辑器无法稳定提供“桶选择器”
- 同一个桶会在不同技能里重复写说明
- 实测修正后很难统一迁移临时桶到正式桶
- 用户很难理解“这个系数和谁相加，和谁相乘”

因此建议新增：

```sql
CREATE TABLE public.coefficient_buckets (
    game_id varchar(64) NOT NULL,
    bucket_key varchar(64) NOT NULL,
    start_version_id bigint NOT NULL,
    end_version_id bigint NOT NULL,
    resolution_domain varchar(16) NOT NULL,
    stage_key varchar(32) NOT NULL,
    target_attr_key varchar(64),
    aggregation_mode varchar(16) NOT NULL,
    provisional boolean NOT NULL DEFAULT false,
    name varchar(100),
    description varchar(255),
    editor_hint jsonb NOT NULL DEFAULT '{}',
    updated_at timestamp NOT NULL DEFAULT NOW(),
    CONSTRAINT pk_coefficient_buckets PRIMARY KEY (game_id, bucket_key)
) PARTITION BY LIST (game_id);
```

建议约束：

- `resolution_domain = attribute` 时，`target_attr_key` 必填
- `resolution_domain = hp_change` 时，`target_attr_key` 为空
- `aggregation_mode` 至少支持：`add / multiply / pick_max / set_final`

## 5.4 与效果配置的关系

第一版不强制把“数值贡献”也单独建表，建议仍保留在效果配置里：

```ts
type CoefficientContribution = {
  bucketKey: string
  value: number | ExprNode
}
```

这样能把复杂度控制在：

- 表层管理“桶定义”
- 配置层管理“贡献值”

后续如果前端要做全局平衡编辑器，再考虑把贡献值进一步独立建表。

## 6. 护盾定义层：`shield_profiles`

## 6.1 作用

`shield_profiles` 定义“这个护盾是什么”，类似于状态机制中的 `status_profiles`。

它适合承载：

- 护盾吸收范围
- 护盾叠加策略
- 默认持续时间
- 默认优先级
- 标签与移除策略

## 6.2 推荐字段

```ts
type ShieldProfile = {
  shieldId: string
  name?: string
  scope: ShieldScope
  tags?: string[]
  stacking?: {

    maxAmount?: number
  }
  durationPolicy?: {
    defaultDurationMs?: number

  consumePolicy?: {

  removalPolicy?: {
    removable?: boolean
    removeTags?: string[]

  | "physical"
  | "magic"
```

示例：

- `shield_generic_basic`

  - `stacking.mode = "refresh"`
- `shield_magic_basic`

- `shield_physical_basic`
  - `scope = "physical"`

## 9. 结算流程建议

## 9.1 护盾创建

1. 执行 `apply_shield`
2. 若存在 `shieldProfileId`，解析 `ShieldProfile`
3. 根据 `shieldKey + ownerId` 查找现有实例
4. 按 `stacking` 处理：
   - `refresh`
   - `stack`
   - `independent`
5. 若有 `durationMs`，入队 `shield_expire`
6. 触发 `on_shield_gain`

## 9.2 生命值结算主链路

### 8.2.1 Damage -> HP

推荐把 damage 最终落到 HP 的标准顺序固定为：

```text
1. 技能 / 普攻 / DoT 公式计算 -> baseAmount
2. 收集 source_outgoing 系数，组内相加、组间相乘
3. 收集 target_incoming 系数，组内相加、组间相乘
4. 根据 damageType 选择 mitigation rule
5. 执行类型化减免公式 -> postMitigationAmount
6. 应用 post_mitigation / final 阶段系数
7. 检查 damage immunity / invulnerable / stasis
8. 检查 shieldPolicy / ignoreShield
9. 进入护盾吸收
10. remaining 才真正扣到 hp
11. 触发 on_damage_taken / on_damage_dealt / on_shield_break
12. 若 hp <= 0，再进入死亡 / 免死 / 斩杀后处理
```

### 8.2.2 Heal -> HP

治疗链路也应走统一的 HP 管线，只是没有护盾吸收和抗性公式：

```text
1. 技能 / 被动 / HoT 公式计算 -> baseAmount
2. 收集 source_outgoing 系数（治疗加成）
3. 收集 target_incoming 系数（受疗提升 / 重伤降低）
4. 应用 final 阶段系数
5. 按 clampPolicy 截断
6. finalHeal 才真正加到 hp
7. 触发 on_heal_done / on_heal_taken
```

### 8.2.3 为什么必须统一到 HP 管线

若把 damage/heal 各自散写为：

- 先伤害自己算一套
- 护盾自己算一套
- 治疗自己算一套

会很快出现这些问题：

- 日志里看不到“最终实际扣/加值”到底怎么来的
- 不同游戏切换时，减免公式和系数组合顺序容易漂移
- 重伤、易伤、伤害放大、护盾穿透等机制会互相打架

因此推荐：

- 所有改写 `hp` 的过程都统一落到 `HpChangePacket`
- `hp` 只有一个写入口：`applyHpChange(packet, runtimeState, combatRules)`

## 9.3 伤害结算中的护盾吸收

```text
damage 结算顺序：
1. 公式计算 baseAmount
2. source_outgoing / target_incoming 系数结算
3. 类型化减免公式 -> postMitigationAmount
4. post_mitigation / final 系数结算
5. 检查 damage immunity / invulnerable / stasis
6. 检查 ignoreShield / shieldPolicy
7. 读取目标 shields[]
8. 按 consumeOrder 遍历 ShieldInstance
9. 查 ShieldInteractionMatrix：
   - consume
   - bypass
   - partial
10. 扣减 shield.amount，汇总 absorbed
11. remaining 扣到 HP
12. 触发 on_damage_taken / on_damage_dealt
13. 若某护盾归零，触发 on_shield_break
```

关键约束：

- 护盾吸收输入必须是“减免公式与前后系数处理完成后的 damage 值”
- 护盾阶段不得再次计算护甲 / 魔抗 / 穿透
- 若目标免伤，则本次伤害不应消耗护盾

### 9.3.1 系数组合规则的明确约束

建议写死以下规则，避免不同模块理解不一致：

1. 同一 `stage + combineGroup` 内：
   - `groupMultiplier = 1 + sum(values)`
2. 不同 group 之间：
   - `stageMultiplier = Π(groupMultiplier)`
3. 阶段之间：
   - 按 `source_outgoing -> target_incoming -> mitigation -> post_mitigation -> final` 顺序推进

这意味着：

- `+20%` 与 `+10%` 若同组，则得到 `1.3`
- 若分别属于不同组，则得到 `1.2 * 1.1`
- 系数可以大于 `1`
- 系数也可以小于 `1`
- 若某组累计后小于 `0`，建议在规则层决定是否 clamp 到 `0`

## 9.4 护盾过期

1. `shield_expire` 到时
2. 移除对应 `ShieldInstance`
3. 触发 `on_shield_expire`

## 9.5 护盾主动移除

1. 执行 `remove_shield`
2. 按 `shieldKey / shieldProfileId / scope` 筛选
3. 移除匹配实例
4. 不触发 `on_shield_break`
