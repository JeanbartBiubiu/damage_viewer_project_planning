# WASM 移动速度机制概要设计（V1 草案）

## 1. 目标

本文补充 WASM 在“移动速度数值计算”上的统一设计，重点解决以下问题：

- 如何在不引入真实空间系统的前提下，正确计算游戏内最终移动速度
- 如何支持 LoL 一类“基础值 + 固定加成 + 百分比加成 + 减速 + 软上限”的复杂规则
- 如何让现有公式系统在不大改 AST 的前提下支持精确的分段计算
- 如何把移动速度作为一个可复用的“派生属性”提供给其他技能公式读取

本文边界：

- 只做“数值上的移动速度”
- 不做位置、路径、碰撞、弹道、绕路、追击、逃跑模拟
- 不做“是否在射程内”这类空间判断

---

## 2. 结论先行

### 2.1 结论

- 现有 `ExprNode` 的算术能力，已经足够表达 LoL 移动速度软上限这种 **分段线性** 规则。
- 真正的难点不在“分段公式写不出来”，而在“移动速度不是单个公式，而是多种来源的分桶聚合”。
- 推荐把移动速度建模为一组中间桶属性，再产出一个最终派生属性：`move_speed_final`。
- 推荐把“最高减速只取一个”“固定值覆盖型减速”作为运行时聚合规则处理，而不是硬塞到普通 `ModifierSpec` 叠加里。
- 公式层推荐采用 **branchless piecewise** 写法，也就是用 `max(0, x-a)` 组合出精确分段函数。

### 2.2 对当前机制的判断

当前机制：

- `ExprNode` 支持 `const / attr / stack / op / clamp`
- 属性值类别支持 `scalar | ratio | rate | flag`

因此：

- **能做**：基础移速、固定加成、百分比加成、软上限公式
- **还不够**：最高减速选择、减速抗性修正、固定值覆盖类减速

所以结论是：

- 现有公式系统 **部分够用**
- 需要补一层“移动速度派生规则”

---

## 3. 规则来源与边界假设

基于 LoL wiki 快照，当前移动速度规则至少包括：

- 总公式：
  - `(Base MS + Flat MS bonuses) × (1 + Additive Percent MS Sum) × Product(1 + Multiplicative MS bonuses) × (1 - Highest Slow Ratio)`
- 上方软上限：
  - `415 ~ 490`
  - `> 490`
- 下方软上限：
  - `< 220`
  - `< 0`
- 减速规则：
  - 只取最高减速
  - 减速强度受 `slow resist` 影响
  - 某些减速会直接把移动速度设置为固定值，且不再受后续增减影响

在本文中，统一采用如下边界：

- 引擎只计算“当前最终移动速度”
- 外部业务若要用移动速度推导赶路时间、追击时间，可自行用 `distance / move_speed_final` 计算

---

## 4. 设计原则

### 4.1 移动速度是“派生属性”，不是普通基础属性

攻击力、法强、护甲等多数属性可以直接累加或乘区叠加；
而移动速度通常需要：

- 按桶聚合
- 应用特殊规则
- 最后经过软上限

因此更适合建模为：

- 若干输入桶属性
- 一个统一派生公式
- 一个最终输出属性 `move_speed_final`

### 4.2 分桶优先于一把梭公式

如果直接把所有技能、装备、状态的移速逻辑塞进一个大公式，会导致：

- 配置难维护
- 无法解释“为什么这个加成进加法桶而那个进乘法桶”
- 很难处理“最高减速”“固定值覆盖”这类选择型逻辑

推荐先做分桶，再做最终公式。

### 4.3 分段线性规则优先用精确数学改写

对于 LoL 的软上限，不建议优先使用：

- `sigmoid`
- `softplus`
- `smoothstep`

这些方法适合做平滑近似，但不适合游戏规则，因为断点会被算歪。

更适合的方法是：

- `hinge / ReLU basis`
- 即 `max(0, x-a)` 的组合

优点：

- 精确
- 可复现
- 只依赖 `max / + / - / *`

### 4.4 选择型逻辑放在运行时聚合层

移动速度里有几类逻辑不适合仅靠普通算术表达：

- 从多个 slow 中只取最高值
- 固定值覆盖型移速
- 某些特殊状态直接阻止移动

这类逻辑应放在运行时聚合层，而不是完全依赖 `ExprNode`。

## 5. 推荐运行时模型

## 5.1 派生桶属性

推荐至少引入以下移动速度相关属性：

```ts
type MoveSpeedDerivedState = {
  baseMs: number
  flatMsBonus: number
  additiveMsPctSum: number
  multiplicativeMsFactor: number
  highestSlowRatio: number
  slowResist: number
  fixedMoveSpeedOverride: number | null

  rawMoveSpeed: number
  finalMoveSpeed: number
}
```

语义说明：

- `baseMs`：英雄 / 单位基础移速
- `flatMsBonus`：鞋子、装备、Buff 带来的固定移速
- `additiveMsPctSum`：加法百分比移速总和
- `multiplicativeMsFactor`：乘法移速因子连乘后的结果，初始值 `1`
- `highestSlowRatio`：当前生效的最高减速强度
- `slowResist`：减速抗性
- `fixedMoveSpeedOverride`：固定值覆盖型移速，`null` 表示没有覆盖
- `rawMoveSpeed`：软上限前的原始移速
- `finalMoveSpeed`：最终可供外部读取的移速

## 5.2 与现有属性系统的关系

建议映射到现有属性值类别时：

- `baseMs`：`scalar`
- `flatMsBonus`：`scalar`
- `additiveMsPctSum`：`ratio`
- `multiplicativeMsFactor`：`ratio`，但语义是“累乘结果”，默认 `1`
- `slowResist`：`ratio`
- `rawMoveSpeed / finalMoveSpeed`：派生属性，不建议直接录入 DB 基础值

说明：

- `multiplicativeMsFactor` 虽然是 `ratio`，但不通过简单加法聚合，而是由运行时做连乘
- `highestSlowRatio` 也不通过简单加法聚合，而是由运行时做 `max`

## 6. LoL 规则拆解

## 6.1 原始移速公式

先定义：

```text
flatBase = baseMs + flatMsBonus
additiveFactor = 1 + additiveMsPctSum
multiplicativeFactor = multiplicativeMsFactor
effectiveSlow = highestSlowRatio * (1 - slowResist)
```

则原始移速：

```text
rawMoveSpeed = flatBase * additiveFactor * multiplicativeFactor * (1 - effectiveSlow)
```

约束：

- `effectiveSlow` 应限制在合理范围内
- `highestSlowRatio` 来自运行时选择，不是所有 slow 直接相加

## 6.2 最高减速规则

LoL 当前规则是：

- 同时存在多个 slow 时，只取最高值
- 其他 slow 暂时忽略，直到更高值 slow 消失

因此推荐运行时维护：

```ts
type SlowCandidate = {
  sourceId: string
  ratio: number
  durationMs: number
  tags?: string[]
}
```

然后：

```text
highestSlowRatio = max(all active slow candidates)
```

## 6.3 减速抗性规则

减速抗性不改变 slow 的持续时间，而改变其强度：

```text
effectiveSlow = highestSlowRatio * (1 - slowResist)
```

例如：

- `slow = 0.60`
- `slowResist = 0.25`
- `effectiveSlow = 0.60 * 0.75 = 0.45`

## 6.4 固定值覆盖型移速

某些效果不是“减少比例”，而是：

- 直接把移动速度设为某个固定值
- 且这个值不再受普通增减影响

因此推荐：

```text
if fixedMoveSpeedOverride != null:
  finalMoveSpeed = fixedMoveSpeedOverride
else:
  finalMoveSpeed = softcap(rawMoveSpeed)
```

## 7. 软上限的精确数学表达

## 7.1 上半区软上限

LoL 规则：

- `x <= 415`：`f(x) = x`
- `415 < x <= 490`：`f(x) = 0.8x + 83`
- `x > 490`：`f(x) = 0.5x + 230`

可精确改写为：

```text
f_high(x) =
  x
  - 0.2 * max(0, x - 415)
  - 0.3 * max(0, x - 490)
```

## 7.2 下半区软上限

LoL 规则：

- `x >= 220`：不处理
- `0 <= x < 220`：`f(x) = 110 + 0.5x`
- `x < 0`：`f(x) = 110 + 0.01x`

可精确改写为：

```text
f_low(x) =
  x
  + 0.5  * max(0, 220 - x)
  + 0.49 * max(0, -x)
```

## 7.3 合并总公式

把上下两部分合并，可得一个单表达式：

```text
softcap(x) =
  x
  + 0.5  * max(0, 220 - x)
  + 0.49 * max(0, -x)
  - 0.2  * max(0, x - 415)
  - 0.3  * max(0, x - 490)
```

该公式对 LoL 当前分段规则是 **精确等价** 的。

## 8. 对现有公式机制的适配结论

## 8.1 现在就能做的部分

你当前的 `ExprNode` 支持：

- `const`
- `attr`
- `op(+ - * / min max)`
- `clamp`

因此：

- `softcap(x)` 可以直接表达
- `rawMoveSpeed` 公式也可以直接表达

换句话说：

- **分段公式本身现在就能做**

## 8.2 现在做不完整的部分

仅靠现在的公式系统，还不能优雅完成这些逻辑：

- 从多个 slow 中只取最高值
- 固定值覆盖型移速
- 区分“加法百分比”和“乘法百分比”来源桶
- 多个乘法移速因子的稳定连乘聚合

所以移动速度不能只当成“一个技能公式”，而要有运行时聚合层。

---

## 9. 推荐实现方案

## 9.1 短期推荐方案（MVP 最稳）

做法：

1. 运行时先聚合移速桶
2. 用公式算出 `rawMoveSpeed`
3. 用公式算出 `finalMoveSpeed`
4. 其他技能公式统一读取 `move_speed_final`

优点：

- 对当前 `ExprNode` 改动最小
- 规则最清楚
- 适合数值引擎边界

## 9.2 中期优化方案（可选）

给 `ExprNode` 新增：

```ts
| { t: "cmp"; cmp: ">"|">="|"=="|"!="|"<="|"<"; left: ExprNode; right: ExprNode }
| { t: "if"; cond: ExprNode; then: ExprNode; else: ExprNode }
| { t: "piecewise"; cases: Array<{ when: ExprNode; then: ExprNode }>; else: ExprNode }
```

用途：

- 让配置层更直观地写分段函数

但建议：

- 对外允许 `piecewise`
- 内部编译成 `max(0, x-a)` 这种 branchless 形式

这样能兼顾：

- 可读性
- 性能
- 可复现性

---

## 10. 运行时流程建议

推荐在“读取属性 / 状态推进 / 施法判定”前，统一刷新移动速度派生值：

1. 聚合当前 `Modifier / Status / Equipment` 对移速的影响
2. 更新移速桶：
   - `flatMsBonus`
   - `additiveMsPctSum`
   - `multiplicativeMsFactor`
   - `slow candidates`
   - `slowResist`
   - `fixedMoveSpeedOverride`
3. 计算 `highestSlowRatio`
4. 计算 `rawMoveSpeed`
5. 计算 `finalMoveSpeed`
6. 写回可读取属性视图

说明：

- 这一步是“派生属性刷新”
- 它不需要单独做成一条公式 profile 绑定给每个技能
- 更适合作为运行时的公共计算步骤

---

## 11. 建议新增的机制语义

为了让移动速度机制真正可落地，推荐补以下聚合语义：

```ts
type AggregationMode =
  | "sum"
  | "product"
  | "max"
  | "override"
```

推荐应用位置：

- `flatMsBonus`：`sum`
- `additiveMsPctSum`：`sum`
- `multiplicativeMsFactor`：`product`
- `highestSlowRatio`：`max`
- `fixedMoveSpeedOverride`：`override`

如果以后要支持更多派生属性，这套聚合语义也可以复用，不只服务于移动速度。

---

## 12. MVP 范围建议

首批建议先支持：

- 基础移速
- 固定移速加成
- 加法百分比移速
- 乘法百分比移速
- 最高减速
- 减速抗性
- LoL 当前软上限
- 最终移速作为派生属性给其他公式读取

首批可以暂不做：

- 固定值覆盖型移速
- 负 slow 值转正增益
- 复杂随时间变化的 slow 曲线
- “移速作为技能距离 / 弹道 / 位移轨迹”的空间联动
