# WASM 引擎协议与数据结构（V1.1）

本文件定义 WASM 的“通用事件驱动 + 伤害计算引擎”对外协议与数据结构强约束。  
目标是支持多款“英雄-技能-装备”类游戏，但 **WASM 输入结构固定**、**场景由前端组装**。

设计边界：
- wasm 只做核心结算（事件推进 + 技能机制执行 + 伤害输出）
- 后端通过接口返回数据，前端负责拿到数据后组装为固定 `init/run` 输入
- 斩杀线、最大伤害、装备对比等场景由前端通过改输入参数完成
- 同一 `bundle + input + seed` 必须可复现

---

## 1. 线程与运行模型

- wasm 运行在 WebWorker 内，避免阻塞主线程
- 一个 worker session 绑定一个已初始化引擎实例（`gameId/versionId/dataHash`）
- 同一 session 可连续执行多次 `run`（每次唯一 `runId`）
- 任意时刻可 `cancel` 某个 `runId`，引擎应尽快停止并返回 `done(stopReason=cancelled)`

---

## 2. 消息协议（Worker <-> WASM）

### 2.1 基础类型

```ts
export type EngineMeta = {
  gameId: string
  versionId: number
  dataHash: string
}

export type EngineError = {
  code: "INVALID_INPUT" | "SEMANTIC_ERROR" | "RUNTIME_ERROR"
  message: string
  details?: unknown
}
```

### 2.2 前端 -> 引擎

```ts
export type WasmToEngineMessage = EngineInitMessage | EngineRunMessage | EngineCancelMessage

export type EngineInitMessage = {
  type: "init"
  meta: EngineMeta
  bundle: EngineBundleV1
  engineConfig?: {
    hpAttrKey?: string
    sampleEveryMs?: number
  }
}

export type EngineRunMessage = {
  type: "run"
  runId: string
  input: EngineRunInput
}

export type EngineCancelMessage = {
  type: "cancel"
  runId: string
}
```

### 2.3 引擎 -> 前端

```ts
export type EngineToWasmMessage =
  | EngineReadyMessage
  | EngineTickMessage
  | EngineDoneMessage
  | EngineErrorMessage

export type EngineReadyMessage = {
  type: "ready"
  meta: EngineMeta
}

export type EngineTickMessage = {
  type: "tick"
  runId: string
  seq: number
  emittedAt: string
  progress: {
    simulatedMs: number
  }
  samples: EngineSamplePoint[]
}

export type EngineDoneMessage = {
  type: "done"
  runId: string
  emittedAt: string
  result: EngineRunResult
}

export type EngineErrorMessage = {
  type: "error"
  runId?: string
  emittedAt: string
  error: EngineError
}
```

### 2.4 Tick 推送节奏

- 引擎内部可高频推进事件
- 对外按 `sampleEveryMs` 采样，以“每 2 秒聚合一次”发送 `tick`
- 同一 `runId` 的 `samples` 必须按 `tMs` 升序且不回退
- 允许空 `samples`（该周期无采样点）

## 3. 初始化 Bundle（固定结构，前端组装）

来源：后端 `GET /api/games/{gameId}/versions/{versionId}/bundle`。  
前端职责：拉取后端数据并组装为 `EngineBundleV1`（可透传，也可轻量裁剪），再传给 wasm。

```ts
export type EngineBundleV1 = {
  meta: {
    gameId: string
    versionId: number
    versionCode: string
    dataHash: string
    generatedAt: string
  }

  attributeDefinitions: AttributeDefinitionDTO[]
  types?: TypeDTO[]
  typeRelations?: TypeRelationDTO[]

  heroes: HeroDTO[] // 历史命名，语义上可视作“角色模板集合”
  skills: SkillDTO[]
  items: ItemDTO[]
}

export type AttributeDefinitionDTO = {
  attrKey: string
  attrName?: string
  attrType?: string
  defaultValue?: number
}

export type TypeDTO = {
  typeId: number
  name?: string
  description?: string
}

export type TypeRelationDTO = {
  typeId: number
  targetCategory: "equipment" | "attribute" | "skill" | "character" | "type"
  targetId: string
  extend?: unknown
}

export type HeroDTO = {
  heroId: string
  name: string
  baseStats: Record<string, number>
  statsByLevel?: unknown
  title?: string
  avatarUrl?: string
}

export type ItemDTO = {
  itemId: string
  name?: string
  goldCost?: number
  iconUrl?: string
  statsModifier?: unknown
  skillRefs?: unknown
  recipeIds?: unknown
}

export type SkillDTO = {
  skillId: string
  ownerType: string
  ownerId: string
  skillKey?: string
  name?: string
  description?: string
  resourceCosts?: unknown
  cooldowns?: unknown
  params?: unknown
  timingProfile?: unknown
  mechanicsConfig: MechanicsConfigV1
}
```

强约束：
- wasm 不直接访问后端接口；只消费前端传入的固定结构
- `hpAttrKey` 默认为 `hp`，可由 `engineConfig` 覆盖
- 引擎不得硬编码 `ownerType`（如只认 hero/item）
- `mechanicsConfig` 必须结构化、可校验、可稳定执行

## 4. Run 输入（固定结构，场景由前端变化输入）

Run 不描述“场景名”，只描述“初始状态 + 停止条件 + 覆盖项”。  
前端通过改 `input` 来实现不同业务场景。

```ts
export type EngineRunInput = {
  seed?: number
  stop: {
    maxSeconds: number
  }
  initial: {
    self: CombatantInit
    enemy: CombatantInit
  }
  overrides?: {
    self?: CombatantOverride
    enemy?: CombatantOverride
  }
}

export type CombatantInit = {
  heroId: string // 协议层历史命名，语义为“对战单位模板 ID”
  level?: number
  itemIds?: string[]
}

export type CombatantOverride = {
  baseStats?: Record<string, number>
  addItemIds?: string[]
  removeItemIds?: string[]
}
```

语义约束：
- `overrides.*.baseStats` 的 key 必须来自 `attributeDefinitions`
- `heroId` 只是字段名，不代表必须是 LoL 英雄；其它游戏由前端映射其角色模板 ID 到该字段
- 引擎内部先应用 `initial`，再应用 `overrides`
- `addItemIds/removeItemIds` 的应用顺序固定：先移除再新增
- 同一 `bundle + input + seed` 必须输出一致

## 5. 输出数据（samples/result）

### 5.1 样本点

```ts
export type EngineSamplePoint = {
  tMs: number

  enemyHp: number

  timeToKillEnemyMs?: number
  timeToDieMs?: number
  lastSample?: EngineSamplePoint
}
```

## 6. 前端场景组装约定（重点）

原则：wasm 结构固定，场景通过前端改输入实现。

1. 斩杀线（二分）  
- 固定角色/装备/seed/maxSeconds  
- 每次改 `overrides.enemy.baseStats[hpAttrKey] = mid`  
- 根据 `result.stopReason` 是否为 `enemyDead` 调整上下界

2. 最大伤害值（枚举/搜索）  
- 前端枚举装备组合或技能参数  
- 每次用不同 `initial.itemIds` 或 `overrides.addItemIds/removeItemIds` 调 `run`  
- 对比 `cumulativeDamageToEnemy` 或 `timeToKillEnemyMs`

3. 装备对比  
- 只改 `itemIds`，其余输入保持一致  
- 输出多组 `samples/result` 给图表对比

4. 属性敏感性分析  
- 批量改 `overrides.*.baseStats`（如双抗、生命、攻击）  
- 观察关键输出曲线变化

## 7. 与后端接口目录的对齐关系

参考：`接口/game_manage/接口定义.md`

- 游戏列表：`GET /api/games`
- 当前版本：`GET /api/games/{gameId}/versions/current`
- 数据包：`GET /api/games/{gameId}/versions/{versionId}/bundle`
- 可选字典：`GET /api/games/{gameId}/owner-categories`

建议前端流程：
1. 先拿 `current`，读取 `versionId/dataHash`
2. 再拉 `bundle`（配合 `ETag/If-None-Match`）
3. 前端组装固定 `EngineBundleV1` 调 `init`
4. 在同一 `init` 下发起多次 `run`（变更 input 完成不同场景）

---

## 8. 跨游戏适配的非功能约束

1. 不写死 Q/W/E/R 槽位模型（技能顺序由数据决定）。  
2. 不写死资源类型（法力/能量/怒气/弹药等由数据表达）。  
3. 不写死角色/装备命名（只用 ID + 属性 + mechanicsConfig 解释）。  
4. 输入非法或语义错误要明确返回 `INVALID_INPUT/SEMANTIC_ERROR`。  
5. 必须支持回放：给定 `bundle + input + seed` 能复现实验结果。
