# WASM 控制、打断与免控状态机制设计（V1 草案）

## 1. 目标

本文补充 WASM 在“控制状态、施法打断、免控/解控”上的统一设计，解决以下场景：

- 角色被眩晕、击飞、沉默、缴械等状态影响时，无法执行普攻、施法、使用物品或其它动作。
- 某些技能或物品可在被控期间施放，并在生效后移除控制，如船长 W、净化类装备。
- 正在施法或引导中的技能可能被打断；不同技能被打断后的后果不同。
- 某些状态提供免控或霸体，能阻止新的控制生效，也不会中断当前动作。

设计目标：

- 不把这类机制写死为 LoL 特判，而是通过数据和规则驱动。
- 不为 `skills` 表增加一堆零散标量列，继续沿用 `params` / `timing_profile` / `mechanics_config` 的三段设计。
- 在 1v1 纯伤害模拟范围内，优先解决“动作权限”和“技能生命周期”问题；不扩展真实位置、碰撞、位移轨迹。

---

## 2. 结论先行

### 2.1 现有系统的能力边界

现有设计已经有这几个基础件：

- `RuntimeState.modifiers`
- `cast_intent` / `cast_resolved`
- 结构化 `mechanicsConfig.triggers`

因此：

- “被控后属性变化”这类效果，现有 `apply_modifier` 有基础承载能力。
- “施法前检查是否允许动作”这一步，事件流模型也已有插点。

但现有契约还不够直接覆盖控制机制，因为缺 6 个关键层：

1. 没有显式的“动作权限 + 强制行为”模型。
2. 没有显式的“瞬时打断（disrupt）”模型。
3. 没有显式的“当前执行中的技能实例”模型。
4. 没有“控制标签 / 免控标签 / 解控规则 / 持续时间修正规则”的统一矩阵。
5. 没有把“技能引导中断”和“效果生效后持续存在”区分开。
6. 没有把“状态部分”和“强制位移 / 强制行为部分”区分开。

### 2.2 本文的设计结论

- `skills` 表本身不需要再加单独字段。
- `timing_profile` 要升级为“施法阶段状态机 + 施法权限声明”。
- `mechanics_config` 要补状态类动作、强制行为动作、瞬时打断事件和条件。
- 引擎运行时要新增 `statusInstances`、`controlDirectives` 和 `activeExecutions`。
- `combat_rule_profiles` 要从“封动作 / 打断 / 免控 / 净化”扩展到“封动作 / 强制行为 / 打断 / 免控 / 净化 / 持续时间修正”。
- DB 层建议新增：
  - `combat_rule_profiles`
  - `status_profiles`

## 3. 设计原则

### 3.1 控制是“状态”，不是“技能特判”

眩晕、沉默、缴械、击飞、压制、恐惧、嘲讽、变形等，本质上都应表现为：

- 给目标挂上一个 `StatusInstance`
- 该状态携带若干 `tags`
- 引擎根据全局规则判断这些 `tags` 会阻止哪些动作、打断哪些执行

### 3.2 强制行为不是动作封锁

`fear / taunt` 这类效果不能只建模成“不能做什么”，还要建模成“被迫做什么”：

- `fear`：被迫朝远离来源的方向行动
- `taunt`：被迫尝试对来源进行普攻
- 同类 `forced action` 在同一目标身上通常会互相覆盖，而不是简单叠加

因此推荐把这类机制拆成两层：

- `StatusInstance.tags`：表达“该单位处于 fear / taunt 控制态”
- `ControlDirectiveInstance`：表达“当前被迫执行的动作”

说明：

- 在 1v1 纯伤害、无真实空间模型的范围内，`forced_move_away` 先只保留“失去自由动作权 + 进入强制移动态”的语义，不展开真实路径与距离变化
- `forced action` 不能强行制造一个本来就被禁用的动作，例如被缴械时的 `taunt` 不能真的执行普攻，只能保留其“不可自由行动”的部分语义

### 3.3 打断分为“状态打断”和“瞬时打断”

不是所有打断都来自一个持续存在的状态：

- `stun / airborne / suppression` 这类效果进入后，会因为其 `statusTag` 触发打断
- `disrupt` 这类机制本身不是状态，而是一次性中止当前 `cast / channel`

因此引擎里要同时支持：

- `causeKind = status_tag`
- `causeKind = effect_tag`

### 3.4 打断是“执行实例”的问题，不是“技能模板”的问题

卡特 R 被打断后，后续匕首不再发射；末日 R 在引导中被打断则整体失败，但一旦引导成功并进入持续伤害阶段，后续控制不应取消已存在效果。

差异不在“技能是否有伤害”，而在：

- 当前技能是否仍处于 `cast/channel` 阶段
- 打断时是否取消未执行事件
- `resolve` 后是否生成独立持续效果实例

### 3.5 免控不是一个标签，而是一组不同维度的免疫

LoL wiki 的控制分类里，至少要区分：

- 普通控制免疫：阻止 `stun / silence / root / taunt / fear / suppression` 等状态生效
- 位移免疫：阻止 `forced_displacement / airborne movement` 这类位移组件生效

因此更适合建模为：

- 角色获得 `immunityTags = ["cc_immune", "displacement_immune", ...]`
- 新控制在应用前先和免控规则比对
- 若免疫，则控制不入场，也不会触发打断

### 3.6 解控分为“移除状态”、“移除强制行为组件”和“允许在控制中施法”

船长 W、净化类装备通常同时包含两个能力：

- 该技能 / 物品在控制中仍允许使用
- 生效后移除一部分控制状态
- 必要时一并移除与该状态绑定的 `forced action` 组件

这两个能力不能混在一起，否则无法表达：

- “能在控制中施放但不解所有控”
- “不能在控制中施放，但可预先获得免控”
- “能移除 fear / taunt，但不能移除 airborne 的位移分量”

### 3.7 持续时间与净化策略是状态内建语义

不是所有控制都吃 `Tenacity`，也不是所有净化都能移除同一种控制的全部组件：

- `stun / silence / root / fear / taunt / sleep` 这类持续时间通常可被 `Tenacity` 修正
- `airborne` 的状态部分和强制位移部分可以有不同净化语义
- `suppression` 的持续时间通常不吃 `Tenacity`，净化也存在例外

因此：

- “是否受 `Tenacity` 影响”
- “是否可被净化”
- “净化是移除整个状态，还是只移除状态部分”

都应该是显式规则，不应只靠一个 `cleanseable_cc` 标签概括

### 3.8 Stasis（金身）是独立的"无敌+无法行动"复合态

与其他控制不同，`Stasis` 同时满足：

- 目标无法执行任何动作（类似最强硬控）
- 目标 **完全免伤**（不受任何伤害）
- 目标 **不可被选取**（不会成为技能目标）

这不是普通控制标签能表达的，需要引入 `invulnerable / untargetable` 概念：

- 引擎在伤害管线中需要增加"目标状态检查"步骤
- 该检查发生在护盾吸收之前
- 若目标存在 `invulnerable` 标签，则伤害直接归零

### 3.9 Charm 与 Berserk 的强制行为方向

`Forced Action` 类控制的方向差异：

- `Fear / Flee`：被迫远离来源
- `Charm`：被迫走向来源（方向相反于 Fear）
- `Taunt`：被迫尝试对来源进行普攻
- `Berserk`：被迫攻击最近单位（含友军，1v1 等价于攻击敌方）

因此 `ControlDirectiveInstance.kind` 需要覆盖这四种方向。

### 3.10 Blind（致盲）是"动作执行但效果无效"而非"动作禁止"

`Blind` 不阻止普攻动作本身，而是使普攻 **miss**（伤害为 0）。这与 `Disarm`（完全禁止普攻）不同。

需要在规则层区分：

- `blocks`：完全禁止动作
- `modifies`：动作可执行但效果被修改（如 miss）

### 3.11 Ground（缚地）只禁止位移类技能

`Ground` 不禁止所有技能，只禁止带 `dash / blink / movement_spell` 标签的位移类技能。

需要技能侧声明 `abilityTags`，规则侧支持按标签过滤。

### 3.12 Sleep（睡眠）的"受伤即醒"机制

`Sleep` 等同于 `Stun`，但受到任何伤害后立即移除。

需要状态支持 `breakOnEvents` 触发移除机制。

## 4. 运行时模型补充

## 4.1 `RuntimeState` 新增容器

在现有 `RuntimeState` 基础上新增：

```ts
type RuntimeState = {
  combatants: Record<string, CombatantRuntime>
  cooldowns: Record<string, unknown>
  stacks: Record<string, unknown>
  modifiers: ModifierInstance[]
  dotInstances: DotInstance[]

  statusInstances: StatusInstance[]
  controlDirectives: ControlDirectiveInstance[]
  activeExecutions: ExecutionInstance[]
}
```

### 4.1.1 `StatusInstance`

```ts
type StatusInstance = {
  instanceId: string
  statusId: string
  sourceId: string
  ownerId: string
  appliedAtMs: number
  expireAtMs: number | null
  stacks: number
  tags: string[]
  linkedDirectiveIds?: string[]
  flags?: {
    dispellable?: boolean
    visible?: boolean
    affectedByTenacity?: boolean
    cleanseMode?: "normal" | "status_only" | "never"
  }
}
```

用途：

- 表达控制、增益、免控、霸体、禁止普攻、禁止施法等持续状态。
- 不直接决定“能否行动”，而是提供标签，由规则矩阵解释。
- 对于 `airborne / fear / taunt` 这类机制，`StatusInstance` 只承载“状态部分”，不强行承载其强制位移 / 强制行为部分。

### 4.1.2 `ControlDirectiveInstance`

```ts
type ControlDirectiveInstance = {
  directiveId: string
  ownerId: string
  sourceId: string
  linkedStatusInstanceId?: string
  kind:
    | "forced_move_away_from_source"   // Fear / Flee
    | "forced_move_toward_source"      // Charm
    | "forced_attack_source"           // Taunt
    | "forced_attack_nearest"          // Berserk
    | "forced_displacement"            // Airborne displacement
  appliedAtMs: number
  expireAtMs: number | null
  priority?: number
  flags?: {
    affectedByTenacity?: boolean
    cleanseMode?: "normal" | "status_only" | "never"
    overridesSameKind?: boolean
  }
}
```

用途：

- 表达 `fear / taunt / airborne` 这类“除了状态，还需要强制某种行为 / 位移”的控制组件。
- 在 1v1 纯伤害模拟里，不要求其携带完整空间轨迹，但要保留“是否失去自由动作权、是否会覆盖同类 directive、是否可被净化”的语义。

### 4.1.3 `ExecutionInstance`

```ts
type ExecutionInstance = {
  executionId: string
  ownerId: string
  skillId: string
  startedAtMs: number
  currentPhaseKey: string
  state: "casting" | "channeling" | "resolved" | "cancelled" | "finished"
  interruptible: boolean
  interruptPriority?: number
  interruptGroupKey?: string
  scheduledEventKeys: string[]
  spawnedPersistentHandles?: string[]
}
```

用途：

- 表示“当前正在执行的某个技能实例”。
- 打断时取消哪些后续事件，依赖这个实例，而不是依赖技能模板本身。
- 当同一单位存在多个执行实例时，通过 `interruptPriority / interruptGroupKey` 决定打断选择策略。

说明：

- `disrupt` 这类一次性打断不需要创建 `StatusInstance`。
- 它更适合在事件流里以 `effect_tag` 的方式直接命中 `ExecutionInstance`。

## 5. 全局规则层：`combat_rule_profiles`

## 5.1 作用

`combat_rule_profiles` 负责定义“标签如何变成行为”，避免把控制逻辑散落到每个技能 JSON 中。

它至少要回答六类问题：

1. 某类状态会阻止哪些动作。
2. 某类状态会强制角色做什么。
3. 某类状态或瞬时效果会打断哪些执行阶段。
4. 哪些免控标签能免疫哪些控制标签 / 强制位移。
5. 哪些净化动作能移除哪些控制标签 / 强制行为组件。
6. 哪些状态持续时间会被 `Tenacity` 等规则修正。

## 5.2 推荐数据结构

```ts
type CombatRulesV2 = {
  version: 2
  actionBlockRules: ActionBlockRule[]
  actionModifyRules: ActionModifyRule[]      // Blind 等"动作可执行但效果被修改"
  forcedActionRules: ForcedActionRule[]
  interruptRules: InterruptRule[]
  immunityRules: ImmunityRule[]
  cleanseRules: CleanseRule[]
  durationModifierRules: DurationModifierRule[]
  damageImmunityRules: DamageImmunityRule[]  // Stasis 等"完全免伤"
}

type ActionBlockRule = {
  statusTag: string
  blocks: Array<"basic_attack" | "cast_skill" | "cast_item" | "move">
  blockSkillsWithTags?: string[]  // Ground: 只禁止带指定标签的技能 (如 "dash", "blink")
}

type ActionModifyRule = {
  statusTag: string
  modifies: "basic_attack"
  effect: "miss"  // Blind: 普攻 miss，伤害为 0
}

type DamageImmunityRule = {
  statusTag: string
  immuneTo: Array<"all" | "physical" | "magic" | "true">
  untargetable?: boolean  // Stasis: 不可被选取
}

type ForcedActionRule = {
  statusTag: string
  directive: "move_away_from_source" | "move_toward_source" | "basic_attack_source" | "basic_attack_nearest"
  requiresEnabledAction?: "move" | "basic_attack"
  overrideGroup?: "forced_action"
}

type InterruptRule = {
  causeKind: "status_tag" | "effect_tag"
  causeKey: string
  interrupts: Array<"cast" | "channel" | "basic_attack_windup" | "dash" | "movement_channel">
  selection?: "highest_priority" | "all"
}

type ImmunityRule = {
  immunityTag: string
  preventsStatusTags: string[]
  preventsDirectiveKinds?: Array<
    "forced_move_away_from_source" |
    "forced_move_toward_source" |
    "forced_attack_source" |
    "forced_attack_nearest" |
    "forced_displacement"
  >
}

type CleanseRule = {
  cleanseTag: string
  removesStatusTags: string[]
  removesDirectiveKinds?: Array<
    "forced_move_away_from_source" |
    "forced_move_toward_source" |
    "forced_attack_source" |
    "forced_attack_nearest" |
    "forced_displacement"
  >
}

type DurationModifierRule = {
  statusTag: string
  affectedBy: Array<"tenacity">
  excludesLinkedDirectiveKinds?: Array<"forced_displacement">
}
```

## 5.3 为什么要单独放全局规则

如果不做这层，全都会散进技能 JSON：

- 眩晕要禁攻禁放
- 沉默只禁放技能
- 缴械只禁普攻
- 恐惧要强制远离来源
- 嘲讽要强制普攻来源
- 击飞会打断引导，但其位移部分不一定可被净化
- 压制不吃 `Tenacity`
- 霸体到底免疫普通控制、位移控制，还是两者都免疫

这样会导致：

- 同一种控制语义在不同技能里被重复定义。
- 平衡或规则调整时需要批量修改技能配置。
- 版本 diff 很脏，不利于检查规则变化。

## 6. 状态定义层：`status_profiles`

## 6.1 作用

`status_profiles` 定义“这个状态是什么”，而 `combat_rule_profiles` 定义“这种状态会造成什么行为后果”。

这层建议新增，而不是强塞进 `types/type_relations`。原因是 `types` 更适合语义分类，不适合承载引擎强语义。

## 6.2 推荐字段

```ts
type StatusProfile = {
  statusId: string
  name?: string
  tags: string[]
  linkedDirective?: {
    kind?: "forced_move_away_from_source" | "forced_move_toward_source" | "forced_attack_source" | "forced_attack_nearest" | "forced_displacement"
    durationSource?: "status_duration" | "separate"
  }
  stacking?: {
    mode: "refresh" | "stack" | "independent"
    maxStacks?: number
  }
  durationPolicy?: {
    defaultDurationMs?: number
    affectedByTenacity?: boolean
  }
  removalPolicy?: {
    cleanseMode?: "normal" | "status_only" | "never"
    cleanseTags?: string[]
    breakOnEvents?: Array<"on_damage_taken" | "on_spell_hit">  // Sleep 受伤即醒
  }
  onExpire?: {
    applyStatus?: string  // Drowsy 结束时施加 Sleep
  }
}
```

示例：

- `stun_basic`
  - `tags = ["hard_cc", "stun"]`
- `silence_basic`
  - `tags = ["soft_cc", "silence"]`
- `fear_basic`
  - `tags = ["hard_cc", "fear"]`
  - `linkedDirective.kind = "forced_move_away_from_source"`
- `taunt_basic`
  - `tags = ["hard_cc", "taunt"]`
  - `linkedDirective.kind = "forced_attack_source"`
- `airborne_basic`
  - `tags = ["hard_cc", "airborne"]`
  - `linkedDirective.kind = "forced_displacement"`
  - `durationPolicy.affectedByTenacity = false`
  - `removalPolicy.cleanseMode = "status_only"`
- `suppression_basic`
  - `tags = ["hard_cc", "suppression"]`
  - `durationPolicy.affectedByTenacity = false`
- `sleep_basic`
  - `tags = ["hard_cc", "sleep"]`
  - `removalPolicy.breakOnEvents = ["on_damage_taken"]` // 受伤即醒
- `charm_basic`
  - `tags = ["hard_cc", "charm"]`
  - `linkedDirective.kind = "forced_move_toward_source"` // 走向施法者
- `berserk_basic`
  - `tags = ["hard_cc", "berserk"]`
  - `linkedDirective.kind = "forced_attack_nearest"` // 攻击最近单位
- `polymorph_basic`
  - `tags = ["hard_cc", "polymorph", "silence", "disarm"]` // 复合：禁止施法+禁止普攻
- `drowsy_basic`
  - `tags = ["soft_cc", "drowsy", "slow"]`
  - `onExpire.applyStatus = "sleep_basic"` // 结束时施加睡眠
- `stasis_basic`
  - `tags = ["hard_cc", "stasis", "invulnerable", "untargetable"]`
  - `durationPolicy.affectedByTenacity = false`
  - `removalPolicy.cleanseMode = "never"` // 不可净化
- `ground_basic`
  - `tags = ["soft_cc", "ground"]`
  - 配合 `ActionBlockRule.blockSkillsWithTags = ["dash", "blink"]`
- `blind_basic`
  - `tags = ["soft_cc", "blind"]`
  - 配合 `ActionModifyRule.effect = "miss"`
- `generic_cc_immune`
  - `tags = ["cc_immune"]`
- `generic_displacement_immune`
  - `tags = ["displacement_immune"]`

## 6.3 为什么建议单独建表

如果只靠 `mechanics_config` 临时写：

- 数据复用差
- 不同技能施加同一控制时容易写出不同语义
- 净化、免疫、持续时间、叠层规则难以统一校验

因此建议新增：

```sql
CREATE TABLE public.status_profiles (
    game_id varchar(64) NOT NULL,
    status_id varchar(64) NOT NULL,
    start_version_id bigint NOT NULL,
    end_version_id bigint NOT NULL,
    status_config jsonb NOT NULL DEFAULT '{}',
    description varchar(255),
    updated_at timestamp NOT NULL DEFAULT NOW(),
    CONSTRAINT pk_status_profiles PRIMARY KEY (game_id, status_id)
) PARTITION BY LIST (game_id);
```

日志表与发布链路按现有 `formula_profiles` 模式做即可。

## 7. `timing_profile` 扩展：技能生命周期状态机

## 7.1 现状问题

当前 `timing_profile` 主要承载前摇、后摇、引导时间等时间参数，但还不够表达：

- 哪个阶段可被打断
- 被打断后取消哪些后续事件
- 技能何时真正 `resolve`
- `resolve` 后是否生成独立持续效果

## 7.2 推荐结构

```ts
type TimingProfileV2 = {
  castPermission?: CastPermissionPolicy
  phases: SkillPhase[]
}

type CastPermissionPolicy = {
  usableWhileBlockedByStatusTags?: string[]
  usableDuringDirectiveKinds?: Array<
    "forced_move_away_from_source" |
    "forced_move_toward_source" |
    "forced_attack_source" |
    "forced_attack_nearest"
  >
}

type SkillPhase = {
  phaseKey: string
  kind: "cast" | "channel" | "recovery" | "persistent_effect"
  durationMs: number
  interruptible?: boolean
  interruptPriority?: number
  interruptGroupKey?: string
  blocksActions?: Array<"basic_attack" | "cast_skill" | "cast_item" | "move">
  onEnterEmit?: string[]
  onFinishEmit?: string[]
  cancelScheduledOnInterrupt?: boolean
  spawnPersistentEffectOnFinish?: boolean
}
```

## 7.3 典型技能差异

### 卡特 R

- `channel` 阶段可打断
- 每个匕首 tick 都属于当前 `ExecutionInstance`
- 被打断时 `cancelScheduledOnInterrupt = true`

### 末日 R

- 先有 `channel` 阶段
- 若在 `channel` 内被打断，则整个技能失败
- 若 `channel` 成功结束，则进入 `persistent_effect`
- 后续伤害由独立效果实例承载，不再依附当前施法状态

### 奥拉夫 R

- 自身施加 `cc_immune`
- 若技能语义还包含“免位移”，则额外施加 `displacement_immune`
- 后续新的控制不会进入，不会触发打断

## 9. 执行流程建议

## 9.1 施法尝试

1. 入队 `cast_intent`
2. 聚合施法者自身身上的 `statusInstances.tags` 与 `controlDirectives`
3. 读取技能自身的 `timing_profile.castPermission`
4. 结合 `combat_rule_profiles.actionBlockRules` 判断是否允许 `cast_skill`
5. 若技能显式声明可在部分控制下施法，则按白名单豁免对应 `statusTag / directive`
6. 若被拦截：
   - 触发 `on_cast_blocked`
   - 本次施法结束
7. 若允许：
   - 创建 `ExecutionInstance`
   - 进入 `timing_profile.phases[0]`

## 9.2 新状态进入时

1. 解析 `StatusProfile`
2. 先过免控矩阵：
   - 若目标当前存在对应 `immunityTag`，则状态不生效
3. 若不免疫：
   - 创建 `StatusInstance`
   - 若 `StatusProfile.linkedDirective` 存在，则创建对应 `ControlDirectiveInstance`
   - 触发 `on_status_gain`
   - 根据 `interruptRules(causeKind = status_tag)` 判断是否中断当前 `ExecutionInstance`

## 9.3 瞬时打断（`disrupt`）发生时

1. 某个动作或命中效果发出 `effectTag = disrupt`
2. 不创建 `StatusInstance`
3. 直接根据 `interruptRules(causeKind = effect_tag)` 选择要中断的 `ExecutionInstance`
4. 触发 `on_disrupt`

## 9.4 打断时

1. 找到目标当前可打断的 `ExecutionInstance`
2. 按 `selection = highest_priority | all` 决定命中的实例集合
3. 标记 `state = cancelled`
4. 根据 `cancelScheduledOnInterrupt` 取消后续计划事件
5. 触发 `on_interrupt`

## 9.5 强制行为进入 / 覆盖时

1. 若目标已有同 `overrideGroup` 的 `ControlDirectiveInstance`，则旧 directive 结束
2. 新 directive 入场
3. 若 directive 依赖的动作当前已被禁用：
   - 不制造非法动作
   - 仅保留“失去自由动作权”的语义

## 9.6 解控时

1. 执行 `cleanse_status`
2. 根据 `cleanseRules` 删除匹配 `StatusInstance`
3. 再根据 `cleanseRules` 删除允许移除的 `ControlDirectiveInstance`
4. 触发 `on_status_cleanse`
5. 已被取消的执行实例不会恢复，除非技能本身另有重启逻辑

## 10. 几个典型例子

## 10.1 船长 W / 净化类物品

目标：

- 被控制期间仍可施放
- 生效后移除可净化控制

表达方式：

- 技能自身声明 `castPermission`
- 动作里执行 `cleanse_status`

示意：

```json
{
  "castPermission": {
    "usableWhileBlockedByStatusTags": ["stun", "fear", "taunt"]
  },
  "actions": [
    {
      "type": "cleanse_status",
      "cleanse": {
        "target": "self",
        "cleanseTags": ["cleanseable_cc"]
      }
    }
  ]
}
```

## 10.2 卡特 R

目标：

- 引导期间持续发射匕首
- 若被打断，后续匕首全部取消

表达方式：

- `timing_profile` 中定义 `channel` 阶段
- 匕首 tick 事件绑定到当前 `ExecutionInstance`
- `cancelScheduledOnInterrupt = true`

## 10.3 末日 R

目标：

- 引导期间被打断则技能失败
- 一旦引导成功，后续 5 秒效果独立存在

表达方式：

- 先 `channel`
- 成功后进入 `persistent_effect`
- 持续伤害实例脱离当前 `ExecutionInstance`

## 10.4 恐惧 / 嘲讽类控制

目标：

- 恐惧期间被迫远离来源
- 嘲讽期间被迫尝试普攻来源
- 同类强制行为互相覆盖

表达方式：

- 先创建 `StatusInstance`
- 再创建与状态关联的 `ControlDirectiveInstance`
- `forcedActionRules` 负责把 `fear / taunt` 标签解释为具体 directive

## 10.5 击飞 / 压制类控制

目标：

- 击飞既会造成控制状态，也会造成强制位移
- 压制会完全封锁动作，但净化 / `Tenacity` 语义和普通硬控不同

表达方式：

- `airborne`：`apply_status + apply_control_directive(kind = forced_displacement)`
- `suppression`：通常只建模为状态本体，不额外强制位移；其 `durationPolicy / removalPolicy` 单独配置

## 10.6 霸体 / 位移免疫类效果

目标：

- 只免疫普通控制
- 或者同时免疫位移控制

表达方式：

- 挂 `cc_immune`
- 必要时再挂 `displacement_immune`
- `combat_rule_profiles.immunityRules` 分别拦截 `statusTag` 与 `directiveKind`

## 11. 对现有 DB 的影响

## 11.1 `skills` 表

不建议新增更多标量列。保持：

- `params`
- `timing_profile`
- `mechanics_config`

原因：

- 控制与打断是结构化生命周期问题，不适合拆成 `is_interruptible`、`can_cast_while_stunned` 这类零散列。
- 复杂技能一定会出现多阶段、多例外、多后果，JSON 状态机更稳。

## 11.2 新增表建议

### 必需：`combat_rule_profiles`

职责：

- 定义控制标签对动作、强制行为和打断的影响
- 定义免控矩阵
- 定义净化矩阵
- 定义持续时间修正规则（如 `Tenacity`）

### 强烈建议：`status_profiles`

职责：

- 统一定义状态模板
- 让技能、装备、被动复用同一状态定义
- 统一描述状态的 `Tenacity / Cleanse / linkedDirective` 语义

- `charm`
- `berserk`
- `sleep`
- `blind`
- `ground`
- `polymorph`
- `stasis`
- `invulnerable`
- `untargetable`
- `cc_immune`
- `displacement_immune`
- `unstoppable`
- `cleanseable_cc`

首批建议先支持这些瞬时效果标签：

- `disrupt`

首批建议先支持这些动作封锁：

- `basic_attack`
- `cast_skill`
- `cast_item`

首批建议先支持这些动作修改：

- `miss` (Blind 致盲)

首批建议先支持这些强制行为：

- `forced_move_away_from_source` (Fear / Flee)
- `forced_move_toward_source` (Charm)
- `forced_attack_source` (Taunt)
- `forced_attack_nearest` (Berserk)

`move` 可以先保留接口，但在 1v1 纯伤害模拟里不做完整空间模型。

补充说明：

- `fear / taunt / charm / berserk` 在 MVP 中先落“动作约束 + 强制目标”语义，不展开真实路径、距离、绕路逻辑
- `airborne` 在 MVP 中必须拆成“状态 + 强制位移组件”，否则后续 `Tenacity / Cleanse / Immunity` 规则无法稳定扩展
- `sleep` 需要支持 `breakOnEvents` 机制
- `stasis` 需要支持 `damageImmunityRules` 和 `untargetable` 检查
- `ground` 需要支持 `blockSkillsWithTags` 按技能标签过滤
- `blind` 需要支持 `actionModifyRules` 的 miss 效果
