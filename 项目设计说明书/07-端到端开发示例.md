## 示例一：给英雄加一个普攻被动（每第 3 次普攻造成额外魔法伤害）

目标机制：某英雄每打出第 3 次普攻命中时，额外造成 `40 + 0.6×AP` 的魔法伤害。

### 步骤 1 · 录入（前端 Admin）

在 `#/skills` 新建/编辑一个被动技能（owner = 该英雄），用技能编辑器（[前端 §6.1](./02-前端设计.md#61-技能机制编辑componentsskill-editor-skillsmodal)）配置 `mechanicsConfig.dpsPassiveEffects`：

```json
{
  "version": 1,
  "triggers": [],
  "dpsPassiveEffects": [
    {
      "passiveId": "every_third_hit_magic",
      "ownerRole": "attacker",
      "triggerKind": "every_n_basic_attack_hit",
      "everyN": 3,
      "internalCooldownMs": 0,
      "operations": [
        {
          "kind": "damage",
          "targetRole": "target",
          "damageType": "magic",
          "amount": 40,
          "attackerAttr": "ability_power",
          "attackerAttrRead": "resolved",
          "attackerAttrRatio": 0.6
        }
      ]
    }
  ]
}
```

保存时前端 `validateDpsPassiveEffects` 校验 `version=1`、`triggers` 为数组、`passiveId/ownerRole/trigger 或 triggerKind/operations` 合法（有 error 阻止保存）。该被动技能需通过 `#/skill-mounts` 挂到目标英雄（`targetCategory=hero`）。

> `amount` 与 `attackerAttr*` 的合成规则见 [Wasm §5.4 `resolveOperationAmount`](./05-Wasm计算引擎设计.md#54-operation-语义机制-配置的操作)：`amount = 40 + AP_resolved × 0.6`。

### 步骤 2 · 存储（后端 + DB）

`PUT /api/admin/games/lol/skills/{skillId}`（[后端 §4.4](./03-后端设计.md#44-代表性请求响应-json可拷贝)）写入：

- `public.skills.mechanics_config`（JSONB）← 上面的 `mechanicsConfig`，绑定 `__workspace__` 版本（`start=end=workspaceVersionId`）。
- `public.skill_mounts` ← 挂载关系。
- 写 `"user".edit_log` 审计。

涉及表见 [数据库 §3.5](./04-数据库设计.md#35-归属英雄技能装备)。

### 步骤 3 · 发布（后端）

`POST /api/admin/games/lol/versions:publish {versionCode:"14.2"}`：`buildBundle()` 把该 skill（含 `mechanicsConfig`）+ `skillMounts` 组装进 `bundle_json`，`validateBundleForPublish()` 校验引用（owner 英雄存在、operations 形态正确），写 `published_bundle_snapshots`，推进版本区间。算法见 [后端 §5.2](./03-后端设计.md#52-版本与发布算法)。

### 步骤 4 · 读取 + 编译（前端适配层）

读端：`loadPublishedBundleSnapshot('lol')`（命中 IndexedDB 则跳过网络）→ 得到 `bundle.skills[].mechanicsConfig`。

`prepareV2DpsInput(bundle, selection, ...)`（[前端 §7.2](./02-前端设计.md#72-适配层存储配置-引擎配置)）把存储层配置**编译为引擎层配置**：解析英雄/装备/技能 → 把该被动展开进 `resolvedSnapshot.passiveEffects[]`（已展开的操作列表）→ 产出 `{ engineBundle, runInput, preflightBlockedReasons }`。Preflight 会检查目标含 `target_dummy`、攻击方有 `basic_attack` 模板等。

### 步骤 5 · 计算（Wasm 引擎）

`init(engineBundle)` → `beginRun(runInput)`（**无 mode 参数**；引擎按 `runInput` 的 JSON 形态识别走 DPS 分支，`single_attacker_dps` 仅为说明性/日志标签）。引擎按 [Wasm §5.2 主循环](./05-Wasm计算引擎设计.md#52-主循环算法)推进站桩普攻：

1. 每次普攻命中 → `processAttackPassives`。
2. 命中计数到第 3 次时 `triggerKind=every_n_basic_attack_hit`（`everyN=3`）门控通过。
3. operation `kind=damage` → `resolveOperationAmount`（`40 + AP×0.6`）→ 走伤害管线（乘区 → 护甲减伤/魔抗+穿透 → 应用 HP）。
4. 产出 `effectBreakdown` 证据（含本次 operation 的数值与 critContext）。

无需改任何 Go 代码——`every_n_basic_attack_hit` 与 `damage` 都是引擎已支持的配置项。

### 步骤 6 · 验证（前端）

`#/wasm-validation-v2-dps` 选该英雄 + 目标假人 → 运行 → ECharts 看 DPS 曲线，证据面板看每第 3 次普攻的额外魔法伤害分量。

### 数据流回顾

```
技能编辑器 mechanicsConfig.dpsPassiveEffects[]   (① 存储层配置)
  → PUT skills → skills.mechanics_config + skill_mounts (DB)
  → publish → buildBundle → bundle.skills[].mechanicsConfig
  → loadPublishedBundleSnapshot
  → prepareV2DpsInput 展开 → passiveEffects[]          (② 引擎层配置)
  → engine begin_run → every_n 门控 → damage operation → 伤害管线
  → effectBreakdown 证据 → DPS 页展示
```

## 示例二：给一条伤害加一个公式（体现"公式即程序"）

目标：把上例的额外伤害从"线性 `40 + 0.6×AP`"改成"由公式表达"，演示公式 AST。

引擎层公式定义（`engineBundle.formulas`，由适配层从公式中心 / 录入编译而来）：

```json
[
  { "id": "extra_base",   "op": "const", "value": 40 },
  { "id": "ap_value",     "op": "attr",  "attr": "ability_power", "attrRead": "resolved" },
  { "id": "ap_ratio",     "op": "const", "value": 0.6 },
  { "id": "ap_part",      "op": "mul",   "left": "ap_value", "right": "ap_ratio" },
  { "id": "extra_magic",  "op": "add",   "left": "extra_base", "right": "ap_part" }
]
```

编译（[Wasm §4.2](./05-Wasm计算引擎设计.md#42-编译表达式树-后缀字节码internalformulaformulago)）后 `extra_magic` 的字节码：

```
[OpConst 40] [OpAttr ability_power(resolved)] [OpConst 0.6] [OpMul] [OpAdd]
```

求值（[Wasm §4.3](./05-Wasm计算引擎设计.md#43-求值栈式虚拟机registryeval-evaltrace)）：注入 `EvalContext.SourceAttrs` = 攻击者属性，栈机依次执行 → 结果 `40 + AP×0.6`；`EvalTrace` 还能逐步输出 breakdown 作为证据。

**要点**：要新增"基于缺失血量""基于等级"等任意公式，只需在配置里组合 `attr/const/mul/add/...` 节点，引擎无需改代码——这就是"公式即程序、引擎即解释器"。

## 通用扩展心法

| 想加什么 | 在哪加（配置优先） | 何时才需改引擎代码 |
|----------|-------------------|--------------------|
| 新英雄/装备/技能数值 | DB 数据 + 录入 | 从不 |
| 新公式（任意数值计算） | `formula` 配置（表达式树） | 从不（除非需要新算子 op） |
| 已支持类型的新被动机制 | `dpsPassiveEffects`（triggerKind + operation） | 从不 |
| 新乘区/属性修饰 | `coefficient_buckets` + operation `bucketKey` | 从不 |
| **全新的触发时机或 operation 类型** | — | 需扩引擎：`dps_contract` 常量 + handler 分支 + 校验（见 [Wasm §10](./05-Wasm计算引擎设计.md#十重开发检查清单)） |
| **新公式算子**（如 pow/clamp） | — | 需扩 `formula.compile` switch + `Eval` switch |

> 判断"加配置还是改代码"的准则：**目标语义能否用现有 triggerKind / operation / 公式算子 组合表达**。能 → 纯配置；不能 → 先扩引擎能力（一次），之后同类机制回到纯配置。
