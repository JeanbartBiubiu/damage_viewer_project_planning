## 一、功能说明：数据库要做什么

1. **多游戏存储**：以 `game_id` 隔离并物理分区多款游戏的机制数据。
2. **版本化**：用「版本区间字段 + 发布快照」记录编辑态与发布态，玩家只读发布快照。
3. **承载可演进机制**：用 JSONB（`mechanics_config`、`base_stats` 等）存放灵活的机制配置。
4. **审计与统计**：独立 `"user"` schema 存账号、编辑日志、PV/UV。

设计取向：**分文件手写 DDL，无 Flyway/Liquibase**；演进靠独立兼容 SQL 手工执行；第一版只保留少量稳定引用的 DB 级 FK（版本区间、类型/归属/公式/技能等基础定义），对 `target_category + target_id`、英雄/装备/技能归属对象等软引用不做全量跨业务 FK，引用完整性主要由后端写入/发布校验保证。

## 二、核心模型与约定（先理解三件事）

### 2.1 版本区间 + `__workspace__` + `_log`（最关键）

| 概念 | 说明 |
|------|------|
| 编辑态版本 | 首次写入时在 `game_versions` 建一行 `version_code='__workspace__'`（保留码，禁止发布），取得 `version_id` |
| 主表存"当前编辑头" | 每个业务 ID 在主表**只有 1 行**（PK 不含版本）；upsert 时 `start_version_id = end_version_id = workspace_version_id` |
| 发布推进区间 | 发布时创建新 `game_versions` 行得 `versionId`；对"自上次发布后变更"的行 `SET start_version_id=end_version_id=versionId`（即发布点快照区间 `[v,v]`），并写入 `_log` 表字段快照 |
| `_log` 表 | PK 含 `start_version_id`，记录该实体在各版本起点的历史快照，用于多版本差异分析 |
| 读模型 | Public **只读** `published_bundle_snapshots.bundle_json`，从不实时拼装主表 |

发布算法详见 [后端 §5.2](./03-后端设计.md#52-版本与发布算法)。

### 2.2 多游戏 LIST 分区

- 业务表 `PARTITION BY LIST (game_id)`；分区表命名 `{父表}_{game_id}`（如 `heroes_lol`）。
- `db/game_manage/triggers.sql` 的 `ensure_game_partitions(game_id)` 幂等为 ~35 张父表（含 `_log`）建分区；`games` AFTER INSERT 触发器自动调用。
- 非分区表：`games`、`game_versions`、`published_bundle_snapshots`、`game_progression_schema`、`owner_categories`、`reserved_type*`。

### 2.3 软删与软引用

`type_relations.deleted` 为 tombstone 软删；发布 bundle 时过滤 `deleted`，对外 DTO 不暴露该字段。无独立 DELETE 端点，删除经"按目标全量替换"实现（见 [前端设计 · 资源页通用机制](./02-前端设计.md)）。

### 2.4 目标类别（target_category）命名

同一英雄实体在不同表用不同 category 字符串（**有意为之**）：`type_relations` 用 `character`；`formula_bindings` / `skill_mounts` 用 `hero`。各表取值以其 CHECK 枚举/约定为准，完整对照见 [适配层规范 §10](./08-适配层编译规范.md#十跨端命名对照消除歧义)。

## 三、game_manage DDL（public schema）

> 约定：分区表以 `PARTITION BY LIST (game_id)` 标注；`_log` 表结构与主表一致但 PK 追加 `start_version_id`、无 `updated_at`，下文统一说明、不逐一展开。

### 3.1 游戏 / 版本 / 发布

```sql
CREATE TABLE public.games (
  game_id      varchar(64) PRIMARY KEY CHECK (game_id ~ '^[a-z0-9_]+$'),
  game_name    varchar(100) NOT NULL,
  game_img_url text,
  created_at   timestamp DEFAULT NOW()
);

CREATE TABLE public.game_versions (
  version_id   bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  game_id      varchar(64) NOT NULL REFERENCES public.games(game_id),
  version_code varchar(64) NOT NULL,           -- '__workspace__' 为编辑态保留码
  release_date date,
  is_current   boolean DEFAULT false,
  data_hash    varchar(64),                    -- 遗留字段，对外不再用
  created_at   timestamp DEFAULT NOW(),
  published_at timestamp,
  UNIQUE (game_id, version_code),
  UNIQUE (game_id, version_id)
);

CREATE TABLE public.published_bundle_snapshots (
  game_id      varchar(64) NOT NULL REFERENCES public.games(game_id),
  version_id   bigint NOT NULL,
  version_code varchar(64) NOT NULL,
  bundle_json  jsonb NOT NULL,                 -- 玩家只读的全量发布快照
  created_at   timestamp NOT NULL DEFAULT NOW(),
  updated_at   timestamp NOT NULL DEFAULT NOW(),
  PRIMARY KEY (game_id, version_code),
  UNIQUE (game_id, version_id),
  FOREIGN KEY (game_id, version_id) REFERENCES public.game_versions(game_id, version_id)
);

CREATE TABLE public.game_progression_schema (
  game_id            varchar(64) PRIMARY KEY REFERENCES public.games(game_id),
  progression_kind   varchar(16) NOT NULL CHECK (progression_kind IN ('LEVEL','STAR')),
  stage_min          int NOT NULL CHECK (stage_min >= 1),
  stage_max          int NOT NULL CHECK (stage_max >= stage_min AND stage_max <= 100),
  stage_label        varchar(32) NOT NULL,
  require_all_stages boolean NOT NULL DEFAULT true,
  updated_at         timestamp NOT NULL DEFAULT NOW()
);
```

CREATE TABLE public.type_relations (
  game_id          varchar(64) NOT NULL,
  start_version_id bigint NOT NULL,

5 张主表（均分区 + `_log`），关键约束摘要：

| 表 | PK | 关键列与 CHECK |
|----|----|---------------|

| `control_state_profiles` | `(game_id, control_profile_id)` | `control_kind`(stun/root/silence/disarm/taunt/fear/charm/airborne/...)；`movement_lock_mode`/`cast_lock_mode`/`attack_lock_mode`/`input_override_mode`/`displacement_kind` 枚举；`priority` 等 |

### 3.10 分区触发器（`triggers.sql`）

```sql
CREATE OR REPLACE FUNCTION public.ensure_game_partitions(p_game_id varchar) RETURNS void AS $$
DECLARE t text;
BEGIN
  FOREACH t IN ARRAY ARRAY[
    'heroes','heroes_log','skills','skills_log','items','items_log',
    'item_stat_modifiers','item_stat_modifiers_log','skill_mounts','skill_mounts_log',
    'attribute_definitions','attribute_definitions_log','images',
    'types','types_log','type_relations','type_relations_log',
    'formula_profiles','formula_profiles_log','formula_bindings','formula_bindings_log',
    'coefficient_buckets','coefficient_buckets_log',
    'status_action_control_rules','status_action_control_rules_log',
    'status_definitions','status_definitions_log',
    'status_modifier_groups','status_modifier_groups_log',
    'status_attribute_modifiers','status_attribute_modifiers_log',
    'status_periodic_hp_effects','status_periodic_hp_effects_log',
    'control_state_profiles','control_state_profiles_log'
  ] LOOP
    BEGIN
      EXECUTE format('CREATE TABLE public.%I PARTITION OF public.%I FOR VALUES IN (%L)',
                     t || '_' || p_game_id, t, p_game_id);
    EXCEPTION WHEN duplicate_table THEN /* 幂等 */ END;
  END LOOP;
END; $$ LANGUAGE plpgsql;

CREATE TRIGGER trg_games_after_insert_create_partitions
  AFTER INSERT ON public.games FOR EACH ROW
  EXECUTE FUNCTION public.ensure_game_partitions(NEW.game_id);
```

> 上述分区表名列表依据 `triggers.sql` 归纳；实际函数体以 `db/game_manage/triggers.sql` 为准。

## 五、数据与 Wasm 引擎的契约

### 5.1 数据流

```
PostgreSQL 编辑表 → 发布校验 → buildBundle() → published_bundle_snapshots.bundle_json
  → GET /api/games/{gameId}/versions/{versionCode}/bundle
  → 前端 tinygoV2*Adapter 解析编译为 EngineBundleV2 + DPS 输入
  → TinyGo 引擎 engine_init / begin_run
```

### 5.2 发布 Bundle 顶层结构（`buildBundle` 实际输出）

```json
{
  "meta": { "gameId": "lol", "versionCode": "14.1", "releaseDate": "...", "publishedAt": "...", "generatedAt": "..." },
  "attributeDefinitions": [], "coefficientBuckets": [],
  "types": [], "typeRelations": [],
  "heroes": [], "skills": [], "skillMounts": [], "items": [],
  "formulaProfiles": [], "formulaBindings": [],
  "statusActionControlRules": [], "statusDefinitions": [], "controlStateProfiles": [],
  "statusModifierGroups": [], "statusAttributeModifiers": [], "statusPeriodicHpEffects": [],
  "dictionaries": { "attrKeyToName": {"atk":"攻击力"}, "typeIdToName": {"1001":"射手"} }
}
```

- 各段元素字段与 Admin GET 单条 DTO 一致（camelCase）；`items[].statModifiers` 必为数组；`skills[].mechanicsConfig` 保留 `dpsPassiveEffects` 扩展字段；`dictionaries` 仅在有非空映射时出现。
- **存储层 → 引擎层并非 1:1**：`heroes/skills/items/skillMounts` 由前端适配层解析展开后才进入引擎。引擎 `EngineBundle`（源码 `EngineBundleV2`）顶层为 `schemaVersion/attributes/resources/actors/actions/statuses/statusActionControlRules/formulas/triggers/damageProfiles/coefficientBuckets/settings`；DPS 的英雄/装备/被动细节进入 `DPSInput.resolvedSnapshot.passiveEffects[]`，而不是作为 `heroes/items/skills` 直传给引擎。完整映射见 [适配层规范 §三](./08-适配层编译规范.md#三引擎层-dtoenginebundlev2-元素) 与 [Wasm §一](./05-Wasm计算引擎设计.md#一功能说明引擎要做什么)。

## 六·b、当前 SQL 待同步差异（诚实标注）

本章 §三/§四 是**设计口径（权威）**；当前 `db/*.sql` 与之存在以下已知差异或清理项，重建/校对时请以本表为准：

| 类别 | 设计口径（本章） | 当前 SQL 现状 | 处置 |
|------|------------------|----------------|------|
| **字段宽度/兼容列** | `version_code varchar(64)`、`attribute_definitions.min/max_value`、`status_periodic_hp_effects` 暴击列等为标准设计 | 旧库需经独立兼容 SQL 升级（`version_code_varchar64_compatibility_migration.sql`、`attribute_definitions_bounds_compatibility.sql`、`status_periodic_hp_effects_crit_compatibility.sql`）才与设计一致；未跑迁移的库会偏旧 | 新库按 §三 建即可；旧库执行 §七 兼容 SQL |
| **分区脚本遗留** | `ensure_game_partitions` 覆盖业务父表（含状态动作控制） | `triggers.sql` 已覆盖 `status_action_control_rules` / `_log` 分区；`lol_status_action_control_partitions.sql` 是早期手动建分区脚本，仍可作为幂等兼容脚本存在 | 非阻塞；后续可更新脚本注释或清理重复入口 |
| **Roadmap 过期/未建表** | `combat_rule_profile`、heal/shield 四通道相关表为 Roadmap（[§八](#八规划路线roadmap)） | SQL 中**无**对应表 | 属规划态，非差异 bug |
| **状态资源扩展 schema** | §三.8 状态资源表为设计的一部分 | 落在独立文件 `status_resource_schema.sql` 等，文件头注释自称"草案"，但后端已全链路接入 | 视为已落地；注释口径待更新 |

> 一句话：**新库以本章设计建表；现有 `db/*.sql` 跑通需对照上表。** 字段/注释类差异按"SQL 追平设计"处理；已自动化但仍留有早期手动脚本的项目按兼容清理处理。不要据此认为"当前 SQL 已与本章逐字一致、可直接按现状 SQL 验证"。
