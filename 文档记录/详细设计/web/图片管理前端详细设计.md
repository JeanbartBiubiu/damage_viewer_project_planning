# 阶段 8 图片管理前端详细设计

方案状态：项目负责人已于 2026-09-05 确认；前端代码、自动检查、隔离桌面端检查和真实后端浏览器验收均已完成。

## 1. 当前前端基线

1. `#/images` 已有页面，但导航名是“图片缓存”，主体是全量同步、增量同步、缓存清理和按稳定单段标识上传。
2. `ImagesPage.tsx` 直接调用通用 `apiClient.ts` 中的图片函数，没有独立图片类型和管理客户端。
3. `resourceImage.ts` 可以将本地图片居中裁切为 64×64 PNG 或 JPEG。
4. `imageCache.ts` 的浏览器本地数据库只保存旧 `uri`、更新时间和 Base64 内容，不认识停用记录。
5. 当前隔离桌面端检查只覆盖图片页可访问，没有覆盖完整图片管理流程。

现有按角色、装备、属性标识推导图片 URI 的辅助函数属于阶段 9 关系建立前的临时约定。阶段 8 删除这些推导函数和对应测试，只把用户明确填写的 `imageKey` 当作图片身份，不从前缀推断用途。

## 2. 页面与导航

保留 `#/images` 路由，将导航和页面标题统一改为“图片管理”。页面按当前桌面管理页模式提供：

1. “本地缓存工具”位于“图片管理”上方，提供同步状态、全量同步、增量同步和清理当前缓存。
2. 图片列表只读取当前游戏的浏览器本地数据库缓存，不请求后端管理列表；缓存为空时提示先执行全量同步。
3. 列表展示缓存缩略图、图片标识、缓存内容状态、启停状态和更新时间；关键词只按缓存中的图片标识筛选，状态筛选只处理缓存记录。
4. 行操作提供查看、编辑、替换图片、停用或启用。维护者点击这些操作后，页面才按图片标识读取后端管理详情。
5. “刷新缓存”、查询、重置和页面重新载入只重新读取浏览器本地数据库。全量或增量同步写入缓存后立即刷新列表，清理缓存后立即显示空状态。

页面不出现业务对象绑定、用途选择、游戏封面设置、发布或计算入口。

## 3. 新建与编辑弹窗

使用现有桌面宽度的 Arco 弹窗，不新增全局弹窗样式。

新建：

1. 图片标识、名称和图片文件必填，说明可空。
2. 图片标识实时按共享规则校验。
3. 选择文件后先检查 PNG/JPEG、源文件不超过 5242880 字节且宽高都在 1～4096 像素之间。
4. 宽高都不超过 64 像素时保留原内容，不放大；任一边超过 64 时按短边居中裁切为正方形，再等比缩小，输出边长为短边与 64 中的较小值。PNG 使用无损编码，JPEG 使用固定 92% 质量。
5. 页面显示实际待提交内容的预览、最终格式、实际尺寸和最终字节数；处理结果超过 262144 字节时不允许提交。
6. 保存前不写服务器或本地缓存。

编辑：

1. 图片标识和创建时间只读。
2. 名称、说明和状态可编辑。
3. 不选择新文件表示保留原图片；选择后显示新旧预览和“将替换图片内容”提示。
4. 停用需要确认；启用可直接保存。

400 或 409 时保持弹窗、字段、所选文件和预览，只定位错误；保存成功后关闭弹窗，以后端响应更新本地缓存，再从缓存刷新图片列表。

## 4. 前端类型与接口

新增独立 `image.ts` 类型和 `imageClient.ts` 客户端，承接管理详情、新建、更新和公开同步。页面不保留管理列表客户端调用。

从通用 `apiClient.ts` 移除图片专用方法，只复用其基础请求和统一错误能力。不保留 `uri` 兼容类型。

客户端应：

1. 对路径中的 `gameId` 和 `imageKey` 分别编码。
2. 创建时提交四个允许字段，其中 `imageBase64` 是浏览器处理完成、宽高均不超过 64 的内容；更新时只有实际替换图片才提交 `imageBase64`。
3. 严格归一化管理详情和公开同步响应；缺失关键字段时作为接口错误，不拼装半成品。
4. 将后端 `fieldIssues` 映射到图片标识、名称、说明、状态或内容区域。
5. 以保存响应中的图片和派生信息为最终结果，不假定浏览器处理结果已经绕过后端复核。
6. 图片裁切、缩放和重新编码只由浏览器负责；本地处理失败或最终内容不满足后端限制时不得提交原图。

## 5. 浏览器图片缓存

`IndexedDB` 是浏览器本地数据库。本阶段将 `image_db` 版本升级为 2，并直接重建可恢复的 `images` 存储区：

`ts
type CachedImageRecord = {
  cacheKey: string
  gameId: string
  imageKey: string
  enabled: boolean
  imageBase64: string | null
  updatedAt: string
}
`

规则：

1. `cacheKey` 固定为 `gameId:imageKey`。
2. 停用记录保留 `updatedAt`、清空图片内容，确保增量起点不会退回。
3. 公开取图只返回 `enabled=true` 且内容非空的记录。
4. 全量同步删除服务器集合之外的当前游戏缓存，再写入完整集合；增量同步只覆盖变化项。
5. 管理写入成功后用响应更新缓存；缓存失败只提示本地缓存异常，服务器成功状态不得伪装成失败回滚。
6. 版本 1 的本地缓存可直接清空，因为它能从服务器恢复；不写兼容迁移。
7. 本阶段不实现旧缓存文档中的跨游戏自动清理、容量统计或其他候选优化。
8. 图片管理列表与缓存统计共用同一次当前游戏缓存读取；列表不补查管理接口，也不因为本地为空而自动同步。

## 8. 前端停止条件

除共享契约停止条件外，若浏览器无法稳定保留合规小图，或无法按冻结规则裁切、缩放和编码出后端接受的最大 64×64 PNG/JPEG，或停用记录会被旧缓存结构误当成可展示图片，停止实现并修正当前方案；不得只显示压缩预览却提交原图，后端不会代为处理，也不得用占位图覆盖服务器上的停用状态。
