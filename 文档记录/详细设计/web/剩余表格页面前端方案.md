# 剩余表格页面前端方案

## 1. 背景与目标

当前后台前端已经围绕 4 张核心表展开设计和开发：

- `formulaProfiles`
- `formulaBindings`
- `coefficientBuckets`
- `statusActionControlRules`

本次需要补齐其余可编辑表的前端页面，重点是页面设计与实现，不扩展后端接口。

本轮补齐范围：

- `attributeDefinitions`
- `types`
- `typeRelations`
- `heroes`
- `skills`
- `items`

不在本轮范围：

- 图片编辑页重做
- 新增后端 `GET list/detail` 管理接口
- 新增前端自动化测试框架
- 调整发布链路的后端行为

## 2. 视觉与交互基调

### Visual Thesis

把后台做成“数据工位”而不是“卡片拼盘”：浅色雾面底、强层级标题、细颗粒状态标签，重点突出资源切换、表格扫描和当前编辑上下文。

### Content Plan

- 顶部：资源状态与当前工作上下文
- 中部左侧：资源列表 / 搜索 / 行状态
- 中部主区：创建、PUT、PATCH 编辑器
- 中部右侧：结构提示、依赖关系、当前记录摘要
- 底部：版本创建 / 发布 / bundle 刷新结果

### Interaction Thesis

- 资源切换时突出“当前资源”与“数据来源”，弱化无关面板
- 列表行通过 `bundle` / `session-draft` / `new` 状态标识让用户知道当前看到的是哪一层数据
- 成功保存后立即更新本地草稿覆盖层，让新增和修改结果不需要等发布也能继续编辑

## 3. 页面范围

保留现有 `#/admin/{resource}` 路由模式，补齐以下 6 个资源页面：

| 资源 | 路由 | 读取来源 | 写入接口 |
| --- | --- | --- | --- |
| 属性定义 | `#/admin/attribute-definitions` | current bundle + session overlay | `PUT/PATCH /attribute-definitions/{attrKey}` |
| 类型 | `#/admin/types` | current bundle + session overlay | `PUT/PATCH /types/{typeId}` |
| 类型关系 | `#/admin/type-relations` | current bundle + session overlay | `PUT/PATCH /type-relations/{typeId}/{targetCategory}/{targetId}` |
| 英雄 | `#/admin/heroes` | current bundle + session overlay | `PUT/PATCH /heroes/{heroId}` |
| 技能 | `#/admin/skills` | current bundle + session overlay | `PUT/PATCH /skills/{skillId}` |
| 装备 | `#/admin/items` | current bundle + session overlay | `PUT/PATCH /items/{itemId}` |

同时保留现有 4 张核心表页面，不改路由语义。

## 4. 关键约束与应对

### 4.1 后端约束

剩余 6 张表只有 `PUT/PATCH`，没有后台管理端的 `GET list/detail`。

同时后端当前明确不会在“非发布写入”后刷新 `currentVersion/bundle` 缓存，因此：

- 写入成功后，公共 bundle 不会立刻看到最新草稿
- 新建记录如果只依赖 bundle，会在列表里消失

### 4.2 前端应对策略

前端读取能力拆成两套：

1. 核心规则表读模型
   - `formulaProfiles / formulaBindings / coefficientBuckets / statusActionControlRules`
   - 继续使用现有 admin `GET list/detail`

2. 基础内容表读模型
   - `attributeDefinitions / types / typeRelations / heroes / skills / items`
   - 使用 `GET /versions/current -> GET /versions/{versionCode}/bundle`
   - 额外拉取 `GET /owner-categories`
   - 在前端生成跨资源引用索引

基础内容表的页面数据再拆成三层：

1. `bundle baseline`
   - 来自当前已发布 bundle
   - 作为列表、详情和跨资源校验的基线

2. `session overlay`
   - 来自当前会话的成功 `PUT/PATCH` 返回体
   - 以 `gameId + resource + key` 作为索引
   - 只保存在前端内存

3. `merged reference index`
   - 把 baseline 与 overlay 合并后生成
   - 提供给右侧提示区和前端校验辅助使用
   - 例如：
     - `skills.ownerType` 可用值来自 `ownerCategories`
     - `skills.ownerId` 从合并后的 `heroes/items` 索引获取
     - `typeRelations` 目标合法性从合并后的多资源索引判断
     - `items.skillRefs / recipeIds` 从合并后的 `skills/items` 索引判断

这样可以满足：

- 保存后列表立即可见
- 新建后可继续编辑
- 不依赖新增后端读取接口

限制必须明确保留：

- overlay 不是跨浏览器持久草稿
- 刷新页面后只保留已发布 baseline，不保留未发布 overlay
- 真正发布结果仍以版本创建 / 发布后的 bundle 为准

### 4.3 overlay 作用域

overlay 不能挂在 `AdminPage` 本地 state。

实现层面必须提升到 `App.tsx` 上层或独立 `admin draft store`，确保：

- 在 `#/admin/*` 资源之间切换时不丢
- 临时离开 `#/admin` 再回来时，本次会话的 overlay 仍在
- 发布成功后可以统一执行 rebase / clear

建议存储结构：

```ts
type AdminDraftOverlayStore = Record<
  string,
  Record<string, JsonObject>
>
```

说明：

- 第一层 key: `gameId:resourceKind`
- 第二层 key: `resourceKey`

### 4.4 无 current version / draft-only 流程

这部分必须写成明确流程，而不是只列状态。

分三种场景：

1. `没有任何 version`
   - 后端会拒绝写入
   - 页面进入阻断态
   - 只显示“先创建 version”引导，不允许对 6 张基础内容表执行写操作

2. `有 latest draft version，但没有 current published version`
   - 6 张基础内容表没有 baseline 可读
   - 页面进入 `bootstrap mode`
   - 允许基于空 baseline + session overlay 做本次会话内的新建和编辑
   - 必须在页面顶部明确提示：刷新后无法重新读回这些未发布草稿

3. `已有 current published version`
   - 正常进入 baseline + overlay 模式

本轮方案默认接受以下硬限制：

- 对这 6 张基础内容表，未 publish 前刷新页面，前端无法重新读回未发布草稿

如果业务不能接受这条限制，本轮不能只靠前端完成，必须补后端 admin `GET` 或 draft snapshot 读接口。

### 4.5 bootstrap mode 的触发判定

基于当前后端接口，前端无法仅靠读取接口区分：

- 完全没有 version
- 有 draft version 但没有 current published version

因为 `GET /versions/current` 在这两种场景下都只会表现为“当前版本不存在”。

所以本轮前端采用保守判定：

1. 当 `GET /versions/current` 失败时，统一先进入阻断态
   - 不直接假设可以 bootstrap
   - 页面提示“当前没有可读的 published baseline”

2. 只有当用户在本次会话内成功执行过 `create version` 后
   - 前端才允许 6 张基础内容表进入 `bootstrap mode`
   - baseline 视为“空 baseline”
   - 所有可见记录仅来自本次会话 overlay

3. 如果存在“历史 draft version 但当前无 published version”
   - 前端本轮不尝试恢复这份历史 draft
   - 用户需要接受无法恢复旧 draft 的限制，或等待后端补 draft 读取能力

## 5. 信息架构

### 5.1 侧边导航

后台资源导航拆成两组：

- 核心规则表
  - 公式档案
  - 公式绑定
  - 乘区档
  - 状态动作规则
- 基础内容表
  - 属性定义
  - 类型
  - 类型关系
  - 英雄
  - 技能
  - 装备

每个资源都保持独立 hash，可直接深链进入。

### 5.2 页面骨架

每个资源页面统一为三段式：

1. 资源顶部条
   - 当前资源名称
   - 当前 gameId
   - 数据来源状态
   - bundle 版本信息
   - overlay 记录数

2. 工作区
   - 左侧：搜索、计数、资源列表
   - 中间：创建 / PUT / PATCH 编辑器
   - 右侧：字段提示、关联约束、当前记录摘要

3. 底部控制区
   - 版本创建
   - 发布
   - 发布后的 current version / bundle 刷新反馈

移动端顺序改为：顶部条 -> 列表 -> 编辑器 -> 右侧提示。

### 5.3 权限边界

- public baseline 读取不依赖 JWT
- admin 写接口和 publish 依赖 JWT
- 401/403 时页面退化到只读态，不清空 overlay
- 401/403、`400.INVALID_BODY`、`422.SEMANTIC_ERROR` 都需要保留当前编辑上下文

## 6. 页面行为设计

### 6.1 列表区

列表区提供：

- 关键字搜索
- 资源计数
- 行来源标签
  - `bundle`
  - `session-draft`
  - `new`
- 打开当前记录按钮

不同资源采用配置化列定义，不为每张表单独手写整页。

### 6.2 编辑区

编辑区保留现有三种模式：

- `新增`
- `编辑 (PUT)`
- `修改 (PATCH)`

新增模式规则：

- 用户先填写资源主键
- 前端根据资源类型生成默认 JSON 草稿
- 点击 `使用 PUT 新增` 后直接走对应 `PUT`

PUT 模式规则：

- 主文本区显示完整 JSON
- 保存成功后更新 overlay

PATCH 模式规则：

- 单独维护局部 JSON
- 成功后用服务端返回体回填完整草稿区

### 6.3 右侧提示区

右侧不是装饰区，必须承担操作辅助：

- 当前资源主键说明
- 服务端强约束字段提示
- 关联关系提示
- 当前选中记录摘要
- 可选 ownerType / targetCategory / targetId 来源
- 服务端返回 `error.details.path` 的定位提示

示例：

- `skills` 需要 `ownerType / ownerId / mechanicsConfig`
- `heroes` 需要 `name / baseStats`
- `typeRelations` 需要目标类别合法且目标存在
- `attributeDefinitions` 的 `valueKind=rate` 时必须带 `rateTargetAttrKey`

右侧提示区的数据来源不是静态写死文本，而是：

- `ownerCategories`
- baseline + overlay 合并后的跨资源索引
- 当前服务端返回的错误详情

## 7. 组件与代码方案

### 7.1 前端实现原则

采用“配置驱动 + 共享工作台”，避免为 6 张表复制页面。

### 7.2 新增或调整的核心前端能力

- 扩展导航配置，加入 6 个资源入口
- 扩展 `App.tsx` 的 hash 解析与资源映射
- 在 `App.tsx` 或独立 store 挂载 overlay 状态
- 在 `api.ts` 中补齐剩余资源类型与可复用响应结构
- 在 `apiClient.ts` 中补齐 6 张表的 `PUT/PATCH` 写接口
- 在 `apiClient.ts` 中明确 public read / admin write 的边界
- 在后台页面中补一层 bundle 读取、ownerCategories 读取与 overlay 合并能力
- 抽离资源配置对象
  - 标签
  - 路由 segment
  - 主键生成 / 解析
  - 列表列定义
  - 默认创建 payload
  - 字段提示
  - 写接口映射
  - 右侧依赖提示规则
  - 行来源标识规则

请求策略明确为：

- public read:
  - 允许无 token
  - 支持取消、去重
- admin write:
  - 必须有 token
  - 不做自动重试
  - 统一把 `status/code/details/path` 透出到编辑器

## 9. 状态与异常

必须覆盖以下页面状态：

- 未选择 gameId
- 未填写 JWT
- 401 / 403 只读降级
- 没有任何 version，禁止写入
- draft-only bootstrap mode
- current version 不存在
- bundle 拉取中
- bundle 拉取失败
- overlay 为空
- 保存成功
- `400.INVALID_BODY`
- `422.SEMANTIC_ERROR`
- 网络失败

在 bundle 读取失败但已有 overlay 时，页面仍保留本次会话可见草稿，并明确标出“基线失效，仅显示本地草稿”。

错误展示规则：

- `error.details.path` 显示到编辑器顶部和右侧提示区
- 401/403 不清空表单
- 写入失败不回滚当前草稿文本
- publish 成功后提示 overlay 已重置或已与新 bundle 对齐
