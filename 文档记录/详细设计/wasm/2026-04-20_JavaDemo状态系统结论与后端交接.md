## 1. 本次结论

针对 `demo/java_engine_v2` 的持续时间 BUFF / DEBUFF 机制，当前可以下结论：

1. **当前实现已经支持“一个状态包含 N 个属性修改，并持续 M 秒”**。
2. **当前实现对“单个状态实例”的应用与移除，已经具备成组原子语义**。
3. **当前实现还不是成熟游戏引擎常见的多实例、可叠层、可分桶的完整 Active Effect 系统**。
4. **如果后续要落到正式数据平台和管理后台，状态定义、状态修饰器、叠层策略、前端结构化编辑模型，仍需补成一条完整链路**。

一句话总结：

> 现在的 Java demo 更像“按状态分组的最小可运行系统”，不是“生产级状态容器系统”。

---

## 2. 当前 Java Demo 是怎么处理持续 BUFF / DEBUFF 的

## 2.1 定义层

Java demo 里一个状态模板可同时携带：

- 状态 ID / 标签
- `durationMs`
- `refreshPolicy`
- `magnitudeFormulaId`
- `attrModifiers[]`
- `triggerSubscriptions[]`

其中 `attrModifiers[]` 支持多个属性修改，每个属性修改包含：

- `attrKey`
- `mode`：当前只支持 `FLAT` / `PERCENT`
- `formulaId`

这意味着下面这种结构，当前已经能表达：

- 攻击力 `+X`
- 攻速 `+Y%`
- 护甲 `+Z`
- 持续 `M` 秒
- 作为一个统一状态效果挂到角色身上

## 2.2 应用层

一次 `ApplyStatus` 执行时，会：

1. 读取状态模板
2. 计算状态幅值
3. 计算持续时间
4. 逐个计算所有属性修改项
5. 把这些结果一次性打包成一个 `StatusInstance`
6. 把该状态实例挂到目标角色
7. 若有持续时间，则补一个过期事件

因此，**不是一个属性一个属性地分散挂载**，而是先整体求值，再生成单个状态实例。

## 2.3 运行时层

运行时保存的是 `StatusInstance`，而不是零散的 modifier 节点。

`StatusInstance` 内部直接携带：

- 状态基础信息
- `expireAtMs`
- `magnitude`
- `appliedAttrModifiers[]`

这说明“同一状态下的多属性效果”在运行时仍然是成组保存的。

## 2.4 生效层

属性不会在挂状态时直接写回 base attribute，而是通过角色属性缓存做统一聚合：

- 先收集所有 active statuses 里的 `AppliedAttrModifier`
- 再把 `FLAT` 汇总
- 再把 `PERCENT` 汇总
- 最后按统一公式得到 resolved attributes

当前聚合口径是：

$$
resolved = (base + flat) \times (1 + percent)
$$

所以当前模型是：

- **状态实例按组保存**
- **角色属性按全局聚合求值**

---

## 3. 回答核心问题：现在算不算“原子处理”

## 3.1 可以算“单状态实例级原子”

当前实现满足下面三点：

1. 一个状态里的多属性修改会一起进入同一个 `StatusInstance`
2. 状态过期时会整组移除
3. 过期事件带 `appliedAtMs` 校验，可防止旧事件误删新实例

因此对“一个状态实例”而言，当前可以认为是**成组原子处理**。

## 3.2 还不算“完整状态系统级原子”

当前仍有明显边界：

1. `activeStatuses` 是按 `statusId` 存单实例，不支持同名多实例并存
2. 没有正式的 stack 概念
3. 没有独立的 stack timer / overflow / source-based stacking
4. 属性修饰只有 `FLAT` / `PERCENT` 两类，尚未分桶
5. 控制效果仍是部分硬编码，不是完全数据驱动

所以更准确的说法是：

> 它已经实现了“一个状态对象内部的原子性”，但还没有实现“完整生产级状态容器”的原子与组合语义。

---

## 4. 当前实现的优点

## 4.1 语义已经按“状态组”组织

这比“每个属性一条 buff”更接近正确方向，后续扩展不会完全推倒重来。

## 4.2 事件驱动的过期机制是正确方向

状态持续时间和过期都走中央事件队列，后续迁移到 TinyGo / Wasm 仍然可复用该拓扑。

## 4.3 状态本身能挂触发器

状态不是单纯属性包，还能承载 `ON_STATUS_APPLIED` / `ON_STATUS_EXPIRED` 等逻辑，这一点已经接近业界常见 effect-owned trigger 模型。

## 4.4 聚合求值方式简单稳定

目前的属性解析方式很适合 demo 阶段验证：实现简单，可测试性强，回归成本低。

---

## 5. 当前实现的主要缺口

## 5.1 同名状态只能保留一个实例

这会限制：

- 多层中毒
- 多段灼烧
- 不同来源同类 debuff 并存
- 多层可独立倒计时的 buff/debuff

## 5.2 叠层策略过于简化

当前只有 `REPLACE` / `TAKE_MAX`，不足以表达：

- refresh duration
- independent instances
- append duration
- stack count
- overflow trigger
- stronger-wins / weaker-wins

## 5.3 属性修饰口径还不够细

当前只支持：

- 平加
- 百分比加成

不支持正式系统中常见的：

- base set / final set
- additive / multiplicative 分层
- bucket priority
- clamp / cap
- 独立最终倍率区

## 5.4 初始状态没有走完整应用链

当前初始状态实例化时，没有统一走 `ApplyStatus` 求值链，因此初始状态与运行时施加状态之间还存在行为差异。

## 5.5 前端结构比运行时更强，二者尚未收口

当前前端 `apply_modifier` 已经有：

- `durationMs`
- `stacking.mode`
- `modifier.stats[]`

但 Java demo runtime 还没有真正实现对应的：

- 多实例栈模型
- 统一状态定义资源
- 与后台资源表一一对应的结构化状态编辑模型

---

## 6. 面向后端 worktree 的交接结论

DB 设计建议转到 `backend_dev` worktree 处理，原因如下：

1. 状态定义已经不再只是 demo 内部问题，而是资源建模问题
2. 状态系统后续必须与 Admin 写接口、发布快照、bundle 编译链对齐
3. 这部分更适合放在后端 schema、DTO、发布视图和管理页面契约里统一推进

本工作区这边的结论可以直接作为后端研究输入。

---

## 7. 建议在 backend_dev 优先研究的 4 个问题

## 7.1 状态定义真源表怎么拆

建议不要继续只靠 `skill.mechanicsConfig` 的原始 JSON 承担全部状态语义。

后端应优先判断是否需要引入独立资源：

- `status_definitions`
- `status_modifier_groups`
- `status_attribute_modifiers`
- `status_stack_policies`

至少要让“状态定义”和“技能动作引用状态”能分开建模。

## 7.2 状态修饰如何和属性定义、公式定义对齐

当前仓库已有：

- `attribute_definitions`
- `formula_profiles`
- `formula_bindings`
- `coefficient_buckets`

后续状态修饰应该尽量复用这些真源，而不是自己再造一套表达方式。

研究重点：

1. 状态 modifier 是否直接引用 `attr_key`
2. 状态 modifier 是否要绑定 `bucket_key`
3. 状态时长 / 幅值 / 每层值是否都通过 `formula_id` 表达
4. 发布后的 bundle 如何把状态定义编译成运行时结构

## 7.3 状态控制规则与状态定义如何分层

现在已有 `status_action_control_rules`，它更像“状态对动作的约束层”。

建议保持分层：

- `status_definitions`：定义状态本身是什么
- `status_action_control_rules`：定义状态对动作执行的限制

不要把“状态内容”和“状态控制副作用”混进一张表。

## 7.4 前端后台页应该怎么配合

建议后端设计时同步考虑 Admin 页最终要支持的结构化字段：

- 状态基础信息
- 时长配置
- 叠层策略
- modifier 列表
- 触发器列表
- 控制规则引用

这样后续 `web` 侧才能从“原始 JSON 编辑器”升级为“状态资源编辑页”。

---

## 8. 建议的后续落地顺序

推荐顺序：

### 阶段 A：后端建模收口

在 `backend_dev` 中先把下面内容做成草案：

1. 状态定义主表
2. 状态 modifier 子表
3. 状态 stack policy 字段或子表
4. 技能 / 装备 / 英雄与状态的绑定关系
5. 发布快照中的 bundle 输出结构

### 阶段 B：前端资源页收口

补一套状态资源页：

1. 状态列表页
2. 状态编辑弹窗 / 详情页
3. modifier 分组编辑器
4. stack policy 编辑器
5. 发布预览 / bundle 预览

### 阶段 C：运行时升级

等后端结构稳定后，再回到引擎侧升级：

1. `StatusInstance` → 多实例活动状态容器
2. 增加 stack group / instance id
3. 初始状态统一走应用链
4. 属性修饰从二元模式升级到分桶

---

## 9. 最终结论

本次分析确认：

1. Java demo 当前已经能承载“持续 M 秒 + N 个属性修改”的 buff/debuff。
2. 当前实现对单个状态实例具备成组原子性。
3. 当前实现仍缺少生产级状态系统最关键的三块：
   - 多实例 / 叠层容器
   - 分桶属性修饰
   - 后台资源化状态定义
4. 因此，**运行时重构不应先孤立推进，下一步应先在 backend worktree 把 DB 与资源模型收口**。

建议把后续重点切到 `backend_dev`：先定状态资源模型，再回推前端页面和运行时容器。
