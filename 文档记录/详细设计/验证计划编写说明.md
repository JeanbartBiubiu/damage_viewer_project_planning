# 验证计划编写说明

本文定义“验证计划”在当前仓库里的写法、落点和最小结构。它服务于 `文档记录/概要设计/验证里程碑.md` 中的 M0 到 M5 gate，把“阶段目标”转成可以执行、可以交给 Codex / 验收 sub agent / 人工复核的最小闭环。

关联文档：
1. `文档记录/概要设计/验证里程碑.md`
2. `文档记录/需求澄清/wasm/WASM需求澄清.md`
3. `文档记录/概要设计/wasm/WASM概要设计.md`

## 1. 文档定位

验证计划回答的是“这一个验证闭环具体怎么跑”。它不是：
1. 里程碑总览。里程碑总览留在 `验证里程碑.md`。
2. 实际跑完后的证据归档。执行结果应落到单独的测试记录或任务记录。
3. 纯实现说明。实现细节应留在对应模块的详细设计或任务文档。

验证计划的主要读者是：
1. 负责补页面、补 ABI、补数据的开发 agent。
2. 负责对比 `wasm 输出`、`OCR/人工基线`、填写验收表的验收 sub agent。
3. 只处理异常项和结论复核的人。

## 2. 什么时候需要新增验证计划

以下情况应新开验证计划，而不是只在聊天里口头约定：
1. 首次打通一个新的里程碑 gate，例如 M1、M2、M3 的第一条闭环。
2. M3 新增一个 canonical case。
3. M4 新增一个 `M4.x` 机制小节。
4. 计划的输入来源、对照方式、误差口径或通过标准发生变化。
5. 需要把同一个 case 交给不同 agent 重复执行时。

以下情况通常不需要新开计划，可以复用已有计划：
1. 已有 case 下的小修小补，没有改变验证输入和对照口径。
2. 单纯修页面展示，不改变 `wasm 输出 -> 基线对照 -> diff 结论` 这条证据链。
3. 单纯补测试记录，不改变计划本身。

## 3. 一个计划对应一个闭环

默认不要把多个机制、多个英雄、多个验证目标混在同一份计划里。推荐粒度如下：
1. `M1`：一个计划覆盖一个“actor 初始属性对齐”闭环。
2. `M2`：一个计划覆盖一个“action 面板值对齐”闭环。
3. `M3`：一个计划覆盖一个“单技能 1v 假人 canonical case”。
4. `M4.x`：一个计划只覆盖一个明确机制，例如资源消耗、冷却、护盾、DoT。
5. `M5`：一个计划只在前面 case 稳定后，作为组合回归入口，不反过来承担发现底层 diff 的职责。

如果一份计划里出现以下情况，应拆分：
1. 既验证直伤，又顺手验证护盾、治疗、触发链。
2. 既验证页面字段投影，又验证完整 runtime 时序。
3. 既写计划，又附大段执行结果和 diff 排查过程。

## 4. 计划存放位置

默认把验证计划放在最接近验证对象的 `文档记录/详细设计/**` 目录，而不是继续塞回概要设计。

当前建议：
1. 跨端通用规则、模板、编写约束，放在 `文档记录/详细设计/` 根下。
2. LoL 最小验证的具体 case 计划，优先放在 `文档记录/详细设计/最小验证/`。
3. Wasm 机制专项计划，如果强依赖某个 wasm 机制实现，可放在 `文档记录/详细设计/wasm/`，但要显式回链到里程碑文档。

命名建议：
1. `验证计划-<主题>.md`
2. `M3-<英雄>-<技能>-验证计划.md`
3. `M4-<机制名>-验证计划.md`

## 5. 每份验证计划必须写清的内容

### 5.1 基本信息

1. 目标里程碑，例如 `M2`、`M3`、`M4.3`。
2. `caseId` 或 canonical case 名称。
3. 适用游戏版本、`versionCode`、`dataHash` 或等价发布快照标识。
4. 当前计划对应的英雄、技能、目标、模式、seed、装备、等级。

### 5.2 验证目标

写清“这次要证明什么”和“明确不证明什么”：
1. 主验证目标只允许有一个。
2. 如果有从属目标，必须写成非阻塞辅助观察，不得替代主目标。
3. 非目标要显式排除相邻机制，防止执行时顺手扩 scope。

### 5.3 输入构造

必须说明验证输入如何得到：
1. Bundle 来源：发布快照、fixture、手工补录，还是混合。
2. Wasm 输入由谁生成：页面、脚本、手工 JSON，还是 adapter 导出。
3. 如果输入依赖页面操作，要写清页面入口、必要选项和最少点击步骤。
4. 如果依赖 seed、时间推进或前置动作，必须固定并写明。

### 5.4 游戏侧基线与证据采集

必须说明游戏侧证据怎么拿，而不是只写“对照游戏”：
1. 截图来自哪里，例如训练营面板、技能面板、结算前后状态。
2. 是否使用 OCR；如果使用，OCR 只作为结构化抽取，不直接代替最终判断。
3. 哪些字段允许直接从截图抄录，哪些字段只能人工解释。
4. 哪些状态在截图里不可见；这些不可见项必须标成 `missing_evidence` 或另找证据链。

### 5.5 Wasm 输出字段

必须列出本计划实际消费的 Wasm 输出，而不是笼统写“看结果”：
1. `snapshot`
2. `action_snapshot`
3. 单次施法后的资源、冷却、伤害、状态变化
4. 需要时补充公式输入、公式输出、gate/blocked reason、tick 顺序等字段

每个字段都要说明：
1. 它来自哪个输出载体。
2. 它对应游戏里的哪个可观测字段或哪条人工结论。

### 5.6 对照表结构

每份计划都要定义验收表最少包含的列，建议固定为：
1. `field`
2. `wasmValue`
3. `baselineValue`
4. `tolerance`
5. `status`
6. `evidenceRef`
7. `note`

`status` 统一使用：
1. `match`
2. `diff`
3. `low_confidence`
4. `missing_evidence`

### 5.7 通过标准

必须写成可执行规则，而不是“看起来差不多”：
1. 主证据字段不得存在未解释 `diff`。
2. 允许存在已归因、已登记、当前不阻塞的差异，但必须落 note。
3. `low_confidence` 和 `missing_evidence` 不能伪装成通过；要么补证据，要么升级人工复核。
4. M5 的组合结果不能覆盖 M1 到 M4 的字段级失败。

### 5.8 升级规则

计划里必须提前写明什么时候交给主 agent 或人：
1. OCR 结果无法稳定读值。
2. 单张截图无法判断时序、隐藏状态或触发顺序。
3. 同一输入下 Wasm 结果不可复现。
4. 当前 diff 无法区分是数据问题、页面映射问题还是 runtime 问题。

## 6. 验收 sub agent 的输入包

为了让验收 sub agent 能稳定工作，每份计划都应明确它要拿到的输入包：
1. `case_meta`：英雄、等级、技能等级、装备、模式、seed、版本。
2. `wasm_output`：页面导出的结构化 JSON 或等价表格。
3. `baseline_input`：OCR 结果、人工基线表或截图索引。
4. `evidence_index`：截图路径、时间点、对应字段说明。

计划要说明：
1. 哪些内容可以由 agent 自动填。
2. 哪些内容必须人工补。
3. agent 输出失败时应该回传什么异常说明。

## 8. 计划与测试记录分离

验证计划写完后，实际执行结果不要继续回填在计划正文里。执行结果应单独写测试记录，至少包含：
1. 日期和环境。
2. 使用的 bundle / wasm / 页面版本。
3. 输入包摘要。
4. 验收表结果摘要。
5. 新出现的 `diff / low_confidence / missing_evidence`。
6. 是否阻塞当前里程碑。

3. 后续每个 `M3 canonical case` 和每个 `M4.x` 机制，都应新增对应验证计划。
4. 与验收 sub agent 对接时，以“计划文档 + 输入包 + 测试记录”三件套为准，而不是聊天口头约定。
