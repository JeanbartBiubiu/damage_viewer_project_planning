# 技能统一编辑入口改造方案

版本：第一版，2026-09-27开发验收完成。设计依据为前后端基线93c07c188及已确认的六模块、MVP取舍；相关技能代码与此前核对的1bc6a8551一致。以下章节保留开发契约，第8.1节记录最终实现与验收；管理页面完成不等于Wasm或完整技能模拟完成。

本文负责页面组织、草稿归属、统一读取与保存契约、改造顺序和验收；表、嵌套字段、引用方向及约束统一引用[技能组合数据模型设计](技能组合数据模型设计.md)，业务取舍引用[技能六模块能力组合表](../../概要设计/项目/技能六模块能力组合表.md)。共享工作入口仍为[管理页面与共性机制迭代计划](管理页面与共性机制迭代计划.md)，逐对象进度不在本文另建。

## 1. 改造结论

采用“先建统一技能编辑入口和共同读写契约，再逐个接入配置模块”。第一段交付就能在统一入口修改主体与参数；后续模块接入同一份技能草稿、同一次保存，不等全部模块做好以后再整合。

统一入口采用现有管理页内的技能编辑工作区，不再增加一层全屏大弹窗。保留技能列表以及角色、装备、符文的技能直达和返回上下文。工作区固定显示六个配置模块及配置总览；复杂的结果、步骤和条件仍可用小弹窗编辑。

统一读取当前技能的完整定义，保存只提交明确新增、修改、删除的对象。一次保存涉及的参数、公式、效果、过程、状态和规则在同一数据库事务内通过最终组合校验；任何一项失败，整次都不写入。没有改动的对象不因页面未展开、模块未接入或读不到目录而被清空。

页面整合本身不要求新建数据库表。已有九张核心表、三张挂载表及引用索引继续使用；内部字段变化沿数据模型方案。本期不展开Wasm调度、运行协议或战斗页面设计，不用运行链完成度阻塞管理入口改造。

**数据库结构变更结论：本版DDL为0项。** 不新增／删除表、物理列、外键、检查约束、索引或触发器；新增的引用键、弹药恢复条件及供值变体均进入已有JSONB列。逐项结构清单、实际保存位置及依据统一见[数据模型设计第7.1、7.2节](技能组合数据模型设计.md#71-ddl变更清单本版为零项)。后端保存与校验以及本批JSON数据仍需修改，不能把“没有DDL”理解为“数据库内容和接口都不用改”。

## 3. 页面及六模块职责

### 3.1 工作区布局

顶部显示来源对象、技能名称和稳定标识，提供“返回”“重新读取”“保存更改”。保存按钮旁显示本次有变化的模块与对象数量；清楚区分“未保存”“保存中”“保存结果待核对”“已保存”。

左侧导航固定为“配置总览”以及六个模块；右侧显示当前模块。切换模块只切视图，不丢草稿、不发保存请求。未接入编辑的模块显示“暂只读”，已有内容仍可查看，不提供会清空数据的空表单。

| 模块 | 作者在这里配置什么 | 与其他模块如何组合 |
| --- | --- | --- |
| 主体与分类 | 名称、说明、最高等级、启停、排序、分类关联 | 向其余模块提供当前技能身份与等级边界；分类目录本身仍在分类页维护 |
| 参数与公式 | 固定值、等级值、场景输入、公式表达式 | 数值选择器同时能选择本技能已保存和待保存的参数、公式 |
| 效果与生命周期 | 伤害、治疗、护盾、修正等结果及持续、层数、刷新、结束关系 | 引用参数／公式；供过程和规则引用；已有目标、单位和时点控件保留 |
| 施放过程 | 施放延迟、步骤、主要冷却、时点挂接、状态操作 | 选择效果与内部状态；不再要求为了选它们退出当前技能分别保存 |
| 内部状态 | 计数、弹药、装填、模式、标记、内部冷却 | 被过程与条件／动作引用；跨技能选择只开放数据模型已确认的方向 |
| 条件与触发 | 事件、条件组、动作顺序、供值和触发限制 | 将前五模块已有对象组合成行为；保留稳定键和前序结果引用校验 |

六模块是作者组织配置的方式，不要求六张新表或六套独立保存按钮。冷却按语义仍归过程或内部状态，读条是过程能力，“联动”通过真实引用体现，不另外造一个只存重复关系的模块。

### 3.2 配置总览和引用定位

总览使用工作区当前草稿，醒目标出未保存；只解释配置，不计算动态公式，也不宣称技能能完整运行。显示使用入口、冷却、命中、结果、状态与结束关联，以及未挂接对象。对本期暂缓的旧配置保留其内容和范围提示，不在打开页面时自动删除。

引用选择器优先显示当前技能；必要时按数据模型允许的字段选择其他技能。名称与稳定标识、目标、单位同时显示；已有目录加载中、加载失败、真实缺失、停用四类提示继续区分。没有加载目录不等于配置引用不存在。

“定位问题”“查看引用处”仍沿现有结构化定位进入模块、根对象、子项和字段。定位找不到稳定键时停在正确对象并提示，不按旧数组下标猜测，不自动创建对象。子弹窗中尚未确认的修改必须先确认或取消，才能定位其他对象或执行顶部保存。

### 3.3 新建、删除与页面外对象

新建技能先在工作区形成本地草稿，填写合法主体即可保存，也可同时创建参数等组成；点击“保存更改”前不产生数据库技能。创建成功后才提供角色／装备／符文挂载操作。挂载仍由现有关系界面显式完成，不把“新建技能”误当作“已经关联”。

删除参数等组成先记为待删除，展示会受影响的引用；允许在同一草稿中改正这些引用后共同保存。对未修改技能的外部引用只展示阻塞，不能自动删掉外部规则来通过保存。整个技能的删除继续使用已有明确删除流程，不与普通配置保存混在一起；当前技能仍有草稿时不开放删除，必须先显式保存或放弃草稿，再按原流程确认删除。

技能行现有“启停”快捷入口改为定位工作区的主体状态字段，通过共同保存生效，不继续直接调用单技能更新接口。主体接入阶段就收口这条独立写入路径，不能只替换“编辑”弹窗而遗漏行按钮。

本技能参数／公式等快捷新建只增加工作区草稿。公共目录的新增不纳入本次技能事务；首版不在技能子弹窗内隐式保存公共对象，作者通过现有公共管理入口显式完成，返回后只刷新目录，不覆盖技能草稿。

## 4. 草稿和读取契约

### 4.1 一份基线、一份技能草稿

工作区维护读取成功的原始基线、当前草稿、尚未确认的子弹窗草稿及各模块的问题。根对象按自身稳定键区分；结果、步骤、条件等按现有子键区分。已保存标识保持只读；未保存标识允许修改，但必须同步本技能草稿内引用并检查重复。参数原先有值而后被清空时，视为待修正问题，不能静默改为零。

未改变的数据不重新拼装为写请求；目录名称、展开状态和排序显示等派生信息不产生业务改动。跨模块删除和新建可以在本地暂时形成不完整组合，保存前必须满足最终约束。首版不增加草稿数据库、自动后台保存或跨设备草稿同步。

只有工作区能向页面外报告“是否有未保存修改”：汇总全部模块及当前子弹窗修改，持续传给应用外壳和角色／装备／符文的来源返回。旧子组件不得独立上报“无修改”覆盖其他模块；关闭某个弹窗也不能清空其他模块的草稿标记。

第一阶段即覆盖模块外导航、Hash路由变化、返回来源、重新读取、浏览器关闭／刷新以及用户发起的连接、游戏、令牌切换。拒绝离开保留全部草稿；确认放弃才清理。凭据或连接从外部失效时，旧请求立即失效，当前内存草稿标记为原上下文数据且禁止向新上下文保存，不将它自动套用到另一技能或游戏。浏览器正常离开使用现有确认方式，本期不承诺崩溃后恢复草稿。

### 4.2 统一读取（拟新增）

路径：`GET /api/admin/games/{gameId}/skills/{skillKey}/configuration`。沿现有管理员鉴权与错误外层结构，不新增一套连接配置。成功响应包括：

| 响应字段 | 内容 |
| --- | --- |
| `skill` | 技能主体详情和分类键，沿现有主体详情字段 |
| `parameters`、`formulas` | 本技能全部参数和完整公式表达式 |
| `effects`、`processes`、`internalStates`、`triggerRules` | 本技能全部根对象详情，含现有嵌套结果、步骤、条件、动作与供值 |
| `baseDigest` | 服务端生成的当前技能配置校验摘要，用来发现读取后已发生的修改，含义见5.3 |

空数组只代表服务端确认该技能没有此类对象。后端在一致的数据库读取快照中组装响应；任何必需组成读取失败就返回失败，不能把成功部分冒充完整配置。前端初次读取失败只提供重试，不能开放默认空表单。已有草稿刷新失败则保留草稿与原基线。

完整定义的范围是当前技能自身拥有的数据，不包含整游戏公共目录、其他技能全文或挂载关系的可写副本。外部目录、引用和反向使用信息按需只读读取。未改旧对象缺少本次新增字段时可以显示“待补配置”，不自动补默认；新字段的完整校验只在模型约定的变更范围执行。

首期就定义并返回以上完整结构；没有编辑界面的模块只读保存于基线，不由前端补空数组。前端对未接入或不能正确解析的根对象禁止生成修改，但不妨碍保留它及编辑已经支持的无关对象。

## 5. 保存契约与后端职责

### 5.1 提交明确的对象变化（拟新增）

更新路径：`PATCH /api/admin/games/{gameId}/skills/{skillKey}/configuration`，表示提交本次局部变化。新建路径使用同一路径的`POST`，表示创建路径指定的技能及其本次组成；已存在则返回冲突。两者复用同一组合校验与事务服务。

| 请求字段 | 更新时的含义 | 新建时的含义 |
| --- | --- | --- |
| `baseDigest` | 必填，与读取到的基线一致 | 不传，服务端要求技能不存在 |
| `skill` | 可省略；提供时为完整的可编辑主体字段，不包含只读时间戳 | 必填；游戏和技能身份以路径为准，不能改名为另一个键 |
| `changes` | 根对象操作列表；未列入的根对象保持原样 | 可为空，只允许新增本技能组成 |

`changes`中每项包含对象类型`objectType`、操作`operation`、稳定键`key`以及需要时的完整可写值`value`。对象类型限定为`PARAMETER`（参数）、`FORMULA`（公式）、`EFFECT`（效果）、`PROCESS`（过程）、`INTERNAL_STATE`（内部状态）、`TRIGGER_RULE`（规则）；操作限定为`CREATE`（新增）、`UPDATE`（修改）、`DELETE`（删除）。类型和操作这些英文值仅用于接口，页面显示中文。

新增必须不存在，修改／删除必须已存在；同类型同键不能在一次请求中出现两次。修改时必须取得该根对象完整详情；只给一个结果字段、遗漏其他结果不能被当成合法完整效果。新增／修改的`value`沿现有对象写入结构及数据模型修订；键、游戏和所属技能必须与外层一致，禁止夹带其他技能的写入。

不传`skill`表示不改主体；`changes`为空表示不改子对象，而非清空子表。所有实际变动模块共用一个“保存更改”；不提供可能把未保存引用拆开的“仅保存当前模块”。结果列表等根对象内部数组沿现有完整替换语义，删除子项必须来自作者明确修改过的完整根对象。

例如：新增一个参数、一条引用它的公式和一个引用该公式的效果，生成三项新增操作，服务端先得到三者都存在的候选配置再检查。删除旧公式并把原效果换成新公式，则提交公式删除与效果修改，两者一起成功或一起失败；请求数组的先后不是业务执行顺序。

### 5.2 一次事务，校验最终组合

统一保存服务依次完成以下工作，公共事务覆盖全部步骤：

1. 锁定本游戏写入边界，读取当前技能与实际受影响的依赖，检查基线及键冲突。
2. 将显式变化应用到候选配置，保留未提交对象；先检查完整请求、键与操作合法性、字段形状和相对原始基线的不可变字段。
3. 参数、公式、状态及效果沿已实现的候选校验处理。过程／规则依赖现有数据库查询时，在同一事务内先写入整次最终未提交行，再复用原组合校验读取该事务的最终配置；失败回滚整次事务，外部读取始终看不到中间写入。不为此复制第二套完整目录或虚拟数据库。
4. 提交前检查当前变更是否破坏未修改对象的引用，提取并替换本次受影响来源对象的引用索引；删除来源只清除该来源索引，不整游戏重建。只读取必要外部依赖，不强制范围外旧对象补齐新字段。
5. 返回此次事务保存的规范化完整技能配置及新`baseDigest`；失败全部回滚，并定位到对象／字段。

复用现有各模块的字段校验、引用解析和数据库读写，新增的服务只负责组装最终状态和事务编排。不能让前端顺序调用旧接口来假装一次保存，也不能简单循环调用会逐项检查旧引用的服务，使中间态先被拒绝。实施时分离“读取／局部字段校验／最终组合校验／实际写入”的责任；过程／规则采用准备写入对象、底层事务写入、最终数据库校验三个入口，原有字段、绑定和循环检查仍须完整执行。上述事务内实现细化不改变一次原子保存、失败全部回滚及未修改数据保护的契约。

具体必须调整现有`GameConfigurationWriteGuard`（游戏配置写入守卫）：它目前会在提交前读取全游戏聚合、做全量校验，再删除并重建整游戏引用索引。改造时由守卫记录本事务实际变更的来源对象，只校验／替换受影响来源，未改来源对被删除或改种类目标的引用通过既有索引只读核对。尚在使用的单对象写入口也必须登记自己的变更范围；只在统一服务增加局部处理、保留原提交钩子的全量处理仍不合格。

本次旧数据整理只覆盖现行49名代表内的实际变更对象；名单不写死到通用保存服务。技能以外的装备／符文范围沿原计划，未修改数据及索引原样保留。具体约束、跨技能读引用和范围外删除保护以数据模型第6、9章为唯一来源。

### 5.3 防止旧页面覆盖新数据

首版使用整技能配置校验摘要`baseDigest`，不新建版本表。摘要由服务端对完整本技能定义、分类及所有子对象作固定排序后的规范化计算，包含有业务含义的数组顺序，不包含目录显示名称等派生内容。统一读取返回摘要；统一更新在同一写锁下重新计算比较，不相同返回409，保留客户端草稿。

现有守卫的`begin(gameId)`已经在可写事务内锁定游戏行；统一保存沿用它要求的`READ COMMITTED`事务隔离级别，即读取当时已提交的数据。必须先取得该游戏锁，再重读及比对摘要；不能在拿锁前比较。统一只读接口则使用一致快照，避免多条查询拼出不同时刻的组合，不调用写入守卫。

不只比较`skills.updated_at`，因为子对象修改不保证更新技能主体时间。整技能摘要会让两个页面修改同技能不同模块也产生冲突，这是首版明确接受的简化；不做自动合并，不增加每个字段的版本。锁与检查必须覆盖仍在使用的旧单对象写入口，避免它在比较与提交之间穿入。

其他技能或公共目录变化不纳入本技能摘要；保存时按最新事实重新校验实际引用。引用目标被删除或改为不兼容类型时定位报错，不靠摘要代替业务约束。

### 5.4 最高等级与参数一起调整

修改最高等级后，页面列出所有受影响的等级参数。扩大时新增格留空，作者填写实际值，真实零允许；缩小时明确列出将移除的等级值。此次主体变化与所有受影响参数必须同一保存提交，参数未填完则不能保存这一组。

后端检查最终参数长度与最终最高等级一致，不在新保存路径内调用旧的自动补零联动。没有等级参数时可以单独改变最高等级。该规则只涉及当前技能，不触发游戏全局等级配置变更。

现有`SkillService.update`会调整全部技能等级参数，缺级填零；现有`SkillParameterService`则按数据库当前最高等级校验。这两个方法不能直接顺序调用来实现新契约。统一服务须按候选最终最高等级检查所有显式提交的受影响参数，检查通过后使用不触发自动补零的底层写入，在同一事务完成主体和参数变更。

### 5.5 错误、响应不明与草稿保留

沿现有`error.code`、`error.message`、`error.details`错误外层。字段和组合问题在`details`中给出模块、根对象稳定键、已有结构化定位及中文原因；外部引用冲突同时给出来源，避免作者只能看到“保存失败”。非法请求返回400，基线不一致或依赖冲突返回409，目标技能不存在返回404，其他失败沿现有错误规范。

保存期间冻结这份草稿和编辑控件，避免响应覆盖请求发出后的新修改。校验失败保留全部草稿与子项；点击问题跳转对应模块。成功响应只表示接口确认保存，另外重新读取核对后才显示已核对；回读不会重放写请求。

超时、连接中断或成功后回读失败时显示“保存结果待核对”，保留已提交的固定内容，先发只读请求。若当前值与提交预期一致，接受新基线；若仍是原基线，提示本次未观察到变更，由作者明确决定重试；若与两者都不同，按冲突展示差异，不自动覆盖或再次创建。同一对象键、新建结果不明也遵守此规则。

每个阶段都集成到同一工作区并验证其已开放能力。第一阶段已经包含完整读取、未修改对象保护和共同保存事务，不能先做六套独立写入再补事务。统一操作类型先定全，尚未接入的类型在阶段内明确拒绝写入；它们的已有数据仍参与必要引用检查并保留。

旧根编辑弹窗随相应模块接入退出主编辑路径，组件中有价值的字段部分继续复用。未接入模块在新工作区只读；不长期维护两套功能相同的编辑入口。旧接口的其他真实消费者先核对，迁入共同写入校验后再删除无人使用的接口，不为历史设计新增双写、转换服务或兼容版本。

前后端可以按已确认契约并行实现各自文件，但同一页面草稿和同一后端事务服务各设一个集成人。字段控件的内部完成不等于阶段完成；每阶段以同一页面上的读、改、存、重开闭环验收。

必须覆盖的管理正确性案例：

1. 只改参数时，其余所有根对象、外部技能、挂载关系和无关索引保持原值；暂只读模块也如此。
2. 同次新增参数、公式和效果成功；同次删旧引用并替换成功；保留外部引用时删除失败且整次回滚。
3. 初次读取失败不显示可保存空表单；目录迟到不覆盖草稿；连接、游戏、技能切换后旧响应失效。
4. 各模块切换保留草稿；返回、路由、刷新及连接／游戏／令牌切换统一保护，子弹窗关闭不能清掉其他草稿。快捷新建的本技能对象不提前落库；启停走共同保存，未处理草稿不能直接删除整个技能。
5. 保存失败、响应丢失、回读失败分别表现正确，页面不会自动重复创建；另一页面已保存时返回冲突且保留当前编辑。
6. 等级扩大不会补零，缩小明确影响范围；同次保存后重新读取，参数长度与技能等级一致。
7. 变更对象遵守新模型，范围外未修改旧对象缺新增字段不阻断保存；实际引用缺失仍会阻断，不借范围隔离放松正确性。

开发时按受影响模块规则做前端、后端检查及真实浏览器验证；本文写作只做文档、代码依据、链接与任务映射核对。页面保存、独立持久化核对、管理配置完整、Wasm运行和完整技能模拟分别记录；本方案不把后两项列为页面改造的统一出口。
