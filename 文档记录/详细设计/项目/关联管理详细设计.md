## 1. 目标与范围

本阶段只建立此前明确后置的对象关系，使维护者可以：

1. 把技能挂载到角色或装备，并维护展示顺序。
2. 为游戏、角色、属性、装备、技能、技能效果和状态设置一张代表图片。
3. 从关系两端查看、新增、调整和移除同一条关系。
4. 技能挂载通过同游戏外键保证一致性；图片关联通过固定来源种类、唯一约束、后端校验和删除清理避免跨游戏、重复和悬空关系。

本阶段不包含发布、计算输入、Wasm、角色可用装备、装备合成路线、技能槽位规则、皮肤、多套图片、多语言图片或批量导入。

角色等级属性、装备直接属性、技能分类关系和技能效果从属关系已经有唯一数据来源，本阶段不重复建立第二套关系。

## 2. 当前基线

1. 当前数据库和后端没有角色与技能、装备与技能或业务对象与图片的现行关系表、接口和服务。
2. skill_category_relations 已经保存技能与技能分类；skill_effects 已经通过 game_id、skill_key、effect_key 从属于技能。本阶段不改写这两类关系。
3. characters 和 equipment 没有停用字段，可以物理删除；其已有属性数据随所属对象删除。
4. attributes、skills 和 statuses 使用 ENABLED、DISABLED 表示启停；images 使用 enabled 表示启停。
5. games.game_img_url 只是没有图片外键的旧文本字段，不是阶段 8 图片资源关系。
6. 当前前端没有“关联管理”路由。各对象页面已经使用列表行入口和弹窗维护子资源，可以直接沿用。
7. 图片页面列表只读浏览器本地缓存；现有公开缓存数据不含图片名称，不能作为关系选择器的完整数据源。

## 3. 关系表清单

本版冻结三张关系表：角色与技能、装备与技能各使用一张明确关系表；七类代表图片关系统一使用 `image_relations`（图片关联表）。两张技能挂载表保留真实外键，图片关联表按项目负责人决定不设置任何数据库外键。

| 关系表 | 关系方向 | 最小字段 | 基数与用途 |
| --- | --- | --- | --- |
| character_skill_relations | 角色 → 技能 | game_id、character_key、skill_key、sort_order | 一个角色可挂载多个技能；同一技能可被多个角色挂载 |
| equipment_skill_relations | 装备 → 技能 | game_id、equipment_key、skill_key、sort_order | 一件装备可挂载多个技能；同一技能可被多件装备挂载 |
| image_relations | 七类对象 → 图片 | game_id、source_type、source_parent_key、source_key、image_key | 每个来源对象最多一张代表图片；同一图片可被多个对象复用 |

图片关联表中的来源种类使用以下七个固定值。`source_parent_key` 表示上级对象标识，只有技能效果使用；其他来源统一保存空字符串，避免可空字段参与主键。

| 来源种类固定值 | 中文含义 | source_parent_key | source_key |
| --- | --- | --- | --- |
| GAME | 游戏 | 空字符串 | game_id |
| CHARACTER | 角色 | 空字符串 | character_key |
| ATTRIBUTE | 属性 | 空字符串 | attribute_key |
| EQUIPMENT | 装备 | 空字符串 | equipment_key |
| SKILL | 技能 | 空字符串 | skill_key |
| SKILL_EFFECT | 技能效果 | skill_key | effect_key |
| STATUS | 状态 | 空字符串 | status_key |

游戏封面在阶段 8 已明确后置到阶段 9，但原阶段 9 概要清单漏写游戏。本设计把它补入最终清单，不继续保留 games.game_img_url 作为第二数据来源。

当前只设计“代表图片”这一种用途，因此图片关联表不增加用途字段、关系状态、备注或预留种类。后续确有第二种图片用途时允许破坏式调整，不在最小可用阶段提前兼容。

## 4. 数据库约束

### 4.1 技能挂载关系

1. character_skill_relations 的主键为 game_id、character_key、skill_key。
2. equipment_skill_relations 的主键为 game_id、equipment_key、skill_key。
3. game_id 必须同时参加关系两端的复合外键，数据库直接禁止跨游戏挂载。
4. sort_order 为大于等于 0 的整数；同一所属对象内按 sort_order、技能名称、skill_key 稳定排序，不要求顺序值唯一。
5. 两张表分别增加以 skill_key 为前导的反向查询索引。

### 4.2 代表图片关系

1. image_relations 的主键为 game_id、source_type、source_parent_key、source_key，因此一个来源对象最多只有一张代表图片。
2. source_type 只能是第 3 节列出的七个固定值；source_parent_key 和 source_key 都是不可空字段。技能效果的 source_parent_key 必须填写 skill_key，其他来源必须保存空字符串；source_key 去除首尾空格后不得为空。
3. 来源种类为 GAME 时，source_key 必须与 game_id 相同。
4. image_key 去除首尾空格后不得为空；同一张图片可以被多个对象复用，不对 image_key 增加唯一约束。
5. 图片关联表不对 game_id、来源对象或 image_key 设置外键，也不依赖数据库级联删除。
6. 图片关联表增加以 game_id、image_key、source_type 为前导的反向查询索引。

### 4.3 无外键的一致性责任

1. 新建或替换图片关系前，后端必须确认游戏存在、来源对象属于该游戏、图片属于同一游戏且处于启用状态，然后才写入关系和编辑日志。
2. 所有对象侧接口继续接收各自明确的稳定标识，由后端转换为 source_type、source_parent_key 和 source_key；前端不拼装图片关联表的内部字段。
3. 物理删除来源对象时，后端必须在同一事务内删除对应图片关系；删除技能时还要清理该技能及其全部技能效果的图片关系。任一步失败都回滚对象删除。
4. 读取或反向查询发现来源对象、游戏或图片已经不存在时，不得静默忽略关系行，返回 409.RELATION_DANGLING 并记录可定位的来源种类和稳定标识。
5. 后端增加完整性检查，逐类验证图片关系指向的游戏、来源对象和图片均存在且属于同一游戏；阶段 9 验收要求悬空和跨游戏结果均为零。

本轮一致性边界：不新增跨写入与删除流程的统一加锁方案或专门并发验收。存在性检查与对象删除并发时仍可能留下悬空图片关系；此项为已知后置问题，不等同于存储容量问题。已有锁机制继续保留；本轮仍要求串行管理流程的校验、同事务清理、错误回读和完整性检查成立，不把这些证据写成已证明并发一致性。

### 4.4 删除方向

1. 删除关系只物理删除关系行，不删除任何一端对象。
2. 删除角色或装备时，技能挂载可按其外键规则清理，后端同时显式删除它自身的图片关系，但不得删除技能或图片。
3. 删除技能时，如果仍被角色或装备挂载，返回 409.SKILL_IN_USE；先移除挂载后，后端显式删除技能及其技能效果的图片关系。
4. 删除技能效果或状态时，后端显式删除其自身图片关系，不删除图片；其他既有引用保护继续生效。
5. 图片本阶段仍不提供删除接口。未来若增加删除，存在任一用途关系时必须返回 409.IMAGE_IN_USE。

## 5. 启停与引用规则

1. 新建或替换关系时，被选择的技能或图片必须启用；停用目标返回 409.REFERENCE_DISABLED。
2. 已有关系的技能或图片后来被停用时，关系保留并可完整回读，页面明确标记“已停用”或“图片不可用”。
3. 已有停用引用可以原样保留；不能重新选择同一停用目标来建立新关系。
4. 调整已有技能挂载的 sort_order 不改变目标，允许保存。
5. 角色和装备没有停用状态，只校验存在性。
6. 属性、技能、状态本身即使已停用，仍允许维护其代表图片；图片目标仍必须启用。

本规则沿用当前项目“停用不破坏已有回读，新增或改选不能引用停用对象”的统一语义，不因停用自动删除关系。

## 6. 管理接口

所有路径继续位于 /api/admin/games/{gameId} 下，要求现有管理权限并写管理编辑日志。路径中的稳定标识分别编码。

### 6.1 角色与技能

| 方法 | 路径 | 用途 |
| --- | --- | --- |
| GET | /character-skill-relations?characterKey=&skillKey= | 按角色或技能查询；至少提供一个过滤条件 |
| POST | /character-skill-relations | 新建一条关系 |
| PUT | /character-skill-relations/{characterKey}/{skillKey} | 只调整 sortOrder |
| DELETE | /character-skill-relations/{characterKey}/{skillKey} | 移除一条关系 |

创建请求只包含 characterKey、skillKey、sortOrder，成功返回 201；调整成功返回 200；移除成功返回 204。查询响应为 items、total，不分页；按角色查询时按 sortOrder、技能名称、skillKey 排序，按技能查询时按角色名称、characterKey 排序。关系响应除稳定键和 sortOrder 外，返回角色名称、技能名称和技能状态，页面不再逐条补查。

同时提供 characterKey 和 skillKey 时按两者共同过滤，并使用角色侧排序；已提供但不存在的对象返回其现有 404 错误。sortOrder 必须是 0～2147483647 的整数，不接受空值、小数或字符串。创建和调整响应均为以下单条对象，查询响应为 `{ "items": [单条对象], "total": 实际条数 }`：

```json
{"gameId":"lol","characterKey":"ezreal","characterName":"伊泽瑞尔","skillKey":"mystic_shot","skillName":"秘术射击","skillStatus":"ENABLED","sortOrder":0}
```

### 6.2 装备与技能

equipment-skill-relations 使用与角色技能关系相同的 GET、POST、PUT、DELETE 结构，把 characterKey 和角色摘要替换为 equipmentKey 和装备摘要；按技能查询时按装备名称、equipmentKey 排序。

### 6.3 代表图片

对象侧使用固定的代表图片子资源：

| 对象 | 路径 |
| --- | --- |
| 游戏 | /representative-image |
| 角色 | /characters/{characterKey}/representative-image |
| 属性 | /attributes/{attributeKey}/representative-image |
| 装备 | /equipment/{equipmentKey}/representative-image |
| 技能 | /skills/{skillKey}/representative-image |
| 技能效果 | /skills/{skillKey}/effects/{effectKey}/representative-image |
| 状态 | /statuses/{statusKey}/representative-image |

每个路径提供 GET、PUT、DELETE：

1. GET 在所属对象存在但尚未设置图片时返回 200 和 image: null，不把“尚未设置”伪装成对象不存在。
2. PUT 请求只包含 imageKey，负责新建或替换关系，成功返回图片标识、名称和启停状态。
3. DELETE 移除关系，成功返回 204；关系不存在返回 404.RELATION_NOT_FOUND。
4. GET /images/{imageKey}/usages 返回 imageKey 以及游戏、角色、属性、装备、技能、技能效果和状态七个分组，不返回图片内容。各组固定返回以下字段：
   - games：gameId、gameName。
   - characters：characterKey、characterName。
   - attributes：attributeKey、attributeName、attributeStatus。
   - equipment：equipmentKey、equipmentName。
   - skills：skillKey、skillName、skillStatus。
   - skillEffects：skillKey、skillName、effectKey、effectName。
   - statuses：statusKey、statusName、statusStatus。
   各组按名称、稳定标识排序；这些键足以定位对应对象侧 DELETE 路径，前端不得从名称反推稳定标识。
5. 图片侧新增或移除关系时仍调用对应对象的固定子资源，不增加通用多态写接口。

GET 和 PUT 使用相同响应结构，PUT 无论新建或替换均返回 200。已有关联原样提交同一张停用图片允许保留；移除后重新建立仍按新增引用校验。

```json
{"image":{"imageKey":"ezreal_portrait","name":"伊泽瑞尔头像","enabled":true}}
```

未设置时固定返回 `{"image":null}`。图片用途响应固定包含 imageKey 及上述七个数组字段；空分组返回 `[]`，不省略字段，技能效果同名同标识时再按 skillKey 排序。所有代表图片响应均不含图片内容或图片关联表的内部来源字段。

### 6.4 图片候选

新增 GET /image-options?keyword=，只返回已启用图片的 imageKey 和 name，不返回 imageBase64。keyword 必填，去除首尾空格后长度为 1～100，每次最多返回前 50 项，按 name、imageKey 排序。该独立路径避免与合法 imageKey 发生路由冲突。

keyword 按名称或图片标识做字面量子串匹配，不把通配字符解释成查询规则。响应为 `{"items":[{"imageKey":"ezreal_portrait","name":"伊泽瑞尔头像"}],"total":1}`；total 仅表示本次返回项数，最多 50，不表示未截断的匹配总数；无匹配时为 `{"items":[],"total":0}`。

该接口只供关系选择器使用。图片管理列表继续只读浏览器本地缓存，不恢复管理列表作为页面数据源；图片预览优先读取当前游戏本地缓存，缓存未命中时显示稳定占位，不要求维护者手输图片标识。

### 6.5 游戏摘要破坏式更新

阶段 9 完成后，GET /api/games 的 gameImgUrl 改为可空 representativeImageKey。前端通过图片缓存解析内容，不再把任意地址当作游戏封面来源，也不保留双字段兼容。

阶段 9 游戏列表切换到 games 缓存中的 all:stage9 键，不再读取旧 all 键，避免升级后命中仍含 gameImgUrl 的旧响应。游戏代表图片 PUT 或 DELETE 成功后，后端必须清除此新缓存键；下一次 GET /api/games 必须重新读取权威关系，不能返回写入前的封面。缓存清理属于游戏封面关系写入的完成条件，并覆盖对应服务测试；另以预置旧缓存验证首次读取只返回新字段。

旧 games.game_img_url 只按以下确定规则处理：

1. 值为 NULL 或去除首尾空格后为空时，不建立游戏封面关系。
2. 非空值只有在与同游戏现有 image_key 完全相等时，才按该键写入 image_relations，其中 source_type 为 GAME、source_parent_key 为空字符串、source_key 为 game_id；比较时不改写原值。
3. 其他非空值全部使迁移前检查失败，由项目负责人另行决定明确映射或清空；不得把网址、文件名、前缀或图片名称自动猜成 image_key。
4. 全部关系写入并读回一致后，才删除 game_img_url 列并切换 GET /api/games 响应；任何失败都不得留下双数据源或部分迁移。

## 7. 错误与事务

| HTTP | 错误码 | 场景 |
| --- | --- | --- |
| 400 | 400.INVALID_BODY | 请求无法绑定 |
| 400 | 400.VALIDATION_FAILED | 查询、必填键或 sortOrder 非法；使用 details.fieldIssues 定位 |
| 404 | 现有对象不存在错误 | 游戏、角色、装备、技能、效果、属性、状态或图片不存在 |
| 404 | 404.RELATION_NOT_FOUND | 修改或移除不存在的关系 |
| 409 | 409.RELATION_EXISTS | 重复新建同一关系 |
| 409 | 409.REFERENCE_DISABLED | 新建或改选停用技能、停用图片 |
| 409 | 409.RELATION_DANGLING | 图片关系指向不存在或不属于同一游戏的对象；串行管理流程不得产生此状态，并发边界见第 4.3 节 |
| 409 | 409.SKILL_IN_USE | 删除仍被角色或装备挂载的技能 |
| 409 | 409.IMAGE_IN_USE | 未来删除仍有用途关系的图片；阶段 9 不新增图片删除 |

每次关系写入在一个事务中完成校验、写入和编辑日志。失败不能留下部分关系，也不能修改关系两端对象。

## 8. 前端行为

本阶段不新增独立导航或“关联管理”总页，关系入口放回业务对象：

1. 角色行增加“关联技能”，装备行增加“关联技能”。
2. 技能行增加“挂载对象”，弹窗分角色和装备两区。
3. 游戏配置页增加独立“代表图片”面板，不混入等级范围表单。
4. 角色、属性、装备、技能和状态行增加“代表图片”。
5. 技能效果列表行增加“代表图片”。
6. 图片行增加“用途关系”，按七类来源分组反向查看。

所有选择器显示名称、稳定标识和启停状态，不按标识前缀猜用途，不要求复制内部标识。新增、调整或移除成功后立即刷新当前弹窗；从另一端重新打开时必须读取到一致结果。400、404、409 保留弹窗和用户已填内容。

七类对象的“代表图片”以本地上传为默认操作：在当前业务页面选择文件、预览，点击“上传并使用”后自动创建图片并设置为当前对象的代表图片。图片名称根据对象名称附加唯一后缀生成，稳定标识自动生成，用户无需填写；名称仍遵守现有同游戏唯一与长度限制。源文件校验和浏览器裁切沿用图片管理规则；上传成功写入当前游戏缓存，立即显示预览。选择已有图片作为次要入口保留。

上传替换会创建一张新图片并切换当前对象的关系，不覆盖旧图片内容，避免改变其他对象共享的图片。既有图片创建接口和代表图片设置接口保持独立：图片创建失败不修改关系；图片已创建而自动设置失败时保留草稿和已上传标识，明确提示并允许直接重试设置，不重复创建图片。读取和文件处理的迟到结果不得带入另一游戏或对象。图片已创建但用户放弃设置时，图片保留在图片管理中，不自动删除。

## 9. 模块责任

### 9.1 后端与数据库

1. 在 schema.sql 中增加两张技能挂载表和一张图片关联表；技能挂载表使用复合外键，图片关联表只使用主键、来源种类检查和反向索引，不设置外键。
2. 增加两类技能挂载服务、一套按七类固定来源校验的代表图片关系服务、图片反向用途查询和轻量图片候选接口。
3. 补强角色、装备、技能、效果和状态删除路径：技能挂载冲突不能泄漏为 500，图片关系必须由后端在同一事务内显式清理。
4. 按第 6.5 节确定规则完成 games.game_img_url 的迁移前检查、关系写入、列删除和 GET /api/games 响应替换。
5. 游戏封面关系写成功后清理 games/all:stage9 缓存，并验证随后读取不会返回旧值。
6. 增加图片关系完整性检查，并使用后端单元测试、数据库集成检查、真实接口和编辑日志读回验证。

### 9.2 前端

1. 新增关系类型与客户端，不把关系字段塞入角色、装备、技能或图片主对象请求。
2. 在现有页面增加关系弹窗和代表图片入口，共享展示组件可以复用，但请求必须落到本契约的明确接口。
3. 本地上传为代表图片默认操作，复用图片处理、创建和缓存能力后自动设置关系；选择已有图片使用轻量候选接口，预览使用当前游戏浏览器缓存。不恢复旧 skill-mounts、旧 combat-data 或按前缀推导图片身份的逻辑。
4. 覆盖关系客户端、弹窗状态、草稿保留、双端刷新和受影响页面浏览器检查。

### 9.3 Wasm

本阶段不修改 Wasm、宿主桥接或计算输入。关系保存成功只代表数据管理合同成立。

## 10. 实施顺序

1. 按本次确认冻结三张关系表：两张技能挂载表和一张不设外键的图片关联表。
2. 单一代表图片、启停规则和页面入口已确认，按第 4.3 节保留本轮并发边界。
3. 补充必要的后端与前端模块详细设计，公共字段、错误和行为仍只以本文为准。
4. 后端完成静态表结构、接口、服务、删除清理和自动检查。
5. 核对真实数据库目标及 games.game_img_url 现值；按第 6.5 节生成逐游戏迁移前检查结果，只有全部可确定且取得明确数据处置授权后才执行迁移和真实接口验证。
6. 前端在冻结接口上完成页面入口、双向查看和图片选择。
7. 依次完成静态检查、单元测试、构建、隔离桌面端、真实数据库、真实接口和真实浏览器验收。
8. 项目负责人确认阶段 9 后，才进入阶段 10 发布管理详细设计。

## 11. 跨端验收

1. 从角色侧挂载技能，技能侧可以查看；从技能侧调整顺序或移除后，角色侧结果一致。
2. 装备与技能完成同样闭环，两类关系不会混入同一对象种类字段。
3. 游戏、角色、属性、装备、技能、技能效果和状态各至少完成一次代表图片设置、替换、刷新回读和移除。
4. 图片侧可以反向查看七类用途；从图片侧移除一条后，对象侧同步为空。
5. 重复关系、跨游戏关系、未知对象、停用目标、悬空关系和非法顺序分别返回稳定错误且无部分写入。
6. 停用已被使用的技能或图片后，旧关系仍可回读并明确显示不可用；不能建立新的停用引用。
7. 删除仍被挂载的技能被阻止；删除角色或装备只移除自身关系，不删除技能或图片。
8. 切换游戏后候选、关系和图片预览严格隔离。
9. 图片关系完整性检查中，悬空来源、悬空图片和跨游戏关系均为零。
10. GET /api/games 不再返回 gameImgUrl，游戏封面只来自 image_relations 中来源种类为 GAME 的记录；设置或移除封面后清理 games/all:stage9 缓存，下一次读取立即一致。
11. 浏览器控制台无未捕获错误，关系页面不调用旧 skill-mounts 或旧 combat-data 接口。

## 12. 停止条件

出现以下任一情况，停止开发并返回项目负责人确认：

1. 任一来源无法用固定的 source_type、source_parent_key 和 source_key 唯一定位，必须保存任意结构或根据名称猜测对象。
2. 实际需求要求同一对象同时维护多种图片用途或多张图片。
3. 角色或装备技能关系必须表达固定槽位、解锁等级、模式集合替换或其他尚未确认的业务含义。
4. 目标数据库中的 games.game_img_url 无法与现有 image_key 明确对应，且需要猜测、丢弃或重写真实数据。
5. 已有同名表与本设计主键、来源种类检查或索引不一致。
6. 需要恢复旧接口、双写旧字段或为旧页面建设兼容层。
7. 未确认真实数据库目标或未获得所需数据处置授权时，停止真实数据库操作；已授权的静态开发和自动检查可继续。
