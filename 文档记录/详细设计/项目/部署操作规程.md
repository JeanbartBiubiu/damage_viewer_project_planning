# Damage 项目部署操作规程（备用）

本规程供当前 MVP 管理工作台部署时使用。沿用旧项目“本机构建 → 上传 → 重启 → 检查”的方式，补齐发布目录、依赖配置、数据库准备和回退步骤。本次交付的是经过文件与脚本核对的备用流程，**尚未在目标服务器演练当前项目的发布**。

默认示例为一台 Linux 服务器，使用 systemd（系统服务管理工具）运行 Java，Nginx（静态网站与反向代理服务）提供页面，连接 PostgreSQL 数据库与 Redis 缓存。管理端先通过 SSH 加密隧道访问。主机、数据库版本、账号和目录须按部署参数表填写；这些是本规程建议值，不是对旧服务器或当前线上状态的描述。

## 1. 旧项目实际怎样部署

以下旧文件是调查资料，不是当前项目应执行的指令。旧服务已停用；仍不应把它的数据库、配置或程序直接当作当前项目的部署产物。

| 入口 | 已核对行为 | 当前项目采用方式 |
| --- | --- | --- |
| `C:\project\damageViewer\dataApi\deploy.sh` 第 4～7 行 | `sync_jar` 先通过 SSH 调用 `ecs` 的停止脚本，再用 `rclone sync` 上传单个 jar 文件 | 完整上传并校验后再停止当前服务；单文件传输用 `copyto`，发布目录用 `copy` |
| 同文件第 10～12 行 | `sync_lib` 同步 `target/lib` | 当前 Spring Boot 构建包含依赖的可执行 jar，不再单独上传 `lib` |
| 同文件第 14～16 行 | `restart` 连接的是 `etc`，与停止使用的 `ecs` 不一致 | 发布参数中只登记一个经过连接确认的目标 |
| 旧远端 `ecs:/root/docker/stop.sh` 第 1 行 | `fuser -k 8888/tcp`，按端口结束进程 | 按明确的 `damage.service` 服务名停止 |
| 旧远端 `ecs:/root/docker/restart.sh` 第 1、3 行 | 结束 8888 端口进程，再用 `/root/openjdk-25/bin/java`、jar 和 `lib/*` 启动 `xyz.game.Application`，指定外部生产配置，放到后台运行 | 用 Java 21 的 `java -jar`，交给 systemd 管理重启和日志 |
| `C:\project\前端\package.json` | Vue 工程；`build:prod` 执行类型检查和 Vite 构建；`deploy` 只执行 `rclone sync ./dist qingliang:/usr/share/nginx/html` | 当前 React 工程使用自身的 `npm run build`；发布完整构建目录，不沿用旧命令名 |

旧脚本只有三个函数定义，没有菜单或参数分发。执行 `bash deploy.sh` 或 `bash deploy.sh restart` 都不会自动调用这些函数。调查中只执行了 Bash 语法检查、加载后的函数枚举，以及 rclone 远端目录和上述脚本的只读查询，没有执行停止、重启或上传。

目录名称 `/root/docker` 不代表使用了容器；读到的旧启动脚本直接在宿主机运行 Java。旧 Maven 配置为 Java 25、独立 jar 加运行依赖目录，当前项目为 Java 21、Spring Boot 3.5.0。旧后端生产配置使用 MySQL，默认配置又指向 PostgreSQL，不能据此确定当前项目应连接哪个库。

旧流程还存在以下具体问题：

- `rclone sync` 用于目录同步，可能删除目标目录中源端不存在的文件；单个文件应使用 `copyto`，不能将整个 `/root/docker` 当成 jar 的同步目标。参见 [rclone 同步说明](https://rclone.org/commands/rclone_sync/)。
- 先停止再上传，上传失败后服务不会自动恢复；脚本没有失败即停止、发布校验或回退处理。
- SSH 主机名与 rclone 远端名是两套配置。当前机器的 OpenSSH 没有把 `ecs`、`etc`、`qingliang` 解析为已配置的主机别名，rclone 的 `ecs:`、`qingliang:` 则可用。
- 本地旧前端指定目录缺少对应源码、锁文件和 `dist`，旧后端缺少可直接复用的目标 jar 与依赖目录；远端还有 `.partial` 文件残留。不能把这些旧产物视为完整发布包。

## 4. 本机构建并制作发布包

先检查 Web、Backend 两个工作树的分支和 `git status --short`。选择一组接口与数据库结构匹配、已经验收的版本；已有未提交工作保留原样，不自动暂存、清理或合并。发布检查结果必须对应实际打包内容。

常规发布使用模块 README 中的验证入口。已经有与最终代码一致的检查结果时可复用；构建则需要使用本次目标 API 地址。前端功能收尾入口为 `lint`、`typecheck`、`test` 和非 Wasm 桌面端到端检查；后端使用 `mvn test`。下面的 `mvn clean package` 会再次运行打包所需的测试。

```powershell
$DamageRelease = '20260910-001' # 每次换一个编号
$DamageBundle = Join-Path 'C:\project\damage-deploy-packages' $DamageRelease
if (Test-Path -LiteralPath $DamageBundle) { throw '发布目录已存在，请换编号' }
New-Item -ItemType Directory -Path "$DamageBundle\backend", "$DamageBundle\web", "$DamageBundle\db" -ErrorAction Stop | Out-Null

Push-Location 'C:\project\damage_backend_dev\server\data_manage' -ErrorAction Stop
try {
    mvn clean package
    if ($LASTEXITCODE -ne 0) { throw '后端打包失败' }
    $DamageJarEntries = @(jar tf target/data_manage-0.1.0-SNAPSHOT.jar)
    if ($LASTEXITCODE -ne 0) { throw 'jar 检查失败' }
    if (-not ($DamageJarEntries -match '^BOOT-INF/classes/') -or -not ($DamageJarEntries -match '^BOOT-INF/lib/')) {
        throw 'jar 缺少应用或依赖内容'
    }
    Copy-Item -LiteralPath 'target/data_manage-0.1.0-SNAPSHOT.jar' -Destination "$DamageBundle\backend\app.jar" -ErrorAction Stop
} finally { Pop-Location }

$DamageOldApiBase = $env:VITE_API_BASE_URL
Push-Location 'C:\project\damage_web_dev\web' -ErrorAction Stop
try {
    npm ci
    if ($LASTEXITCODE -ne 0) { throw '前端依赖安装失败' }
    $env:VITE_API_BASE_URL = 'http://localhost:18080'
    npm run build
    if ($LASTEXITCODE -ne 0) { throw '前端构建失败' }
    if (-not (Test-Path -LiteralPath 'dist\index.html')) { throw '缺少网页入口' }
    Copy-Item -Path 'dist\*' -Destination "$DamageBundle\web" -Recurse -ErrorAction Stop
} finally {
    $env:VITE_API_BASE_URL = $DamageOldApiBase
    Pop-Location
}

Copy-Item -LiteralPath 'C:\project\damage_backend_dev\db\game_manage\schema.sql' -Destination "$DamageBundle\db\schema.sql" -ErrorAction Stop
Copy-Item -LiteralPath 'C:\project\damage_backend_dev\db\game_manage\triggers.sql' -Destination "$DamageBundle\db\triggers.sql" -ErrorAction Stop
```

`jar` 清单应包含 `BOOT-INF/classes/` 和 `BOOT-INF/lib/`，不要上传 `.jar.original`、源码目录或旧项目的 `lib`。构建命令、产物名称变化时，以发布版本自己的 `pom.xml` 为准。

有迁移时，另将**本次已审查的具体迁移文件**及必要直接依赖复制到发布包 `db/migrations/`，使用 `-ErrorAction Stop`，不要复制整个历史迁移目录。迁移若依赖 Java 工具、SQL 子文件或特定源码版本，应一并准备匹配的执行环境，并在恢复副本上先演练；不能只上传一个入口文件就认为可以执行。

在发布包中增加 `release-info.json`，记录发布编号、Web/Backend 的完整提交号、是否含未提交修改、实际 Node/npm/Java/Maven 版本、API 地址、数据库结构来源、必要迁移的相对路径与执行顺序，以及已完成的验证。不要记录凭据。仅有提交号不能解释未提交改动；有此类改动时保留对应的非敏感差异证据和本次完整产物。

清单完成后生成 SHA-256 文件校验表：

```powershell
$DamageHashLines = Get-ChildItem -LiteralPath $DamageBundle -File -Recurse -ErrorAction Stop |
    Where-Object Name -ne 'SHA256SUMS' |
    Sort-Object FullName |
    ForEach-Object {
        $relative = $_.FullName.Substring($DamageBundle.Length + 1).Replace('\', '/')
        '{0}  {1}' -f (Get-FileHash -LiteralPath $_.FullName -Algorithm SHA256 -ErrorAction Stop).Hash.ToLowerInvariant(), $relative
    }
if (-not $DamageHashLines) { throw '发布包没有可校验文件' }
[IO.File]::WriteAllText((Join-Path $DamageBundle 'SHA256SUMS'), (($DamageHashLines -join "`n") + "`n"), [Text.UTF8Encoding]::new($false))
```

只有本次涉及引擎或宿主变更时，才追加 Wasm 模块 README 的构建、Node 调用检查和实际浏览器验证。`wasm/tinygo_engine_v2/scripts/build-wasm.ps1` 仅产生本模块 `dist/tinygo_engine_v2.wasm`，不会自动更新 Web 中的资源；该更新必须作为明确的前端产物变更完成后再构建发布包。

## 5. 首次准备服务器

### 5.1 目录和私有配置

以下命令仅首次准备时执行。已有同名账号或目录时先核对用途；不要覆盖其他应用的配置。

```bash
id damage >/dev/null 2>&1 || useradd --system --home-dir /opt/damage --shell /usr/sbin/nologin damage
install -d -m 0755 /opt/damage /opt/damage/releases
install -d -m 0750 -o root -g damage /etc/damage
install -d -m 0700 /var/backups/damage
```

在服务器本地创建 `/etc/damage/application.env`，替换下列占位值，权限设为 `root:damage`、`0640`。数据库、Redis 可以位于其他私网主机，按实际修改。systemd 环境文件不是 Shell 脚本，不写 `export`，不要 `source` 它；按其格式正确引用包含特殊字符的值。

```ini
SERVER_ADDRESS=127.0.0.1
SERVER_PORT=8080
SPRING_DATASOURCE_URL=jdbc:postgresql://127.0.0.1:5432/damage_manage
SPRING_DATASOURCE_USERNAME=damage
SPRING_DATASOURCE_PASSWORD="<在服务器本地填写>"
IT_REDIS_HOST=127.0.0.1
IT_REDIS_PORT=6379
IT_REDIS_PASSWORD="<在服务器本地填写>"
IT_REDIS_DATABASE=1
APP_STARTUP_FAIL_FAST=true
APP_AUTH_JWT_DISABLED=true
```

数据库和 Redis 不对公网开放。`APP_AUTH_JWT_DISABLED=true` 只适用于本文受控的隧道访问；服务器本地用户也能访问回环端口，应属于可信使用者。不要把数据库密码、令牌放到 `VITE_*` 中，这类变量会进入浏览器产物。

### 5.2 后端服务

创建 `/etc/systemd/system/damage.service`，核实 `/usr/bin/java` 实际为 Java 21：

```ini
[Unit]
Description=Damage management backend
Wants=network-online.target
After=network-online.target

[Service]
Type=simple
User=damage
Group=damage
WorkingDirectory=/opt/damage/current/backend
EnvironmentFile=/etc/damage/application.env
ExecStart=/usr/bin/java -jar /opt/damage/current/backend/app.jar --spring.config.additional-location=optional:file:/etc/damage/application-extra.yml
Restart=on-failure
RestartSec=5
TimeoutStopSec=60
UMask=0027
StandardOutput=journal
StandardError=journal

[Install]
WantedBy=multi-user.target
```

执行 `systemd-analyze verify /etc/systemd/system/damage.service`、`systemctl daemon-reload` 和 `systemctl enable damage`。此时暂不启动；先完成数据库、上传和版本指向。日志使用 `journalctl -u damage`，无需沿用旧 `nohup`、后台 `&` 或按端口杀进程。

### 5.3 Nginx 站点

确认主配置在 `http` 段加载 `/etc/nginx/conf.d/*.conf`，再创建 `/etc/nginx/conf.d/damage.conf`。模板假定全站路径属于本应用，静态目录对 Nginx 用户可读。

```nginx
server {
    listen 127.0.0.1:18080;
    server_name localhost;
    root /opt/damage/current/web;
    index index.html;
    client_max_body_size 2m;

    if (-f /opt/damage/maintenance) { return 503; }

    location /api/ {
        proxy_pass http://127.0.0.1:8080;
        proxy_http_version 1.1;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_read_timeout 60s;
        proxy_cache off;
    }

    location = /index.html {
        add_header Cache-Control "no-cache" always;
    }

    location /assets/ {
        try_files $uri =404;
        add_header Cache-Control "public, max-age=31536000, immutable";
    }

    location / {
        try_files $uri $uri/ /index.html;
        add_header Cache-Control "no-cache" always;
    }
}
```

主配置应加载 Nginx 自带 `mime.types`，以正确返回 JavaScript、CSS 等内容类型。若后续发布实际包含 `.wasm`，核对其类型为 `application/wasm`；缺少资源应返回 404，不能返回网页 HTML 冒充脚本。

`proxy_pass` 这里没有末尾路径斜线，会保留 `/api/...` 原路径；写成 `http://127.0.0.1:8080/` 会在该配置下替换匹配到的 `/api/` 前缀。参见 [Nginx 代理路径规则](https://nginx.org/en/docs/http/ngx_http_proxy_module.html#proxy_pass)。管理与公开接口均不在 Nginx 做额外缓存；`ETag` 响应头保留。

执行 `nginx -t`，成功后再 `systemctl reload nginx`；首次尚未运行则启动 Nginx。不要把整份旧站点配置直接覆盖到当前服务器。

## 6. 数据库准备：只选择符合实际的一条

应用启动不会自动建表或迁移。使用独立业务数据库，由业务账号拥有应用表，并具有 `public` 模式的 `USAGE`、`CREATE` 权限；新增游戏时需要创建图片分区。管理工具通过受保护的 PostgreSQL 密码文件或交互提示取密码，不把密码写在命令行。

### A. 全新空库

由数据库管理员创建 `damage_manage` 和业务账号后，设置当前会话的 `PGHOST`、`PGPORT`、`PGUSER`、`PGDATABASE`，核对 `SELECT current_database(), current_user;`。确保目标为新建空库，再在已上传的发布目录中执行：

```bash
psql -X -v ON_ERROR_STOP=1 --single-transaction \
  -f db/schema.sql -f db/triggers.sql
```

两份 SQL 按顺序放在同一事务中。没有必跑业务种子，不执行 `migrations/**` 全目录、旧 MySQL 初始化、`db/user_manage` 或任务治理 SQLite。新库没有游戏时，`GET /api/games` 返回 `[]` 是正常的；业务内容另按当前录入流程准备。

### B. 把当前 Damage 数据库一起搬过去

先阻止源库写入，使用与源库版本匹配的 `pg_dump -Fc -f damage.dump` 制作完整备份，包含业务表、图片分区、函数和触发器；记录数据库版本、备份时间及来源。目标新建空库，由目标业务账号执行：

```bash
pg_restore --exit-on-error --single-transaction --no-owner --no-privileges \
  --dbname=damage_manage damage.dump
```

连接地址和账号仍取自明确设置的 PostgreSQL 连接参数。完整恢复后不再执行 A 的建表脚本；核对图片、游戏、角色、装备、符文及技能数据。`--no-owner` 让恢复出的对象归恢复账号所有，`--no-privileges` 不带入源库授权。参见 [PostgreSQL 恢复说明](https://www.postgresql.org/docs/current/app-pgrestore.html)。

### C. 已有当前项目数据库，部署新版程序

先备份，按发布版本后端 README 核对当前结构与具体升级差异，只运行本次已审查的迁移。当前示例：24 表聚合存储库需要符文功能时，使用 `db/game_manage/migrations/rune_management.sql` 追加到 27 表；全新库已经包含它，不重复执行。

## 7. 上传与切换版本

### 7.1 先上传，保持当前服务运行

在 Windows 上确认 rclone 远端与 SSH 指向同一主机；`rclone listremotes` 只列名称，连接检查可用 `rclone lsd damage-host:/opt/damage/releases`。预先确认目标发布编号不存在，然后执行：

```powershell
rclone copy $DamageBundle "damage-host:/opt/damage/releases/$DamageRelease" --dry-run
if ($LASTEXITCODE -ne 0) { throw '上传预演失败' }
rclone copy $DamageBundle "damage-host:/opt/damage/releases/$DamageRelease"
if ($LASTEXITCODE -ne 0) { throw '上传失败，保持当前版本' }
```

这里上传独立目录，不对当前网站目录执行 `sync`。单独补传某个文件时使用 `copyto`，但不得修改已经启用的发布目录。上传失败或连接中断后先核对远端结果；校验失败的目录不进入切换步骤。

服务器上进入该发布目录，执行 `sha256sum -c SHA256SUMS`，确认 `backend/app.jar`、`web/index.html`、数据库文件和 `release-info.json` 存在。确保发布目录不可被匿名写入、程序及静态文件可读。发布编号不得包含路径分隔符。

### 7.2 建立恢复点，再切换

下面是一次发布的顺序示例。发布中断后保持维护标记，先查当前指向、服务状态和数据库结果，再决定续做或回退，不直接重放整段。

```bash
set -euo pipefail
RELEASE_ID='20260910-001'
[[ "$RELEASE_ID" =~ ^[A-Za-z0-9_-]+$ ]]
RELEASE_DIR="/opt/damage/releases/$RELEASE_ID"
BACKUP_DIR="/var/backups/damage/$RELEASE_ID"
test -d "$RELEASE_DIR"
test "$(realpath "$RELEASE_DIR")" = "$RELEASE_DIR"
test ! -e "$BACKUP_DIR"
test ! -e /opt/damage/current || test -L /opt/damage/current
test ! -e /opt/damage/current.next
test ! -L /opt/damage/current.next
cd "$RELEASE_DIR"
sha256sum -c SHA256SUMS
test -s backend/app.jar
test -s web/index.html
test -s release-info.json
install -d -m 0700 "$BACKUP_DIR"
PREVIOUS_RELEASE=''
if test -L /opt/damage/current; then
    PREVIOUS_RELEASE="$(readlink -e /opt/damage/current)"
    [[ "$PREVIOUS_RELEASE" == /opt/damage/releases/* ]]
    test -d "$PREVIOUS_RELEASE"
fi
printf '%s\n' "$PREVIOUS_RELEASE" > "$BACKUP_DIR/previous-release.txt"
cp -a /etc/damage "$BACKUP_DIR/config"
cp -a /etc/systemd/system/damage.service "$BACKUP_DIR/"
cp -a /etc/nginx/conf.d/damage.conf "$BACKUP_DIR/"

touch /opt/damage/maintenance
systemctl stop damage

# PGHOST/PGPORT/PGUSER/PGDATABASE 已核实为本次目标库；密码取受保护的密码文件。
psql -X -v ON_ERROR_STOP=1 -c 'SELECT current_database(), current_user;'
pg_dump -Fc -f "$BACKUP_DIR/database.dump"
test -s "$BACKUP_DIR/database.dump"
pg_restore --list "$BACKUP_DIR/database.dump" > "$BACKUP_DIR/database-contents.txt"

# 若本次有数据库升级，在这里执行已审查的具体迁移并验收结果。
# 首次部署的数据库准备应已完成第 6 节；未完成时到这里停止。

ln -sT "$RELEASE_DIR" /opt/damage/current.next
mv -Tf /opt/damage/current.next /opt/damage/current
systemctl start damage
```

数据库备份和迁移期间还应暂停其他连接该库的录入程序或写入任务。切换前若准备修改配置文件或服务定义，应**先备份旧版本**，再做配置修改；上面的快照不能替代修改前备份。备份目录含私有配置，保持管理员专用。数据库备份清单可读只证明备份可解析，完整恢复能力需要实际恢复演练。

通过 `journalctl -u damage -n 100 --no-pager` 查看启动，确认没有数据库、Redis、端口或配置异常。不要将可能含凭据的完整日志公开粘贴。然后在服务器检查：

```bash
systemctl is-active damage
curl --fail --silent --show-error --max-time 10 http://127.0.0.1:8080/api/games
```

按实际启动耗时重试，有明确上限，例如 60 秒；到时仍失败则进入回退，保持站点维护状态。成功后检查返回值确实为预期 JSON，再移除本次维护文件并验证 Nginx 路径：

```bash
rm -- /opt/damage/maintenance
curl --fail --silent --show-error --max-time 10 http://127.0.0.1:18080/api/games
curl --fail --silent --show-error --max-time 10 -I http://127.0.0.1:18080/index.html
```

这里移除的是本规程创建的单个维护文件。前端使用带 `#` 的页面路由，浏览器片段不会发送到服务器，验收必须实际打开页面。尚未完成页面验收前，不把服务启动或 HTTP 200 记为发布完成。

## 8. 发布后验收与回退

在 Windows 打开 SSH 隧道，连接目标填写第 3 节登记的值：

```powershell
ssh -N -o ExitOnForwardFailure=yes -L 18080:127.0.0.1:18080 damage-host
```

保持这个终端连接，浏览器打开 `http://localhost:18080/#/attributes`。按下表验收并记录发布编号和结果：

| 检查 | 通过条件 |
| --- | --- |
| API 基址 | 页面显示 `http://localhost:18080`；请求没有发到旧地址或访问者自己的 8080 端口。浏览器曾保存地址时在页面修改并保存，旧本地值会覆盖构建值 |
| 公共读取 | `/api/games` 返回正确游戏列表；对已有游戏检查公开图片同步，不能只依赖可能命中 Redis 的游戏列表证明数据库读取正常 |
| 管理页面 | 打开属性、角色、装备、符文、技能、图片与游戏配置等当前页面；代表数据可读，没有 404、500 或结构解析错误 |
| 管理写入 | 使用明确的部署验收对象完成一次新增/修改、关闭后独立读回，再清理临时对象；记录失败请求及清理结果，不用真实业务对象随意试写 |
| 图片 | 在图片页同步后查看图片；列表主要来自浏览器 IndexedDB（本地数据库），刚部署后本地列表为空不直接代表后端没数据 |
| 资源 | 页面请求的 JS、CSS 和图片成功返回，缺失文件不返回 `index.html` 冒充资源；本次实际包含 Wasm 功能时追加真实编译、运行和释放检查 |
| 服务与日志 | `damage` 持续运行，数据库和 Redis 连接正常，没有反复退出重启或请求异常 |

**程序回退只适用于数据库仍可被上一版程序读取的情况。** 旧程序不能读取新结构时，必须连同数据库和配置一起恢复；MVP 允许破坏式升级，不补旧协议兼容层。

程序回退流程：

1. 创建 `/opt/damage/maintenance` 并 `systemctl stop damage`，停止其他写入源。
2. 读取本次备份目录的 `previous-release.txt`，核实它确实位于 `/opt/damage/releases/` 内、包含完整 jar 与网页，且对应数据库兼容。首次发布没有前一版，只能保持维护并排查。
3. 若配置有变化，恢复修改前的配置备份及对应服务/站点配置；有服务文件变化时 `systemctl daemon-reload`，有 Nginx 配置变化时先 `nginx -t`，成功后执行 `systemctl reload nginx`，确认维护状态仍然有效。
4. 确认 `/opt/damage/current.rollback` 不存在（包括悬空链接），用 `ln -sT` 把旧发布目录创建为该符号链接，再用 `mv -Tf` 切换为 `/opt/damage/current`；临时链接已存在时先核查来源，不覆盖未知文件。
5. 启动后端，完成与发布相同的直连 HTTP、代理、浏览器读写验收，成功后恢复访问。打开旧页面的用户重新加载，避免继续使用上一轮已加载的前端代码。

数据库不兼容时，保持维护，先备份故障时的现状，再把发布前 `database.dump` 恢复到**另一个新建空库**，核对业务与图片数据，修改私有连接配置指向恢复库，并切回对应旧程序。这样可以保留故障库供检查，无需直接删除它。恢复会失去恢复点之后的业务写入；若开放访问后已有新写入，先明确这部分数据的处理方式，不能直接恢复旧备份覆盖它们。

保留至少本次与前一版产物，以及对应配置和数据库恢复点。验收完成后按明确目录和保留范围清理更老版本；不运行模糊匹配的全目录删除，也不清空共用 Redis。数据库恢复后需清除本应用的缓存；只有确认整个 Redis 逻辑库专用时才可清空该库，否则按实际应用键前缀定向处理。前端旧图片缓存通过页面重新同步或清理后重建。

## 9. 若改为公网访问

公网开放是一次明确的部署参数变更，应先完成以下事项再开放入口：

1. 配置实际域名与 HTTPS 证书，Nginx 监听公网 443；保持 Java 8080、数据库和 Redis 仅对回环或必要私网开放。
2. 前端重新用实际 `https://域名` 构建，浏览器清理或更正保存的旧 API 地址，避免 HTTPS 页面请求 HTTP 接口。
3. 设置 `APP_AUTH_JWT_DISABLED=false`。在 `/etc/damage/application-extra.yml` 中通过 `app.auth.jwt.es256-public-key-pem` 配置 ES256 验签公钥；服务模板已加载该可选文件，缺少有效公钥时不能按鉴权模式启动。
4. 事先准备可信的令牌签发方式和持有对应私钥的管理员。当前仓库实现的是验签，没有现成的登录或发令牌页面。令牌要求 ES256 签名、有效的整数 `exp`、非空 `email`、布尔 `canEdit` 和 `paid`，管理访问要求 `canEdit=true`。私钥不进入服务器静态目录或前端包。
5. 验证管理接口无令牌为 401、有效但无编辑权限为 403、有效编辑令牌可读写；游戏列表和公开图片接口维持公开。没有完成签发与鉴权验收时，继续使用隧道方案。

本节只说明现有鉴权能力的部署要求，不新增账号系统、兼容旧登录或更改权限实现。

## 10. 常见故障定位

| 现象 | 优先检查 |
| --- | --- |
| Nginx 502 | `systemctl status damage`、监听端口、Java 版本、依赖启动检查和私有配置；不要结束任意占用端口的进程 |
| API 返回 HTML 或 404 | `/api/` 代理是否保留原路径、是否被静态页回退覆盖、是否用了已经删除的旧接口 |
| 页面请求旧机器 | 页面内已保存的 API 地址，以及这次构建的 `VITE_API_BASE_URL` |
| 图片上传 413 | Nginx 请求体限制；本模板为 2 MiB，后端仍只接受 PNG/JPEG、解码后不超过 256 KiB、宽高分别不超过 64 像素 |
| 新表/字段不存在 | 发布包与数据库结构不匹配，应用不会自动迁移；不要临时补回已删除的旧表 |
| 游戏列表旧、图片列表空 | 分别检查 Redis 缓存和浏览器图片同步，核对真实接口后再处理各自缓存 |
| 上传后站点失败 | 校验 `SHA256SUMS`、当前链接、目录权限、JS/CSS 类型和实际请求路径；旧 `.partial` 文件不能算完成产物 |
| 管理接口 401/403 | JWT 开关、验签公钥、签名算法、到期时间与 `canEdit`；不能靠开放 CORS 解决权限问题 |
