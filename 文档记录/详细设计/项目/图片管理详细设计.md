## 1. 目标与范围

本阶段交付按游戏独立维护的图片资源，使维护者可以：

1. 从浏览器本地缓存查询并预览已同步图片。
2. 新建图片，维护稳定标识、名称和说明。
3. 替换图片内容而不改变图片身份。
4. 停用和重新启用图片。
5. 让浏览器通过全量或增量同步取得最新图片和停用变化。
6. 通过图片管理页面上传超出 64×64 范围的源图片时，由浏览器自动压缩为最大 64×64 的图片。

本阶段只管理图片资源本身，不建立图片与角色、属性、装备、技能或游戏封面的用途关系。所有业务对象图片关系统一留到阶段 9。

本阶段不做物理删除、批量上传、原图留存、任意输出尺寸、动态图、矢量图、对象存储、内容分发网络、图片版本发布、计算或 Wasm。

## 2. 当前基线与替换边界

当前静态实现基线为：

1. PostgreSQL 的 `images` 按 `game_id` 分区，仅保存 `uri`、`image_base64` 和创建更新时间。
2. 后端公开接口支持全量或按 `updatedAfter` 增量读取；管理接口按 `uri` 直接覆盖图片内容。
3. 前端 `#/images` 页面可以上传、同步、清理浏览器缓存和预览，但没有独立资源的名称、说明、状态、明确新建或编辑流程。
4. 当前后端只检查数据地址前缀，图片标识规则、真实格式、解码大小和尺寸没有形成后端权威校验。

阶段 8 直接替换上述不完整契约：

1. 现有 `uri` 的真实含义是“图片稳定标识”，统一改名为 `imageKey`；数据库列改为 `image_key`。
2. 不保留 `uri` 字段别名、双写、旧请求体或旧响应体。
3. 现有图片内容在通过迁移前检查后原样保留，不因字段收敛自动删除或重新压缩。
4. 浏览器本地缓存是服务器图片的可恢复副本，可以在前端升级时清空并重新同步，不作为业务真源。
5. 图片管理页面的列表直接读取当前游戏的浏览器本地缓存；打开页面、筛选和刷新缓存都不请求管理列表接口。缓存为空时显示空状态，由维护者主动执行全量同步后取得并展示服务器图片。

## 3. 图片资源模型

统一图片对象：

`json
{
  "gameId": "lol",
  "imageKey": "character_vayne",
  "name": "薇恩头像",
  "description": null,
  "imageBase64": "data:image/png;base64,...",
  "mimeType": "image/png",
  "byteSize": 12345,
  "width": 64,
  "height": 64,
  "enabled": true,
  "createdAt": "2026-09-05T00:00:00Z",
  "updatedAt": "2026-09-05T00:00:00Z"
}
`

字段规则：

1. `gameId`：路径确定，图片不能跨游戏移动。
2. `imageKey`：创建时去除首尾空格；以字母或数字开头，只含字母、数字、点、下划线或连字符，最长 128；同一游戏唯一，创建后不可修改，大小写敏感。前缀只帮助人识别，不代表或自动建立业务对象关系。
3. `name`：去除首尾空格后 1～100；同一游戏忽略首尾空格和大小写唯一。
4. `description`：可省略或为 `null`；去除首尾空格后空串保存为 `null`，最长 2000。
5. `imageBase64`：已经处理完成、宽高均不超过 64 像素的图片 Base64 数据地址；创建时必填，更新时省略表示保留原内容，传 `null` 或空串均拒绝。响应返回后端实际保存的内容。
6. `mimeType`、`byteSize`、`width`、`height`：后端从解码后的图片内容生成，只读，客户端不得提交。
7. `enabled`：创建时固定为 `true`；更新时必填。停用只阻止公开图片内容继续分发，服务器仍保留内容，重新启用不要求再次上传。
8. `createdAt`、`updatedAt`：后端生成的标准时间。名称、说明、内容或状态任一保存成功都刷新 `updatedAt`。

数据库继续使用一张关系表，不拆分元数据表和内容表，也不使用 JSONB。图片内容与元数据同生同灭、同事务保存，没有独立关系生命周期。

## 4. 图片内容约束

1. 只接受 PNG 和 JPEG，媒体类型分别为 `image/png`、`image/jpeg`。
2. 图片管理页面选择的源文件必须大于 0 且不超过 5242880 字节，宽和高都必须在 1～4096 像素之间。
3. 浏览器收到宽和高都不超过 64 像素的源图片时保留原内容，不放大。任一边超过 64 时，以短边长度截取居中的最大正方形，再等比缩小；输出边长为短边与 64 中的较小值。这里的自动压缩包含居中裁切、等比缩小和重新编码，不允许直接拉伸。
4. 浏览器自动压缩时保持源图片格式；PNG 使用无损编码，JPEG 使用固定 92% 质量，并展示实际待提交内容的预览。
5. 后端只接受已经处理完成的图片：宽和高都必须在 1～64 像素之间，解码后的文件大小必须大于 0 且不超过 262144 字节。
6. 后端只做 Base64、真实格式、最终大小和最终尺寸校验，校验通过后原样保存；不负责裁切、缩放、压缩或重新编码。直接调用接口提交大图时直接拒绝。
7. 数据地址声明的媒体类型、解码后的真实文件类型和实际内容必须一致。
8. 非法 Base64、伪造格式、无法解码、接口图片超限、任一边超过 64、动态图或矢量图全部拒绝。
9. 替换内容时后端先完成全部校验，再在同一事务更新原始提交内容和四项派生信息；失败不得改变名称、说明、状态或旧图片内容。
10. 编辑日志只记录图片标识、名称、状态和“是否替换内容”，不得保存 `imageBase64`。

## 5. 管理接口

管理接口均要求现有管理权限。

`text
GET  /api/admin/games/{gameId}/images?keyword=&enabled=
GET  /api/admin/games/{gameId}/images/{imageKey}
POST /api/admin/games/{gameId}/images
PUT  /api/admin/games/{gameId}/images/{imageKey}
`

列表响应为 `{"items":[],"total":0}`，不分页：

1. `keyword` 按标识和名称模糊查询；去除首尾空格后空串等同省略，最长 100。
2. `enabled` 只接受 `true` 或 `false`；省略表示全部。
3. 结果按 `imageKey` 升序，列表和详情都返回完整统一图片对象，便于直接预览。

创建请求：

`json
{
  "imageKey": "character_vayne",
  "name": "薇恩头像",
  "description": null,
  "imageBase64": "data:image/png;base64,..."
}
`

创建成功返回 201 和统一图片对象；`enabled` 固定为 `true`。

更新请求：

`json
{
  "name": "薇恩头像",
  "description": "64 像素头像",
  "enabled": true,
  "imageBase64": "data:image/png;base64,..."
}
`

`imageBase64` 可以省略；其余三个字段按全量基本资料更新。成功返回 200 和更新后的统一图片对象。阶段 8 不提供 DELETE。

所有请求拒绝未知顶层字段、客户端提交的派生字段和版本字段。

管理列表接口仍是后端管理能力，但阶段 8 图片管理页面不把它作为列表数据源。页面只有在维护者明确查看、编辑、替换或切换状态时，才按图片标识请求管理详情；新建和更新继续使用对应管理写接口。

## 6. 公开同步接口

`text
GET /api/games/{gameId}/images
GET /api/games/{gameId}/images?updatedAfter={标准时间}
`

响应：

`json
{
  "gameId": "lol",
  "images": [
    {
      "imageKey": "character_vayne",
      "enabled": true,
      "imageBase64": "data:image/png;base64,...",
      "updatedAt": "2026-09-05T00:00:00Z"
    },
    {
      "imageKey": "old_icon",
      "enabled": false,
      "imageBase64": null,
      "updatedAt": "2026-09-05T00:01:00Z"
    }
  ]
}
`

同步规则：

1. 不带 `updatedAfter` 时返回当前游戏全部图片；停用项以不带内容的停用记录返回。
2. 带参数时只返回 `updatedAt > updatedAfter` 的变化；参数必须是标准时间。
3. 浏览器缓存同时保存启用图片和停用记录，并用全部记录的最大更新时间作为下一次增量起点。
4. 收到停用记录后，公开预览立即不再返回旧图片内容；重新启用后下一次增量重新取得内容。
5. 全量同步以服务器集合为准，清理本地多余记录；增量同步只覆盖返回项。
6. 图片不进入发布版本，也不触发 Wasm 或业务配置修订。
7. 页面中的本地缓存工具位于图片列表上方。全量或增量同步成功写入浏览器本地缓存后，页面重新读取该缓存并立即刷新列表；清理缓存后列表立即变为空状态。

## 7. 稳定错误

| HTTP | code | 场景 |
| --- | --- | --- |
| 400 | `400.INVALID_BODY` | JSON 无法绑定、未知字段、非法布尔值或客户端提交只读字段 |
| 400 | `400.VALIDATION_FAILED` | 标识、名称、说明或查询参数不符合规则 |
| 400 | `400.IMAGE_CONTENT_INVALID` | Base64、真实格式、接口图片大小或最大 64×64 尺寸不符合要求 |
| 404 | `404.GAME_NOT_FOUND` | 游戏不存在 |
| 404 | `404.IMAGE_NOT_FOUND` | 图片不存在 |
| 409 | `409.IMAGE_KEY_EXISTS` | 同一游戏图片标识重复 |
| 409 | `409.IMAGE_NAME_EXISTS` | 同一游戏规范化名称重复 |

可定位错误统一使用 `details.fieldIssues`；字段名使用 `imageKey`、`name`、`description`、`enabled` 或 `imageBase64`。

## 8. 实施顺序

1. 项目负责人确认本共享契约。
2. 后端完成迁移前检查、最终表结构、强类型接口和自动检查。
3. 核对准确数据库目标后执行迁移，读回结构和既有图片，再启动后端完成真实接口验证。
4. 前端在冻结接口上完成图片管理页、图片处理和浏览器缓存升级，并以浏览器本地缓存作为页面列表的唯一数据源。
5. 运行前端静态、单元、构建和隔离桌面端检查，再连接真实后端完成浏览器验收。
6. 项目负责人确认阶段 8 后，才开始阶段 9 关联管理设计。

前后端不能并行猜测公共字段。后端接口和错误冻结后，前端实现可以与后端剩余局部测试并行。

## 9. 跨端验收

必须证明：

1. 空缓存、新建、详情、按图片标识查询和状态筛选符合契约。
2. 新建后关闭弹窗、刷新页面和重启后端仍能回读名称、说明、内容及派生信息。
3. 替换图片后 `imageKey` 与 `createdAt` 不变，内容、派生信息和 `updatedAt` 更新。
4. 停用后管理页仍可查看和重新启用；公开同步只返回停用记录，浏览器不再展示旧缓存。
5. 重新启用后公开增量同步重新取得图片内容。
6. 宽和高都不超过 64 的合规源图片通过页面提交时保持原尺寸和内容，不被放大或重新编码。
7. 任一边超过 64 的合规源图片可以通过页面上传；浏览器按规则处理后，后端保存和响应中的图片宽高均不超过 64。
8. 直接接口提交任一边超过 64 或解码后超过 262144 字节的图片时，后端返回冻结错误，不裁切、不压缩且不产生部分写入。
9. 页面选择任一边超过 4096 或源文件超过 5242880 字节的图片时阻止提交；非图片、伪造类型或损坏 Base64 也不得写入。
10. 重复标识、重复名称、未知游戏和未知图片返回冻结错误。
11. 编辑日志不含图片 Base64；前端 400/409 保存失败时保留完整草稿和所选图片预览。
12. 页面只管理独立图片，不出现角色、属性、装备、技能或游戏封面绑定控件。
13. 新链路不依赖旧战斗数据、发布、计算或 Wasm。
14. 打开图片管理页、查询、重置、刷新页面和刷新缓存均不请求管理列表接口；空缓存提示维护者全量同步，全量同步完成后列表直接展示写入浏览器本地数据库的数据。

## 10. 停止条件与审核门禁

出现以下任一情况，停止开发并回到本契约：

1. 目标数据库中的既有图片无法通过格式、大小、尺寸或标识检查。
2. `images` 不是预期的列表分区父表，或已有分区结构与父表不一致。
3. 必须删除、重编码或丢弃真实图片数据才能迁移，但尚未取得明确授权。
4. 实际需求包含多种输出尺寸、动态图、矢量图、原图存档或对象存储。
5. 阶段 8 被要求同时建立任何业务对象图片关系。
6. 后端无法在不改变图片内容的前提下权威校验真实格式、文件大小和最大 64×64 尺寸。
7. 自动检查、真实数据库、真实接口或真实浏览器验收无法完成，且不能定位原因。

项目负责人已确认本方案；实现仍须遵守上述停止条件，真实数据库操作须先核对准确目标。
