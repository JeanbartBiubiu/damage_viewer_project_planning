# 构筑系统管理与场景装配

## 1. 目标与结论

本文定义跨游戏的构筑系统。这里的“构筑系统”是游戏在角色固有资料之外提供的一套额外选择体系，例如英雄联盟的符文、赛博朋克2077的义体和剑星的技能加点。游戏负责定义系统、分组、稳定位置、可选项和选择规则；玩家或测试场景完成选择后，将整套配置一次性赋予某个战斗角色实例。

构筑定义不挂在某个角色主数据上，完整配置也不写回角色基础资料。同一套配置可以用于不同角色或同一角色的不同场景；每次装配都先完整校验，再整体生效。代码与接口前缀统一使用 `build`，表示本文所说的“构筑”。

现行符文专用模型是本次破坏式替换的迁移基线，不再作为目标模型。`runes`、`rune_paths`、`rune_skill_relations`，以及基石、小符文、属性碎片、符文系、碎片组等固定类别，均不得继续充当跨游戏公共契约。旧接口、旧页面和旧类型在新链路验收后直接删除，不增加双写、别名接口或兼容转换层。

## 2. 范围与非目标

本次范围包括：

1. 按游戏维护一个或多个构筑系统。
2. 维护系统内的分组、稳定位置、可选项、代表图和技能授予关系。
3. 表达当前实例确需的位置选择、分组选择、投入等级、点数或容量、前置和互斥规则。
4. 形成不持久化的完整配置值，并在场景装配时一次性赋予角色实例。
5. 将现有英雄联盟符文身份、布局、图片和技能挂载迁移到新模型。
6. 分开验收管理保存、真实数据库、浏览器选择、宿主装配和真实 Wasm 运行。

本次不做以下内容：

- 不保存用户命名方案、收藏、分享、导入导出或历史版本。
- 不建立角色与构筑系统、角色与可选项的永久关系表。
- 不新增另一套技能、公式、效果、过程或触发模型；可选项继续授予现有技能。
- 不实现任意规则脚本、任意表达式或可编程规则编辑器。
- 不根据示例游戏猜测未核实的点数、容量、等级门槛、前置关系或战斗时点。
- 不因为管理数据迁移成功就宣称构筑效果已进入战斗运行。

## 3. 领域分层与数据流

领域关系固定为：

```text
游戏
└─ 构筑系统
   ├─ 分组
   │  └─ 稳定位置
   │     └─ 候选可选项
   └─ 可选项
      └─ 技能授予关系

场景角色实例 + 完整构筑配置
    → 读取同游戏构筑定义
    → 完整校验分组、位置、选项、等级、预算、前置和互斥
    → 展开全部技能授予关系
    → 以选择位置为实例边界挂到角色
    → 初始化、编译和运行
```

各层职责如下：

| 层次 | 职责 | 不承担的职责 |
| --- | --- | --- |
| 角色主数据 | 角色身份、基础属性和固有技能 | 不保存符文、义体或技能树选择 |
| 构筑系统 | 当前游戏的一类额外选择体系及整套规则 | 不代表任何角色已选择 |
| 分组与稳定位置 | 排列候选、约束位置和承载可重复引用 | 不复制可选项身份 |
| 可选项 | 选择身份、投入等级和成本 | 不直接复制技能内部组成 |
| 技能授予关系 | 指向现有技能并说明何时、以何等级授予 | 不保存角色实例 |
| 完整构筑配置 | 某次场景的完整选择值 | 首期不持久化，不修改管理定义 |
| 场景装配 | 校验配置并将授予内容挂到战斗角色实例 | 不改写角色基础数据 |

一个游戏可以有多个构筑系统；同一角色实例也可以接收当前游戏内多个不同系统的配置。同一角色实例中同一 `systemKey` 只能出现一次，防止同一体系被重复整套装配。

## 4. 静态存储模型

### 4.1 `build_systems`（构筑系统）

| 字段 | 含义 |
| --- | --- |
| `game_id`、`system_key` | 同游戏内稳定身份，联合主键 |
| `name`、`description` | 游戏内名称和说明，例如“符文”“义体”“技能加点” |
| `configuration_mode` | `SLOT_SELECTION` 表示按位置选择；`POINT_ALLOCATION` 表示向选项投入等级 |
| `sort_order` | 当前游戏内显示顺序，非负整数 |
| `selection_rules` | 严格校验的完整选择规则对象 |
| `created_at`、`updated_at` | 创建和更新时间 |

同游戏的规范化名称唯一。稳定键创建后不可修改。已有分组或规则时不得改变 `configuration_mode`；需要改变时先清空对应结构，避免旧位置被另一种配置含义继续解释。

`SLOT_SELECTION`（按位置选择）要求所有可选项 `max_rank=1`，每次选择的 `rank` 固定为1，`rank_costs[0]`可以表达义体容量等一次性成本。`POINT_ALLOCATION`（按点投入）允许 `max_rank` 大于1，配置必须显式给出最终投入等级，累计成本按各级成本求和。两种方式共用分组、稳定位置和完整配置形状，不建立两套表。

### 4.2 `build_options`（构筑可选项）

| 字段 | 含义 |
| --- | --- |
| `game_id`、`system_key`、`option_key` | 系统内稳定身份，联合主键 |
| `name`、`description` | 游戏内名称和说明 |
| `max_rank` | 最大投入等级，至少为1 |
| `rank_costs` | 从第1级到 `max_rank` 的非负整数成本数组，长度必须完全一致 |
| `created_at`、`updated_at` | 创建和更新时间 |

英雄联盟普通符文迁移为 `max_rank=1`、`rank_costs=[0]`。点数或容量如何取得由系统规则定义，不能从角色等级、属性名或说明文字自动推断。

可选项不再保存全局固定类别。基石、属性碎片、义体部位或技能分支都由所在系统的分组、位置和规则表达，不扩充公共枚举。

同一系统内规范化可选项名称唯一；不同系统可以使用相同名称和局部稳定键。`rank_costs` 必须是 JSON 数组，数据库检查其顶层种类，服务负责长度、整数和范围校验。

### 4.3 `build_groups`（构筑分组）

| 字段 | 含义 |
| --- | --- |
| `game_id`、`system_key`、`group_key` | 系统内稳定身份，联合主键 |
| `name`、`description` | 分组名称和说明 |
| `sort_order` | 系统内显示顺序，非负整数 |
| `slots` | 完整有序位置数组 |
| `created_at`、`updated_at` | 创建和更新时间 |

每个位置采用以下严格形状：

```text
{
  slotKey,
  name,
  minimumSelections,
  maximumSelections,
  optionKeys
}
```

`slotKey` 在所属分组内唯一且创建后不可修改；配置引用使用 `groupKey + slotKey`，数组下标只负责显示顺序。`minimumSelections`、`maximumSelections` 为非负整数且前者不大于后者；`optionKeys` 为当前系统内有序、去重的可选项键。

同一可选项允许出现在不同位置。英雄联盟的同一属性碎片可以出现在两行，仍只保存一个可选项身份。配置选择和运行挂载必须保留两个位置实例，不能按 `optionKey` 去重。同一位置内不得重复放入同一可选项。

按位置选择的系统允许同一可选项出现在多个位置并在一套配置中多次选择，每个位置分别计成本和授予。按点投入的系统中，同一可选项在整个系统布局内最多出现一次，在完整配置中也最多有一个选择实例；前置规则据此读取唯一投入等级，不合并多个位置的等级。

同一系统内规范化分组名称唯一；不同系统可以复用分组名称和局部稳定键。`slots` 必须是 JSON 数组，数组顺序是唯一显示顺序，不另存位置排序字段。

### 4.4 `build_option_skill_relations`（可选项技能授予）

| 字段 | 含义 |
| --- | --- |
| `game_id`、`system_key`、`option_key`、`skill_key` | 可选项与现有技能的联合关系身份 |
| `activation_rank` | 可选项达到该投入等级时才授予，至少为1 |
| `skill_level_mode` | `FIXED` 使用固定技能等级；`SAME_AS_OPTION` 使用可选项投入等级 |
| `fixed_skill_level` | 固定模式必填，随投入等级模式必须为空 |
| `sort_order` | 同可选项内授予顺序，非负整数 |

新增关系只接受当前游戏内已启用技能。既有技能之后被停用时，关系仍可见、可调序和解绑，但不能参与新的可运行配置。删除被关系引用的技能继续受保护。删除可选项时只清自己的技能关系和代表图，不删除共享技能或图片本体。

一个没有技能授予关系的可选项仍可维护和选择，但页面与运行摘要必须显示“当前没有可计算授予内容”，不得暗示它已经影响伤害结果。

外键与删除语义固定为：分组、可选项引用构筑系统并随整个系统删除；技能授予同时引用可选项和技能，删除可选项时清授予，删除技能时受保护。为技能反向查询建立 `(game_id, skill_key, system_key, option_key)` 索引。位置与规则保存在系统聚合 JSON 中，由持有同游戏写锁的服务作正向校验和删除反查，不用 JSON 文本搜索代替正式校验。

### 4.5 图片关系

复用单表 `image_relations`，将符文专用来源替换为：

- `BUILD_OPTION`：构筑可选项代表图；
- `BUILD_GROUP`：构筑分组代表图。

两者父键均保存 `system_key`，来源键分别保存 `option_key` 或 `group_key`，从而保证同一游戏不同系统可以复用相同局部键。图片表继续不设来源外键；后端在写入前核对系统、来源对象和图片属于同一游戏，在来源删除时同事务清理，在用途反查时拒绝悬空关系。

`image_relations` 的来源检查同步允许 `BUILD_OPTION`、`BUILD_GROUP`，并要求这两类父键非空；除技能效果和这两类来源外，其他来源继续要求父键为空。图片用途响应删除 `runes`、`runePaths`，新增 `buildOptions:[{systemKey,optionKey,optionName}]` 与 `buildGroups:[{systemKey,groupKey,groupName}]`，空用途返回空数组。

## 5. 选择规则

`selection_rules` 只允许以下有限结构，不接受任意字段、脚本或表达式：

| 规则 | 含义 |
| --- | --- |
| 分组角色 | 定义主系、副系、固定碎片组等角色，可指定允许选择的分组数和分组集合 |
| 角色互异 | 指定两个分组角色不能选择同一分组 |
| 位置总数 | 指定某个分组角色需要选择的最少和最多位置数 |
| 角色位置规则 | 按分组角色和候选分组指定允许、必选及最多选择的位置 |
| 预算 | 定义点数或容量键，以及固定上限或场景必须显式提供的上限 |
| 前置 | 某可选项达到指定等级前，要求另一可选项至少达到指定等级 |
| 互斥 | 一组可选项在同一配置中最多选择指定数量 |

请求与响应中的严格形状为：

```text
{
  groupRoles: [
    {
      roleKey,
      name,
      groupKeys,
      minimumGroups,
      maximumGroups,
      minimumSelectedSlots,
      maximumSelectedSlots,
      distinctFromRoleKeys,
      slotRules: [
        {
          groupKey,
          slotKey,
          minimumSelections,
          maximumSelections
        }
      ]
    }
  ],
  budget: null | {
    budgetKey,
    name,
    maximumSource,
    fixedMaximum
  },
  prerequisites: [
    {
      optionKey,
      minimumRank,
      requiredOptionKey,
      requiredMinimumRank
    }
  ],
  exclusions: [
    {
      optionKeys,
      maximumSelected
    }
  ]
}
```

`roleKey`、`budgetKey` 使用稳定键格式。同一角色键只能出现一次；`groupKeys`、`distinctFromRoleKeys` 和互斥选项数组均去重。分组数量、已选位置数量和 `maximumSelected` 都是非负整数，最小值不得大于最大值。每个参与完整配置的分组必须出现在至少一个分组角色中；固定分组使用仅含一个分组键且最小、最大分组数都为1的角色表达，不增加另一种固定分组字段。

`slotRules` 以当前角色下的 `groupKey + slotKey` 为身份，同一位置只能出现一次，并且必须引用 `groupKeys` 中的分组及其真实位置。配置在该角色和分组下只能选择 `slotRules` 明确列出的位置；未列出的位置禁止选择。角色位置最小、最大值必须处于分组位置自身允许范围内，分组角色的 `minimumSelectedSlots`、`maximumSelectedSlots` 统计实际至少选择一项的位置数。这样同一符文系作为主系时可以要求基石及各行，作为副系时可以禁止基石并只允许指定数量的小符文行，而不复制分组或可选项身份。

`maximumSource` 只接受 `FIXED`（固定上限）或 `SCENARIO_INPUT`（场景显式输入）。固定上限时 `fixedMaximum` 必须是非负整数；场景输入时它必须为 `null`。每个系统首期至多有一个预算池；没有预算时 `budget=null` 且所有可选项成本必须为0。

前置规则表示：当 `optionKey` 达到 `minimumRank` 时，`requiredOptionKey` 必须至少达到 `requiredMinimumRank`。互斥规则统计数组中实际被选择的不同可选项，不能用同一选项在两个位置出现两次绕过或重复消耗名额。未知字段和不符合当前配置方式的规则整体拒绝。

规则中的分组、位置和可选项只能引用当前系统。前置关系不得自引用或形成直接、间接循环；循环检查失败时定位到具体规则。预算成本是各选择从第1级累计到目标等级的 `rank_costs` 总和，不把目标等级的单级成本误当累计成本。

具体游戏规则必须来自已核实资料。当前结构能够承载英雄联盟的主副系和碎片组、义体位置与容量、技能树等级与前置；在对应资料未进入录入范围前，只实现并显示已经核实的规则，不用默认值补齐示例游戏。

## 6. 完整配置契约

完整配置是场景输入值，不是管理实体。单个角色实例的形状为：

```text
buildConfigurations: [
  {
    systemKey,
    groupAssignments: [
      { roleKey, groupKey }
    ],
    selections: [
      { roleKey, groupKey, slotKey, optionKey, rank }
    ],
    budgets: {
      budgetKey: value
    }
  }
]
```

`groupAssignments` 记录系统规则中需要显式选择的分组角色；固定分组可由页面生成，但进入装配前必须规范化为完整值。同一 `roleKey + groupKey` 不能重复；是否允许同一分组分配给不同角色由 `distinctFromRoleKeys` 决定。互异约束按无向关系处理，无论写在哪一侧都同时限制两个角色，反向重复声明拒绝。

`selections` 以 `roleKey + groupKey + slotKey + optionKey` 为身份，角色和分组必须存在于 `groupAssignments`，位置必须存在于对应角色的 `slotRules`。同一位置内同一选项不能重复。按位置选择时，同一可选项出现在不同角色或位置是多个合法选择实例；按点投入时，同一可选项在整个系统配置中最多选择一次。`rank` 为正整数且不超过 `max_rank`。

`budgets` 只提供规则明确要求的场景值。固定预算不重复提交；场景预算缺失、非有限值、非整数或小于0时拒绝。不得把缺失预算补0，也不得自动读取名称相似的角色属性。

首期不为完整配置生成数据库标识。以后如果用户明确要求保存或分享方案，应复用本节值对象另建用户方案能力，不能回写角色主表或改变本契约；该能力不属于当前实施范围。

## 7. 校验与删除保护

### 7.1 定义写入校验

所有写入口沿用当前同游戏写保护，在一个事务内读取并校验完整受影响系统：

1. 游戏、系统、分组、位置、可选项、技能和图片必须属于同一游戏。
2. 稳定键沿用小写字母起始、小写字母数字下划线、最多64字符的现行规范。
3. 名称去首尾空白后非空且不超过100字符；说明为空时保存为 `null`，最长2000字符。
4. 位置引用、规则引用、技能等级和投入等级全部合法后才写入；任何一项失败时整体回滚。
5. 允许先建立空系统、空分组、空位置和未入布局的可选项，以便分步录入；它们不因此成为可运行配置。
6. 修改完整位置数组时，以新数组与系统其他定义共同校验，不把自身旧值误算成冲突。
7. 未知字段、重复键、错误数值种类、非整数等级和成本一律拒绝，不自动清理后保存。

### 7.2 完整配置校验

Web 宿主在修改场景预览时可以逐项提示，但点击运行时必须重新校验完整配置。校验顺序固定为：

1. 游戏与系统身份；
2. 分组角色及互异要求；
3. 分组角色、角色位置规则、位置与候选归属；
4. 重复选择和投入等级；
5. 位置及分组选择数量；
6. 前置与互斥；
7. 预算与累计成本；
8. 技能授予关系和技能启用状态；
9. 角色实例及运行所需明确输入。

任一错误都阻止整套系统装配；同一角色的多个构筑系统中任一系统失败时，本次角色构筑全部不生效，也不调用 Wasm。错误路径必须定位到 `buildConfigurations[i]`、`groupAssignments[j]`、`selections[j]` 或 `budgets.<key>`，不能只返回自由文本。

### 7.3 删除行为

- 删除被位置或规则引用的可选项返回占用错误，并列出系统、分组、位置或规则路径；维护者须先显式解除引用。
- 删除被系统规则引用的分组返回占用错误；空分组可直接删除。
- 删除整个构筑系统属于明确的聚合删除：同事务删除其分组、可选项、授予关系及图片关系，不删除技能和图片本体。页面必须显示将删除的对象数量并二次确认。
- 完整配置不持久化，因此管理库不为外部配置建立反向引用。场景中保留的旧配置在下次校验时按缺失对象整体拒绝，不按名称猜测替代项。

## 8. 管理接口

接口前缀沿用 `/api/admin/games/{gameId}`，新增以下资源并删除符文专用资源：

| 资源 | 能力 |
| --- | --- |
| `/build-systems`、`/build-systems/{systemKey}` | 系统列表、详情、新增、修改、删除 |
| `/build-systems/{systemKey}/definition` | 同一只读事务返回系统、分组、位置、可选项和技能授予的完整定义快照 |
| `/build-systems/{systemKey}/groups`、`.../groups/{groupKey}` | 分组及完整位置布局增改删 |
| `/build-systems/{systemKey}/options`、`.../options/{optionKey}` | 可选项增改删 |
| `/build-option-skill-relations` | 按系统与可选项或按技能双向查询、挂载、调序和解绑 |
| 分组与可选项的 `representative-image` 子资源 | 代表图查询、替换和解除 |

写入体固定如下，修改接口不接受对应稳定键：

| 对象 | 新增字段 | 修改字段 |
| --- | --- | --- |
| 构筑系统 | `systemKey/name/description/configurationMode/sortOrder/selectionRules` | 除 `systemKey` 外其余完整字段 |
| 构筑分组 | `groupKey/name/description/sortOrder/slots` | 除 `groupKey` 外其余完整字段 |
| 构筑可选项 | `optionKey/name/description/maxRank/rankCosts` | 除 `optionKey` 外其余完整字段 |
| 技能授予 | `systemKey/optionKey/skillKey/activationRank/skillLevelMode/fixedSkillLevel/sortOrder` | 路径确定三个稳定键，请求包含其余完整字段 |

`FIXED` 授予模式要求 `fixedSkillLevel` 是正整数且不超过被授予技能最高等级；`SAME_AS_OPTION` 要求该字段为 `null`，并且可选项最高等级不超过技能最高等级。`activationRank` 不得超过可选项最高等级。按位置选择的系统只接受固定技能等级模式；按点投入的系统可以使用两种模式。

技能授予列表查询至少提供 `skillKey`，或同时提供 `systemKey + optionKey`；没有查询范围时返回请求错误。新增使用集合资源，修改和删除路径为 `/build-option-skill-relations/{systemKey}/{optionKey}/{skillKey}`，保证技能页可以反查所有构筑来源，而不必枚举每个系统。

完整定义快照固定返回 `{system,groups,options,skillRelations}`，各集合使用本文规定的确定顺序。后端使用单次聚合查询或可重复读事务取得快照，并在返回前重新校验全部同游戏、同系统引用；发现已存悬空或非法结构时返回 `500.INVALID_STORED_BUILD_DEFINITION`，不返回可被宿主部分使用的数据。管理页面可以使用分散资源编辑，试配、场景校验和宿主装配只能消费完整定义快照，不能并行拼接多次列表响应。

列表继续返回 `{items,total}`，按关键词过滤并由页面本地分页。系统和分组按 `sortOrder`、稳定键排序，可选项按名称和稳定键排序。新增体包含稳定键，修改体拒绝稳定键变更。详情和关系响应必须返回 `gameId` 与 `systemKey`，前端拒绝异游戏或异系统响应。

错误至少区分：

- `400.INVALID_BUILD_SYSTEM_REQUEST`
- `400.INVALID_BUILD_GROUP_REQUEST`
- `400.INVALID_BUILD_OPTION_REQUEST`
- `404.BUILD_SYSTEM_NOT_FOUND`
- `404.BUILD_GROUP_NOT_FOUND`
- `404.BUILD_OPTION_NOT_FOUND`
- `409.BUILD_SYSTEM_KEY_EXISTS`、`409.BUILD_SYSTEM_NAME_EXISTS`
- `409.BUILD_GROUP_IN_USE`
- `409.BUILD_OPTION_IN_USE`
- 现有技能、图片和关系的对应错误

管理后端只保存并校验构筑定义，不保存场景完整配置，也不组装 Wasm 请求。不得恢复旧 `/combat-data/**`、版本发布或已删除的旧实体链路。

## 9. 管理页面与场景入口

导航将“符文管理”替换为“构筑系统管理”。页面先绑定当前连接和游戏，再选择当前系统，提供四个视图：

1. **系统与规则**：维护名称、说明、配置方式、排序和有限规则。
2. **可选项**：维护身份、投入等级、成本、代表图和技能授予关系，可直达现有技能统一编辑工作区。
3. **分组与位置**：维护完整有序位置、候选顺序及分组代表图。
4. **试配与校验**：按当前定义形成一套临时配置，展示分组、位置、等级、预算、前置和互斥问题；不保存用户方案。

页面公共文案使用“构筑系统、分组、位置、可选项”。具体游戏名称显示系统数据中的“符文”“义体”“技能加点”等，不在公共类型和导航中硬编码基石、碎片或符文系。关系弹窗和技能工作区来源改为“构筑可选项”，并显示系统名称、可选项名称和稳定键。

新增、修改、删除和试配都纳入未保存草稿保护。切换连接、游戏或系统前确认草稿；切换后清除旧系统上下文，迟到响应不得恢复。保存成功后独立读取最终对象；响应不明时重新读取，不重放创建请求。

场景页在角色实例旁选择完整构筑配置。选择状态只属于当前场景；更换角色可以保留配置草稿并重新校验，但不得自动写入新角色。来源未配置计算内容时明确提示，不把“已选择”显示为“已进入计算”。

## 10. 场景装配与运行边界

Web 宿主是完整配置到运行对象的装配方。后端提供定义，TinyGo V2 Wasm 只接收已经展开并通过校验的通用编译输入；本设计不新增游戏专用 Wasm 接口。

装配步骤固定为：

1. 为当前游戏每个已选系统读取一次完整定义快照；系统之间没有交叉规则，因此分别取得的完整快照可以共同进入本次场景输入。
2. 按第7.2节完整校验，不产生部分中间挂载。
3. 依照系统、分组角色、分组、位置、可选项和授予排序生成确定顺序。
4. 将每个选择实例的技能组成展开为角色拥有的运行来源。
5. 运行实例身份至少包含角色实例、系统、分组角色、分组、位置、可选项和技能，保证同一可选项在两个位置可以形成两个独立实例。
6. 合并角色固有、装备和构筑来源后统一初始化，不通过先后执行数值结果来制造隐含优先级。
7. 生成最终配置摘要，再执行 `engine_compile`、`engine_run`、`engine_release_session`。

同一选择实例因重试、恢复或重复渲染不得二次挂载。不同位置选择同一可选项时不得按技能键或定义键静默去重；如果现有宿主或 Wasm 不能表达两个合法实例，必须以明确路径拒绝，并将其记录为运行能力缺口。

管理保存、技能授予存在和宿主成功展开都不单独证明战斗效果正确。只有实际使用最终 Wasm 产物完成编译、运行、释放并得到预期结果，才能记录该代表配置的运行通过。

## 11. 现有英雄联盟数据的破坏式迁移

迁移前以真实数据库和管理接口冻结当前摘要，至少记录：69个身份、6个分组、23个位置、71个候选位置、74项代表图用途，以及实际技能挂载数量和键集合。固定数量只用于核对当前英雄联盟数据，不成为通用表约束。

迁移映射如下：

| 现有数据 | 新数据 |
| --- | --- |
| 当前游戏的全部符文与碎片 | `system_key=runes` 下的 `build_options`，原 `rune_key` 保持为 `option_key` |
| 五个符文系和一个碎片组 | 同系统下的 `build_groups`，原 `path_key` 保持为 `group_key` |
| 槽位数组 | 带稳定 `slotKey` 的位置数组 |
| 符文技能挂载 | 可选项技能授予，`activation_rank=1`、固定技能等级1 |
| `RUNE`、`RUNE_PATH` 图片用途 | `BUILD_OPTION`、`BUILD_GROUP`，父键写入 `runes` |

23个稳定位置键必须使用一次性人工核对的迁移映射，不能从中文名称、数组下标或当前排序自动生成。迁移映射同时记录原分组键、原下标、位置名称和新位置键，执行前检查23项一一对应。承担相同选择含义的五个符文系使用相同语义位置键，使主系、副系角色可以共用位置规则；适应之力、成长生命等跨位置复用保持一个可选项身份和多个位置引用。

真实迁移执行要求：

1. 核对目标数据库、当前结构、服务停写状态和可恢复备份。
2. 在单事务中创建新表、复制并校验数据、迁移图片关系和技能授予。
3. 事务内核对身份、顺序、位置、引用和关系集合；任何差异整体回滚。
4. 部署只使用新接口和新页面的后端、前端及宿主代码。
5. 独立只读回查新接口与数据库，确认迁移摘要和图片用途一致。
6. 删除旧三表、旧约束、旧控制器、旧服务、旧页面、旧类型和旧路由；不保留双写或旧路径转发。

用户本次仅授权删除旧设计文档并编写新方案，不等于已经授权执行真实数据库迁移。执行迁移前仍须按本节核对具体目标数据库和数据处置范围。

| 阶段 | 责任 | 可独立验收结果 |

| 2 后端定义管理 | 后端实现四表、接口、保护和迁移脚本 | 新结构与接口保存、回读、引用保护通过；未宣称场景运行 |
| 3 前端管理 | 前端替换导航、页面、类型、服务、图片及技能关系入口 | 真实浏览器可维护系统、选项、分组、位置和规则 |
| 4 配置试配 | 前端形成完整配置并执行纯校验 | 重复位置、等级、预算、前置、互斥和跨游戏错误可定位 |

## 13. 验收门槛

### 13.1 静态定义与真实数据库

- 新表主键、外键、检查约束、索引及事务保护符合本文。
- 同一游戏可维护至少两个不同构筑系统，局部键互不串用。
- 空系统、空分组、空位置和未入布局选项可保存；非法引用和循环前置整体拒绝。
- 迁移后69个可选项、6个分组、23个稳定位置、71个候选位置、74项图片用途，以及实际技能关系集合与迁移前一致。
- 旧三表和符文专用接口按实施顺序删除，没有兼容层。

### 13.2 浏览器管理与试配

- 新增系统、选项、分组、位置、图片和技能授予后，关闭重开与独立回读一致。
- 同一可选项放入两个位置仍只有一个身份；试配同时选择两处时保留两个选择实例。
- 同一符文系分别作为主系和副系时，角色位置规则允许的行不同；副系不能选择主系专属位置，位置总数按对应角色独立计算。
- 切换连接、游戏、系统及离开页面的草稿保护和迟到响应隔离通过。
- 跨游戏、未知位置、非法等级、超预算、缺前置和互斥冲突显示具体字段，原草稿保留。
- 没有可计算授予内容的选项显示明确限制，不冒充战斗已生效。

### 13.3 宿主与真实 Wasm

- 同一完整配置可分别赋予两个角色实例，角色管理数据保持不变，运行来源归属各自独立。
- 未选择的可选项不进入最终编译输入；同一选项的两个合法角色或位置实例不被错误合并，运行身份包含 `roleKey`。
- 任一系统配置失败时不调用编译；编译或运行失败不写回管理定义或角色主数据。
- 至少选择一个已有完整技能组成的可选项，使用最终产物实际完成编译、运行和释放，并证明预期属性或效果变化。
- 管理接口、真实数据库、浏览器、宿主装配和战斗运行证据分别记录；未执行的层级明确标为未验证。
