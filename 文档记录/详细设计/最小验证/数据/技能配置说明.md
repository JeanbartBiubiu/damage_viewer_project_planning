# 技能配置说明

## 1. 目标
这份说明用于最小验证阶段的技能/装备效果配置，目标有两件事：

1. 前端可以直接按这份结构做技能配置页雏形。
2. 配置能够平滑映射到 wasm 侧预期的计算模型，避免后面再把页面和数据整体推翻。

结合当前仓库里的 `web/src/types/api.ts`、`wasm/概要设计-WASM内部事件流.md`、`wasm/概要设计-控制与打断状态机制.md`，建议从现在开始把技能定义拆成 5 块：

- `基础信息`：技能归属、技能键、名称、描述。
- `params`：数值表、系数、可复用变量，只负责“怎么算”。
- `timingProfile`：前摇、引导、后摇、持续、多段节奏，只负责“什么时候发生”。
- `mechanicsConfig`：触发事件、条件、动作，只负责“算出来后怎么应用”。
- `mvpExtensions`：当前样例里已经存在，但 wasm DSL 还没正式收敛的效果，例如攻击特效联动、普攻重置。

当前 `Katarina技能相关.json` 和 `装备关联技能.json` 已经包含了这些信息，但混在 `param`、`cd`、`effection/effective`、`triggerType`、`triggerTime` 里了，所以前端如果直接照旧字段做页面，会把语义混乱一起带过去。

## 2. 建议统一的顶层结构
推荐前端和最小验证数据都围绕下面这层结构来组织：

```json
{
  "skillId": "hero_katarina_e",
  "ownerType": "hero",
  "ownerId": "Katarina",
  "skillKey": "E",
  "name": "瞬步",
  "description": "可选，展示文案",
  "resourceCosts": [],
  "cooldowns": [],
  "params": {
    "vars": {}
  },
  "timingProfile": {
    "phases": []
  },
  "mechanicsConfig": {
    "version": 1,
    "stacks": [],
    "triggers": []
  },
  "mvpExtensions": {},
  "notes": []
}
```

建议：

- 顶层结构和可引用 ID 尽量用英文稳定 key。
- 中文放到 `name`、`description`、`label`、`notes` 这类展示字段里。
- 变量、计数器、tick、trigger 都应该有稳定 ID，后面前端编辑器、静态校验、diff 才好做。

## 3. 现有定义里需要优先收口的问题

### 3.1 字段命名不统一
当前样例里同时出现了下面这些情况：

- `effection` 和 `effective` 混用。
- `type` 有时表示“效果类型”，有时又承担“属性类型”。
- `attribute`、`type`、`object` 的语义边界不清。
- 顶层字段和子字段中文英文混用。

这会直接导致前端表单不知道该按“动作类型”还是“属性修改”去建模。

### 3.2 触发方式还是自然语言
例如卡特被动里“Q 技能或者 W 技能释放 1 秒后自动触发”，现在还是说明文字。  
这类内容前端可以展示，但如果想对齐 wasm，应该拆成结构化触发规则，例如：

- `event = on_spell_cast`
- 条件里限制 `skillKey in [Q, W]`
- 通过 `schedule_tick` 或延迟触发来表达“1 秒后”

### 3.3 `param` 过于压缩
当前 `param` 用 `v / d / a / t / max / min / time` 这套写法可以先记数据，但不利于页面和校验：

- `v` 同时承担常量、数组、映射表三种含义。
- `d` 只靠字符串表达“按英雄等级还是技能等级取值”。
- `a` 既像属性引用，又像缩放来源。
- `t=计数器` 会把“变量定义”和“运行时状态”混在一起。

### 3.4 公式变量作用域不清
当前样例里已经出现变量命名不一致的问题：

- `弹射之刃` 的参数叫 `法强加成`，公式写的是 `基础伤害+法术加成`
- `死亡莲华` 的“可触发攻击特效”公式里直接出现了 `v`

如果前端继续允许自由字符串公式，至少也要同时维护一份变量清单和作用域说明。

### 3.5 计数器 / 持续效果 / cd 不应继续和参数混放
从 wasm 事件流的角度看：

- 计数器应该归 `stacks`
- 持续属性增减应该归 `apply_modifier`
- 多段 / DoT / HoT 应该归 `schedule_tick + on_tick`
- 冷却应该归 `cooldowns` 或运行时 `cooldowns`

不建议继续把这些都塞回 `param`。

## 4. 跟 wasm 计算模型对齐时的几条原则

### 4.1 伤害、治疗、护盾、属性修改要分通道
wasm 侧已经明确在往“四通道”靠：

- `damage`
- `heal`
- `shield`
- `modifier`

所以文档里不要再用一个模糊的 `type=伤害` 去包所有效果。至少要明确：

- 是直接掉血的伤害
- 是属性加减
- 是治疗
- 是护盾

### 4.2 配置层只订阅稳定事件
文档里应该优先使用这些“配置可见事件”来描述触发时机：

- `on_spell_cast`
- `on_basic_attack_hit`
- `on_damage_dealt`
- `on_damage_taken`
- `on_tick`
- `on_stack_change`

不要把 `damage_apply`、`cast_intent` 这类内部过程事件直接暴露给前端配置页。

### 4.3 `params` 只定义数值，不直接改状态
建议把职责分清：

- `params` 只负责定义基础数值、等级表、属性系数、映射表
- `mechanicsConfig` 负责决定这些数值最终打到哪里

也就是说：

- “基础伤害 80/115/150/185/220” 属于 `params`
- “对敌方造成魔法伤害” 属于 `mechanicsConfig.actions`

### 4.4 多段 / 延迟 / 引导要落到 `timingProfile + tick`
当前卡特样例里已经有几类典型需求：

- `Q` 的命中延迟
- `被动` 的延迟触发
- `R` 的 2.5 秒 15 发匕首
- 会不会被打断

这些都不该只写在文案里，建议至少拆出：

- `timingProfile.phases`
- `schedule_tick`
- `on_tick`
- `interruptible`
- `cancelScheduledOnInterrupt`

### 4.5 公式最好区分“展示文本”和“执行表达式”
页面录入时可以保留 `formulaText` 方便人看，但真正用于执行的表达式最好是结构化的。  
MVP 阶段如果暂时只录字符串，也建议同时保留变量引用清单，避免公式无法校验。

## 5. 各区块建议怎么写

### 5.1 基础信息
建议统一保留：

- `skillId`：稳定唯一 ID，例如 `hero_katarina_e`、`item_rageblade_passive_2`
- `ownerType`：例如 `hero`、`item`
- `ownerId`：拥有者 ID
- `skillKey`：推荐用稳定键，例如 `A / P / Q / W / E / R / passive_1 / active_1`
- `name`
- `description`

不建议继续用“普通攻击 / 主动技能 / 被动”直接兼做 `skillKey`，因为这会让同一拥有者下的多个主动技能无法稳定区分。

### 5.2 `params`
推荐把参数定义成更显式的结构，而不是继续压缩在 `v/d/a/t` 里：

```json
{
  "params": {
    "vars": {
      "base_damage": {
        "label": "基础伤害",
        "kind": "table",
        "by": "skillLevel",
        "values": [80, 115, 150, 185, 220]
      },
      "ap_ratio": {
        "label": "法强系数",
        "kind": "scaled_attr",
        "attr": "self.ability_power",
        "coefficient": 0.4
      }
    }
  }
}
```

建议支持的最小类型：

- `const`：固定值
- `table`：按等级取值
- `scaled_attr`：按属性缩放
- `mapping`：根据某个离散条件取值，例如近战/远程

推荐字段：

- `label`：中文展示名
- `kind`
- `value` 或 `values`
- `by`：`skillLevel` / `championLevel`
- `attr`：属性 key，建议引用属性字典里的稳定 key
- `coefficient`
- `min`
- `max`
- `notes`

补充建议：

- 计数器不要继续放在 `params.vars` 里，移到 `mechanicsConfig.stacks`
- 属性引用尽量不要写“法强 / 当前攻击力”这种展示名，尽量写成稳定 attrKey

### 5.3 `cooldowns` 和 `resourceCosts`
这两块不建议再写成裸数组或混合字符串，最好和 `params` 使用同样的数值定义思路：

- 常规技能冷却：按技能等级的 `table`
- 普攻冷却：可用 `formulaText = 1 / attack_speed`
- 法力 / 能量消耗：按技能等级的 `table`

如果要支持减 cd、充能、可变资源消耗，前端页面也需要预留：

- `formulaText`
- `charges`
- `cooldownGroup`
- `canModifyCooldown`

### 5.4 `timingProfile`
建议把时序相关字段统一放这里，不再散落在 `延迟读条`、`后摇`、说明文字里：

```json
{
  "timingProfile": {
    "phases": [
      {
        "phaseKey": "cast",
        "kind": "cast",
        "durationMs": 200
      },
      {
        "phaseKey": "recovery",
        "kind": "recovery",
        "durationMs": 100
      }
    ]
  }
}
```

当前最小需要覆盖：

- `cast`：前摇
- `channel`：引导
- `recovery`：后摇
- `persistent_effect`：施法后继续独立存在的效果

建议字段：

- `phaseKey`
- `kind`
- `durationMs`
- `interruptible`
- `cancelScheduledOnInterrupt`
- `onEnterEmit`
- `onFinishEmit`

页面如果一开始不做完整 phase 编辑器，也至少要保留下面这些扁平字段，后面再转换成 `phases`：

- `castMs`
- `channelMs`
- `recoveryMs`
- `interruptible`
- `hitCount`
- `hitIntervalMs`

### 5.5 `mechanicsConfig`
这部分建议直接按 wasm 的“规则卡片”思路组织。每一条规则都包含：

- `id`
- `event`
- `conditions`
- `actions`

最小结构：

```json
{
  "mechanicsConfig": {
    "version": 1,
    "stacks": [],
    "triggers": [
      {
        "id": "cast_damage",
        "event": { "type": "on_spell_cast" },
        "actions": []
      }
    ]
  }
}
```

当前最值得支持的动作类型：

- `deal_damage`
- `apply_modifier`
- `add_stack`
- `remove_stack`
- `schedule_tick`
- `if`

当前最值得支持的事件类型：

- `on_spell_cast`
- `on_basic_attack_hit`
- `on_damage_dealt`
- `on_damage_taken`
- `on_tick`
- `on_stack_change`

建议把页面里的“效果列表”理解为 `triggers[].actions[]`，而不是再单独维护一个没有触发上下文的 `effective` 数组。

### 5.6 `stacks`
像鬼索这类“叠层 / 满层 / 第三次触发”的逻辑，建议统一收进 `mechanicsConfig.stacks`：

```json
{
  "stacks": [
    {
      "id": "rageblade_as_stack",
      "name": "攻速层数",
      "max": 4,
      "resetOn": ["timeout", "combat_end"],
      "timeoutMs": 6000
    }
  ]
}
```

这样比把“计数器”塞进 `param` 更接近 wasm 的运行时模型，也更适合页面做可视化编辑。

### 5.7 `mvpExtensions`
当前样例里已经有几类效果，现有 wasm DSL 还没有完全标准化，但前端页面又不能丢：

- `可触发攻击特效`
- `可消耗攻击特效`
- `可重置普通攻击计时器`
- “总共发射 15 发匕首”
- “可被打断”

建议暂时单独保留一个扩展区：

```json
{
  "mvpExtensions": {
    "attackInteraction": {
      "canTriggerOnHit": true,
      "consumeOnHit": false,
      "resetBasicAttackTimer": true
    },
    "delivery": {
      "hitCount": 15,
      "hitIntervalMs": 166.7,
      "canBeInterrupted": true
    }
  }
}
```

这块的目标不是长期保留，而是先让页面和最小验证数据不丢信息，后续再逐步并入正式 DSL。

## 6. 旧字段到新结构的映射建议

### 6.1 卡特样例

- `param` -> `params.vars`
- `消耗` -> `resourceCosts`
- `cd` -> `cooldowns`
- `延迟读条` -> `timingProfile.castMs` 或 `phases.cast.durationMs`
- `后摇` -> `timingProfile.recoveryMs`
- `effection` -> `mechanicsConfig.triggers[].actions`
- “Q/W 1 秒后触发” -> `event + condition + schedule_tick`
- “2.5 秒 15 发匕首” -> `channel + schedule_tick + delivery.hitCount`

### 6.2 装备被动样例

- `triggerType` + `triggerTime` -> `mechanicsConfig.triggers[].event`
- `param.计数器` -> `mechanicsConfig.stacks`
- `effective.condition` -> `TriggerRule.conditions` 或 `if.cond`
- `object=self.xxx.cd` -> 独立的 cd / runtime 引用，不建议继续走字符串 object
- `攻击特效do 2次` -> 先放 `mvpExtensions.attackInteraction`

## 7. 推荐示例

### 7.1 卡特 E：瞬步
下面这个例子重点展示“伤害 + 触发攻击特效 + 重置普攻计时器”应该怎么拆：

```json

  "ownerType": "hero",
  "ownerId": "Katarina",
  "skillKey": "E",
  "name": "瞬步",

    "vars": {
      "base_damage": {
        "label": "基础伤害",
        "kind": "table",
        "by": "skillLevel",
        "values": [20, 30, 40, 50, 60]
      },
      "ad_ratio": {
        "label": "当前攻击力系数",
        "kind": "scaled_attr",
        "attr": "self.attack_damage_current",
        "coefficient": 0.4
      },
      "ap_ratio": {
        "label": "法强系数",
        "kind": "scaled_attr",
        "attr": "self.ability_power",
        "coefficient": 0.25
      }
    }
  },
  "cooldowns": [
    {
      "kind": "table",
      "by": "skillLevel",
      "values": [12, 11, 10, 9, 8]
    }
  ],
  "timingProfile": {
    "phases": [
      {
        "phaseKey": "recovery",
        "kind": "recovery",
        "durationMs": 100
      }
    ]
  },

    "version": 1,
    "triggers": [
      {
        "id": "cast_damage",

            "type": "deal_damage",
```

## 8. 最后给前端页面的分区建议
如果页面雏形直接从这份文档出，建议至少分成下面 5 个编辑区：

1. `基础信息`
2. `资源与冷却`
3. `参数与等级表`
4. `时序与阶段`
5. `触发规则与效果`

额外再留一个：

6. `MVP 扩展效果`

这样页面不会一上来就把“数值定义、施法时序、运行时动作”混在一张表里，后面无论是继续往 wasm 规则收敛，还是拆更细的编辑器，成本都会低很多。

## 9. 固定选项速查
固定 code、输入方式和“该手填还是该选择”的分类，统一见 `技能配置固定选项.md`。  
做前端配置页时，优先把固定 code 做成下拉或多选，把本地引用字段做成引用选择器，尽量不要再让用户手敲这些字段。
