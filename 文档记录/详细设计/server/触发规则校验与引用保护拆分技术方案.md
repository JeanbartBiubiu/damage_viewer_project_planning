# 触发规则校验与引用保护拆分技术方案

本方案供独立后端开发会话实施，范围是触发规则服务中的结构校验、目录与引用检查及调用接线。目标是让保存入口负责事务和顺序，让规则结构变化与其他对象的变更保护各有明确所有者。

本轮后端实现及本地验收已完成，实现与持续验证入口见[后端说明](../../../server/data_manage/README.md)，历史独立复核与数据库回读从Git追溯。任务状态以[任务规则](../../../db/task_doc_governance/task_rules.json)为准。前端并行工作见[模拟来源与通用编译拆分方案](../web/模拟来源与通用编译拆分技术方案.md)，两端不改变接口契约，没有先后实施依赖。

## 2. 范围与保持项

本轮分离规则结构校验和目录、引用保护，调整真实调用方；不扩展触发能力，不改变请求、响应、数据库或循环规则。

必须保持：

- 单独规则读写和技能统一保存的请求、响应、状态码、业务错误码、字段路径及问题排列顺序。
- 游戏写锁、父技能和规则行锁、已有引用与新增引用的启停判定差异，以及原锁定和检查顺序。
- 整技能摘要 `baseDigest` 的冲突保护，统一保存的“先准备、再写入、最后检查最终组合”阶段。
- 引用保护、动态输入依赖、运行输入绑定、循环检查、结果时机及额度限制的现行规则。
- 保存失败回滚、删除图片关系与编辑留痕的原位置、失败行为及响应。

`support/authoring/` 整理、效果服务内部拆分、模型分包、SQL 映射和数据库迁移均为后续候选，不纳入本轮。允许修改效果等服务的构造注入和保护调用，不重写这些模块的业务流程。

## 3. 目标责任与依赖

以下布局表达责任，内部辅助文件和类型名称由实施者按实际调用决定。

```text
service/skilltrigger/
  SkillTriggerRuleService.java       规则读写与统一保存阶段的协调
  SkillTriggerRuleAssembler.java     现有读取装配
  SkillTriggerRuntimeInputAnalyzer.java
  SkillTriggerCycleValidator.java    复用现有循环算法
  validation/
    SkillTriggerPayloadValidator.java
    ValidatedRule.java               内部校验结果
  reference/
    SkillTriggerCatalogValidator.java
    SkillTriggerReferenceGuard.java
```

| 所有者 | 责任与边界 |
| --- | --- |
| 规则服务 | 公共读写、准备结果、事务入口、加锁和保存的固定顺序、调用校验及检查、统一配置阶段接线 |
| 结构校验 | 标识、名称、排序、事件、条件组、动作、输入绑定与限制的形状校验；形成原规范化结果及引用需求，不持有数据库访问对象 |
| 目录校验 | 在调用者当前事务中按原顺序锁定并检查目录；验证身份、类型、启停状态、效果与过程形状及运行输入依赖；返回本次调用需要的目录结果 |
| 引用保护 | 技能、效果、过程、步骤、状态、选项、公式、参数与状态定义的变更保护；提供原错误和问题列表，不负责保存业务对象 |
| 已有分析器和循环检查器 | 保留实际分析算法；引用保护或协调层在原位置调用，不复制遍历或新建第二套规则图 |

依赖方向为“规则服务 → 结构校验、目录校验、引用保护及已有分析器”，以及“其他业务服务 → 引用保护或现有循环检查器”。校验和保护组件不反向调用规则增删改服务；它们不依赖效果、过程等业务服务，只使用现有 mapper、请求模型和只读辅助能力。

效果和过程目前通过 `assertCurrentSkillCycle` 间接使用循环检查。改为在原调用时点直接调用现有检查器，或由引用保护提供有限组合；不能为移除服务依赖而提前检查，也不能只迁移删除保护后仍把全部业务服务接回规则服务。

不要求为每类事件、条件或动作建立接口。纯规则优先使用具体类和明确辅助函数；新增子包必须承接实际算法和状态，不能只有委托方法。

## 4. 数据与关键顺序

### 4.1 校验结果和可见性

现有私有 `ValidatedRule` 及引用需求集合随结构校验一起调整。跨子包使用的内部类型只公开所需读取能力，不进入 `model/skilltrigger/`，不作为接口响应，也不暴露可写全局集合。

结构校验在一次调用内拥有问题列表、重复检测集合和引用需求。目录检查接收该结果，在一次调用内拥有锁定目录和依赖分析结果；任何有状态结果不保存在单例组件字段。

引用需求中的 `referenceIssues` 继续随准备结果携带，并在原目录检查结束的位置报告；不能因为引用收集迁入结构校验，就提前抛出这些问题。

`Prepared` 继续表达统一保存的一次准备结果。可以调整内部组成及消费者编译接线，但不能通过再次读取旧数据库对象重建准备结果，或把尚未提交的对象过滤掉。保留原规范化、复制和稳定排序边界，不能顺便改变请求集合的原地修改行为。

### 4.2 单独保存与最终组合

单独创建、更新继续沿当前源码的顺序执行校验、游戏写锁、父对象与规则加锁、目录检查、写入及后续循环检查。各入口原有顺序可能不同，不为统一结构而重排。

统一保存先执行 `prepareConfigurationCreate`、`prepareConfigurationUpdate` 的形状检查；引用和目录检查仍等待全部根对象落地后执行。`writePreparedWithinConfiguration`、`validatePreparedAgainstFinalDatabase`、`validateAffectedConfigurationFinal` 等阶段继续使用外层同一事务。中间态缺少引用目标不能提前变成最终错误。

新组件沿用调用者事务，不启动新的独立事务，不在内部提前提交、吞掉异常或自动重试。原公开入口的事务注解和代理边界保持，不能因方法迁移改变事务是否真正生效。

### 4.3 反向引用保护

把现有 `assertSourceSkillNotReferenced`、效果变更与删除检查、过程与步骤检查、内部状态与选项检查、公式、参数和状态定义检查迁入引用保护。问题列表返回和直接抛错两种入口分别保留，不能统一为一个布尔值。

`SkillService` 调用的 `SkillTriggerRuleService.deleteAllForSkill` 仍归规则服务，因为它是实际写入；不能把写操作塞入引用保护。效果、过程需要的循环检查继续复用现有检查器。

原有新增引用、保留引用、停用对象、删除中的对象及最终组合判定分别保持；字段错误和引用错误不可因为抽离而合并为新的通用错误。

## 5. 允许修改范围

- 主体：`server/data_manage/src/main/java/xyz/game/datamanage/service/skilltrigger/**`。
- 接线：`service/skillconfiguration/`、`skilleffect/`、`skillprocess/`、`skillinternalstate/`、`skillformula/`、`skillparameter/`、`skill/`、`status/` 中实际注入或调用上述能力的文件；仅做必要接线。
- 测试：后端 `src/test/java/` 中相关规则、引用保护、事务与统一配置测试；按新所有者迁移私有规则测试，组合测试保留生产入口。
- 说明：本方案及必要的 `server/data_manage/README.md` 入口说明。

前端、Wasm、数据库脚本、SQL 映射、模型包、认证配置与 `support/authoring/` 实现均只读。`src/main/resources/simulation-verification/**` 由前端并行任务维护，后端会话不刷新正式证明。

若构造注入变化影响启动装配测试，修正相关测试配置；不能为让旧测试构造器通过新增兼容构造器、可空依赖或绕过校验的分支。

## 6. 实施顺序

1. 核对保护方法的全部定义与引用，记录各入口的事务、锁和最终校验时点；运行相关现有测试建立基线。
2. 先迁移 `validatePayload` 及事件、条件、动作、绑定和限制的结构规则，连同校验结果和引用需求一起迁移；保留问题收集及规范化顺序。
3. 抽离目录加锁和目录合法性检查，复用现有运行输入分析器；规则服务按原时点接收结果并写入。
4. 抽离反向引用保护，逐个调整真实调用方；循环检查接回现有检查器，规则删除等写操作仍由规则服务承担。
5. 清理旧私有实现和无生产调用的转发，核对统一保存及回滚边界，完成独立复核、全量后端验证，报告实际结果与限制。

结构移动与任何发现的业务修复分开。若需要改变 SQL、循环算法、公开错误或统一保存阶段，先在对应开发会话重新界定范围。

完成要求：结构校验无数据库依赖；目录与引用检查归明确组件；其他业务服务不再为了保护检查依赖规则增删改入口；单独保存和统一保存的错误、顺序、锁与回滚保持；最终服务及独立回读有证据。原始日志、响应与测试输出放忽略目录，实际检查结果与限制在任务交付中报告，细则见[开发与独立评审流程](../../项目说明/开发与独立评审流程说明.md)。

## 8. 独立开发与交接

两个开发会话从包含本方案的最新 `master` 分别建立短期分支。并行开发使用不同临时工作树，不在同一个检出中交替切分支；本后端会话只写第 5 节范围。

实现阶段不同时修改共享任务规则。各自收尾合入主干时串行更新自己的任务条目，重读最新内容并保护另一任务的状态；合入后清理本任务临时工作树。推送按会话中的实际授权处理。

遇到基线失败无法归因、需要改变引用或循环语义、必须扩大数据或源码写入范围时，保留证据并回到对应开发会话收敛；无关脏改按根规则保护。最终交接列出职责归属、调用方变化、独立复核、实际测试和 HTTP 回读结果及未完成项，不以本方案代替验收。
