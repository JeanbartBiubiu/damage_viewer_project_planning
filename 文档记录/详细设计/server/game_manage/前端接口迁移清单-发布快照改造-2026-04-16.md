# 前端接口迁移清单：发布快照改造（2026-04-16）

本文档给前端迁移使用，说明本轮后端发布链路改造后的破坏性变更、替代接口与迁移步骤。

## 1. 本轮变更结论

后端已从“按 `versionId` 发布 / 读取 bundle”的模型，切换为“按 `versionCode` 发布当前编辑工作区 / 读取已发布快照”的模型。

前端需要同步接受以下事实：

1. 不再使用 `versionId` 作为 bundle 拉取标识。
2. 不再依赖 `dataHash` 作为版本一致性字段。
3. 不再对 bundle 请求使用 `If-None-Match` / `ETag`。
4. 轮询当前版本时，只看 `versionCode` 是否变化。
5. 读取 bundle 时，使用 `versionCode` 命中发布快照。

---

## 2. 需要替换的接口

### 2.1 Public：当前版本轮询

#### 旧接口
`GET /api/games/{gameId}/versions/current`

#### 旧返回关键字段
```json
{
  "gameId": "lol",
  "versionId": 123,
  "versionCode": "14.1",
  "dataHash": "sha256...",
  "updatedAt": "2026-02-08T12:00:00Z"
}
```

#### 新返回关键字段
```json
{
  "gameId": "lol",
  "versionCode": "14.1",
  "releaseDate": "2026-02-08",
  "publishedAt": "2026-02-08T12:00:00Z",
  "updatedAt": "2026-02-08T12:00:00Z"
}
```

#### 前端迁移动作
- 删除对 `versionId` 的读取。
- 删除对 `dataHash` 的读取。
- 轮询结果改为只比较 `versionCode`。
- 如页面需要展示发布时间，可直接使用 `publishedAt`。
- 如页面需要展示版本发布日期，可使用 `releaseDate`。

---

### 2.2 Public：bundle 拉取

#### 旧接口
`GET /api/games/{gameId}/versions/{versionId}/bundle`

#### 新接口
`GET /api/games/{gameId}/versions/{versionCode}/bundle`

#### 旧请求习惯
- 可能附带请求头：`If-None-Match`
- 可能依赖响应头：`ETag`

#### 新请求习惯
- 不再传 `If-None-Match`
- 不再依赖 `ETag`
- 直接按 `versionCode` 请求完整已发布快照

#### 前端迁移动作
- 所有 bundle URL 参数从 `versionId` 改为 `versionCode`。
- 删除 bundle 请求上的 `If-None-Match`。
- 删除对响应头 `ETag` 的读取逻辑。
- 删除基于 `dataHash` 的 bundle 一致性判断。

#### 新语义
- 仅返回已发布快照。
- 如果请求的 `versionCode` 在后端快照中不存在，返回 `404`。
- 后端不会在读取时临时从编辑工作区拼装 bundle。

---

### 2.3 Admin：发布接口

#### 已废弃接口 1
`POST /api/admin/games/{gameId}/versions`

#### 已废弃接口 2
`POST /api/admin/games/{gameId}/versions/{versionId}:publish`

#### 新接口
`POST /api/admin/games/{gameId}/versions:publish`

#### 新请求体
```json
{
  "versionCode": "14.1",
  "releaseDate": "2026-02-08"
}
```

#### 新响应体
```json
{
  "gameId": "lol",
  "versionCode": "14.1",
  "releaseDate": "2026-02-08",
  "publishedAt": "2026-02-08T12:00:00Z",
  "updatedAt": "2026-02-08T12:00:00Z"
}
```

#### 前端迁移动作
- 删除“先创建版本，再发布”的两段式调用。
- 发布时只提交 `versionCode`，`releaseDate` 可选。
- 删除发布成功后对 `versionId` / `dataHash` 的依赖。
- 发布成功后，如需刷新线上数据，重新请求 `current`，再按返回的 `versionCode` 获取 bundle。

## 3. Bundle 数据结构变更

### 3.1 `meta` 字段变化

#### 旧结构
```json
{
  "meta": {
    "gameId": "lol",
    "versionId": 123,
    "versionCode": "14.1",
    "dataHash": "sha256...",
    "generatedAt": "2026-02-08T12:00:00Z"
  }
}
```

#### 新结构
```json
{
  "meta": {
    "gameId": "lol",
    "versionCode": "14.1",
    "releaseDate": "2026-02-08",
    "publishedAt": "2026-02-08T12:00:00Z",
    "generatedAt": "2026-02-08T12:00:00Z"
  }
}
```

#### 前端迁移动作
- 删除 `meta.versionId`
- 删除 `meta.dataHash`
- 新增可选读取：`meta.releaseDate`
- 新增可选读取：`meta.publishedAt`
- 保留读取：`meta.gameId`、`meta.versionCode`、`meta.generatedAt`

## 4. 推荐前端调用流程

### 4.1 Public 读链路

1. 调用 `GET /api/games/{gameId}/versions/current`
2. 取返回中的 `versionCode`
3. 调用 `GET /api/games/{gameId}/versions/{versionCode}/bundle`
4. 把 bundle 按前端既有方式写入本地缓存 / IndexDB

### 4.2 轮询判断建议

旧逻辑：
- 比较 `versionId`
- 或比较 `dataHash`

新逻辑：
- 只比较 `versionCode`

即：
- 若 `current.versionCode` 未变化，则不重新拉取 bundle
- 若 `current.versionCode` 变化，则重新拉取对应 `versionCode` 的 bundle

## 6. 兼容性说明

本次变更是破坏性变更，后端不再兼容以下旧契约：

- `POST /api/admin/games/{gameId}/versions`
- `POST /api/admin/games/{gameId}/versions/{versionId}:publish`
- `GET /api/games/{gameId}/versions/{versionId}/bundle`
- Public 响应中的 `versionId`
- Public 响应中的 `dataHash`
- bundle 的 `If-None-Match` / `ETag` 协议依赖

因此前端切换时，不能只改类型定义，必须同步改 URL、状态管理和缓存 key。

## 7. 建议联调用例

### 用例 1：正常轮询
1. 请求 `current`
2. 读取 `versionCode`
3. 请求对应 bundle
4. 校验 `bundle.meta.versionCode === current.versionCode`

### 用例 2：版本未变化
1. 连续两次请求 `current`
2. 若 `versionCode` 未变化，则前端不重复拉 bundle

### 用例 3：版本已切换
1. 发布新版本后请求 `current`
2. 发现 `versionCode` 从 `14.1` 变为 `14.2`
3. 请求 `/versions/14.2/bundle`
4. 校验返回成功，且 `meta.versionCode = 14.2`

### 用例 4：历史版本无快照
1. 请求一个不存在的 `versionCode`
2. 预期收到 `404`
3. 前端按“无可用快照”处理，不回退到编辑态数据
