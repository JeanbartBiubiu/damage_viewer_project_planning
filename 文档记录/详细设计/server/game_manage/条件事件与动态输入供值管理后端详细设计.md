## 4. 数据库总原则

1. 所有表以 `game_id + skill_key + rule_key` 为聚合前缀；子项继续增加自己的稳定标识。
2. 聚合内部外键使用 `ON DELETE CASCADE`；指向技能、过程、效果、结果、生命周期、状态、属性、公式、参数和内部状态的业务引用使用 `RESTRICT`。
3. 跨技能只允许事件筛选的 `source_skill_key`，外键为 `(game_id, source_skill_key) -> skills(game_id, skill_key)`。
4. 同技能引用使用完整复合外键，不允许只按名称、单列键或约定字符串关联。
5. 类型明细采用基表加专属明细表；不在一个宽表保存大量互斥空列，不使用 JSONB 或数组。
6. 需要跨多表才能判断“恰好一种明细”和“至少一个子项”的形状，使用可延迟到事务结束的约束触发器；Service 仍必须在写库前返回业务 400。
7. 所有反向引用建立以被引用复合键开头的索引，保证删除保护和全技能循环检查不依赖全表扫描。

## 5. 规则与事件表

### 5.1 `skill_trigger_rules`

| 列 | 约束 |
| --- | --- |
| `game_id/skill_key/rule_key` | 三列主键；前两列引用技能。 |
| `name/description/sort_order` | 共享契约基本字段。 |
| `event_type` | 第 5.1 节固定 17 种之一。 |
| `created_at/updated_at` | 与现有管理聚合一致。 |

规则本表直接拥有事件种类。没有专属明细的普通攻击、伤害、控制和击杀事件只需本表一行；其余事件必须恰好拥有对应明细一行。

### 5.2 八张事件明细表

| 表 | 对应事件与主要列 |
| --- | --- |
| `skill_trigger_rule_process_events` | `PROCESS_MOMENT`、`PROCESS_CANCEL_REQUESTED`；`process_key/moment_type/step_key`。取消事件的时点字段必须为空。 |
| `skill_trigger_rule_skill_events` | `SKILL_USED`、`SKILL_HIT`；可空 `source_skill_key`、可空 `use_kind`。仅技能使用事件允许且必须提供 `use_kind`。 |
| `skill_trigger_rule_result_events` | `RESULT_AVAILABLE`；`effect_key/result_key`。 |
| `skill_trigger_rule_lifecycle_events` | `LIFECYCLE_MOMENT`；`effect_key/lifecycle_moment`。 |
| `skill_trigger_rule_status_events` | `STATUS_CHANGED`；`subject/status_key/change_kind`。 |
| `skill_trigger_rule_health_threshold_events` | `HEALTH_THRESHOLD_CROSSED`；`subject/attribute_key/threshold_formula_key/direction`。 |
| `skill_trigger_rule_internal_state_events` | `INTERNAL_STATE_CHANGED`；`state_key/change_kind`。 |
| `skill_trigger_rule_subject_events` | `ENTITY_DIED`、`ENTITY_UNTARGETABLE`；`subject`。 |

每张表的主键和外键都是 `game_id/skill_key/rule_key`。结果事件使用到 `skill_effect_results` 的完整复合外键；生命周期事件同时引用效果和一对一生命周期；过程时点使用过程与步骤完整复合外键；阈值事件的公式引用同技能公式。

### 5.3 事件形状约束

延迟触发器在事务结束前检查：

1. 有明细事件恰好存在对应表一行，其他七张事件明细不存在。
2. 无明细事件在八张表都没有行。
3. 过程时点与 `step_key` 组合符合阶段 7.3；`STEP_TIMEOUT` 只引用允许超时的步骤。
4. 结果事件只引用没有生命周期的效果结果；效果新增生命周期前也必须先处理入站结果事件引用。
5. 生命周期事件不允许 `PERSISTENT`，且目标效果真实拥有生命周期；`PERIODIC` 还要求周期间隔，`NATURAL_END` 还要求自然持续时间和非仅显式移除到期方式，其他三个离散时点不要求效果内存在同名结果。
6. 生命阈值属性只校验为当前游戏启用的数值属性；现有属性没有生命值分类，后端不得通过键名 `hp` 或中文名称猜测。
7. 跨技能来源技能只用于允许的两种事件。
8. 当前目标绑定、`EVENT_SOURCE` 可用性和事件值白名单逐行实现共享契约第 5.2 节；不允许 Backend 自建更宽能力表。
9. 内部状态事件按状态种类限制为 `VALUE_CHANGED/OPTION_SELECTED/FLAG_CHANGED/COOLDOWN_READY`；不保存或接受 `VALUE_REACHED`。

## 6. 条件表

### 6.1 `skill_trigger_rule_condition_groups`

主键为 `game_id/skill_key/rule_key/group_key`，保存 `name/sort_order`。规则可以没有组；存在的每组必须至少有一个条件。

### 6.2 `skill_trigger_rule_conditions`

主键在组主键后增加 `condition_key`，保存 `condition_type/sort_order`。`condition_type` 固定为四种条件之一。

### 6.3 四张条件明细表

| 表 | 主要列与引用 |
| --- | --- |
| `skill_trigger_rule_attribute_conditions` | `subject/attribute_key/attribute_value_kind/comparator/comparison_formula_key`。 |
| `skill_trigger_rule_status_conditions` | `subject/status_key/check_kind/source_effect_key/source_result_key/comparator/comparison_formula_key`。 |
| `skill_trigger_rule_internal_state_conditions` | `state_key/value_kind/option_key/expected_boolean/comparator/comparison_formula_key`。 |
| `skill_trigger_rule_event_value_conditions` | `event_value_key/comparator/comparison_formula_key`。 |

约束触发器保证每个条件恰好一张匹配明细。状态层数或剩余时间检查的来源结果使用完整复合外键，并由 Service 检查 `PERSISTENT + STATUS_OPERATION + APPLY + statusKey` 一致；内部状态明细使用复合外键保护模式选项。

## 7. 动作表

### 7.1 `skill_trigger_rule_actions`

主键为 `game_id/skill_key/rule_key/action_key`，保存 `name/action_type/sort_order/target_context`。同一规则最多一个失败动作；数据库延迟触发器和 Service 都检查它按稳定排序位于最后。

### 7.2 两张动作明细表

| 表 | 对应动作与主要列 |
| --- | --- |
| `skill_trigger_rule_effect_actions` | `EXECUTE_EFFECT`；`effect_key`。 |
| `skill_trigger_rule_process_actions` | `START_PROCESS`、`FAIL_PROCESS`；`process_key/failure_reason`。启动时失败原因为空，失败时必填。 |

效果动作另建 `(game_id,skill_key,rule_key,action_key,effect_key)` 唯一键，供前序结果来源建立真实复合外键。约束触发器保证动作恰好一种明细。`effect_key` 和 `process_key` 使用同技能复合外键。执行效果和启动过程必须保存 `target_context`，失败过程必须为 null；事件不具备事件来源对象时由 Service 拒绝 `EVENT_SOURCE`。

## 8. 动态输入绑定表

### 8.1 `skill_trigger_rule_runtime_input_bindings`

主键为动作主键后增加 `binding_key`，保存 `parameter_key/source_type`，并以 `(game_id, skill_key, parameter_key)` 引用技能参数。一个动作内对 `parameter_key` 建唯一约束。

### 8.2 四张来源明细表

| 表 | 主要列与引用 |
| --- | --- |
| `skill_trigger_rule_internal_state_bindings` | `state_key/value_kind/option_key`。 |
| `skill_trigger_rule_combat_status_bindings` | `subject/status_key/value_kind/source_effect_key/source_result_key`。 |
| `skill_trigger_rule_event_value_bindings` | `event_value_key`。 |
| `skill_trigger_rule_prior_result_bindings` | 请求字段对应 `source_action_key/source_result_key/output_kind`；表内另存由来源动作推导的 `source_effect_key`。 |

前序结果表以 `(game_id,skill_key,rule_key,source_action_key,source_effect_key)` 复合外键引用执行效果动作的唯一键，再以 `(game_id,skill_key,source_effect_key,source_result_key)` 真外键引用效果结果。`source_effect_key` 由 Service 从来源动作填入，不进入公共请求。两条复合外键都使用 `DEFERRABLE INITIALLY DEFERRED`；PUT 仍按“先删受影响绑定和动作明细，再插入候选动作明细与绑定”写入。普通外键不能表达排序更早，Service 先校验，延迟触发器在事务结束前兜底。

### 8.3 可达参数分析

新增 `SkillTriggerRuntimeInputAnalyzer`，只做静态关系分析：

1. 执行效果动作收集目标效果结果数值规则和生命周期四类公式；生命周期操作需要数值时仍由该结果自己的数值规则覆盖，不另找明细公式。
2. 启动过程动作收集过程普通冷却、全部步骤明细、内部状态操作直接公式，以及 `RESET`、内部冷却 `START/RESET` 等操作实际读取的内部状态定义公式；过程直接效果挂接再按上一项收集。
3. 从 `skill_formula_nodes` 中收集上述公式直接引用的 `RUNTIME_INPUT` 参数；公式不能引用公式，因此不需要递归公式图。
4. 实际绑定集合必须与可达参数集合完全相等。缺失和多余项一次返回全部字段问题。
5. 整数事件值、计数、弹药、布尔 `0/1` 可供整数或小数参数；生命周期毫秒、属性值和基础结果值按小数来源处理，只能供小数参数。

分析器不执行公式，也不读取某次属性、状态或过程实例。

## 9. 修正与保护表

### 9.1 `skill_trigger_rule_result_modifiers`

主键为动作主键后增加 `result_key`，保存 `fixed_multiplier/fixed_min_value/fixed_max_value`。完整复合外键引用目标效果结果；Service 和延迟触发器检查动作是 `EXECUTE_EFFECT`、结果属于其目标效果且拥有数值规则。

### 9.2 `skill_trigger_rule_per_target_cooldowns`

与规则一对一，保存 `duration_formula_key/target_context`，公式引用同技能公式。

### 9.3 `skill_trigger_rule_process_limits`

与规则一对一，保存 `process_key/limit_formula_key`，过程和公式都引用当前技能。约束触发器和 Service 要求规则事件为 `PROCESS_MOMENT`，且事件明细 `process_key` 与本表完全相同；其他事件不得插入本表。

## 10. 索引、约束触发器和反向锁

### 10.1 必备索引

除主键和唯一约束外，至少增加：

1. 规则列表 `(game_id, skill_key, sort_order, rule_key)`。
2. 所有 `effect_key/result_key`、`process_key/step_key`、`state_key/option_key`、`status_key`、`attribute_key`、`formula_key`、`parameter_key` 和跨技能 `source_skill_key` 的反向引用索引。
3. 前序动作引用 `(game_id, skill_key, rule_key, source_action_key)`。
4. 循环检查使用的事件种类、动作目标和保护存在性索引。

### 10.2 延迟形状触发器

新增一个统一入口函数，覆盖：

1. 规则事件明细恰好形状。
2. 条件明细恰好形状。
3. 动作明细恰好形状、至少一个动作和失败动作最后。
4. 绑定来源明细恰好形状。
5. 状态来源结果、前序动作结果和修正目标的跨表一致性。
6. 条件组至少一个条件。

触发器挂在所有参与表的 INSERT、UPDATE、DELETE 上并可延迟到事务结束。迁移和 `triggers.sql` 必须保持同一受控清单，数据库契约测试逐表断言。

### 10.3 聚合锁

POST、PUT、DELETE 先锁技能；PUT、DELETE 再锁规则。循环检查额外按固定顺序锁当前技能全部规则摘要，防止两个并发更新分别通过但组合后形成无保护环。

## 11. 迁移

新增 `condition_event_dynamic_input_management_migration.sql`：

1. 先核对阶段 6、7.1、7.2、7.3 和阶段 7.4 最终表、复合键及必要唯一约束。
2. 26 张目标表全部缺失时按依赖顺序创建；全部存在且结构、约束、索引和触发器一致时幂等通过。
3. 部分存在、列或约束漂移时主动报错停止，不补建半套结构。
4. 不写业务记录，不读取旧 combat-data，不自动迁移、删除、发布或启动服务。
5. 新库真源同步写入 `schema.sql`；延迟约束入口同步写入 `triggers.sql`。

本设计阶段不执行迁移。开发获批后也必须由负责人确认准确数据库目标后单独执行。

## 12. 强类型模型

在 `model/skilltrigger` 建立：

1. 规则摘要、详情、创建和更新请求。
2. `SkillTriggerEventSource` 及固定事件明细联合类型。
3. 条件组、`SkillTriggerCondition` 及四种条件明细联合类型。
4. `SkillTriggerAction` 及执行效果、启动过程、令过程失败联合类型。
5. `SkillTriggerRuntimeInputBinding` 及四种来源联合类型。
6. 固定结果修正、每目标冷却和单次过程最大触发次数。
7. 与数据库一一对应的 Row 类型，仅供 Mapper，不暴露到 Controller。

请求反序列化采用阶段 7.2/7.3 的“种类先判别、专属明细强绑定、未知字段拒绝”方式。不能用一个带大量可空字段的请求类型接受所有形状。

## 13. Mapper 与聚合装配

1. 列表查询只读取规则本表和条件组、动作、两类保护的计数，不加载完整子项。
2. 详情按规则主键批量读取事件、条件、动作、绑定、修正和保护；不得为每个条件或动作发一次查询。
3. `SkillTriggerRuleAssembler` 按 `sortOrder/key` 组装强类型响应，并在出现数据库不可能形状时抛出明确数据完整性异常。
4. 写入顺序固定为规则 → 事件 → 条件组与条件 → 动作 → 绑定与修正 → 保护；删除使用反向顺序，最后提交前触发延迟约束。
5. 反向引用 Mapper 返回精确规则键和字段来源，供 Service 映射稳定 409，不向调用方暴露数据库约束名。

## 14. Service 校验与事务

### 14.1 统一校验顺序

1. 验证游戏、技能和规则身份。
2. 校验基本字段、稳定标识、重复项和不可修改种类。
3. 校验事件联合形状、事件引用、时点及事件能力。
4. 校验条件组和四类条件形状与引用。
5. 对动作稳定排序，校验三类动作、目标上下文和失败动作位置。
6. 拒绝事件筛选、条件和两类触发保护公式中的 `RUNTIME_INPUT` 参数；再收集每个动作可达公式和 `RUNTIME_INPUT` 参数，校验绑定完整性、来源形状和值类型。
7. 校验前序动作排序、即时结果可用性和固定结果修正。
8. 校验每目标冷却；单次过程最大触发次数只允许精确匹配同一 `PROCESS_MOMENT.processKey`。
9. 把候选规则替换进当前技能规则快照，执行无保护循环检查。
10. 一次返回全部能确定的字段问题；通过后才写库和编辑日志。

### 14.2 创建和全量更新

POST 在技能锁内检查 `ruleKey` 唯一并写完整聚合。PUT 锁定规则后：

1. 比较旧、新子项稳定标识和种类。
2. 在内存中先完成全部引用、绑定和循环校验。
3. 一般子项按“删除已移除 → 更新保留 → 插入新增”处理；执行效果动作变更 `effectKey` 时服从第 8.2 节，先删除受影响前序绑定和旧动作明细，再插入候选动作明细与绑定，不原地 UPDATE 被复合唯一键引用的行。
4. 事务结束前强制延迟约束立即检查，再写一条规则级管理编辑日志。
5. 任一失败回滚全部变化，返回旧聚合仍可完整查询。

### 14.3 循环检查实现

新增 `SkillTriggerCycleValidator`：

1. 加载当前技能所有规则，并用候选聚合替换本次创建或更新对象。
2. 图节点固定为 `ruleKey`。逐个动作按共享契约第 10.3 节封闭生产表展开可能事件，再与当前技能每条规则的精确事件筛选匹配；不得在实现中增加“可能接入”的自由判断。
3. 过程直接效果挂接在 `START_PROCESS` 动作内递归按执行效果展开；生命周期操作只按操作种类展开目标效果 `FULL_STACKS/EARLY_REMOVE`，不把目标效果误当成被重新执行。
4. 伤害因没有生命属性分类而忽略属性键，但只匹配相同 subject 的 `DOWNWARD` 生命阈值；直接治疗同理只匹配 `UPWARD`；属性变化还必须匹配相同 `attributeKey` 并按 `INCREASE/DECREASE/SET` 限制方向。普通护盾、资源和冷却结果不产生生命阈值边。其余精确键和宽事件按共享匹配表处理。
5. 边标签保存 `sourceRuleKey/actionKey/producedEvent/targetRuleKey`。每目标冷却或合法过程次数保护属于目标规则，删除所有进入受保护规则的边。
6. 对剩余图按 `ruleKey/actionKey/eventType` 稳定顺序执行深度优先或强连通分量检查；自环或多节点环均拒绝，并返回一条稳定循环路径。
7. 效果、结果、生命周期、过程、步骤或内部状态形状更新也用候选对象重新计算当前技能规则图；如果新增无保护环，在原聚合事务中返回同一 `400.TRIGGER_RULE_CYCLE_UNGUARDED`，不改成 409，也不留下失效规则。

### 14.4 删除和反向保护

1. 删除规则只清理自身聚合和日志引用。
2. 删除或修改效果、结果、生命周期、过程、步骤、内部状态、模式选项、公式、参数、状态或技能前，查询规则反向引用并映射共享契约错误。
3. 修改效果、过程或生命周期虽然不删除稳定标识，但如果使已有事件、绑定、修正或循环图失效，也必须在原聚合事务内拒绝。
4. 效果同时受过程挂接或触发规则引用时优先 `409.SKILL_EFFECT_IN_USE`；只有不存在这两类引用、仅受阶段 7.4 生命周期操作引用时才使用 `409.SKILL_EFFECT_LIFECYCLE_IN_USE`。删除结果用字段 `results` 和拒绝值 `resultKey`，移除生命周期用字段 `lifecycle`。
5. 删除技能自身时先删除自身规则；其他技能 `sourceSkillKey` 仍阻止删除。

## 15. Controller 与错误映射

1. 新增 `SkillTriggerRuleAdminController`，只提供共享契约五个路径。
2. Controller 只负责路径解码、Admin Token、请求绑定和 HTTP 状态；业务形状与引用由 Service 负责。
3. Jackson 绑定失败统一映射 `400.INVALID_BODY`；Service 字段问题保留完整下标路径。
4. 数据库约束异常只作为并发兜底，并重新查询业务引用后映射稳定 409；无法识别时记录日志并返回既有内部错误，不泄露 SQL。

## 18. 后端停止条件

出现以下任一情况停止编码并回到共享契约：

1. 阶段 7.4 最终表、模型、时点或删除语义与设计基线不一致。
2. 无法用明确表和复合外键表达事件、条件、动作、绑定或前序结果，必须使用 JSONB、数组或通用多态键。
3. 需要修改阶段 7.2 结果目标、阶段 7.3 过程时点或阶段 7.4 生命周期公共契约。
4. 可达参数集合只能通过执行公式或保存运行值才能确定。
5. 循环检查不能在单技能聚合和明确关系内完成，必须引入战斗运行时、全游戏自由事件图或 Wasm。
6. 实现需要增加阶段 7.6 丰富结果、暴击、吸血、法术护盾、结算或实际伤害字段。
7. 目标数据库存在不明漂移，无法由显式预检和受控破坏式迁移处理。
