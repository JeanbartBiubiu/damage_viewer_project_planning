# 技能参数与公式管理后端详细设计

方案版本：`skill-parameter-formula-management-v4-frozen`

方案状态：已按冻结版本完成数据库、接口和事务实现，并于 2026-08-27 通过真实 PostgreSQL 与服务重启回读验收。

本文实施[技能参数与公式管理共享契约](../../项目/技能参数与公式管理详细设计.md)。公共字段、HTTP 路径、错误含义、属性取值方式、等级调整规则和跨端验收只以共享契约为准，本文只负责数据库、后端事务和后端验证。

## 1. 后端职责

1. 用独立表保存技能参数、技能公式和公式节点。
2. 用复合外键保证公式不能跨游戏或跨技能引用。
3. 将前端嵌套表达式转换成关系行，查询时稳定还原为同一棵表达式。
4. 校验四种参数取值方式、完整等级 Map、表达式结构、引用存在性和属性状态。
5. 保存属性的施法者/目标范围和基础值、加成值、最终值、当前值、已损失值或比例选择。
6. 在技能最大等级或游戏等级范围变化时事务性调整已有等级参数。
7. 为技能参数和技能公式提供完整增删改查与编辑日志。
8. 不建立游戏级计算变量表，不保存计算时传入参数的实际值，不执行公式，不调用 Wasm。

## 3. 数据库设计

### 3.1 `public.skill_parameters`

```sql
CREATE TABLE public.skill_parameters (
    game_id varchar(64) NOT NULL,
    skill_key varchar(64) NOT NULL,
    parameter_key varchar(64) NOT NULL,
    name varchar(100) NOT NULL,
    value_type varchar(16) NOT NULL,
    value_mode varchar(24) NOT NULL,
    fixed_value numeric,
    level_values jsonb,
    description varchar(2000),
    sort_order integer NOT NULL DEFAULT 0,
    created_at timestamptz NOT NULL DEFAULT now(),
    updated_at timestamptz NOT NULL DEFAULT now(),
    CONSTRAINT pk_skill_parameters
        PRIMARY KEY (game_id, skill_key, parameter_key),
    CONSTRAINT fk_skill_parameters_skill
        FOREIGN KEY (game_id, skill_key)
        REFERENCES public.skills (game_id, skill_key),
    CONSTRAINT ck_skill_parameters_key
        CHECK (parameter_key ~ '^[a-z][a-z0-9_]{0,63}$'),
    CONSTRAINT ck_skill_parameters_name
        CHECK (btrim(name) <> ''),
    CONSTRAINT ck_skill_parameters_value_type
        CHECK (value_type IN ('DECIMAL', 'INTEGER')),
    CONSTRAINT ck_skill_parameters_value_mode
        CHECK (value_mode IN (
            'FIXED', 'SKILL_LEVEL', 'CHARACTER_LEVEL', 'RUNTIME_INPUT'
        )),
    CONSTRAINT ck_skill_parameters_value_shape
        CHECK (
            (value_mode = 'FIXED'
                AND fixed_value IS NOT NULL
                AND level_values IS NULL)
            OR
            (value_mode IN ('SKILL_LEVEL', 'CHARACTER_LEVEL')
                AND fixed_value IS NULL
                AND level_values IS NOT NULL
                AND jsonb_typeof(level_values) = 'object')
            OR
            (value_mode = 'RUNTIME_INPUT'
                AND fixed_value IS NULL
                AND level_values IS NULL)
        ),
    CONSTRAINT ck_skill_parameters_sort_order
        CHECK (sort_order >= 0)
);

CREATE INDEX ix_skill_parameters_list
    ON public.skill_parameters
    (game_id, skill_key, sort_order, name, parameter_key);

CREATE INDEX ix_skill_parameters_character_level
    ON public.skill_parameters
    (game_id, skill_key, parameter_key)
    WHERE value_mode = 'CHARACTER_LEVEL';
```

数据库只检查固定值、等级 Map 和计算时传入参数的互斥形状；Map 是否完整、键范围、整数要求和数值格式由服务层严格校验。

`fk_skill_parameters_skill` 不设置级联删除。删除技能时服务必须先删公式和参数，避免参数引用保护被绕过。

### 3.2 `public.skill_formulas`

```sql
CREATE TABLE public.skill_formulas (

    sort_order integer NOT NULL DEFAULT 0,
    created_at timestamptz NOT NULL DEFAULT now(),
    updated_at timestamptz NOT NULL DEFAULT now(),
    CONSTRAINT pk_skill_formulas
        PRIMARY KEY (game_id, skill_key, formula_key),
    CONSTRAINT fk_skill_formulas_skill
        FOREIGN KEY (game_id, skill_key)
        REFERENCES public.skills (game_id, skill_key),
    CONSTRAINT ck_skill_formulas_key
        CHECK (formula_key ~ '^[a-z][a-z0-9_]{0,63}$'),
    CONSTRAINT ck_skill_formulas_name
        CHECK (btrim(name) <> ''),
    CONSTRAINT ck_skill_formulas_sort_order

CREATE INDEX ix_skill_formulas_list
    ON public.skill_formulas
    (game_id, skill_key, sort_order, name, formula_key);
```

公式表只保存资料；表达式拆到公式节点表。

### 3.3 `public.skill_formula_nodes`

```sql
CREATE TABLE public.skill_formula_nodes (
    game_id varchar(64) NOT NULL,
    skill_key varchar(64) NOT NULL,
    formula_key varchar(64) NOT NULL,
    node_id uuid NOT NULL,
    parent_node_id uuid,
    child_order smallint NOT NULL,
    node_type varchar(16) NOT NULL,
    operation varchar(16),
    parameter_key varchar(64),
    attribute_owner varchar(16),
    attribute_key varchar(64),
    attribute_value_kind varchar(24),
    CONSTRAINT pk_skill_formula_nodes
        PRIMARY KEY (game_id, skill_key, formula_key, node_id),
    CONSTRAINT fk_skill_formula_nodes_formula
        FOREIGN KEY (game_id, skill_key, formula_key)
        REFERENCES public.skill_formulas (game_id, skill_key, formula_key)
        ON DELETE CASCADE,
    CONSTRAINT fk_skill_formula_nodes_parent
        FOREIGN KEY (game_id, skill_key, formula_key, parent_node_id)
        REFERENCES public.skill_formula_nodes
            (game_id, skill_key, formula_key, node_id)
        ON DELETE CASCADE
        DEFERRABLE INITIALLY DEFERRED,
    CONSTRAINT fk_skill_formula_nodes_parameter
        FOREIGN KEY (game_id, skill_key, parameter_key)
        REFERENCES public.skill_parameters
            (game_id, skill_key, parameter_key),
    CONSTRAINT fk_skill_formula_nodes_attribute
        FOREIGN KEY (game_id, attribute_key)
        REFERENCES public.attributes (game_id, attribute_key),
    CONSTRAINT uq_skill_formula_nodes_child
        UNIQUE (game_id, skill_key, formula_key, parent_node_id, child_order),
    CONSTRAINT ck_skill_formula_nodes_child_order
        CHECK (
            (parent_node_id IS NULL AND child_order = 0)
            OR
            (parent_node_id IS NOT NULL AND child_order IN (0, 1))
        ),
    CONSTRAINT ck_skill_formula_nodes_payload
        CHECK (
            (node_type = 'OPERATION'
                AND operation IS NOT NULL
                AND operation IN (
                    'ADD', 'SUBTRACT', 'MULTIPLY', 'DIVIDE', 'MIN', 'MAX'
                )
                AND parameter_key IS NULL
                AND attribute_owner IS NULL
                AND attribute_key IS NULL
                AND attribute_value_kind IS NULL)
            OR
            (node_type = 'PARAMETER'
                AND operation IS NULL
                AND parameter_key IS NOT NULL
                AND attribute_owner IS NULL
                AND attribute_key IS NULL
                AND attribute_value_kind IS NULL)
            OR
            (node_type = 'ATTRIBUTE'
                AND operation IS NULL
                AND parameter_key IS NULL
                AND attribute_owner IS NOT NULL
                AND attribute_owner IN ('SOURCE', 'TARGET')
                AND attribute_key IS NOT NULL
                AND attribute_value_kind IS NOT NULL
                AND attribute_value_kind IN (
                    'BASE', 'BONUS', 'TOTAL', 'CURRENT', 'MISSING',
                    'CURRENT_RATIO', 'MISSING_RATIO'
                ))
        )
);

CREATE UNIQUE INDEX uq_skill_formula_nodes_root
    ON public.skill_formula_nodes (game_id, skill_key, formula_key)
    WHERE parent_node_id IS NULL;

CREATE INDEX ix_skill_formula_nodes_parameter_ref
    ON public.skill_formula_nodes (game_id, skill_key, parameter_key)
    WHERE parameter_key IS NOT NULL;

CREATE INDEX ix_skill_formula_nodes_attribute_ref
    ON public.skill_formula_nodes (game_id, attribute_key)
    WHERE attribute_key IS NOT NULL;
```

后端为每个节点生成 UUID；`node_id` 和 `parent_node_id` 都是数据库内部结构，不进入 HTTP 请求或响应。

数据库保证同公式父子关系、同技能参数引用和同游戏属性引用。数据库无法仅靠简单约束保证运算节点恰好两个子节点、引用节点没有子节点、整棵树无环；这些规则由服务层先验证，公式详情回读时再次做一致性检查。

### 3.4 不把表达式存成 JSONB 的原因

技能参数和属性都需要真实外键和删除保护。若把引用键藏在 JSONB 中，数据库无法阻止删除仍被公式使用的参数，也无法可靠查询反向引用。本阶段因此只在 HTTP 中使用嵌套结构，数据库按节点逐行保存。

## 4. 迁移策略

1. 新鲜建库由 `db/game_manage/schema.sql` 直接创建三张新表、约束和索引。
2. 已有数据库使用 `skill_parameter_formula_management_migration.sql`。
3. 迁移不读取、不复制、不删除 `provider_formulas` 或任何旧战斗数据。
4. 迁移不创建 `calculation_variables`，不预置参数和公式，也不对现有技能补空记录。
5. 第一次运行创建缺失对象；重复运行只核对已经存在的对象。
6. 如果同名表已存在但列、约束或主键不符合本方案，迁移必须在写入前中止并输出不一致对象，不能静默补列后继续。
7. 迁移文件通过 SQL 契约测试后，开发验收阶段必须在真实 PostgreSQL 执行；不能只凭 `schema.sql` 或测试断言数据库已经更新。

仓库采用 MVP 破坏式更新，不为旧结构提供兼容视图、触发器、双写或回填脚本。

## 5. 后端包与模型

### 5.1 技能参数

`skillparameter` 包包含：

1. `SkillParameterAdminController`
2. `SkillParameterService`
3. `SkillParameterLevelService`：集中负责完整 Map 校验和等级范围重排
4. `SkillParameterMapper` 及 XML
5. 持久化模型、创建/更新请求和响应模型

HTTP 模型中的 `levelValues` 使用 `Map<String, BigDecimal>`。持久化层沿用项目当前 JSONB 写法，将 Map 序列化为 JSON 字符串交给 Mapper，不新增全局 MyBatis 类型处理器。

`RUNTIME_INPUT` 使用同一参数模型，固定值和等级 Map 均为空，不另建运行时参数表。

### 5.2 技能公式

`skillformula` 包包含：

1. `SkillFormulaAdminController`
2. `SkillFormulaService`
3. `SkillFormulaMapper` 及 XML
4. 公式摘要、公式详情、创建/更新请求
5. 运算节点、参数节点和属性节点的请求/响应模型

表达式模型使用明确的可辨别节点类型，不用 `Map<String, Object>` 接收任意 JSON。反序列化失败走现有 `400.INVALID_BODY`；结构合法但业务规则不满足走 `400.VALIDATION_FAILED`。

## 6. 查询与还原

### 6.1 列表

1. 技能参数列表按共享契约排序并返回完整值。
2. 公式列表只查 `skill_formulas`，不加载节点。
3. 所有列表先明确检查父游戏和技能存在，再执行列表查询，避免把不存在的父级伪装成空列表。

### 6.2 公式详情

1. 一次查询公式资料，一次查询该公式全部节点。
2. 节点查询按 `node_id` 稳定返回即可，服务按 `parent_node_id` 和 `child_order` 重建，不依赖数据库返回顺序。
3. 必须恰好有一个根节点。
4. 运算节点必须恰好有 `child_order=0` 和 `child_order=1` 两个子节点；引用节点必须没有子节点。
5. 每个节点必须且只能从根节点访问一次；发现孤儿、重复访问或环时按服务端数据损坏处理并记录日志，不返回残缺公式。
6. 响应中不返回数据库节点 UUID。

## 7. 写入事务

### 7.1 公共归一化

所有写入先完成：

1. 路径键格式和父级存在性校验。
2. 名称去除首尾空白，空字符串拒绝。
3. 可空说明将纯空白归一化为 `null`，最长 2000。
4. 排序校验为非负整数。
5. 请求体不得携带非空稳定标识覆盖路径键。

### 7.2 全局锁顺序

同一事务需要多类行锁时固定按以下顺序获取：

1. `games` 的当前游戏行。
2. `game_level_configs` 的当前游戏行；不存在时仍由游戏行串行化首次创建。
3. `skills`，按 `skill_key` 升序。
4. `skill_parameters`，按 `(skill_key, parameter_key)` 升序。
5. `skill_formulas`，按 `(skill_key, formula_key)` 升序。
6. `characters`，按 `character_key` 升序。
7. `character_attributes`，按 `character_key` 升序。

事务可以从自己实际需要的第一类锁开始，但获取较后面的锁后不得回头获取更前面的锁。参数和公式的新增、更新、删除都先锁父技能，使同一技能下的子记录写入与技能删除串行化。技能删除持有父技能锁后，按外键要求执行“公式 → 参数 → 技能”的删除顺序；由于其他同技能子记录事务无法越过父技能锁，该删除顺序不形成反向并发锁。

`SkillParameterMapper` 和 `CharacterMapper` 各自提供行锁查询，确保角色等级参数写入、角色等级属性写入和游戏等级配置更新持有同一个游戏行及等级配置行锁直到提交。

### 7.3 技能参数

创建或更新时：

1. 先在不持锁的草稿阶段完成枚举、字段形状和稳定标识格式检查。
2. 目标模式为 `CHARACTER_LEVEL` 时，先锁当前游戏行，再 `FOR UPDATE` 读取等级配置；不存在返回 `409.LEVEL_CONFIG_REQUIRED`。
3. 再锁父技能并读取 `max_level`；其他模式从这一步开始加锁。
4. 更新时再锁目标参数；创建时依靠同技能主键和父技能行锁串行化。
5. `FIXED` 校验一个配置值；等级模式校验完整 Map；`RUNTIME_INPUT` 拒绝任何固定值和等级 Map。
6. JSON 值只接受数字，不接受字符串、布尔值、数组、对象或 null。
7. `INTEGER` 使用 `BigDecimal.stripTrailingZeros().scale() <= 0` 判断，不能用 `double` 比较。
8. 创建检查同技能参数键重复；更新整块替换可变字段和值。
9. 删除先锁父技能和目标参数，再统计公式节点引用；有引用返回 `409.SKILL_PARAMETER_IN_USE`，并以外键冲突作为并发兜底。

固定值和等级值不统一限制正负，也不套用属性定义的最小值或最大值。计算时传入参数的实际值不进入本服务。

### 7.4 技能公式

创建或更新按以下顺序执行：

1. `FOR UPDATE` 锁定父技能并校验公式基本资料；创建依靠父技能锁串行化同技能公式键，更新和删除随后锁定目标公式。
2. 以前序遍历检查节点字段互斥和两个子节点；根深度为 1、子节点为父深度加 1，任意节点深度不超过 32，包含根节点的总节点数不超过 256，同时记录请求字段路径。
3. 一次收集全部参数键、属性键和 `(attributeOwner, attributeKey, attributeValueKind)`。
4. 分别批量查询同技能参数和同游戏属性，汇总全部缺失引用并返回 `400.INVALID_FORMULA_REFERENCE`。
5. 创建时所有属性必须启用。
6. 更新时先锁旧公式并读取旧属性引用集合；只对新增加的三元组要求属性启用。
7. `attributeOwner` 和 `attributeValueKind` 只按共享枚举校验。本阶段不读取或计算基础值、加成值、当前值和派生比例。
8. 为验证后的节点分配 UUID，按父子关系拍平成节点行。
9. 创建先插入公式资料，再批量插入节点。
10. 更新先删除旧节点，再更新公式资料并插入全部新节点。
11. 任一步失败时回滚，不能保留无表达式的公式或半棵树。
12. 成功后重新查询详情返回，确保数据库还原结果与提交结构一致。

删除公式先锁父技能，再锁目标公式并删除公式资料；节点由外键级联删除。

## 8. 等级联动与技能删除

### 8.1 技能最大等级

现有 `SkillService.updateSkill` 事务增加：

1. 锁定技能后比较旧 `maxLevel` 和新 `maxLevel`。
2. 若变化，按 `parameter_key` 排序锁定该技能全部 `SKILL_LEVEL` 参数。
3. 保留重叠等级、补零新增等级、删除超出等级。
4. 批量更新参数 Map 和 `updated_at`。
5. 再完成技能资料和分类关系更新。

任一参数 JSON 无法解析或更新行数异常时，技能资料与分类关系全部回滚。`RUNTIME_INPUT` 不参与重排。

### 8.2 游戏等级配置

现有游戏等级配置更新改为：

1. 先锁 `games` 当前游戏行。
2. 再锁现有 `game_level_configs` 并记录旧范围。
3. 按顺序锁当前游戏全部技能行、`CHARACTER_LEVEL` 参数、角色行和角色属性行。
4. 用同一份新旧等级区间在内存中重排全部角色属性和角色等级参数 Map。
5. 批量写回；任一异常立即回滚。
6. 最后插入或更新 `game_level_configs`。

首次创建等级配置时不应已经存在角色等级属性或 `CHARACTER_LEVEL` 参数；发现不一致数据即失败。所有创建或替换角色等级属性的现有写入路径也必须先锁游戏行和等级配置行。`RUNTIME_INPUT` 不参与重排。

### 8.3 删除技能

现有技能删除事务改为固定顺序：

1. 锁定技能。
2. 删除该技能全部公式；公式节点随公式级联删除。
3. 删除该技能全部参数。
4. 删除技能；现有分类关联按当前约束清理。

## 9. 控制器、错误与编辑日志

1. 两个控制器沿用现有 `/api/admin/games/{gameId}/skills/{skillKey}/...` 管理接口风格和响应状态。
2. 参数和公式路径必须先解析游戏、技能，再解析子键。
3. POST、PUT、DELETE 成功后写现有编辑日志，资源类型使用 `SKILL_PARAMETER`、`SKILL_FORMULA`，资源键带完整父级路径。
4. 唯一约束、引用外键和父级外键按具体约束名映射为共享契约中的稳定错误。
5. 未识别的数据库完整性错误不能一律伪装成重复键，继续作为服务端错误并保留约束名日志。
6. 公式引用错误按前序遍历字段路径排序，保证同一请求稳定返回相同问题顺序。

## 11. 后端停止条件

出现以下任一情况停止编码并回到共享方案：

1. 需要建立游戏级计算变量表或另一套动态输入目录。
2. 关系表无法在不隐藏引用的情况下表达参数和属性取值。
3. 需要引入条件、效果、公式执行或 Wasm 语义。
4. 等级调整无法与现有技能或游戏等级事务放在同一提交边界。
5. 真实数据库存在同名但用途不同的表或约束，迁移前置检查无法安全处理。
6. 必须扩大到旧公式表、旧能力接口或发布链才能通过验证。

只有自动检查、真实数据库迁移、真实接口回读和跨端验收都通过后，后端任务才能标记完成。
