## 1. 当前仓库事实

1. `db/game_manage/schema.sql` 当前包含 119 张父表定义。其中当前阶段 0～7.4 使用 44 张业务父表，图片管理使用分区父表 `images`，其余 74 张属于旧版本、旧类型、旧实体、Provider、Ability 和旧效果链路。
2. 当前阶段 0～7.4 表对待删除的 74 张表没有外键依赖；旧表可作为一个完整集合删除。
3. `db/game_manage/triggers.sql` 同时包含旧游戏分区、旧数据状态、旧效果步骤完整性逻辑和当前技能效果、过程、生命周期逻辑，不能整文件删除。
4. `db/game_manage/seeds` 当前 103 份种子脚本全部建立在旧类型、旧实体、Provider、Ability 和旧效果模型上，没有当前阶段 0～7.4 可直接保留的种子入口。
5. 后端仍有管理端和公开端旧战斗数据控制器、`service/combatdata/**`、`mapper/combatdata/**` 及对应映射和测试。
6. `GameDataService` 和 `PostgresReadStore` 同时承载需要保留的游戏、图片能力和需要删除的旧当前版本、旧阶段配置能力，必须定点收敛，不能整类删除；`PostgresWriteStore` 当前只剩图片和编辑日志写入，只做引用核对，不再假定其中有旧发布写入分支。
7. 阶段 7.5 方案已经明确不读取、迁移或复用旧 Ability、Provider 和旧战斗数据表；删除旧链路不会要求阶段 7.5 改产品契约。

1. 把新鲜建库脚本收敛为当前 45 张父表、只服务 `images` 的分区能力及当前业务触发器。

5. 建立静态清理契约测试、后端回归测试和真实数据库验收步骤。

## 7. 迁移设计

新增：

`db/game_manage/migrations/breaking/drop_legacy_combat_data_chain.sql`

迁移固定步骤：

1. 开启事务，并取得能避免并发结构修改的数据库级锁或等价保护。
2. 检查第 4 节 45 张父表全部存在，`images` 确实是按 `game_id` 列表分区的父表；任一条件不满足即抛错并回滚。
3. 从 PostgreSQL 目录建立本次允许删除的依赖闭包：第 5 节 74 张明确父表；通过 `pg_inherits` 递归取得的这些父表全部运行时子分区，不按名称猜测；第 6.2 节十一项触发器和两个函数；`ensure_game_data_state(varchar)`；以及上述对象自身拥有的索引、约束、序列、TOAST 等内部对象。`ensure_game_partitions`、`trg_games_after_insert_create_partitions()` 和 `games` 上的触发器是保留并改写对象，不进入删除闭包。
4. 检查删除闭包之外是否有表、视图、物化视图、触发器或函数依赖闭包内对象；有则列出对象并抛错回滚。闭包内部依赖、旧父表与其 `pg_inherits` 子分区关系、两个待删函数对旧表的依赖不视为未知依赖；仍禁止 `CASCADE`。
5. 用 `CREATE OR REPLACE` 把 `ensure_game_partitions` 和 `trg_games_after_insert_create_partitions` 收敛为第 6.1 节的图片专用实现，保留 `games` 触发器，并删除 `ensure_game_data_state`。
6. 按第 6.2 节顺序显式删除旧效果步骤的十一个触发器和两个函数；表已不存在时通过存在性检查跳过，保证重复执行。
7. 按反向依赖顺序对第 5 节 74 张父表执行 `DROP TABLE IF EXISTS`，禁止 `CASCADE`。PostgreSQL 按分区关系随父表删除第 3 步记录的运行时子分区；删除后再次用目录核对这些子分区全部消失，出现游离子表即回滚。
8. 为 `games` 当前记录幂等补建 `images` 子分区，提交事务。

重复执行契约：

1. 第二次执行时旧表和旧函数已经不存在，迁移仍成功。
2. 45 张保留父表和 `images` 分区形状检查仍执行。
3. 图片专用分区函数、触发函数和现有游戏子分区保持可用。
4. 不重新创建旧对象，不修改保留数据。

迁移前的操作门禁：

1. 明确 PostgreSQL 主机、端口、数据库名和用户。
2. 确认当前连接不是共享、测试外的正式数据库；如是正式或不可丢弃数据库，必须有可恢复备份。
3. 记录 45 张保留父表的结构存在性、`images` 的分区定义、现有 `images_<gameId>` 子分区，以及 `games`、`attributes`、`characters`、`equipment`、`skills`、`statuses`、`images` 和阶段 7.2～7.4 主要表行数。
4. 记录实际存在的 74 张旧表及行数，供删除结果审计，不用于迁移数据。
5. 停止仍加载旧 Mapper 的后端进程。

8. 增加旧 HTTP 路径 404 测试，防止旧控制器被遗漏。

## 12. 验证命令与证据

开发获得批准后，驱动模型必须在 Backend worktree 亲自执行：

1. 最近层 README 规定的完整 Maven 测试。
2. Maven 打包验证；如果只因仓库明确允许跳过外部运行依赖，必须记录原因。
3. 数据库清理契约测试和迁移静态检查。
4. 通过仓库既有 JDBC 路径对明确目标数据库执行迁移，不能用静态 SQL 代替真实执行。
5. 连续执行破坏式迁移两次，再执行当前 `triggers.sql`；核对已有游戏的图片子分区均存在。
6. 新增一个验收用测试游戏，证明数据库触发器自动建立对应图片子分区；通过现有图片接口写入和读取后再按当前受控方式清理测试数据。
7. 重启后端并检查启动日志无缺失 Mapper、无旧表查询、无触发器创建失败。
8. 请求游戏列表、图片和阶段 0～7.4 当前接口；请求每类旧路径并确认 404。

真实数据库证据至少记录：连接目标的非敏感标识、执行时间、迁移前后表集合、关键行数、两次迁移结果、后端启动结果和接口状态。不记录密码、令牌或完整连接密钥。

## 13. 后端停止条件

1. 当前 Java 代码仍有待删除表的必要运行时引用，但不在本任务边界内可安全移除。
2. 74 张表之外出现旧模型表，或任一待删表被保留表依赖。
3. `GET /api/games` 的实际前端消费者仍需要除三项冻结字段外的信息。
4. 图片接口必须依赖待删除的旧实体表才能工作。
5. 破坏式迁移只能依赖 `CASCADE` 才能执行。
6. 目标数据库、备份或可丢弃性质无法确认。
7. 保留表结构、数据行数、当前测试或接口出现非预期变化。
8. `images` 不是预期的列表分区父表，或收窄后的函数无法为已有和新增游戏建立图片子分区。

遇到停止条件时报告事实和影响，不扩大删除清单、不临时增加兼容层，也不继续执行真实数据库写入。
