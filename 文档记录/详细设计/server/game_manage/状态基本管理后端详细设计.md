## 4. 数据库设计

```sql
CREATE TABLE public.statuses (
    game_id varchar(64) NOT NULL,
    status_key varchar(64) NOT NULL,
    name varchar(100) NOT NULL,
    description varchar(2000),
    status varchar(16) NOT NULL DEFAULT 'ENABLED',
    sort_order integer NOT NULL DEFAULT 0,
    created_at timestamptz NOT NULL DEFAULT now(),
    updated_at timestamptz NOT NULL DEFAULT now(),
    CONSTRAINT pk_statuses PRIMARY KEY (game_id, status_key),
    CONSTRAINT fk_statuses_game
        FOREIGN KEY (game_id) REFERENCES public.games (game_id),
    CONSTRAINT ck_statuses_key
        CHECK (status_key ~ '^[a-z][a-z0-9_]{0,63}$'),
    CONSTRAINT ck_statuses_name CHECK (btrim(name) <> ''),
    CONSTRAINT ck_statuses_status CHECK (status IN ('ENABLED', 'DISABLED')),
    CONSTRAINT ck_statuses_sort_order CHECK (sort_order >= 0)
);

CREATE UNIQUE INDEX uq_statuses_name
    ON public.statuses (game_id, lower(btrim(name)));
```

表只保存共享契约字段，不增加分类、层数、持续时间、生命周期、JSONB、公式、发布版本或运行时状态列。

## 5. 迁移

1. `schema.sql` 增加 `public.statuses`，作为新库真源。
2. 新增 `status_basic_management_migration.sql`，用于把同一张新表应用到已存在的开发数据库；它不是旧数据兼容迁移，不读取或复制任何旧状态表。
3. 迁移先检查 `to_regclass('public.statuses')`。表不存在时创建；表存在时必须核对列、类型、主键、游戏外键、检查约束和唯一索引，完全一致才保持幂等。
4. 表存在但结构不一致时主动报错停止，不能靠 `CREATE TABLE IF NOT EXISTS` 静默通过。
5. 迁移不得创建、修改或删除 `status_definitions`，也不得执行 DROP、DELETE、CASCADE、种子写入或发布。
6. 开发获批后必须对项目负责人确认的真实开发数据库执行迁移；只提交 SQL 文件不算完成。

## 7. 查询与写入

### 7.1 查询

1. 列表先验证游戏存在，再规范化关键词和状态筛选。
2. Mapper 按共享契约查询和排序；空列表返回空数组和 `total=0`。
3. 详情先验证游戏，再按复合主键查询；不存在返回稳定 404。

### 7.2 创建

1. 请求对象去除 `statusKey`、`name` 和 `description` 首尾空格，空说明转 null。
2. 校验字段和游戏。
3. 校验同游戏标识和规范化名称不存在。
4. 插入后回读完整响应。
5. `pk_statuses` 和 `uq_statuses_name` 是并发最终真源，按约束名映射稳定冲突错误。

### 7.3 更新

1. 按 `(game_id, status_key)` 使用 `FOR UPDATE` 锁定；不存在返回 404。
2. 拒绝请求体中的非 null `statusKey`。
3. 排除当前记录后检查规范化名称重复。
4. 全量更新名称、说明、启停状态、排序和 `updated_at`，再回读完整响应。

### 7.4 删除

1. 先锁定状态；不存在返回 404。
2. 删除未引用记录。
3. 只把 PostgreSQL SQLSTATE `23503` 外键冲突映射为 `409.STATUS_IN_USE`；其他完整性异常不得伪装为引用冲突。
4. 删除不使用 CASCADE，也不手工删除任何未来引用方。

## 8. 控制器与编辑日志

1. 控制器路径严格使用共享契约中的 `/statuses`。
2. POST 返回 201，PUT 返回 200，DELETE 返回 204。
3. POST、PUT、DELETE 沿用 `AdminEditLogHelper`。
4. 启停复用 PUT，不新增单独状态切换接口。
5. controller 不解析数据库错误文本，统一错误继续由全局错误处理器输出。

## 11. 后端停止条件

1. 目标数据库已经存在结构不一致的 `public.statuses`。
2. 新接口必须依赖或恢复旧 `status_definitions`、combat-data 状态结构、Provider 或 Ability。
3. 实现必须提前增加状态生命周期、效果或计算表。
4. `statuses` 无法避开旧清理脚本的删除范围。
5. 完整 Maven 测试、真实数据库迁移或接口验证不能完成，且无法定点确认原因。

出现任一项时保留证据并停止，不增加兼容读取或绕过数据库约束。
