## 4. 数据库总原则

1. 效果特殊表统一以 `game_id + skill_key + effect_key + result_key` 为前缀，完整外键到 `skill_effect_results` 并随结果级联删除。
2. 公式、伤害类型、属性、其他效果和其他结果引用使用完整复合外键及 `RESTRICT`，不得只保存约定字符串。
3. 阶段 7.5 新事件明细以 `game_id + skill_key + rule_key` 为主键，外键到规则聚合并随规则级联删除。
4. 可选一对一明细使用“没有行 = null”，不在主表增加大量互斥空列。
5. 列表、集合和固定联合均使用子表；API 可以返回数组，数据库不得用数组或 JSONB 保存关系。
6. 跨表“恰好一种明细”、生命周期合法形状和结果类型组合使用 `DEFERRABLE INITIALLY DEFERRED` 约束触发器；Service 必须先做业务校验并返回 400。
7. 所有反向引用建立以被引用复合键开头的索引，保证删除保护不依赖全表扫描。

## 6. 八种新结果明细表

以下表都以结果完整键为主键并外键到 `skill_effect_results`：

1. `skill_effect_damage_modifier_details`：`direction/operation/damage_type_key/delivery_kind/origin_kind/critical_filter`。
2. `skill_effect_healing_modifier_details`：`direction/operation/healing_kind`。
3. `skill_effect_damage_immunity_details`：`damage_type_key/delivery_kind/origin_kind`。
4. `skill_effect_health_floor_details`：`attribute_key`，复合外键到同游戏属性。
5. `skill_effect_execute_details`：`attribute_key`，复合外键到同游戏属性。

`SPELL_SHIELD`、`HIT_LINK_APPLICATION` 和 `ATTACK_LINK_APPLICATION` 的 `detail = {}`，沿用当前直接治疗空明细做法，不建立没有业务列的空表。结果类型检查和延迟形状函数必须确认它们没有其他类型明细。

数值规则要求：

1. `DAMAGE_MODIFIER / HEALING_MODIFIER / HEALTH_FLOOR / EXECUTE / HIT_LINK_APPLICATION / ATTACK_LINK_APPLICATION` 必须有一行 `skill_effect_result_values`。
2. `DAMAGE_IMMUNITY / SPELL_SHIELD` 禁止数值规则。
3. 伤害修正、治疗修正、伤害免疫、生命下限和法术护盾五种结果必须有生命周期且行为为 `PERSISTENT`。
4. 伤害修正、治疗修正必须 `APPLICATION_SNAPSHOT`，允许 `SHARED / PER_STACK`，并沿用阶段 7.4 对重复值字段的完整约束。
5. 生命下限必须 `APPLICATION_SNAPSHOT + SHARED`，重复值只允许 `KEEP / REPLACE`。
6. 伤害免疫和法术护盾的 `value_read_mode/stack_value_mode/reapplication_value_mode` 都必须为空。
7. 斩杀和两种联动结果禁止 `PERSISTENT`；使用其他离散时点时按阶段 7.4 数值读取和周期字段规则校验。

3. 当前子阶段目标表的结构状态必须可解释：全部缺失时创建；全部存在时逐列、约束和索引核对；部分存在主动失败。五段累计形成十二张最终新表，但任一迁移只检查自己和已验收前置结构，不能提前创建后续表。
4. 伤害明细扩列先添加可空列，使用受控 `UPDATE ... WHERE delivery_kind/origin_kind IS NULL` 把既有行补为 `SKILL + DIRECT`，再设置非空和检查；不写业务样本。
5. 使用 `INSERT ... SELECT ... WHERE NOT EXISTS` 为每个既有 `DAMAGE` 补 `critical_mode = DISALLOWED`、倍率公式为空的暴击策略，为每个既有 `NORMAL_SHIELD` 补伤害类型为空、`decay_mode = NONE` 的护盾交互；重复执行不得产生重复行。
6. 阶段 7.5 `DAMAGE_DEALT / DAMAGE_TAKEN` 现有规则用相同幂等插入补 `skill_trigger_rule_damage_events` 的 ANY/null 明细，不删除或复制规则。
7. 替换检查前必须逐项核对：结果类型、21 种事件类型、十种前序结果 `output_kind`，以及 `skill_trigger_rule_event_value_conditions` 和 `skill_trigger_rule_event_value_bindings` 两处 `event_value_key`；任一未知原定义都停止。
8. 两处 `event_value_key` 的最终允许集合必须保留阶段 7.5 既有 `STEP_EXECUTION_INDEX / CHARGE_DURATION_MS / RECAST_COUNT / HIT_INDEX / LIFECYCLE_STACKS / PERIOD_INDEX / REMAINING_MS / STATE_BEFORE / STATE_AFTER / ATTRIBUTE_BEFORE / ATTRIBUTE_AFTER / THRESHOLD_VALUE`，并追加本阶段 `RAW_DAMAGE / POST_DEFENSE_DAMAGE / HEALTH_BEFORE / PROJECTED_HEALTH_AFTER / SHIELD_ABSORBED / ACTUAL_HP_LOSS / BLOCKED / IMMUNE / KILLED / LINK_INDEX / LINK_COUNT`；不得用本阶段十一项覆盖既有集合。十种 `output_kind` 为 `CONFIGURED_VALUE / RAW_DAMAGE / POST_DEFENSE_DAMAGE / SHIELD_ABSORBED / ACTUAL_HP_LOSS / ACTUAL_HEALING / BLOCKED / IMMUNE / STATUS_APPLIED / KILLED`。
9. 改写阶段 7.5 事件聚合形状函数：三类伤害事件必须恰好一条伤害明细，两个联动事件和法术护盾事件各自恰好一条专属明细；其他 15 种事件必须把三张新明细表计为 0，不能继续走“所有新明细都为零”的旧 ELSE。
10. 把 `skill_effect_results.result_type` 和触发器局部结果类型变量从 24 扩到 32；先核对现有列和函数定义，未知漂移停止。
11. 单个子阶段的“迁移已完成”必须同时满足该段表、列、回填、CHECK、形状函数和约束触发器挂载一致；全部五段完成后才以十二张表、最终列宽、十六种结果、二十一种事件和十种输出检查总体完成。表存在但其他任一项未完成时不得直接 no-op。
12. 不使用 `CASCADE`，不迁移旧 combat-data，不创建兼容视图或双写。

### 8.3 `triggers.sql`

扩展：

1. 结果形状函数的 16 个 `result_type` 分支都必须显式统计九张新增效果子表：暴击策略、吸血规则、普通护盾交互、法术护盾阻挡范围和五张新类型明细。不能只为八种新结果增加 `ELSIF`。
2. `DAMAGE` 必须恰好一条暴击策略、可有 0～4 条不同吸血规则；只有 `target = TARGET` 且生命周期时点不是持续生效时才可有 0～1 条法术护盾范围，否则必须为 0；普通护盾交互和五张新类型明细都为 0。`DIRECT_HEAL` 的九张新增效果子表全部为 0。`NORMAL_SHIELD` 必须恰好一条普通护盾交互，法术护盾范围、暴击、吸血和五张新类型明细全部为 0。`ATTRIBUTE_CHANGE / RESOURCE_CHANGE / COOLDOWN_CHANGE / STATUS_OPERATION / LIFECYCLE_OPERATION` 五种既有结果也必须逐表声明允许数和禁止数：仅在 `target = TARGET`、生命周期时点不是持续生效且共享契约未固定禁止时允许 0～1 条法术护盾范围，否则该表行数为 0。
3. 八种新结果各自必须恰好拥有它的类型明细或明确空 detail，并把其他既有明细与九张新增效果子表计为 0；通用法术护盾范围只在共享契约允许的离散结果分支允许 0～1 行。
4. 暴击、吸血、普通护盾和新结果与生命周期字段组合按共享矩阵检查。
5. 事件形状函数的 21 个事件分支都显式统计三张新增事件明细表；三类伤害事件、两类联动事件和法术护盾事件各自恰好一条专属明细，其他 15 种事件三表都为 0。
6. 法术护盾事件目标效果资格。
7. 约束触发器挂载清单必须覆盖九张新增效果子表和三张新增事件明细表；对这些表执行 INSERT/UPDATE/DELETE 都能在提交时重新检查对应父聚合。既有父表和既有子表挂载继续保留。
8. 每次替换累计结果形状函数时都必须保留冷却目标计数：`COOLDOWN_CHANGE` 恰好一条明细且至少一条目标关系，其他结果不得拥有冷却目标；`skill_effect_cooldown_change_targets` 的 INSERT/UPDATE/DELETE 继续触发完整结果形状检查。

触发器只兜底原子形状和真实引用；跨规则可达公式、动作顺序、输出类型和规则图由 Service 返回业务错误。

## 9. 效果模型与序列化

### 9.1 结果类型

扩展 `SkillEffectResultType` 和 `SkillEffectResultDetail` permits 列表。为五种有业务明细的新结果增加不可变请求/响应/Row 类型；三个空明细结果使用明确空 detail 类型，不能用 Map。

`SkillEffectResultRequestDeserializer` 必须按 16 种结果完整 switch；未知类型、缺 detail 或其他种类字段继续形成 `400.INVALID_BODY`，不得静默忽略。

### 9.2 公共字段

请求和响应结果增加可空 `spellShieldBlockScope`。Service 返回 null 时不得伪造默认范围；Mapper 通过一对一表组装。

既有 `COOLDOWN_CHANGE` detail 继续使用 `affectedSkillKeys: List<String>`。`spellShieldBlockScope` 属于结果公共字段，一条非空范围同时约束该结果的全部受影响技能，不按目标关系复制策略行。

### 9.3 伤害与护盾

`SkillEffectDamageDetail` 增加来源、暴击和吸血联合；Service 从三张关系表组装，吸血固定按共享契约种类顺序返回。普通护盾从空 detail 改为明确强类型 detail。

## 10. `SkillEffectService` 聚合流程

### 10.1 读取

1. 一次读取结果主行、数值规则、原有类型明细、冷却变化目标关系、五张新类型明细、生命周期、暴击、吸血、法术护盾范围和普通护盾交互。
2. 按结果键建立精确 Map；重复行、孤儿行或类型不匹配视为数据库契约损坏，不能挑第一行继续。
3. 响应只返回当前类型合法 detail，不返回数据库内部行或空的其他类型明细。

### 10.2 校验

在写库前收集全部字段问题：

1. 16 种结果的数值规则和 detail 形状。
2. 暴击模式与倍率公式组合、吸血种类唯一和值来源。
3. 法术护盾范围与 target、结果类型和生命周期时点组合；`DIRECT_HEAL / NORMAL_SHIELD` 即使作用于当前目标且不是持续生效也必须为 null。
4. 普通护盾的伤害类型、衰减和生命周期。
5. 五种持久特殊结果和斩杀、命中联动、攻击联动三种离散结果的生命周期字段矩阵。
6. 同技能公式、同游戏伤害类型和属性引用。
7. 当前候选效果是否破坏阶段 7.5 事件或丰富输出绑定。

先锁父技能和当前效果，再按稳定排序锁公式、伤害类型、属性及被引用效果，保持现有锁顺序，避免不同服务反向加锁。

### 10.3 写入顺序

创建：效果 → 生命周期 → 结果主行 → 数值规则 → 原有/新增类型明细（包含普通护盾交互）→ 暴击 → 吸血 → 法术护盾范围 → 生命周期行为。

更新：

1. 锁当前聚合并形成旧/新结果快照。
2. 完成入站引用、丰富输出和候选规则图校验。
3. 删除待移除结果的吸血、暴击、法术护盾、普通护盾、新类型明细和生命周期行为。
4. 删除结果；更新保留结果；新增结果。
5. 全量同步全部新子表和生命周期。
6. 提交时再由延迟触发器确认完整形状。

任一步失败必须回滚。不得先删除旧聚合后依赖重新插入成功。

## 11. 触发规则服务扩展

阶段 7.5 最终 Service 增加：

1. 21 种事件联合的完整 switch 和三张新事件明细读写。
2. 事件值能力表中的新数值和值类型。
3. `PRIOR_ACTION_RESULT` 十种 output kind 与来源结果类型矩阵。
4. 执行效果可达公式收集中的暴击倍率、吸血效率和六种数值特殊结果。
5. 新事件生产边、伤害筛选匹配和法术护盾效果匹配；`DAMAGE_PENDING` 本地边只由 `target=SOURCE` 的伤害产生，`target=TARGET` 对应对方技能的伤前/受伤事件，挂载未知时不建本地边。
6. 生产表还必须逐行落实 `EXECUTE → KILL / ENTITY_DIED` 和普通护盾耗尽可能产生所属生命周期 `EARLY_REMOVE`；不能因为它们不是新增事件而从阶段 7.6 候选图漏掉。
7. 任一规则执行含 `originKind = REFLECTED` 的伤害效果时，事件必须是 `DAMAGE_PENDING / DAMAGE_TAKEN`，动作目标必须是 `EVENT_SOURCE`，且 `eventSource.detail.originKind = DIRECT` 或存在合法每目标冷却；其他事件、其他目标或 `ANY / REFLECTED` 无保护组合都返回反伤闭环错误。

`DAMAGE_PENDING` 事件不能选择结算后事件值；`ACTUAL_HEALING` 只有直接治疗或含吸血规则的伤害可选。字段问题必须定位实际规则数组下标。

## 12. 引用与删除保护

1. `SkillFormulaService` 删除前检查暴击倍率、吸血效率和所有数值特殊结果；继续返回 `409.SKILL_FORMULA_IN_USE`。
2. `DamageTypeService` 删除前检查伤害、普通护盾、伤害修正、免疫和伤害事件筛选；返回 `409.DAMAGE_TYPE_IN_USE`。
3. 属性若未来提供删除，必须检查生命下限和斩杀；当前停用只限制新增引用。
4. `SkillEffectService` 删除或修改结果前检查 `SPELL_SHIELD_BLOCKED` 的效果引用和丰富前序结果可用性；冲突返回 `409.SKILL_EFFECT_IN_USE`。
5. 删除技能自身时先删除自身规则，再删除效果特殊子表；其他技能联动事件的 `sourceSkillKey` 继续返回 `409.SKILL_IN_USE`。
6. 同一请求存在阶段 7.3 过程、7.5/7.6 规则和 7.4 生命周期操作冲突时，继续使用共享契约既有优先级：过程或规则的 `409.SKILL_EFFECT_IN_USE` 优先于生命周期专属冲突。
7. `SkillService` 同时保留冷却目标关系入站引用和阶段 7.6.4 联动事件 `sourceSkillKey` 入站引用；两类查询都排除所属技能自身聚合，任一外部引用均返回既有 `409.SKILL_IN_USE`。

## 13. 错误映射

Service 负责把共享契约错误映射为稳定字段问题，数据库异常只作最后兜底：

1. 暴击/吸血/特殊结果形状 → `400.VALIDATION_FAILED`。
2. 公式、伤害类型、属性 → `400.INVALID_SKILL_EFFECT_REFERENCE`。
3. 新事件或护盾效果引用 → `400.INVALID_SKILL_TRIGGER_RULE_REFERENCE`。
4. output kind 与结果不匹配 → `400.INVALID_RUNTIME_INPUT_BINDING`。
5. 反伤或新事件闭环 → `400.TRIGGER_RULE_CYCLE_UNGUARDED`。
6. 唯一、外键、检查和延迟触发器异常必须按约束名精确归类；未知约束不得泛化为业务 400，保留服务端错误并在测试中暴露。

## 17. 后端停止条件

出现以下任一情况停止编码并回到共享契约：

1. 阶段 7.5 最终表、事件联合、绑定表、规则图或错误与本设计前提不一致。
2. 结果或事件必须保存为 JSONB、数组、自由字符串或通用多态关系才能实现。
3. 效果或规则无法在一次事务内维护，必须暴露子项半成品接口。
4. 需要执行公式、随机暴击、护盾、吸血、事件、结算或 Wasm 才能完成校验。
5. 新公式、伤害类型、属性、效果或结果无法使用真实复合外键和明确删除保护。
6. 反伤或联动闭环无法用固定筛选、现有保护和封闭生产表收敛。
7. 真实数据库、接口或重启回读验收不可用，且无法定点确认原因。
8. 实现方试图按本总设计一次创建十二张表、扩展全部结果/事件或执行一个总迁移。

在 Cursor 只读评审、项目负责人确认和阶段 7.5 完整验收之前，本总设计不授权任何 Backend、SQL、数据库或服务操作；获批后也只能执行对应子阶段详细设计的明确子集。
