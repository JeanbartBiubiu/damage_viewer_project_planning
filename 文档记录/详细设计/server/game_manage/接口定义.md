# game_manage 接口定义（强约束）
本文件是“游戏内容管理与发布”的唯一契约来源：后端实现与前端调用必须严格遵循本文档。若需要变更接口，必须先更新本文档，再进入实现阶段。

## 0. 术语与目标
- 读用户：只读访问已发布版本数据（高并发、强缓存、无编辑能力）。
- 写用户：具备编辑权限，可修改“原始表”数据，但修改不会直接影响读用户。
- 发布：把“原始表”冻结为某个版本的“快照数据”，供读用户拉取与缓存。

## 1. 全局约束
### 1.1 版本字段隐藏（重要）
数据库层可能存在 `start_version_id/end_version_id/version_id` 等字段，但它们属于内部实现细节：
- 前端编辑器不得展示任何版本字段。
- 所有写接口（Admin）请求体不得出现任何版本字段；后端必须忽略/拒绝这些字段。
- 读接口只允许暴露 `versionId/versionCode/dataHash` 这三个版本相关字段（见 2.1）。

### 1.2 统一响应包装
#### 成功
- `2xx`：直接返回 JSON 对象或数组（不做额外 wrapper）。

#### 失败
```json
{
  "error": {
    "code": "400.INVALID_BODY",
    "message": "human readable message",
    "details": {
      "path": "/mechanicsConfig/triggers/0/actions/1",
      "reason": "missing field: type"
    }
  }
}
```

### 1.3 错误码集合
- `400.INVALID_BODY`：JSON 结构缺字段/类型错误/不符合最小约束
- `401.UNAUTHORIZED`：未登录或 token 无效
- `403.FORBIDDEN`：无写权限访问 admin 接口
- `404.NOT_FOUND`：资源不存在（gameId、heroId、skillId 等）
- `409.CONFLICT`：唯一键冲突（如重复创建）
- `422.SEMANTIC_ERROR`：语义校验失败（引用不存在、stackId 未定义、表达式非法等）
- `500.INTERNAL_ERROR`：未预期错误

### 1.4 标识符规范
- `gameId`：`^[a-z0-9_]+$`
- `targetCategory`：`equipment | attribute | skill | character | type`
- `ownerType`：`^[a-z0-9_]+$`（可扩展；不再固定为 hero/item/rune）
- `uri`：建议形如 `equipment_100` / `hero_ahri`（由业务约束保证唯一）

## 2. 读接口（Public）
读接口面向高并发用户，必须满足：
- 不分页：默认全量返回（按当前方案：前端直接全表拉取进 IndexDB）
- 强缓存：优先依赖 `ETag`/`If-None-Match`（基于 `dataHash`）

### 2.0 获取可用游戏列表
用于前端动态展示可用 `gameId` 列表；后端新增游戏后前端可直接拉取。

## 3. 写接口（Admin：游戏内容与关系管理）
写接口只修改“原始表数据”，不会改变读接口返回的当前版本，除非执行“发布”。

### 3.1 鉴权
- 所有 `/api/admin/**` 必须携带 `Authorization: Bearer <jwt>`
- jwt 必须为 `ES256` 签名，并至少包含 `email`、`canEdit`、`paid`；其中写权限由 `canEdit` 决定（对外表现为 `403.FORBIDDEN`）

### 3.2 Upsert 约定
- `PUT`：全量覆盖（请求体必须包含该资源的必要字段）
- 后端必须执行结构校验与语义校验，不允许写入“无法发布”的脏数据
- 为保障编辑器实时感知未发布的最新态，所有可编辑资源都应提供全量 `GET list` 接口；前端在保存成功后可重新拉取对应列表。

### 3.4 关系语义强约束（用于实现与校验一致性）
#### type_relations.targetCategory / targetId 的含义
- `equipment`：`targetId = itemId`
- `attribute`：`targetId = attrKey`
- `skill`：`targetId = skillId`
- `character`：`targetId = heroId`
- `type`：`targetId = typeId`（字符串形式；用于层级关系）

#### skill.ownerType / ownerId 的含义
- `ownerType` 是“归属类别 key”（可扩展），由后端字典维护（DB 侧对应 `owner_categories`）
- 约束：`ownerType` 必须是该 `gameId` 下已登记的类别；否则返回 `422.SEMANTIC_ERROR`
- 目前默认约定（可扩展）：
  - `ownerType = hero`：`ownerId = heroId`
  - `ownerType = item`：`ownerId = itemId`
  - `ownerType = rune`：`ownerId = runeId`（如未落表，需先定义 rune 的实体形态与校验规则）

#### items.skillRefs / recipeIds 的约束
- `skillRefs`：引用的 `skillId` 必须存在（建议数组）
- `recipeIds`：引用的 `itemId` 必须存在（建议数组）

## 4. 发布接口（Admin）
发布负责把“原始表”冻结成“版本快照”，并更新 `current` 指针。

### 4.1 创建版本（草稿）
`POST /api/admin/games/{gameId}/versions`

请求：
```json
{
  "versionCode": "14.1",
  "releaseDate": "2026-02-08"
}
```

响应：
```json
{
  "gameId": "lol",
  "versionId": 123,
  "versionCode": "14.1"
}
```

### 4.2 发布版本
`POST /api/admin/games/{gameId}/versions/{versionId}:publish`

行为约束：
- 后端必须对将要发布的数据做全量校验（结构 + 语义）。
- 发布成功后必须生成 `dataHash`，并使 `GET /versions/current` 指向该版本。

响应：
```json
{
  "gameId": "lol",
  "versionId": 123,
  "versionCode": "14.1",
  "dataHash": "sha256-hex-string"
}
```

## 6. mechanics_config（强约束 JSON）
目标：编辑器可视化配置；避免脚本字符串；支持计数器（三环）、DoT、条件、穿透/减甲、暴击等。

### 6.1 MechanicsConfigV1
```ts
export type MechanicsConfigV1 = {
  version: 1
  stacks?: StackDef[]
  triggers: TriggerRule[]
}
```

### 6.2 TriggerRule / TriggerEvent
```ts
export type TriggerRule = {
  id: string
  event: TriggerEvent
  conditions?: ConditionNode
  actions: ActionNode[]
}

export type TriggerEvent =
  | { type: "on_basic_attack_hit" }
  | { type: "on_spell_cast" }
  | { type: "on_damage_dealt" }
  | { type: "on_tick"; tickKey: string }
  | { type: "on_stack_change"; stackId: string }
```

### 6.3 ConditionNode（条件树）
```ts
export type ConditionNode =
  | { op: "and"; args: ConditionNode[] }
  | { op: "or"; args: ConditionNode[] }
  | { op: "not"; arg: ConditionNode }
  | { op: "chance"; p: number }
  | { op: "cmp"; left: ExprNode; cmp: ">"|">="|"=="|"!="|"<="|"<"; right: ExprNode }
```

### 6.4 ActionNode（动作）
```ts
export type ActionNode =
  | { type: "deal_damage"; damage: DamageSpec }
  | { type: "apply_modifier"; modifier: ModifierSpec }
  | { type: "add_stack"; stackId: string; amount: number; max?: number }
  | { type: "remove_stack"; stackId: string; amount?: number; all?: boolean }
  | { type: "schedule_tick"; tickKey: string; everyMs: number; times: number }
  | { type: "if"; cond: ConditionNode; then: ActionNode[]; else?: ActionNode[] }
```

### 6.5 ExprNode（结构化表达式）
```ts
export type ExprNode =
  | { t: "const"; v: number }
  | { t: "attr"; who: "self"|"enemy"; key: string }
  | { t: "stack"; stackId: string }
  | { t: "op"; op: "+"|"-"|"*"|"/"|"min"|"max"; args: ExprNode[] }
  | { t: "clamp"; v: ExprNode; min: ExprNode; max: ExprNode }
```
