# game_manage 接口定义（强约束）
本文件是“游戏内容管理与发布”的唯一契约来源：后端实现与前端调用必须严格遵循本文档。若需要变更接口，必须先更新本文档，再进入实现阶段。

## 0. 术语与目标
- 读用户：只读访问已发布版本数据（高并发、强缓存、无编辑能力）。
- 写用户：具备编辑权限，可修改“原始表”数据，但修改不会直接影响读用户。
- 发布：把“原始表”冻结为某个版本的“快照数据”，供读用户拉取与缓存。

## 1. 全局约束
### 1.1 版本字段隐藏（重要）
数据库层可能存在 `start_version_id/end_version_id/version_id` 等字段，但它们属于内部实现细节：
- 前端编辑器不得展示任何版本字段。
- 所有写接口（Admin）请求体不得出现任何版本字段；后端必须忽略/拒绝这些字段。
- Public 当前版本接口只暴露 `versionCode` 以及可选的 `releaseDate/publishedAt/updatedAt`。
- Bundle 读取使用 `versionCode` 命中已发布快照；`versionId/dataHash` 不再作为对外一致性字段。

### 1.1.1 新通用 Wasm 的 Deprecated 边界

以下 `Deprecated` 仅限制**新通用 Wasm**的调用方向，不改变旧页面、普通数据管理或历史版本读取的现有可用性：

1. `GET /api/games/{gameId}/versions/{versionCode}/bundle` 与 `GameDataBundleV1` 是 **Deprecated for direct new-Wasm consumption**。新 Worker 不得把其 `skills`、`skillMounts`、`mechanicsConfig`、旧 `typeId` 或数组式属性资源直接组装为 Wasm ABI。
2. 新 Worker 的唯一后端数据源是 `GET /api/games/{gameId}/versions/{versionCode}/wasm-catalog`；缺少 Catalog 返回 `404.NOT_FOUND` 时必须显示未配置状态，禁止回退 `/bundle`。
3. `/bundle` 仍是旧页面、非 Wasm 消费者、历史 Bundle 与受控 Bootstrap 的兼容接口，当前不发送 HTTP `Deprecation`/`Sunset` 响应头，也没有删除日期。
4. 任何全局下线 `/bundle` 或其底层 `published_bundle_snapshots` 的方案，必须先另立迁移任务并完成消费者清点、Catalog 覆盖、历史保留与双链路发布回归；不得在前端接入 Catalog 时顺带删除。

### 1.2 统一响应包装
#### 成功
- `2xx`：直接返回 JSON 对象或数组（不做额外 wrapper）。

#### 失败
```json
{
  "error": {
    "code": "400.INVALID_BODY",
    "message": "human readable message",
    "details": {
      "path": "/mechanicsConfig/triggers/0/actions/1",
      "reason": "missing field: type"
    }
  }
}
```

### 1.3 错误码集合
- `400.INVALID_BODY`：JSON 结构缺字段/类型错误/不符合最小约束
- `401.UNAUTHORIZED`：未登录或 token 无效
- `403.FORBIDDEN`：无写权限访问 admin 接口
- `404.NOT_FOUND`：资源不存在（gameId、heroId、skillId 等）
- `409.CONFLICT`：唯一键冲突（如重复创建）
- `422.SEMANTIC_ERROR`：语义校验失败（引用不存在、stackId 未定义、表达式非法等）
- `500.INTERNAL_ERROR`：未预期错误

### 1.4 标识符规范
- `gameId`：`^[a-z0-9_]+$`
- `targetCategory`：`equipment | attribute | skill | character | type`
- `ownerType`：`^[a-z0-9_]+$`（可扩展；不再固定为 hero/item/rune）
- `uri`：建议形如 `item_100` / `character_ahri` / `attribute_ad`（由业务约束保证唯一）

## 2. 读接口（Public）
读接口面向高并发用户，必须满足：
- 不分页：默认全量返回（按当前方案：前端直接全表拉取进 IndexDB）
- 版本变化判断以 `current.versionCode` 为准。
- Bundle 只读取发布时固化的快照，不从编辑工作区临时拼装。

## 3. 写接口（Admin：游戏内容与关系管理）
写接口只修改“原始表数据”，不会改变读接口返回的当前版本，除非执行“发布”。

### 3.1 鉴权
- 所有 `/api/admin/**` 必须携带 `Authorization: Bearer <jwt>`
- jwt 必须为 `ES256` 签名，并至少包含 `email`、`canEdit`、`paid`；其中写权限由 `canEdit` 决定（对外表现为 `403.FORBIDDEN`）

### 3.2 Upsert 约定
- `PUT`：全量覆盖（请求体必须包含该资源的必要字段）
- 后端必须执行结构校验与语义校验，不允许写入“无法发布”的脏数据
- 为保障编辑器实时感知未发布的最新态，所有可编辑资源都应提供全量 `GET list` 接口；前端在保存成功后可重新拉取对应列表。

### 3.2.1 Wasm Catalog Source
- `GET /api/admin/games/{gameId}/wasm-catalog-source`
- `PUT /api/admin/games/{gameId}/wasm-catalog-source`：`WasmCatalogSourceV1`

该资源是 P0 的原子编辑单元：`PUT` 全量替换当前游戏的 source，成功后只更新编辑态，不会直接影响 Public catalog。请求中禁止 `meta`、`schemaHash`、`rulesHash`、任何版本字段；这些字段仅能在发布时由服务端生成。结构错误返回 `400.INVALID_BODY`，type/ref/旧字段/数值等 source 语义错误返回 `422.SEMANTIC_ERROR`；不允许保存部分有效 source，发布时会重复相同校验。

P0 不提供 provider/ability/formula 的独立 Admin CRUD，避免产生暂时无法发布的半成品。后续细粒度编辑器可替代 source 的存储实现，但必须物化为完全相同的 `WasmCatalogSourceV1`。

`GET` 与 `PUT` 成功时都返回：
```ts
export type WasmCatalogSourceResponse = WasmCatalogSourceV1 & {
  updatedAt: string // ISO-8601；仅编辑态观察值，不参与 hash
}
```

#### 3.2.1.1 从 Legacy Bundle 初始化首批 ADC Catalog 草稿

`POST /api/admin/games/{gameId}/wasm-catalog-source:bootstrap-legacy-adc`

请求体必须为 `{ "sourceVersionCode": string }`。后端只从该 game 对应的已发布 Bundle snapshot 读取固定的 6 个 ADC（薇恩、提莫、韦鲁斯、卡莎、图奇、克格莫）与 3 个训练假人，并写入一份尚未发布的 source 草稿。没有对应 snapshot 返回 `404.NOT_FOUND`；`gameId` 不是 `lol` 或固定实体缺失返回 `422.SEMANTIC_ERROR`；已有 source（包括并发重复请求）返回 `409.CONFLICT`。所有失败场景均不写入或覆盖 source。

返回 `{ source: WasmCatalogSourceResponse, importReport }`。`importReport.unmappedLegacySkillIds` 明确列出未转换的 legacy DPS skill；它不属于 source，不参与 hash。该操作不会自动发布、不会切换 current version、不会清理 Public cache 或写入 catalog snapshot；Public `wasm-catalog` 仍须等后续显式版本发布后才返回快照。完整映射见 [WasmLegacyAdcBootstrapAdapter详细设计.md](WasmLegacyAdcBootstrapAdapter详细设计.md)。

### 3.4 关系语义强约束（用于实现与校验一致性）
#### type_relations.targetCategory / targetId 的含义
- `equipment`：`targetId = itemId`
- `attribute`：`targetId = attrKey`
- `skill`：`targetId = skillId`
- `character`：`targetId = heroId`
- `type`：`targetId = typeId`（字符串形式；用于层级关系）

#### skill.ownerType / ownerId 的含义
- `ownerType` 是“归属类别 key”（可扩展），由后端字典维护（DB 侧对应 `owner_categories`）
- 约束：`ownerType` 必须是该 `gameId` 下已登记的类别；否则返回 `422.SEMANTIC_ERROR`
- 目前默认约定（可扩展）：
  - `ownerType = hero`：`ownerId = heroId`
  - `ownerType = item`：`ownerId = itemId`
  - `ownerType = rune`：`ownerId = runeId`（如未落表，需先定义 rune 的实体形态与校验规则）

#### items.skillRefs / recipeIds 的约束
- `skillRefs`：引用的 `skillId` 必须存在（建议数组）
- `recipeIds`：引用的 `itemId` 必须存在（建议数组）

## 4. 发布接口（Admin）
发布负责把“原始表”冻结成“版本快照”，并更新 `current` 指针。

### 4.1 发布版本
`POST /api/admin/games/{gameId}/versions:publish`

请求：
```json
{
  "versionCode": "14.1",
  "releaseDate": "2026-02-08"
}
```

行为约束：
- `versionCode` 必填，`releaseDate` 可选。
- `versionCode = "__workspace__"` 是内部工作区保留值，不允许发布。
- 后端必须对将要发布的数据做全量校验（结构 + 语义）。
- 发布成功后必须写入 `published_bundle_snapshots`，并使 `GET /versions/current` 指向该 `versionCode`。
- 若该 game 已配置 Wasm catalog source，发布还必须在同一事务写入 `published_wasm_catalog_snapshots`；source 不存在时 legacy bundle 发布保持成功，Wasm catalog 读取返回 404。

响应：
```json
{
  "gameId": "lol",
  "versionCode": "14.1",
  "releaseDate": "2026-02-08",
  "publishedAt": "2026-02-08T12:00:00Z",
  "updatedAt": "2026-02-08T12:00:00Z"
}
```

### 5.1.1 WasmCatalogSourceV1 / WasmCatalogV1
```ts
export type WasmCatalogSourceV1 = {
  schemaVersion: "generic-p0"
  typeCatalog: {
    types: Array<{ key: `${string}/${string}`; domain: string; group?: string }>
    relations: Array<{ parent: string; child: string }>
  }
  combatantTemplates: Array<{
    templateKey: string
    displayName?: string
    types?: string[]
    tags?: string[]
    attributes: Record<string, { base: number; current: number; max: number; resolved: number }>
    resources: Record<string, { current: number; max: number }>
    providers: Array<{ providerRef: string; definitionRef: string; initialState?: object; initialAbilityState?: object }>
  }>
  sharedProviders: ProviderDefinition[]
  rules: { operations: OperationDefinition[]; modifiers: ModifierDefinition[]; listeners: ListenerDefinition[]; triggerRules: unknown[] }
  formulas: NamedFormula[]
  settings: { maxEvents?: number; maxCommandsPerEvent?: number; maxQueueEvents?: number; maxChainDepth?: number }
}

export type WasmCatalogV1 = Omit<WasmCatalogSourceV1, "schemaVersion"> & {
  meta: {
    gameId: string
    versionCode: string
    publishedAt: string
    generatedAt: string
    schemaVersion: "generic-p0"
    schemaHash: `sha256:${string}`
    rulesHash: `sha256:${string}`
  }
}
```

source 中出现在 listener、operation 等位置的 `abilityRef` 必须使用模板态 `$owner.provider[<providerRef>].ability[<abilityKey>]` 或 `$opponent.provider[<providerRef>].ability[<abilityKey>]`。前端选定两个 template 后，必须把每个 catalog provider clone 为 source/target 两个 runtime definition，再按 clone slot 将 `$owner/$opponent` 改写为 `source/target` runtime abilityRef；source 中不得出现裸 ability key、`self/opponent` runtime 前缀或直接的 `source/target` 前缀。`apply_provider.providerDefinitionRef` 写 catalog provider key，由前端按 operation target 选择相应 slot clone。完整 materialize 算法与 initialSnapshot 默认值见 [WasmCanonicalCatalog后端详细设计.md](WasmCanonicalCatalog后端详细设计.md)。

P0 的 `rules.operations/modifiers/listeners/triggerRules` 必须都是空数组；所有带 owner 的规则放在 provider 内，顶层 rules 不得含 ability/provider/formula 引用。`formulas` 也按 source/target 双槽 clone；source formula path 仅允许 `$owner.attr.*`、`$opponent.attr.*`、`$owner.resource.*`、`$opponent.resource.*`、`ability.param.*`，clone 后前四类才改写为 Wasm 的 `source.*` / `target.*` 路径，最后一类保持原样。每个 `NamedFormula.expression` 必须递归遍历 `args/expr/min/max`，将所有 `op=ref` 的裸 catalog formula key 改为当前 owner slot 的 `<slot>::<key>`。P0 不支持非空 `initialAbilityState`。

provider 内 `operation.target` 只允许 `self | opponent`，不得在 catalog 写死 `source | target`；`apply_provider.providerDefinitionRef` 是 catalog provider key，前端依当前 clone slot 与 target 选择对应的 `<slot>::<providerKey>` definition。attribute modifier 的 `target` 只允许 `$owner.attr.<attrKey>` 或 `$opponent.attr.<attrKey>`，再按 clone slot 改写为 Wasm resolver 支持的 `source.attr.*` / `target.attr.*`。

`ProviderDefinition`、`OperationDefinition`、`ModifierDefinition`、`ListenerDefinition`、`NamedFormula` 的字段以 Wasm `CompileRequest` 的 canonical DTO 为准；它们不得使用 `EngineBundleV2`、`ActionTemplateV2`、`skillMounts`、`definitionKey` 或数组式 `attributes/resources`。详细 shape、校验和 hash 范围见 [WasmCanonicalCatalog后端详细设计.md](WasmCanonicalCatalog后端详细设计.md)。
