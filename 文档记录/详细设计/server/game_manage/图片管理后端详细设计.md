## 1. 当前后端基线

1. `ImageAdminController` 只有按路径标识覆盖内容的 PUT。
2. `ImagePublicController` 只有公开全量或按更新时间增量读取。
3. `GameDataService`、`PostgresReadStore`、`PostgresWriteStore` 使用 `ObjectNode` 和通用 Map 传递图片，没有图片专用强类型模型。
4. `ImagesMapper` 只处理 `uri`、`image_base64` 和更新时间。
5. `images` 是按 `game_id` 列表分区的父表；`ensure_game_partitions` 只负责该父表。

这些事实来自当前源码和建库脚本核对，不代表已验证目标数据库。

## 2. 最终数据库结构

继续使用一张 `images` 分区表：

1. 复合主键：`(game_id,image_key)`；`game_id` 外键到 `games`。
2. 业务字段：`image_key varchar(128)`、`name varchar(100)`、`description varchar(2000)`、`image_base64 text`、`enabled boolean`。
3. 派生字段：`mime_type varchar(32)`、`byte_size integer`、`width smallint`、`height smallint`。
4. 审计字段：`created_at`、`updated_at`，均非空。
5. 检查约束锁定标识格式、名称非空、两种媒体类型、字节范围、宽高各 1～64 像素。
6. 唯一索引：`(game_id,lower(btrim(name)))`。

新鲜建库脚本直接使用最终结构。`triggers.sql` 不增加新业务触发器，只验证现有图片分区函数继续可用。

## 3. 既有数据库迁移

新增当前阶段迁移：`db/game_manage/migrations/compatibility/image_management_migration.sql`。

执行前必须先用仓库内检查器读取每条既有图片，核对：

1. `uri` 均符合最终标识规则且长度不超过 128。
2. `image_base64` 能解码为真实 PNG 或 JPEG。
3. 解码大小不超过 262144 字节，宽和高都在 1～64 像素之间。
4. 父表、全部现有子分区、主键和时间字段与当前基线一致。

执行检查前停止后端和其他图片写入。检查器同时记录行数与键集合；任一记录失败时只输出 `gameId`、旧标识和失败原因，不输出图片内容，并在执行 DDL 前停止。

外部只读检查通过后，迁移在单事务内：

1. 固定旧时间列的解释时区，取得 `images` 父表排他锁。
2. 在锁内重新完成全部图片内容预检并生成回填数据，确保内容和派生字段来自同一版本。
3. 复核行数与键集合后，将 `uri` 重命名为 `image_key`。
4. 新增最终字段，既有行以 `image_key` 作为初始名称、说明为 null、状态为启用。
5. 按锁内检查的内容回填媒体类型、解码字节数和实际尺寸，不重新编码图片。
6. 设置非空、检查约束和规范化名称唯一索引。
7. 核对行数、键集合和分区集合与迁移前一致后提交。

迁移再次执行时，最终结构完整则只核对并通过；旧结构与最终结构部分混合时主动失败。不得删除图片、保留旧列、双写或建立兼容视图。

## 4. 后端模块

建立图片专用强类型链路：

1. 图片请求、响应、服务、Mapper 记录放入独立 `image` 模块。
2. 管理控制器提供列表、详情、新建和更新；公开控制器只提供同步读取。
3. 图片服务拥有字段归一化、唯一性、内容解码、真实格式识别、文件大小与尺寸校验、事务和响应组装。
4. Mapper 返回明确记录，不继续用 `Map<String,Object>` 作为图片业务模型。
5. 从 `GameDataService`、`PostgresReadStore`、`PostgresWriteStore` 移除图片职责；不保留转发方法。
6. 图片公开读取不新增后端缓存。浏览器缓存是当前主缓存，避免按任意更新时间生成无限缓存键。
7. 管理写操作继续使用现有认证和编辑日志，但日志请求体必须移除 `imageBase64`。

不修改全局异常格式。图片服务用现有 `ApiException` 产生共享契约冻结的错误和 `fieldIssues`。

图片内容校验固定为：

1. 解析数据地址前，先按 262144 字节解码上限推导的 Base64 编码长度检查内容，明显超限时直接拒绝，不进入图片读取。
2. 解码后确认文件大小大于 0 且不超过 262144 字节。
3. 识别真实 PNG/JPEG，确认数据地址声明与真实格式一致，并检查宽和高都在 1～64 像素之间。
4. 校验通过后原样保存提交字节，再据此生成媒体类型、字节数、宽和高四项派生信息。

后端不得裁切、缩放、压缩或重新编码图片，也不得为这些能力引入处理依赖。页面负责在提交前完成大图压缩；直接接口提交任一边超过 64 或文件超限的图片时返回 `400.IMAGE_CONTENT_INVALID`。

## 5. 事务与并发

1. 新建先校验游戏、字段和最终图片内容，再检查标识与名称唯一，最后插入。
2. 更新锁定目标图片行；先构造完整候选状态并完成最终图片校验，再一次更新。
3. 内容省略时保留旧内容和派生信息；提供内容时四项派生信息必须随内容一起更新。
4. 唯一索引是并发重复的最终保护；数据库冲突转换为共享 409 错误。
5. 每次成功更新刷新 `updated_at`；失败回滚全部字段。

## 7. 验证

后端自动检查至少覆盖：

1. 标识、名称、说明、查询参数和未知字段。
2. 不超过 262144 字节且宽高各在 1～64 像素内的 PNG/JPEG 原样成功；包含小于 64×64 的样例，响应和数据库内容与提交字节一致，四项派生信息正确。
3. 超过 262144 字节、任一边超过 64、伪造类型、损坏 Base64 和空内容直接失败；后端不产生压缩结果。
4. 新建、重复标识、重复名称、详情、筛选、元数据编辑、内容替换、停用和启用。
5. 内容省略保持旧内容；替换失败保持全部旧字段。
6. 公开全量、增量、停用记录和重新启用内容。
7. 编辑日志不含 Base64。
8. 新鲜结构、迁移形状、行数保留、分区函数和部分结构主动失败。
