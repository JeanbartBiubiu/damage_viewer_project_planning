# 验证里程碑

本文定义 Damage Viewer 在 Wasm、Web、Server 三条开发线共同参考的阶段性验证目标。当前优先目标不是一次性做完整 1v1 战斗模拟，而是先建立能和游戏训练营、技能面板逐字段比对的最小证据链。

关联入口：

1. `文档记录/需求澄清/wasm/WASM需求澄清.md`
2. `文档记录/概要设计/wasm/WASM概要设计.md`
3. `文档记录/详细设计/最小验证/数据/技能配置说明.md`

## 1. 当前决策

1. 首期验证从完整 1v1 收缩为训练营可观测数值对齐。
2. 训练营属性和技能面板基线由个人进入游戏人工查看、人工记录、人工比对。
3. 如果人工比对发现 diff，再 review Wasm 代码、Web/Server 数据映射和公式配置，排查根因。
4. Web 和 Server 的开发优先服务这些小验证闭环，不提前要求完整游戏数据、完整交互编排或完整 1v1 场景。
5. TinyGo Wasm 仍是正式计算引擎方向；旧 Rust/Katarina crate 已删除，历史参考只保留在文档和验证记录中。

## 2. 里程碑总览

| 阶段 | 名称 | 目标 | 通过标准 |
| --- | --- | --- | --- |
| M0 | 口径冻结 | 确认人工基线记录格式、游戏版本、误差阈值、字段命名 | 同一 case 能被 Wasm/Web/Server 用同一组字段描述 |
| M1 | Actor 初始属性对齐 | 验证 Wasm 初始化后的攻击方属性与训练营一致 | 核心属性逐字段一致，diff 能定位到字段 |
| M2 | Action 面板值对齐 | 验证 Wasm 内 action 面板投影值与游戏技能面板一致 | 技能基础值、加成、消耗、冷却可逐项比对 |
| M3 | 单技能 1v 假人 | 固定假人、单技能一次结算，只计算攻击方主动行为 | 输出公式输入、公式结果、最终伤害、资源/CD 变化 |
| M4 | 单机制扩展 | 在 M3 基础上逐个加入代表性机制 | 每次只新增一类机制，并保留可回归 case |
| M5 | 小型 1v1 回归 | 在前面证据链稳定后再恢复双方交互 | 双方动作、控制、触发链有独立 gate 和回归样例 |

## 3. M0 口径冻结

M0 的目标是让人工基线不会变成口头记忆。每个验证 case 至少记录：

1. 游戏名称、游戏版本、模式、地图或训练环境。
2. 英雄、等级、技能等级、装备、符文、天赋或模式强化。
3. 假人配置，包括生命、护甲、魔抗、抗性选项和是否允许反击。
4. 训练营属性字段和游戏内显示值。
5. 技能面板字段、显示值、取整现象和特殊说明。
6. Wasm 输出值、人工比对结果、diff 结论和排查状态。

首批样本要刻意小：一个英雄、一个固定假人、一个技能即可。只有这个样本跑通后，才扩同类技能或同类属性。

误差口径先保守处理：

1. 整数面板字段要求完全一致。
2. 小数字段记录游戏显示精度，并标注是否可能被四舍五入影响。
3. 计算内部值和面板展示值必须分开记录，不能用展示取整值反推内部公式。

## 4. M1 Actor 初始属性对齐

M1 只验证初始化，不验证技能释放。

Wasm 侧需要输出攻击方初始化后的属性快照，至少包含：

1. 生命、法力或其他主资源。
2. 攻击力、法术强度、攻速、护甲、魔抗。
3. 暴击、技能急速、移动速度等后续计算会读取的核心属性。
4. `base/current/max/resolved` 中当前引擎已经支持的视图。

TinyGo V2 侧使用 `engine_snapshot_initial(ptr, size)` 作为 M1 专用 ABI：它在 `engine_init` 后接收与 `engine_begin_run` 相同的 run frame/payload，忽略 `initialActions`，不推进 scheduler，只输出初始化后的 `snapshot` frame。

Web 侧参考目标：

1. 能展示或导出 Wasm 初始化快照。
2. 能让开发者把人工记录的训练营字段和 Wasm 字段逐项对照。
3. 承载人工记录和人工 diff 结论，不承担战斗真值计算，也不自动裁决游戏结果对错。
4. 不要求先做完整模拟页面，也不要求自动进入游戏采集。

Server 侧参考目标：

1. 优先保证英雄、等级成长、装备、符文等原始数据能稳定组成初始化输入。
2. 不要求一开始覆盖全部英雄和装备。
3. 字段命名、版本标识和数据快照标识要能支撑人工 case 复盘。
4. 后续可提供 `versionCode`、`generatedAt` 或等价快照标识，确保 Web、Server、Wasm 比对的是同一份配置。

## 5. M2 Action 面板值对齐

M2 验证 action 的面板投影值，不跑完整战斗。

Wasm 侧关注：

1. 技能基础值。
2. 属性加成系数。
3. 消耗资源。
4. 冷却时间。
5. 技能等级影响。
6. 当前属性参与后得到的面板展示结果。

Web 侧参考目标：

1. 技能编辑和展示应保留“面板字段”和“计算字段”的区别。
2. 页面可以先服务少量手工 case，不要为了全量技能录入阻塞验证。
3. diff 展示优先按字段展开，而不是只给一个总通过或总失败。

Server 侧参考目标：

1. 技能数据模型优先支持基础值、等级成长、属性系数、消耗、冷却这些 M2 字段。
2. 复杂触发、状态、召唤物、多段文本可以暂缓结构化。
3. 发布数据时要保留版本和配置快照标识，以便和人工记录的游戏版本对应。

## 6. M3 单技能 1v 假人

M3 是第一条真正的计算闭环，但仍不是 1v1。

运行边界：

1. 固定攻击方。
2. 固定假人。
3. 假人不主动行动。
4. 每个 case 只释放一个技能。
5. 先只验证攻击方主动行为和目标受到的直接数值结果。

Wasm 输出应优先证明：

1. 施放是否被接受。
2. 公式输入值。
3. 公式原始输出。
4. 抗性、减免或伤害类型处理后的最终伤害。
5. 攻击方资源消耗和冷却变化。
6. 同输入、同版本、同 seed 的结果可复现。

Web 侧参考目标：

1. 提供最小 case runner 或结果展示，不需要完整战斗编排 UI。
2. 能把 Wasm 输出和人工基线放在同一视图或同一导出记录中。
3. 失败时能保留输入、输出和人工记录，方便跨端 review。

Server 侧参考目标：

1. 数据接口先满足构造单技能 case 的最小 bundle。
2. 不要把完整 1v1 所需的敌方 AI、动作队列和触发链作为 M3 前置条件。
3. 数据缺失时允许使用小样本 fixture 或人工补录 case 推进验证。

## 7. M4 单机制扩展

M4 按机制扩展，不按英雄数量扩展。推荐顺序：

1. 直伤。
2. 资源消耗和冷却。
3. 护盾和治疗。
4. 标记和条件命中。
5. DoT、HoT、多段伤害。
6. 暴击和随机数。
7. 控制、打断和动作 gate。
8. 触发链、历史窗口、计数器、模式强化。

每次新增机制都必须保留一个最小 case，且 case 能回退到 M1/M2/M3 的字段级证据。

## 8. M5 小型 1v1 回归

只有当 M1 到 M4 的主要 case 稳定后，才恢复完整双方交互。

M5 的通过标准不是“看起来像能打”，而是：

1. 双方 actor 初始化均可对齐。
2. 双方 action 面板均可对齐。
3. 单技能结果已经独立通过。
4. 调度、控制、触发链的每类 diff 都能回到独立机制 case 排查。
5. 最终 1v1 结果只是组合验证，不再承担首次发现所有数值问题的压力。

## 9. Diff 排查顺序

里程碑通过条件不是零 diff，而是无阻塞级未解释 diff。允许存在已归因、已登记、暂不影响当前阶段的非阻塞差异。

发现 diff 时按以下顺序排查：

1. 人工记录是否抄错、漏记录版本或训练环境。
2. 游戏面板是否存在取整、隐藏修正或显示口径差异。
3. Web/Server 字段映射是否丢失等级、装备、符文、技能等级或版本。
4. Server 数据是否缺字段、字段类型错误或发布版本不一致。
5. Web bundle 编译是否把字段转换成了错误的 Wasm 输入。
6. Wasm 公式、属性读取、资源读取或伤害结算是否实现错误。
7. Wasm runtime 调度、状态或事件顺序是否影响了结果。

## 10. 明确非目标

以下内容不作为 M1 到 M3 的阻塞项：

1. 自动从游戏客户端采集训练营数据。
2. 全量英雄、装备、符文、技能覆盖。
3. 完整 1v1 双方动作调度。
4. 敌方 AI 或自动循环释放。
5. 复杂控制状态、反击触发链和多机制叠加。
6. 面向最终用户的完整模拟页面。
7. 后端完整数据治理闭环。

这些能力仍是长期方向，但必须在最小验证闭环稳定后逐步纳入。
