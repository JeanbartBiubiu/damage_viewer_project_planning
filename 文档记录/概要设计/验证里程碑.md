# 验证里程碑

本文定义 Damage Viewer 在 Wasm、Web、Server 三条开发线共同参考的阶段性验证目标。当前优先目标不是一次性做完整 1v1 战斗模拟，而是先建立能和游戏训练营、技能面板逐字段比对的最小证据链。

关联入口：

1. `文档记录/需求澄清/wasm/WASM需求澄清.md`
2. `文档记录/概要设计/wasm/WASM概要设计.md`
3. `文档记录/详细设计/最小验证/数据/技能配置说明.md`

## 1. 当前决策

1. 首期验证从完整 1v1 收缩为训练营可观测数值对齐。
2. 训练营属性和技能面板基线由个人进入游戏人工查看、人工记录、人工比对。
3. 如果人工比对发现 diff，再 review Wasm 代码、Web/Server 数据映射和公式配置，排查根因。
4. Web 和 Server 的开发优先服务这些小验证闭环，不提前要求完整游戏数据、完整交互编排或完整 1v1 场景。
5. TinyGo Wasm 仍是正式计算引擎方向；旧 Rust/Katarina crate 已删除，历史参考只保留在文档和验证记录中。

## 2. 里程碑总览

| 阶段 | 名称 | 目标 | 通过标准 |
| --- | --- | --- | --- |
| M0 | 口径冻结 | 确认人工基线记录格式、游戏版本、误差阈值、字段命名 | 同一 case 能被 Wasm/Web/Server 用同一组字段描述 |
| M1 | Actor 初始属性对齐 | 验证 Wasm 初始化后的攻击方属性与训练营一致 | 核心属性逐字段一致，diff 能定位到字段 |
| M2 | Action 面板值对齐 | 验证 Wasm 内 action 面板投影值与游戏技能面板一致 | 技能基础值、加成、消耗、冷却可逐项比对 |
| M3 | 单技能 1v 假人 | 固定假人、单技能一次结算，只计算攻击方主动行为 | 输出公式输入、公式结果、最终伤害、资源/CD 变化 |
| M4 | 单机制扩展 | 在 M3 基础上逐个加入代表性机制 | 每次只新增一类机制，并保留可回归 case |
| M5 | 小型 1v1 回归 | 在前面证据链稳定后再恢复双方交互 | 双方动作、控制、触发链有独立 gate 和回归样例 |

## 3. M0 口径冻结

M0 的目标是让人工基线不会变成口头记忆。每个验证 case 至少记录：

1. 游戏名称、游戏版本、模式、地图或训练环境。
2. 英雄、等级、技能等级、装备、符文、天赋或模式强化。
3. 假人配置，包括生命、护甲、魔抗、抗性选项和是否允许反击。
4. 训练营属性字段和游戏内显示值。
5. 技能面板字段、显示值、取整现象和特殊说明。
6. Wasm 输出值、人工比对结果、diff 结论和排查状态。

首批样本要刻意小：一个英雄、一个固定假人、一个技能即可。只有这个样本跑通后，才扩同类技能或同类属性。

误差口径先保守处理：

1. 整数面板字段要求完全一致。
2. 小数字段记录游戏显示精度，并标注是否可能被四舍五入影响。
3. 计算内部值和面板展示值必须分开记录，不能用展示取整值反推内部公式。

## 4. M1 Actor 初始属性对齐

M1 只验证初始化，不验证技能释放。

Wasm 侧需要输出攻击方初始化后的属性快照，至少包含：

1. 生命、法力或其他主资源。
2. 攻击力、法术强度、攻速、护甲、魔抗。
3. 暴击、技能急速、移动速度等后续计算会读取的核心属性。
4. `base/current/max/resolved` 中当前引擎已经支持的视图。

TinyGo V2 侧使用 `engine_snapshot_initial(ptr, size)` 作为 M1 专用 ABI：它在 `engine_init` 后接收与 `engine_begin_run` 相同的 run frame/payload，忽略 `initialActions`，不推进 scheduler，只输出初始化后的 `snapshot` frame。

Web 侧参考目标：

1. 能展示或导出 Wasm 初始化快照。
2. 能让开发者把人工记录的训练营字段和 Wasm 字段逐项对照。
3. 承载人工记录和人工 diff 结论，不承担战斗真值计算，也不自动裁决游戏结果对错。
4. 不要求先做完整模拟页面，也不要求自动进入游戏采集。

Server 侧参考目标：

1. 优先保证英雄、等级成长、装备、符文等原始数据能稳定组成初始化输入。
2. 不要求一开始覆盖全部英雄和装备。
3. 字段命名、版本标识和数据快照标识要能支撑人工 case 复盘。
4. 后续可提供 `versionCode`、`generatedAt` 或等价快照标识，确保 Web、Server、Wasm 比对的是同一份配置。

## 5. M2 Action 面板值对齐

M2 验证 action 的面板投影值，不跑完整战斗。

Wasm 侧关注：

1. 技能基础值。
2. 属性加成系数。
3. 消耗资源。
4. 冷却时间。
5. 技能等级影响。
6. 当前属性参与后得到的面板展示结果。

Web 侧参考目标：

1. 技能编辑和展示应保留“面板字段”和“计算字段”的区别。
2. 页面可以先服务少量手工 case，不要为了全量技能录入阻塞验证。
3. diff 展示优先按字段展开，而不是只给一个总通过或总失败。

Server 侧参考目标：

1. 技能数据模型优先支持基础值、等级成长、属性系数、消耗、冷却这些 M2 字段。
2. 复杂触发、状态、召唤物、多段文本可以暂缓结构化。
3. 发布数据时要保留版本和配置快照标识，以便和人工记录的游戏版本对应。

## 6. M3 单技能 1v 假人

M3 是第一条真正的计算闭环，但仍不是 1v1。

运行边界：

1. 固定攻击方。
2. 固定假人。
3. 假人不主动行动。
4. 每个 case 只释放一个技能。
5. 先只验证攻击方主动行为和目标受到的直接数值结果。

Wasm 输出应优先证明：

1. 施放是否被接受。
2. 公式输入值。
3. 公式原始输出。
4. 抗性、减免或伤害类型处理后的最终伤害。
5. 攻击方资源消耗和冷却变化。
6. 同输入、同版本、同 seed 的结果可复现。

Web 侧参考目标：

1. 提供最小 case runner 或结果展示，不需要完整战斗编排 UI。
2. 能把 Wasm 输出和人工基线放在同一视图或同一导出记录中。
3. 失败时能保留输入、输出和人工记录，方便跨端 review。

Server 侧参考目标：

1. 数据接口先满足构造单技能 case 的最小 bundle。
2. 不要把完整 1v1 所需的敌方 AI、动作队列和触发链作为 M3 前置条件。
3. 数据缺失时允许使用小样本 fixture 或人工补录 case 推进验证。

## 7. M4 单机制扩展

M4 按机制扩展，不按英雄数量扩展。M4 的目标不是一口气补齐所有战斗复杂度，而是把单个机制拆成可独立验证、可独立回归、可直接交给 Codex `goal` 执行的小闭环。

M4 通用规则：

1. 每个 M4.x 小节都必须绑定一个唯一的 canonical case，并固定 `versionCode`、等价发布快照标识、攻击方、技能、技能等级、目标、前置状态和 seed。
2. canonical case 优先复用 M3 的最小战斗边界：固定攻击方、固定目标、固定一次主动行为，不额外引入无关机制。
3. 每个小节都必须明确回扣到 M1、M2、M3 的字段级证据，不能只给“结果看起来对”。
4. Wasm 侧优先复用现有 `snapshot`、`action_snapshot` 和 M3 结果输出；如果证据面不够，该小节必须把新增 ABI、frame 或宿主展示位标记为阻塞项。
5. Web 侧优先服务人工录入、人工对照、diff 留痕和导出，不以完整战斗编排 UI 为前置条件。
6. 每个小节都要写清本节非目标，避免 `goal` 顺手把相邻机制一起实现。
7. 每个小节都继承第 9 节的 diff 规则：允许存在已归因、已登记、当前不阻塞的差异，但本机制主证据字段不能有未解释 diff。
8. `直伤` 不再视为新增机制，而是后续所有 M4.x 小节的统一回归基准；任何后续机制扩展都不能破坏它。

推荐顺序如下：

1. 直伤回归基准。
2. 资源消耗。
3. 冷却。
4. 护盾。
5. 治疗。
6. 标记施加。
7. 条件命中。
8. DoT。
9. HoT。
10. 多段伤害。
11. 暴击。
12. 随机数。
13. 控制。
14. 打断。
15. 动作 gate。
16. 触发链。
17. 历史窗口。
18. 计数器。
19. 模式强化。

### 7.1 直伤回归基准

1. 目标：把 M3 单技能直伤 case 固化为后续所有 M4.x 的统一回归门槛。
2. 最小 case：直接复用 M3 的 canonical case，不新增前置状态、随机因素或被动触发。
3. 前置输入：复用 M1 的 actor 初始化快照、M2 的 action 面板投影和 M3 的单次施法输入。
4. Wasm 证据：至少保留施法是否被接受、公式输入、公式原始输出、抗性处理后的最终伤害、资源变化和冷却变化。
5. Web 对照：至少能把 M3 的人工基线、Wasm 输出和 diff 结果放在同一条记录里。
6. 回扣链路：属性来源回扣 M1，技能展示字段回扣 M2，单次结算结果回扣 M3。
7. 非目标：不把它扩展成多机制混合 case，也不借机引入双方交互。
8. 通过标准：后续每个 M4.x 小节开始前，直伤基准 case 先通过，且无新的未解释 diff。

### 7.2 资源消耗

1. 目标：验证施法时资源按约定扣减，且扣减结果能独立解释。
2. 最小 case：在直伤基准 case 上只新增资源消耗，不引入回复、返还、折扣或命中后返资源。
3. 前置输入：复用 M1 的资源快照、M2 的 `resourceCosts` 和 M3 的单次施法接受路径。
4. Wasm 证据：至少能看到施法前后资源值、消耗解析值和施法是否因资源不足被拒绝。
5. Web 对照：至少能录入资源面板值、技能消耗值和施法前后资源变化。
6. 回扣链路：资源上限和当前值回扣 M1，消耗字段回扣 M2，施法后资源状态回扣 M3。
7. 非目标：不同时验证冷却、护盾、治疗或条件返还等相邻机制。
8. 通过标准：资源消耗主证据字段无未解释 diff，且不破坏直伤回归基准。

### 7.3 冷却

1. 目标：验证施法后冷却进入、冷却数值和可再次施法时间符合约定。
2. 最小 case：在直伤基准 case 上只新增冷却，不引入减 CD、充能、重置或多段施法。
3. 前置输入：复用 M2 的 `cooldownMs`、`readyAtMs` 和 M3 的单次施法路径。
4. Wasm 证据：至少能看到施法前可施放状态、施法后冷却值、就绪时间和再次施法 gate。
5. Web 对照：至少能录入技能冷却面板值，并展示施法前后 `canCast` 与冷却变化。
6. 回扣链路：冷却展示字段回扣 M2，施法后冷却状态回扣 M3。
7. 非目标：不顺手覆盖资源折扣、连击刷新或时间推进后的完整调度。
8. 通过标准：冷却主证据字段无未解释 diff，且不破坏直伤回归基准。

### 7.4 护盾

1. 目标：验证护盾施加、护盾吸收和护盾剩余量的最小闭环。
2. 最小 case：使用一个固定技能或前置状态给目标施加单层护盾，再用固定直伤命中一次。
3. 前置输入：复用 M1 的生命和护盾快照、M2 的技能面板字段、M3 的单次伤害路径。
4. Wasm 证据：至少能看到护盾施加量、受击前后护盾值、吸收后的最终生命变化。
5. Web 对照：至少能录入护盾面板值、受击前后护盾和生命值。
6. 回扣链路：护盾和生命基础状态回扣 M1，技能展示字段回扣 M2，受击结果回扣 M3。
7. 非目标：不覆盖多层护盾、护盾衰减、转化治疗或反伤。
8. 通过标准：护盾主证据字段无未解释 diff，且直伤基准 case 不受影响。

### 7.5 治疗

1. 目标：验证治疗量、治疗目标生命变化和溢出处理的最小闭环。
2. 最小 case：固定一个受损目标，只施加一次治疗，不叠加护盾、吸血或回复增幅。
3. 前置输入：复用 M1 的生命快照、M2 的治疗相关面板字段和 M3 的单次施法路径。
4. Wasm 证据：至少能看到治疗解析值、治疗前后生命值和是否触发生命上限截断。
5. Web 对照：至少能录入目标受损基线、治疗面板值和治疗后生命结果。
6. 回扣链路：生命基础状态回扣 M1，面板展示字段回扣 M2，单次结算结果回扣 M3。
7. 非目标：不同时覆盖吸血、持续回复、重伤或治疗转护盾。
8. 通过标准：治疗主证据字段无未解释 diff，且不破坏直伤回归基准。

### 7.6 标记施加

1. 目标：验证一次动作能按约定给目标或攻击方施加标记。
2. 最小 case：固定一个施法，只施加一个标记，不要求标记立即触发额外效果。
3. 前置输入：复用 M2 的 effectRows 和 M3 的单次施法接受路径。
4. Wasm 证据：至少能看到标记施加是否成功、标记目标、标记层数或持续状态。
5. Web 对照：至少能录入本次施法预期施加的标记，并展示施法后标记状态。
6. 回扣链路：动作展示字段回扣 M2，施法结果回扣 M3。
7. 非目标：不同时验证条件命中、消耗标记、引爆标记或多层堆叠策略。
8. 通过标准：标记施加主证据字段无未解释 diff，且不破坏直伤回归基准。

### 7.7 条件命中

1. 目标：验证技能在满足或不满足条件时，命中结果按约定分支。
2. 最小 case：固定同一个技能，分别跑“条件成立”和“条件不成立”两个最小输入。
3. 前置输入：复用标记、状态或属性条件输入，以及 M3 的单次施法路径。
4. Wasm 证据：至少能看到条件判定结果、命中是否成立和分支后的最终输出。
5. Web 对照：至少能录入条件前置状态，并展示命中分支和结果差异。
6. 回扣链路：前置状态来源回扣 M1 或上一节标记状态，技能字段回扣 M2，结果回扣 M3。
7. 非目标：不一次性覆盖多条件优先级、复杂脚本判断或触发链联动。
8. 通过标准：条件判定和命中结果主证据字段无未解释 diff，且不破坏直伤回归基准。

### 7.8 DoT

1. 目标：验证持续伤害的施加、tick 触发和每次伤害结果。
2. 最小 case：固定一个技能施加单个 DoT，只观察有限次数 tick，不叠加第二个持续效果。
3. 前置输入：复用标记或状态施加路径、M3 的直伤结算路径和固定时间推进。
4. Wasm 证据：至少能看到 DoT 是否挂上、tick 时间点、每次 tick 的伤害值和剩余持续状态。
5. Web 对照：至少能录入 DoT 面板或说明字段，并展示每次 tick 的时序和结果。
6. 回扣链路：前置施加结果回扣 M3，持续状态可回扣 M1 快照，伤害处理沿用直伤基准。
7. 非目标：不同时验证 HoT、双持续并存、刷新策略或爆炸性结算。
8. 通过标准：DoT 主证据字段无未解释 diff，且直伤基准 case 不受影响。

### 7.9 HoT

1. 目标：验证持续治疗的施加、tick 触发和每次回复结果。
2. 最小 case：固定一个技能施加单个 HoT，只观察有限次数 tick，不叠加其他回复来源。
3. 前置输入：复用治疗基础路径、状态施加路径和固定时间推进。
4. Wasm 证据：至少能看到 HoT 是否挂上、tick 时间点、每次治疗值和生命上限截断。
5. Web 对照：至少能录入 HoT 面板或说明字段，并展示每次 tick 的时序和结果。
6. 回扣链路：生命基础状态回扣 M1，技能展示字段回扣 M2，单次回复逻辑回扣治疗小节。
7. 非目标：不同时覆盖吸血、群体回复、刷新策略或持续效果叠层。
8. 通过标准：HoT 主证据字段无未解释 diff，且直伤基准 case 不受影响。

### 7.10 多段伤害

1. 目标：验证一次施法内多次独立伤害结算的顺序和总结果。
2. 最小 case：固定一个技能，单次施法产生有限段数伤害，不混入 DoT 或触发链。
3. 前置输入：复用 M2 的 effectRows、M3 的直伤路径和固定的段数配置。
4. Wasm 证据：至少能看到每段伤害的顺序、每段结果和总伤害汇总。
5. Web 对照：至少能按段展示人工基线和 Wasm 输出，而不是只显示总和。
6. 回扣链路：技能面板字段回扣 M2，每段伤害处理回扣直伤基准，总体结果回扣 M3。
7. 非目标：不同时覆盖暴击、持续伤害、命中丢失或段间条件变化。
8. 通过标准：多段伤害主证据字段无未解释 diff，且直伤基准 case 不受影响。

### 7.11 暴击

1. 目标：验证暴击是否触发、暴击倍率和暴击后的最终结果。
2. 最小 case：固定一个可暴击动作，在固定 seed 下分别观察暴击和不暴击两种结果。
3. 前置输入：复用 M1 的暴击相关属性、M2 的动作展示字段和 M3 的单次伤害路径。
4. Wasm 证据：至少能看到是否暴击、暴击倍率来源和暴击后的最终伤害。
5. Web 对照：至少能录入暴击率、暴击伤害或等价面板字段，并展示触发结果。
6. 回扣链路：暴击属性来源回扣 M1，技能展示字段回扣 M2，伤害结果回扣 M3。
7. 非目标：不同时覆盖随机数引擎全量验证、连锁暴击或复杂暴击修正。
8. 通过标准：暴击主证据字段无未解释 diff，且固定 seed 下结果可复现。

### 7.12 随机数

1. 目标：验证随机机制在固定 seed 下可复现，在不同 seed 下可解释。
2. 最小 case：固定一个带随机分支的技能或效果，只观察最小必要的随机结果。
3. 前置输入：复用已有动作路径，并显式固定 seed 和随机前置状态。
4. Wasm 证据：至少能看到 seed、随机判定结果和随机分支后的输出。
5. Web 对照：至少能录入 seed，并展示同输入重复运行时的结果稳定性。
6. 回扣链路：动作字段回扣 M2，结果字段回扣 M3，暴击类随机可回扣上一节。
7. 非目标：不一次性验证全局概率平衡、长局分布或 Monte Carlo 类分析。
8. 通过标准：固定 seed 时结果完全可复现，主证据字段无未解释 diff。

### 7.13 控制

1. 目标：验证控制状态的施加、存在和对目标状态的最小影响。
2. 最小 case：固定一个技能施加单个控制状态，只观察状态建立和状态存在。
3. 前置输入：复用状态施加路径、M1 快照和 M2 的 effectRows。
4. Wasm 证据：至少能看到控制状态是否挂上、目标是谁和状态持续信息。
5. Web 对照：至少能录入控制状态的人工基线，并展示施法后状态结果。
6. 回扣链路：状态来源回扣 M2，施法结果回扣 M3，状态展示可回扣 M1 快照。
7. 非目标：不同时验证打断、动作 gate、控制免疫或复杂递减规则。
8. 通过标准：控制主证据字段无未解释 diff，且不破坏直伤回归基准。

### 7.14 打断

1. 目标：验证运行中的动作或引导会因特定事件被打断。
2. 最小 case：固定一个可被打断的动作，固定一个打断来源，只观察一次打断。
3. 前置输入：复用控制或事件输入、动作运行状态和最小时间推进。
4. Wasm 证据：至少能看到动作开始、打断事件、打断后状态和未完成结果。
5. Web 对照：至少能展示打断前动作状态、打断触发点和打断后结果。
6. 回扣链路：动作初始状态回扣 M2，运行结果回扣 M3，控制来源可回扣上一节。
7. 非目标：不同时验证多来源打断优先级、连锁取消或完整调度器恢复策略。
8. 通过标准：打断主证据字段无未解释 diff，且不破坏直伤回归基准。

### 7.15 动作 gate

1. 目标：验证动作在特定状态下能否施放，以及阻塞原因是否可解释。
2. 最小 case：固定一个技能，分别跑“可施放”和“被 gate 阻塞”两个最小输入。
3. 前置输入：复用 M2 的 `canCast`、`blockedReason`、资源和冷却字段，以及控制或标记前置状态。
4. Wasm 证据：至少能看到准入判断顺序、阻塞原因和最终接受或拒绝结果。
5. Web 对照：至少能展示 `canCast`、`blockedReason` 和对应前置条件。
6. 回扣链路：动作初始状态回扣 M2，施法是否成功回扣 M3，相关状态来源回扣 M1 或前序小节。
7. 非目标：不把所有 gate 类型一次性塞进同一个 case，也不要求完整双方调度。
8. 通过标准：gate 主证据字段无未解释 diff，且阻塞原因可稳定复现。

### 7.16 触发链

1. 目标：验证一个明确的事件能触发一个明确的后续效果，并保留触发顺序证据。
2. 最小 case：固定一个起始动作，只允许一层额外触发，不递归扩展更多链条。
3. 前置输入：复用动作结算结果、触发配置和最小事件上下文。
4. Wasm 证据：至少能看到起始事件、触发判定、触发效果和执行顺序。
5. Web 对照：至少能把起始动作和触发动作放在同一条验证记录里。
6. 回扣链路：起始动作回扣 M3，触发条件可回扣标记、状态或计数器相关小节。
7. 非目标：不同时覆盖多层递归触发、反击链或完整被动生态。
8. 通过标准：触发链主证据字段无未解释 diff，且顺序稳定可复现。

### 7.17 历史窗口

1. 目标：验证系统能在有限历史窗口内读取前序事件并影响当前判定。
2. 最小 case：固定一个需要读取最近一次或最近几次事件的技能，只保留最小历史长度。
3. 前置输入：复用前序动作记录、最小时间顺序和当前动作输入。
4. Wasm 证据：至少能看到历史记录被写入、被读取和读取后的当前结果。
5. Web 对照：至少能展示本次判定依赖了哪些前序事件。
6. 回扣链路：前序动作结果回扣 M3，当前动作字段回扣 M2，历史依赖结果回扣触发链或条件命中小节。
7. 非目标：不扩展到完整战斗日志浏览、长窗口统计或复杂回放系统。
8. 通过标准：历史窗口主证据字段无未解释 diff，且窗口边界行为稳定。

### 7.18 计数器

1. 目标：验证计数器的增加、读取、消耗或清空行为符合约定。
2. 最小 case：固定一个只涉及单个计数器的技能或状态，不并行维护多个计数器。
3. 前置输入：复用最小事件序列、计数器前置状态和当前动作输入。
4. Wasm 证据：至少能看到计数器初值、变化过程、读取点和最终值。
5. Web 对照：至少能展示计数器在每一步之后的状态，而不是只看最终结果。
6. 回扣链路：前置事件可回扣 M3 或触发链小节，当前动作字段回扣 M2。
7. 非目标：不同时覆盖多计数器联动、复杂优先级或长局累计行为。
8. 通过标准：计数器主证据字段无未解释 diff，且边界行为可稳定复现。

### 7.19 模式强化

1. 目标：验证某个模式、形态或强化开关会稳定改变技能或属性行为。
2. 最小 case：固定同一个技能，分别跑“普通模式”和“强化模式”两个最小输入。
3. 前置输入：复用 M1 的属性输入、M2 的动作字段和模式开关的最小配置。
4. Wasm 证据：至少能看到模式状态、模式切换后的面板或结算差异和最终输出。
5. Web 对照：至少能录入模式状态，并并排展示普通模式与强化模式结果。
6. 回扣链路：基础属性回扣 M1，动作展示字段回扣 M2，单次结算结果回扣 M3。
7. 非目标：不同时覆盖完整形态系统、全英雄模式树或多阶段进化流程。
8. 通过标准：模式强化主证据字段无未解释 diff，且普通模式直伤基准仍保持稳定。

## 8. M5 小型 1v1 回归

只有当 M1 到 M4 的主要 case 稳定后，才恢复完整双方交互。

M5 的通过标准不是“看起来像能打”，而是：

1. 双方 actor 初始化均可对齐。
2. 双方 action 面板均可对齐。
3. 单技能结果已经独立通过。
4. 调度、控制、触发链的每类 diff 都能回到独立机制 case 排查。
5. 最终 1v1 结果只是组合验证，不再承担首次发现所有数值问题的压力。

## 9. Diff 排查顺序

里程碑通过条件不是零 diff，而是无阻塞级未解释 diff。允许存在已归因、已登记、暂不影响当前阶段的非阻塞差异。

发现 diff 时按以下顺序排查：

1. 人工记录是否抄错、漏记录版本或训练环境。
2. 游戏面板是否存在取整、隐藏修正或显示口径差异。
3. Web/Server 字段映射是否丢失等级、装备、符文、技能等级或版本。
4. Server 数据是否缺字段、字段类型错误或发布版本不一致。
5. Web bundle 编译是否把字段转换成了错误的 Wasm 输入。
6. Wasm 公式、属性读取、资源读取或伤害结算是否实现错误。
7. Wasm runtime 调度、状态或事件顺序是否影响了结果。

## 10. 明确非目标

以下内容不作为 M1 到 M3 的阻塞项：

1. 自动从游戏客户端采集训练营数据。
2. 全量英雄、装备、符文、技能覆盖。
3. 完整 1v1 双方动作调度。
4. 敌方 AI 或自动循环释放。
5. 复杂控制状态、反击触发链和多机制叠加。
6. 面向最终用户的完整模拟页面。
7. 后端完整数据治理闭环。

这些能力仍是长期方向，但必须在最小验证闭环稳定后逐步纳入。

## 11. 验证计划文档边界

本文是里程碑 gate 文档，不是具体执行计划。后续验证工作应补充单独的“验证计划”文档，负责把这里的阶段目标转成可执行 case。

验证计划的基本边界如下：
1. 一个验证计划对应一个最小闭环，不要把多个机制、多个英雄或多个目标混写在同一份计划里。
2. `M1`、`M2` 可以各自有阶段级计划；`M3` 应按 canonical case 写计划；`M4` 应按 `M4.x` 机制小节写计划；`M5` 只作为组合回归入口。
3. 验证计划必须写清输入构造、游戏侧基线来源、Wasm 输出字段、对照表结构、误差口径、通过标准和升级规则。
4. 验证计划服务开发 agent、验收 sub agent 和人工复核；实际执行结果应落单独测试记录，不回填进本 overview 文档正文。
5. 验证计划的详细写法见 `文档记录/详细设计/验证计划编写说明.md`。
