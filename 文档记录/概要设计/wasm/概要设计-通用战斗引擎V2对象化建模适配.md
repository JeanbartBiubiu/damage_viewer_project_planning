# 概要设计：通用战斗引擎 V2 对象化建模适配

> 日期：2026-04-11
> 状态：草案
> 对应主文档：[概要设计-通用战斗引擎V2架构.md](./概要设计-通用战斗引擎V2架构.md)
> 目标：说明 V2 各章节如果采用“对象化状态组织 + 中央事件管线执行”的实现口径，应如何落地

---

## 1. 文档目的

这份文档不推翻 V2 主架构稿，而是回答一个更具体的问题：

- 如果运行时状态按对象聚合来组织，V2 各章节该怎么适配
- 哪些地方适合对象化
- 哪些地方必须继续坚持中央管线、中央事件队列、统一 damage/heal/modifier/shield 通道

本文中的“对象化建模”不是经典面向对象互调，而是以下口径：

- `ActorRuntime`、`SkillRuntimeRef`、`ItemRuntimeRef`、`StatusInstance` 等运行时数据按对象聚合
- 对象可以持有自己的配置引用、局部状态、订阅关系
- 事件排序、事件分发、伤害结算、日志输出、RNG 消费仍由中央引擎控制
- 对象之间不直接相互调用，不绕开中央管线直接改对方状态

一句话结论：

- `状态组织` 可以对象化
- `执行拓扑` 仍应保持事件驱动和过程式管线

---

## 2. 先给结论

推荐把 V2 实现成下面这种混合模型，而不是二选一：

| 层次 | 推荐风格 | 原因 |
|------|----------|------|
| 运行时状态容器 | 对象化聚合 | 便于表达角色、技能、装备、状态实例的归属关系 |
| 事件调度 | 中央过程式 | 需要稳定顺序、确定性、可回放 |
| 伤害/治疗/护盾/修改器管线 | 中央过程式 | 需要统一结算顺序和统一日志 |
| 公式求值 | 无状态服务 | 公式天然适合纯函数/纯服务化 |
| 触发订阅 | 中央索引 + 对象持有订阅声明 | 避免对象互相遍历和互调 |
| 子系统实现 | trait/handler + runtime state | 便于解耦和单测 |

因此，V2 不应该实现成：

- `target.onDamageTaken()` 里直接回调 `thornmail.onHit()`
- `thornmail` 再直接调用 `attacker.takeDamage()`

V2 更适合实现成：

1. `damage_apply` 在中央管线中完成
2. 派生 `on_damage_taken`
3. 中央 `TriggerIndex` 找到订阅该事件的 effect handle
4. 对应对象化 effect 产出标准 action / packet
5. action / packet 再回到中央通道结算

对象只负责“我拥有什么能力、我当前有什么状态、我订阅了什么事件”，不负责“我自己决定何时越权执行整个战斗流程”。

## 3. 推荐的对象模型边界

### 3.1 静态模板层

```rust
struct EngineBundle {
    actor_templates: HashMap<ActorTemplateId, ActorTemplate>,
    skill_templates: HashMap<SkillTemplateId, SkillTemplate>,
    item_templates: HashMap<ItemTemplateId, ItemTemplate>,
    status_templates: HashMap<StatusTemplateId, StatusTemplate>,
    formula_catalog: FormulaCatalog,
    subsystem_templates: HashMap<SubsystemType, SubsystemTemplate>,
}
```

这一层的对象是模板，不带战斗时态。

### 3.2 编译快照层

```rust
struct CompiledSnapshot {
    compiled_formulas: CompiledFormulaCatalog,
    trigger_index: TriggerIndex,
    action_catalog: ActionCatalog,
    pipeline_registry: PipelineRegistry,
    actor_blueprints: [ActorBlueprint; 2],
}
```

这一层把配置编译成执行时更容易消费的数据。

### 3.3 运行时状态层

```rust
struct RuntimeState {
    now_ms: u32,
    rng: RngRuntime,
    queue: EventQueue,
    self_actor: ActorRuntime,
    enemy_actor: ActorRuntime,
    subsystems: SubsystemRuntimeRegistry,
    diagnostics: RuntimeDiagnostics,
}

struct ActorRuntime {
    actor_id: ActorId,
    attrs: AttributeMap,
    skills: Vec<SkillRuntimeRef>,
    items: Vec<ItemRuntimeRef>,
    statuses: Vec<StatusInstance>,
    resources: ResourceStateMap,
    counters: CounterStateMap,
    history: HistoryStateMap,
}
```

这里的对象化重点是“归属关系”和“局部状态归档”，不是让对象互相驱动执行。

### 3.4 中央服务层

```rust
struct EngineServices {
    formula_engine: FormulaEngine,
    pipeline_runner: PipelineRunner,
    event_dispatcher: EventDispatcher,
    trigger_dispatcher: TriggerDispatcher,
    validation: ValidationService,
}
```

这里仍由中央服务驱动，对象只作为输入上下文。

## 4. V2 各章节的对象化适配

## 4.1 第 1 章：设计目标

原文的 6 个目标不需要改，只需要重新解释对象化边界：

| 目标 | 对象化适配口径 |
|------|----------------|
| G1 零硬编码 | 对象里不能塞游戏专属逻辑分支；对象只引用配置和 runtime state |
| G2 子系统解耦 | 不允许 `SkillRuntime` 直接调用 `ShieldSubsystemRuntime` 之类对象 |
| G3 公式外置 | 对象不自带业务公式，只持有 `formula_id`、`table_id`、`tag` |
| G4 游戏无关 | `ActorRuntime` 是通用 runtime actor，不是 LoLChampion 类 |
| G5 功能完备 | 对象字段可以是通用 slot/map，不要求为每个游戏单独开类层级 |
| G6 1v1 拓扑 | 仍固定 `self/enemy` 两个 ActorRuntime；对象化不改变拓扑约束 |

结论：

- 对象化不应侵蚀“配置驱动”和“游戏无关”
- 如果对象设计逼着我们写 `AkaliSkillE2Runtime` 这种类，说明已经跑偏

## 4.2 第 2 章：架构总览

主文档里的架构图可以按对象化补成下面的理解：

- Host、WASM ABI、Rust Engine Core 不变
- `Attr Store` 可以变成 `ActorRuntime.attrs`
- `Subsystem Registry` 可以变成 `SubsystemRuntimeRegistry`
- `Damage Pipeline` 仍是中央组件，不下沉到对象方法
- `Simulation Loop` 仍是中央循环，不交给对象自治

对象化后的心智模型应该是：

```text
Engine Core
  ├─ RuntimeState
  │   ├─ self_actor: ActorRuntime
  │   ├─ enemy_actor: ActorRuntime
  │   └─ subsystem states
  ├─ EventQueue
  ├─ TriggerIndex
  ├─ PipelineRunner
  └─ FormulaEngine
```

不是：

```text
SelfActor.attack(EnemyActor)
EnemyActor.onHit(SelfActor)
EnemyActor.items[i].react(SelfActor)
```

## 4.3 第 3 章：核心概念

### 4.3.1 3.1 Attribute Store

适配方式：

- `AttributeStore` 仍然是铺平 `HashMap<String, f64>`
- 只是它的归属从“游离全局 store”变成 `ActorRuntime.attrs`
- 如果存在 pair 级、skill 级、status 级临时值，仍然不要挤进 actor attrs，而应放独立 runtime state

推荐：

```rust
struct ActorRuntime {
    attrs: HashMap<String, f64>,
    derived_attrs: HashMap<String, f64>,
}
```

不推荐：

- 为每个属性族建一棵深层对象树，例如 `actor.hp.current/max/base`
- 这会让公式引用退化成路径访问，反而破坏 V2 想要的 flat attr key

### 4.3.2 3.2 Formula Engine

适配方式：

- 公式引擎仍然是独立服务
- `FormulaRuntimeView` 可以从对象化 runtime 中取值
- 对象本身不负责解析公式 AST

对象化收益主要体现在 `view` 的数据来源更清晰：

- `source_actor.attrs`
- `target_actor.statuses`
- `packet.flags`
- `history_window`

### 4.3.3 3.3 Event Queue

适配方式：

- `EventQueue` 仍然是中央最小堆/批处理队列
- 事件负载里可以保存对象 handle，例如 `actor_id`、`status_instance_id`、`execution_id`
- 不要把事件队列拆成每个对象自己的 inbox

原因：

- 多对象 inbox 会让全局时序比较难统一排序
- 中央堆更容易保证确定性和 debug 可回放

## 4.4 第 4 章：子系统框架

### 4.4.1 4.1 设计原则

对象化后的子系统原则应改写成：

- 子系统状态可以对象化保存
- 子系统执行仍由中央 registry 调度
- 子系统只读写允许的 runtime state，不直接调其他子系统对象方法

推荐形态：

```rust
trait SubsystemHandler {
    fn on_internal_event(&mut self, ctx: &mut EngineContext, event: &InternalEvent);
    fn on_trigger(&mut self, ctx: &mut EngineContext, trigger: &TriggerEvent);
    fn register_pipeline_stages(&self, registry: &mut PipelineRegistry);
}
```

### 4.4.2 4.2 子系统间通信

主文档里的两条通道继续成立，只是对象化后边界更清晰：

- 持久状态：写入 `ActorRuntime` / `PairRuntimeState` / `SubsystemRuntimeState`
- 单次结算上下文：写入 `PipelineContext` / `TriggerContext`

不建议新增“对象直接调对象”作为第三条通信渠道。

### 4.4.3 4.3 子系统类型目录

目录不需要因为对象化而重写。

真正需要补的只是“每类状态归属到哪里”：

- actor 级：资源、护盾、暴击计数、控制状态、装备持有
- pair 级：每目标冷却、mark source-target 关系、锁定窗口
- action/execution 级：cast stage、剩余充能、执行中实例
- scheduler 级：dot/hot/status 过期事件

### 4.4.4 4.4 每个子系统的配置结构

适配方式：

- 配置结构保持 JSON 可编译形态
- 运行时对象只持有编译后的引用和 instance state

例如：

```rust
struct ItemRuntimeRef {
    item_id: String,
    template_ref: ItemTemplateRef,
}

struct StatusInstance {
    instance_id: String,
    template_ref: StatusTemplateRef,
    expires_at_ms: Option<u32>,
    stacks: u32,
}
```

## 4.5 第 5 章：Damage Pipeline

这一章是最不能被 OO 互调污染的地方。

适配方式：

- `DamagePacket` 仍然是通道标准输入
- `PipelineRunner` 仍然按固定阶段执行
- 对象化只影响“谁提供上下文”，不影响“谁决定顺序”

推荐流程：

1. 某个对象化 effect 产出 `DamagePacketIntent`
2. 中央引擎把 intent 规范化成 `DamagePacket`
3. `PipelineRunner` 处理暴击、增减伤、穿透、减伤、霸体/0 伤害、护盾、HP 扣减
4. 结算完毕后才派生 `on_damage_dealt / on_damage_taken`

反甲就是典型例子：

- 反甲能力挂在受击者的 `items` 列表里
- 但不是物品对象自己直接回击
- 而是受击后派生 trigger，再由中央 runner 产出反向 `DamagePacket`

## 4.6 第 6 章：Action 系统

对象化后，这一章可以更自然。

推荐拆分：

```rust
struct ActionTemplate {
    action_id: String,
    behavior_tags: Vec<String>,
    effects: Vec<EffectHandle>,
}

struct ActionRuntimeState {
    action_id: String,
    cooldown_until_ms: u32,
    charges: u32,
    cast_stage: Option<String>,
}
```

主动技能、被动技能、装备被动都可以统一看成“能力对象”，但是否进入决策循环不同：

- 主动能力：进入 `ActionSelector`
- 被动能力：通过 `TriggerIndex` 订阅触发事件
- 状态能力：由 `StatusInstance` 驱动

因此，“技能在对象的技能列表里”是合理的；但真正执行时仍然由中央系统做：

- 可施放性检查
- 资源扣减
- 进入执行阶段
- 触发 effect
- 安排后续事件

## 4.7 第 7 章：配置模型（EngineInitPayload V2）

适配方式：

- `EngineInitPayload` 仍然是纯数据
- 编译阶段把纯数据转成对象模板和索引
- 运行阶段实例化成 `ActorRuntime`、`StatusInstance`、`ActionRuntimeState`

建议把“对象化”只出现在编译后和运行时，不要把接口协议本身改成 OOP 风格 payload。

也就是：

- payload 里仍然传数组、映射、配置块
- 不传“对象行为”
- 不传脚本闭包

## 4.8 第 8 章：WASM 接口

对象化不应泄露到 ABI。

WASM 接口仍应保持：

- `engine_init(payload_json)`
- `engine_run(run_input_json)`
- `engine_response_ptr/len`

对象化只是内部组织方式，外部不应知道 Rust 内部到底是 struct 组合还是过程式表驱动。

这样有两个好处：

- ABI 稳定
- 后续内部重构不会传染到前端

## 4.9 第 9 章：从 MVP 继承的模块

适配口径：

- 从 MVP 继承的是“可复用执行能力”，不是“类层级”
- 例如公式编译、事件排序、伤害分量、回归日志，都可以直接保留成中央模块

对象化主要作用于：

- 运行时状态布局
- trigger 订阅归属
- 能力实例引用

不需要为了对象化去重写成熟的基础服务。

## 4.10 第 10 章：子系统详细规格

这一章最适合补“状态归属表”。建议如下：

| 子系统 | 主要运行时归属 | 是否进入中央管线 | 对象化适配要点 |
|--------|----------------|------------------|----------------|
| mitigation | `PipelineRunner` + actor attrs | 是 | 不做对象方法，作为 damage stage |
| penetration | `PipelineRunner` + actor attrs | 是 | 只读 source/target attrs |
| critical_strike | actor crit state + `PipelineRunner` | 是 | 暴击资格/倍率由中央 packet 解析 |
| shield | `ActorRuntime.statuses` 或 `shield_state` | 是 | 护盾实例归 actor，吸收顺序归中央 |
| life_steal | actor attrs | 是 | 回复行为仍走 heal 通道 |
| dot | `Scheduler` + `StatusInstance` | 是 | dot 实例对象化，tick 调度中央化 |
| crowd_control | `ActorRuntime.statuses` | 是 | 状态实例归 actor，控制链路归中央 |
| resistance_modifier | actor or target-bound status | 是 | 层数实例可对象化，抗性读取统一 |
| cooldown | `ActionRuntimeState` | 否 | 冷却状态归 action runtime |
| attack_speed | actor attrs + derived stats | 否 | 只影响基础节奏，不单独对象调度 |
| regen | actor attrs + scheduler | 是 | 回复包走 heal 通道 |
| conversion | actor attrs + compiled rules | 否 | 初始化/重算服务，不是对象行为 |
| resource | `ResourceStateMap` | 否 | mana/energy/ferocity 等归 actor |

补充归属建议：

- `mark_state` 更适合 pair 级或 target-bound status
- `per_target_lockout` 更适合 pair 级 map
- `damage_history_window` 更适合 actor 级 history buffer
- `defensive_window` 更适合 actor 状态实例 + damage stage gate

## 4.11 第 11 章：DamageTypeTag 系统

适配方式：

- `DamageTypeTag` 仍然挂在 `DamagePacket` / `EffectIntent`
- 对象只负责声明自己产生什么 tag
- 是否命中某条规则，由中央 `PipelineRunner` 和 `TriggerDispatcher` 判断

不要把 tag 判定逻辑埋进对象方法里。

## 4.12 第 12 章：引擎不再包含的东西

对象化后更要坚持这一章：

- 不引入英雄专属类
- 不引入物品专属类
- 不引入游戏语义专属接口
- 不让对象自己决定战斗大流程

否则对象模型会重新把游戏逻辑写死进 Rust。

## 4.13 第 13 章：实施阶段建议

如果按对象化落地，实施顺序建议调整为：

1. 先定 `RuntimeState / ActorRuntime / ActionRuntimeState / StatusInstance / PairState`
2. 再定中央 `EventQueue / TriggerIndex / PipelineRunner`
3. 然后把子系统逐个接到统一管线
4. 最后再做对象级 helper、builder、diagnostics

不要先写一堆对象方法，再回头补中央事件流。

## 4.14 第 14 章：Fail-Fast 校验规则

适配方式：

- 模板层校验：对象模板构造前完成
- 编译层校验：trigger 引用、formula id、pipeline binding 在 snapshot compile 阶段完成
- 运行时校验：handle 查找失败、状态实例缺失、非法事件载荷在 dispatch 阶段 fail-fast

对象化会新增两类校验：

- runtime handle 是否悬空
- 某类状态是否被错误归属到 actor/pair/action 错层

## 4.15 第 15 章：RNG 契约与回放保证

对象化后 RNG 仍应集中保存在 `RuntimeState` 或 `RngRuntime` 中。

不建议：

- 每个技能对象各自持有随机器
- 每个装备对象各自自由消费随机数

推荐：

- 中央 RNG 按 `seed_key` 分序列
- 对象只声明“我要消费哪条随机序列”
- 真正消费由公式引擎/trigger runner 执行

这样回放不会因为对象遍历顺序变化而漂移。

## 4.16 第 16 章：Payload 编译契约

这一章是对象化最重要的落点之一。

推荐编译流水线：

1. 解析 JSON payload
2. 编译公式、校验引用
3. 生成对象模板：
   - `ActorTemplate`
   - `SkillTemplate`
   - `ItemTemplate`
   - `StatusTemplate`
4. 生成中央索引：
   - `TriggerIndex`
   - `ActionCatalog`
   - `PipelineRegistry`
5. 根据 run input 实例化 `RuntimeState`

也就是说：

- payload 编译阶段负责“把纯数据变成对象模板 + 中央索引”
- run 阶段负责“把对象模板变成运行时实例”

## 4.17 第 17 章：开放问题

对象化后，开放问题应主要集中在这些边界，而不是“要不要纯 OO”：

- 哪些状态归 actor，哪些归 pair，哪些归 action execution
- `StatusInstance` 是否统一承载 dot/shield/cc/mark
- `TriggerIndex` 是否按事件类型 + owner scope 双层索引
- `ActionRuntimeState` 和 `ExecutionInstance` 是否拆开

这些都是真问题；“要不要把引擎改成对象互调”不是。

## 5. 反甲示例：对象化后应该怎么走

对象化语义可以这样表达：

- 敌方 `ActorRuntime.items` 持有一个 `Thornmail` item ref
- 该 item ref 编译时声明：
  - 订阅 `on_damage_taken`
  - 触发条件：这次伤害 `can_trigger_on_hit = true`
  - 产出效果：`deal_damage(formula=retaliate_formula, source=owner, target=attacker, damage_type=magic)`

但执行流仍然必须是中央的：

1. 我方普攻生成 `DamagePacket`
2. `PipelineRunner` 结算护盾/减伤/HP
3. 派生 `on_damage_taken`
4. `TriggerIndex` 找到反甲订阅
5. 反甲 effect 构造反向 `DamagePacket`
6. 反向 `DamagePacket` 再回到 `PipelineRunner`

这个模型兼顾两点：

- 业务语义上，反甲确实“挂在被攻击者身上”
- 工程实现上，顺序、日志、RNG、shield/crit/mitigation 仍统一

## 6. 推荐的最小实现口径

如果要把这套对象化适配真正写进 V2 实现，我建议先拍板下面 8 条：

1. `ActorRuntime` 是对象化状态容器，但不拥有执行主循环。
2. `SkillRuntimeRef / ItemRuntimeRef / PassiveRef` 只持有模板引用和少量局部状态，不互相直调。
3. 一切实际数值结算都进入四通道 runner：`damage / heal / modifier / shield`。
4. 一切触发都先变成标准 `TriggerEvent`，再由中央 `TriggerIndex` 分发。
5. `PairState` 是一等公民，用来承载 mark、每目标冷却、锁定窗口。
6. `ExecutionInstance` 独立于 `ActionRuntimeState`，用来承载施法阶段、飞行体、延迟结算等时态对象。
7. `StatusInstance` 可统一承载 shield/cc/dot/mark/defensive_window 等时态状态。
8. ABI 和 payload 仍保持数据驱动，不暴露内部对象实现细节。

## 7. 与主文档的关系
