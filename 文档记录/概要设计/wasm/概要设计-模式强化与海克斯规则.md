# WASM 模式强化与海克斯规则概要设计（V1 草案）

## 1. 目标

本文补充 WASM 在“模式强化 / 海克斯 / 第三方局内强化”上的统一设计，重点解决以下场景：

- 像 Arena 海克斯这样，不属于英雄技能、也不属于装备技能，但会参与局内结算的强化系统
- 属性转换、属性封顶、溢出属性转收益这类模式级规则
- 技能暴击、持续伤害暴击、治疗/护盾暴击这类“改伤害资格”的规则
- 既有“像技能一样触发”的强化效果，也有“像全局规则一样改口径”的强化效果
- 在不硬编码 LoL 专用逻辑的前提下，为其他游戏保留同类扩展位

本文边界：

- 只讨论“进入引擎后如何表达与结算”
- 不讨论前端选秀 UI、刷新商店、随机池抽取
- 不讨论数据库物理表设计细节；只定义 WASM 侧需要的 bundle / run / runtime 结构

---

## 2. 结论先行

### 2.1 设计结论

- 模式强化是 **一类独立于 hero / item / rune 的运行时能力来源**，不应直接并入某个英雄技能 JSON。
- “像技能的强化效果”可以继续复用 `skills + mechanicsConfig`，但“像全局规则的强化效果”必须进入 **模式级规则层**。
- 推荐新增三层能力：
  - `AugmentDTO`：静态定义“这个强化是什么”
  - `selectedAugmentIds`：运行时声明“本局这个单位带了哪些强化”
  - `derived rules + damage policies`：表达“这些强化如何改属性口径、改暴击资格、改伤害通道”
- 对于属性转换类海克斯，必须把属性拆成 **raw / effective / overflow / converted** 多套口径，否则会算错。
- 对于暴击类海克斯，不能只靠 `canCrit: boolean`，必须改成 **`DamagePacket.tags + crit policy + 模式规则`** 的组合。

### 2.2 对当前体系的判断

当前文档里已经有几个很适合承接这类能力的点：

- `mechanicsConfig`：适合承接“像技能一样触发”的强化效果
- `DamagePacket.tags`：适合承接“这段伤害属于什么类型”
- `combat_rule_profiles`：适合承接“标签如何变成全局行为”
- 派生属性思路：移动速度文档已经证明“复杂属性口径”不应塞回普通 modifier 叠加

因此推荐方案不是重写现有技能模型，而是 **在现有模型上补模式强化层**。

## 3. 设计原则

### 3.1 强化归属与强化效果分离

“这个强化是什么”和“这个强化会做什么”不是一回事：

- `AugmentDTO` 负责定义：
  - 唯一 ID
  - 名称 / 稀有度 / 图标 / 描述
  - 技能引用
  - 派生规则
  - 伤害策略
- 真正执行时：
  - 技能型效果走 `mechanicsConfig`
  - 规则型效果走 `derived rules / damage policies`

这样做的好处是：

- 强化可以拥有多个技能效果
- 强化也可以完全没有技能，只改规则
- 前端和运行时都能明确区分“展示元数据”和“结算逻辑”

### 3.2 模式规则不能硬塞进英雄技能

像下面这些效果，如果直接塞进英雄技能 JSON，会导致语义污染：

- 固定攻速，同时把多余攻速转攻击力
- 允许技能暴击
- 允许持续伤害暴击
- 暴击率溢出转其他属性
- 法强与额外攻击力互转

这些效果都不是某个英雄技能“自身拥有”的能力，而是 **当前对局模式赋予该单位的附加规则**。

### 3.3 派生属性必须分阶段计算

属性转换类规则最大的风险不是“公式难写”，而是：

- 来源口径不清
- 覆盖顺序不清
- 溢出值与最终值混用
- 双向转换形成死循环

因此模式强化规则必须运行在一个 **分阶段的派生属性流水线** 上，而不是临时在任意地方读写属性表。

### 3.4 暴击资格用标签和策略表达

对模式强化来说，“能否暴击”不是一个固定布尔值，而是：

- 这段伤害本身属于什么类别
- 当前单位携带了哪些强化
- 模式规则如何解释这些标签
- 暴击倍率由哪一层提供

所以推荐使用：

- `DamagePacket.tags`
- `DamagePacket.critPolicy`
- `activeDamagePolicies`

而不是只增加一个 `canCrit`

### 3.5 规则必须可复现、可解释、可拒绝

同一 `bundle + input + seed` 必须可复现，因此模式强化规则需要：

- 固定结算阶段
- 固定优先级
- 固定聚合方式
- 循环依赖检测
- 冲突时明确拒绝初始化，而不是运行时默默覆盖

## 4. 适用场景分类

推荐先把模式强化能力分成三大类：

### 4.1 技能型强化

特征：

- 可以写成某个事件触发的效果
- 本质仍然是 `deal_damage / apply_modifier / heal / shield`

示例：

- 施放大招后获得攻速
- 普攻附带额外伤害
- 每次技能命中叠层

推荐承载方式：

- 继续复用 `skills`
- 强化本身通过 `grantedSkillRefs` 或 `ownerType = augment` 的 skill 归属来挂载

### 4.2 派生属性型强化

特征：

- 会修改属性口径
- 通常不是一次触发，而是持续生效

示例：

- 固定攻速
- 多余攻速转攻击力
- 法强转额外攻击力
- 额外攻击力转法强
- 技能急速转移速

推荐承载方式：

- `derivedRules`
- 运行在派生属性刷新节点

### 4.3 伤害策略型强化

特征：

- 不直接产生数值，而是改变伤害包的解释方式

示例：

- 技能可以暴击
- 持续伤害可以暴击
- 治疗/护盾可以暴击
- 某类伤害使用不同倍率

推荐承载方式：

- `damagePolicies`
- 作用于 `DamagePacket / HealPacket / ShieldPacket`

## 5. Bundle 与 Run 输入扩展

## 5.1 推荐的 Bundle 扩展

```ts
export type EngineBundleV1 = {
  meta: {
    gameId: string
    versionId: number
    versionCode: string
    dataHash: string
    generatedAt: string
  }

  attributeDefinitions: AttributeDefinitionDTO[]
  types?: TypeDTO[]
  typeRelations?: TypeRelationDTO[]

  heroes: HeroDTO[]
  skills: SkillDTO[]
  items: ItemDTO[]
  augments?: AugmentDTO[]

  combatRuleProfiles?: CombatRuleProfileDTO[]
}
```

说明：

- `augments` 定义“有哪些模式强化”
- `combatRuleProfiles` 定义“这些强化带来的标签与规则如何解释”
- 如果短期内 `combatRuleProfiles` 还没进入 bundle，也可以先把规则内联到 `AugmentDTO`

## 5.2 `AugmentDTO`

```ts
export type AugmentDTO = {
  augmentId: string
  ownerType: string        // 建议对 Arena 用 "hex"
  systemKey: string        // 例如 "arena"
  name?: string
  description?: string
  rarityCode?: string
  iconUrl?: string

  tags?: string[]
  grantedSkillRefs?: string[]
  derivedRules?: DerivedRuleSpec[]
  damagePolicies?: DamagePolicySpec[]
}
```

语义：

- `grantedSkillRefs`：像技能的强化效果
- `derivedRules`：改属性口径
- `damagePolicies`：改伤害/治疗/护盾的暴击或解释方式

## 5.3 Run 输入扩展

```ts
export type CombatantInit = {
  heroId: string
  level?: number
  itemIds?: string[]
  augmentIds?: string[]
}
```

说明：

- 模式强化属于本局输入，而不是英雄模板固有数据
- 同一英雄在不同局可以带不同强化
- 当前 1v1 MVP 可认为 `augmentIds` 在 run 开始时固定，不支持中途替换

## 6.1 `CombatantRuntime` 建议补充

```ts
type CombatantRuntime = {
  attrs: Record<string, number>
  hp: number
  maxHp: number

  augmentIds: string[]

  activeDamagePolicies: DamagePolicySpec[]
}
```

## 6.2 推荐显式区分的常见属性口径

以下字段不要求一次性全部落地，但推荐优先把最容易出错的几组拆开：

```ts
type DerivedAttrSnapshot = {
  attack_speed_bonus_raw: number
  attack_speed_total_raw: number
  attack_speed_current: number
  attack_speed_overflow: number
  attack_damage_bonus_from_attack_speed: number

  crit_chance_raw: number
  crit_chance_current: number
  crit_chance_overflow: number

  move_speed_raw: number
  move_speed_final: number
}
```

说明：

- `*_raw`：常规装备、buff、成长都加完后，但还没被模式规则改写
- `*_current` / `*_final`：最终用于常规结算的口径
- `*_overflow`：超过封顶、阈值或固定值之后留下来的可转化部分
- `*_from_*`：某种转换规则的产物

## 7. 派生属性流水线

## 7.1 推荐结算阶段

```text
1. base/template
2. raw aggregation
3. derived pre-cap
4. cap / set-final / override
5. overflow conversion
6. final aggregation
7. skill formula read
8. damage/heal/shield packet resolution
```

各阶段含义：

### 7.1.1 `base/template`

- 英雄基础属性
- 等级成长
- 默认模板值

### 7.1.2 `raw aggregation`

- 装备、技能、自身 buff、敌方 debuff 带来的常规加成
- 此时只得到“原始属性口径”

### 7.1.3 `derived pre-cap`

- 从 raw 属性推导出其他中间属性
- 不做最终锁定或覆盖

### 7.1.4 `cap / set-final / override`

- 固定值覆盖
- 上下限截断
- 特殊模式规则锁定

### 7.1.5 `overflow conversion`

- 计算封顶后溢出的部分
- 把溢出转换成其他属性收益

### 7.1.6 `final aggregation`

- 汇总最终可供普通规则读取的属性
- 例如 `attack_damage_current`

### 7.1.7 `skill formula read`

- 技能公式明确声明自己读取哪一套属性口径

### 7.1.8 `packet resolution`

- 伤害/治疗/护盾通道结合 packet tags 和 damage policies 做最终解释

## 7.2 刷新时机

建议在以下事件后统一触发一次派生属性刷新：

- run 初始化
- 获得或失去装备
- 获得或失去状态
- 获得或失去模式强化
- 影响派生属性的层数变化

这与移动速度的“派生属性更新节点”思路保持一致，不建议每次读属性时临时重算。

## 8. 派生规则原语

## 8.1 目标

模式强化不应该为每个海克斯单独写一段特判代码，而应抽象成少量可复用原语。

推荐先支持以下 5 种：

```ts
type DerivedRuleKind =
  | "derived_stat"
  | "full_convert"
  | "overflow_convert"
  | "set_final"
  | "clamp_final"
```

## 8.2 `DerivedRuleSpec`

```ts
export type DerivedRuleSpec = {
  ruleId: string
  kind: DerivedRuleKind
  priority?: number

  readStage: "raw" | "pre_cap" | "post_cap" | "overflow" | "final"
  writeStage: "pre_cap" | "post_cap" | "overflow" | "final"

  sourceAttr?: string
  sourceAttrs?: string[]
  targetAttr: string

  formulaText?: string
  thresholdFormulaText?: string
  fixedValueFormulaText?: string

  aggregationMode?: "add" | "set_final" | "pick_max"
  consumeSource?: boolean
}
```

约束：

- `writeStage` 不能早于 `readStage`
- `set_final` 与 `consumeSource` 冲突时必须显式报错或定义优先级
- 同一 `targetAttr` 的多个 `set_final` 规则如果同时命中，应按 `priority` 决定唯一结果

## 8.3 各原语语义

### 8.3.1 `derived_stat`

从已有属性推导出另一个属性，但不消耗来源。

适用：

- 技能急速转移速
- 法强转技能急速

### 8.3.2 `full_convert`

把某个来源属性整体按比例转换到另一个属性。

适用：

- 额外攻击力转法强
- 法强转额外攻击力

注意：

- 是否消耗来源必须显式配置
- 如果消耗来源，来源最终口径要被覆盖或置零，不能只做一次“目标加值”

### 8.3.3 `overflow_convert`

把超过阈值或固定值的部分转换到另一属性。

适用：

- 多余攻速转攻击力
- 超过 100% 的暴击率转其他属性

### 8.3.4 `set_final`

直接把目标属性设为某个最终值。

适用：

- 攻速固定为某值
- 移速固定为某值

### 8.3.5 `clamp_final`

把目标属性限定在上下限之间。

适用：

- 模式级属性封顶
- 特殊场景最小值保护

## 9. 暴击策略模型

## 9.1 为什么不能只用 `canCrit`

`canCrit` 只能表达“能不能”，但表达不了：

- 默认不能，海克斯开启后能
- 技能暴击和持续伤害暴击是两套来源
- 暴击倍率由强化定义，而不是技能自带
- 治疗/护盾也可能存在暴击

因此推荐把暴击拆成三层：

- packet tags
- packet crit policy
- active damage policies

## 9.2 `DamagePacket` 扩展

现有 `DamagePacket.tags` 设计可以继续复用，推荐增加 `critPolicy`：

```ts
type CritPolicy = {
  mode: "never" | "native" | "rule_enabled"
  baseMultiplierFormulaText?: string
  bonusMultiplierFormulaText?: string
}

type DamagePacket = {
  packetId: string
  sourceId: string
  targetId: string
  damageType: string
  rawAmount: number
  postMitigationAmount: number
  tags: string[]
  critPolicy?: CritPolicy
}
```

说明：

- `never`：永不暴击
- `native`：技能自身就允许暴击
- `rule_enabled`：只有当模式规则命中时才允许暴击

## 9.3 `DamagePolicySpec`

```ts
export type DamagePolicySpec = {
  policyId: string
  appliesToPacketKind: "damage" | "heal" | "shield"
  requireAnyTags?: string[]
  requireAllTags?: string[]

  enableCrit?: boolean
  overrideBaseMultiplierFormulaText?: string
  extraMultiplierFormulaText?: string
}
```

说明：

- 技能可暴击海克斯：匹配 `crit_type_skill`
- 持续伤害可暴击海克斯：匹配 `damage_pattern_dot`
- 治疗/护盾暴击海克斯：分别作用于 `heal` 或 `shield`

## 9.4 暴击判定流程

```text
1. 技能 action 生成 DamagePacket / HealPacket / ShieldPacket
2. packet 自带 tags 与 critPolicy
3. 读取单位当前 activeDamagePolicies
4. 找出命中的 policy
5. 解析是否允许暴击、倍率是多少
6. 按期望模式或 seed 驱动的随机模式求最终结果
```

注意：

- 具体倍率由数据层配置，不建议写死在引擎代码里
- 引擎只负责“如何解释”，不负责“某个海克斯当前数值是多少”

## 10. 技能配置层的最小扩展建议

## 10.1 `deal_damage` 建议支持 tags 与 critPolicy

```json
{
  "type": "deal_damage",
  "damage": {
    "source": "self",
    "target": "enemy",
    "damageType": "magic",
    "formulaText": "base_damage + ad_damage + ap_damage",
    "tags": ["crit_type_skill", "damage_pattern_dot"],
    "critPolicy": {
      "mode": "rule_enabled"
    }
  }
}
```

说明：

- 技能本身不必知道“哪一个海克斯存在”
- 技能只需要正确声明“我是什么类型的伤害”
- 海克斯通过 `DamagePolicySpec` 决定这些标签对应的效果

## 10.2 技能公式必须显式选择属性口径

像下面两种读取是有本质区别的：

- 普攻冷却：读 `self.attack_speed_current`
- 卡特 R 乘区：读 `self.attack_speed_bonus_raw`

技能配置不能再笼统写“攻速”，必须写清：

- 读的是原始攻速
- 读的是最终攻速
- 读的是溢出部分
- 读的是转化后的附加攻击力

## 11. 典型案例

## 11.1 案例 A：固定攻速 + 多余攻速转攻击力

这类规则的核心不是一个 buff，而是一套派生规则：

```text
1. 正常聚合 attack_speed_total_raw
2. 把 attack_speed_current 设为 fixedValue
3. overflow = max(0, attack_speed_total_raw - fixedValue)
4. attack_damage_bonus_from_attack_speed = overflow * ratio
5. attack_damage_current 再把转换值吃进去
```

推荐表达：

```ts
[
  {
    ruleId: "set_attack_speed_final",
    kind: "set_final",
    readStage: "raw",
    writeStage: "post_cap",
    targetAttr: "self.attack_speed_current",
    fixedValueFormulaText: "arena_fixed_attack_speed",
    aggregationMode: "set_final"
  },
  {
    ruleId: "convert_attack_speed_overflow_to_ad",
    kind: "overflow_convert",
    readStage: "raw",
    writeStage: "overflow",
    sourceAttr: "self.attack_speed_total_raw",
    targetAttr: "self.attack_damage_bonus_from_attack_speed",
    thresholdFormulaText: "arena_fixed_attack_speed",
    formulaText: "overflow_amount * arena_attack_speed_to_ad_ratio",
    aggregationMode: "add"
  }
]
```

## 11.2 案例 B：卡特琳娜 R 双吃攻速

如果游戏规则确实允许：

- 多余攻速转攻击力
- 同时 R 仍继续读原始额外攻速乘区

那么模型必须允许这两个口径同时存在：

```text
attack_speed_bonus_raw         -> 供 R 公式读取
attack_speed_current           -> 供普攻频率读取
attack_speed_overflow          -> 供转换规则读取
attack_damage_bonus_from_attack_speed -> 供 AD 相关公式读取
```

也就是说：

- `set_final` 只改最终攻速口径
- 不应覆盖 `attack_speed_bonus_raw`
- 转化结果再回流到最终攻击力

这正是为什么需要 raw / final / overflow 三层口径。

## 11.3 案例 C：技能可暴击 / 持续伤害可暴击

技能层只负责：

- 给 packet 打上 `crit_type_skill`
- 如果是持续伤害，再打上 `damage_pattern_dot`
- `critPolicy.mode = rule_enabled`

模式强化层负责：

- 匹配标签
- 开启暴击
- 注入倍率

这样同一个技能可以在不同模式下拥有不同暴击资格，而无需改技能定义。

## 12. 循环依赖与冲突处理

## 12.1 为什么会有循环

下面这类规则很容易形成回路：

- 法强转额外攻击力
- 额外攻击力再转法强
- 暴击率溢出转攻击力
- 攻击力又反过来提高另一个参与转换的属性

如果不加约束，很容易出现：

- 无限增益
- 不同实现顺序得到不同结果
- 同一输入无法复现

## 12.2 规则约束建议

推荐至少做以下限制：

- 每条 `DerivedRuleSpec` 必须声明 `readStage / writeStage`
- 只允许从前一阶段读，向后一阶段写
- 同一阶段内不允许形成互相依赖
- `set_final` 类型对同一属性同阶段只能有一个最终赢家
- publish 或 init 时做 DAG 检查，发现环路直接报错

## 12.3 不建议做运行时迭代收敛

对于当前 MVP，不建议把这类规则做成“循环迭代直到收敛”，原因是：

- 可解释性差
- 结果受精度与阈值影响大
- 很难稳定复现

更适合的做法是：

- 在数据层明确阶段
- 在初始化时拒绝非法互转组合

## 13. 与现有文档的关系

## 13.1 与 `mechanicsConfig`

- `mechanicsConfig` 继续负责技能触发与动作执行

## 13.2 与 `DamagePacket.tags`

- 本文直接复用已有 `DamagePacket.tags` 设计

## 13.3 与派生属性文档

- 移动速度文档已经验证“复杂属性规则应走派生流水线”

推荐后续在 `combat_rule_profiles` 中新增或扩展以下能力：

- `derivedStatResolution`
- `damageCritResolution`
- `overflowConversionRules`

是否最终挂在 `combat_rule_profiles` 还是拆到独立 profile，不影响本文的核心结论：

- 这些规则必须是模式级全局规则
- 不能散落在每个英雄技能里单独硬编码

## 14. 最小实现顺序建议

推荐按风险和收益分三步走：

### Phase 1

- `CombatantInit.augmentIds`
- `AugmentDTO`
- `DerivedRuleSpec`
- `DamagePolicySpec`
- `DamagePacket.critPolicy`
- 攻速 raw/final/overflow 三口径

目标：

- 先支持“固定攻速 + 溢出转 AD”
- 先支持“技能可暴击 / DoT 可暴击”

### Phase 2

- `full_convert`
- 暴击率溢出转属性
- 技能急速转移速
- 法强与额外攻击力互转

### Phase 3

- 治疗/护盾暴击
- 更复杂的模式级覆盖规则
- 更细的冲突优先级与调试日志

---

## 15. 本文结论

海克斯这类模式强化不应该被视为“又一组英雄技能”，而应该视为：

- 一类独立的运行时来源
- 一组模式级派生属性规则
- 一组作用于 packet 的伤害策略

对 WASM 来说，真正需要补的是：

- 强化定义入口
- 强化选择输入
- 派生属性流水线
- packet 级暴击策略

而不是为每个海克斯单独加一段特判代码。
