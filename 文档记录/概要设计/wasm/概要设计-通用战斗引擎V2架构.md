## 1. 设计目标

| 编号 | 目标 | 说明 |
|------|------|------|
| G1 | 零硬编码 | 代码中不允许出现任何游戏专属的属性 key、公式、数值常量 |
| G2 | 子系统解耦 | 每个子系统独立开关，默认关闭，不依赖其他子系统 |
| G3 | 公式外置 | 除加减乘除四则运算外，所有计算逻辑由前端配置传入 |
| G4 | 游戏无关 | 引擎不知道自己在算哪个游戏，一切语义由配置注入 |
| G5 | 功能完备 | 配置可以不配（子系统关闭），但代码必须支持所有已定义的子系统类型 |
| G6 | 1v1 拓扑 | 固定两个 Actor（source / target），不做 NvN |

## 3. 核心概念

### 3.1 Attribute Store

**存储结构：铺平 HashMap + 定义层声明维度关系**

```rust
/// 引擎内部完全不知道任何属性的含义
struct AttributeStore {
    values: HashMap<String, f64>,
}
```

- 无预定义 key。所有 key 由 `attributeDefinitions[]` 注入。
- Actor 初始化时从配置 `attrs: {}` 写入。
- 运行时通过 `attr(key) -> f64` 读取。

**为什么用铺平 HashMap 而不是 `Map<String, Map<String, f64>>`：**

- 公式引擎引用属性时用 `ActorAttr { attr_key: "hp_max" }` 即可，不需要额外 `dimension` 字段。
- 如果用两层 Map（如 `hp → { current: 1200, max: 2100, base: 800 }`），公式节点就变成 `ActorAttr { attr_key: "hp", dimension: "max" }`，每个公式节点多一个字段，配置膨胀。
- 铺平后 `hp`、`hp_max`、`hp_base` 各自独立存储，公式编写更直觉。
- 维度关系（哪些 key 是同一组属性）在 `attributeDefinitions` 中通过 `relatedKeys` 声明，用于初始化联动和校验。

```jsonc
// attributeDefinitions 示例
{
  "attrKey": "hp",
  "defaultValue": 0,
  "relatedKeys": {
    "max": "hp_max",
    "base": "hp_base"
  }
}
```

**HP 属性约定**：引擎**不固定任何属性 key 名**，但通过 `engineConfig.hpAttrKey` 声明引擎需要的 HP key（判断角色死亡用）。引擎唯一硬需求是"需要知道哪个 key 代表当前生命值"，key 叫 `hp`、`health`、`生命值` 均可。

**未注册 key 的访问策略（fail-fast 校验，见 15.1 节）**：
- `init` 阶段：对 actor attrs、公式引用、子系统 config 中出现的所有 attr key 做注册检查，未注册 → 返回校验错误。
- `run` 阶段：`attr(key)` 对未注册 key 返回 `0.0`（运行时性能优先），但在 `engineConfig.strictMode = true` 时抛出错误。

### 3.2 Formula Engine（继承 + 扩展）

沿用 MVP 的 AST 表达式树，新增节点：

| 节点 | 语义 | 用途 |
|------|------|------|
| `If { condition, then, else }` | 条件 > 0 走 then，否则 else | 技能等级分支、回合判定 |
| `Clamp { value, min, max }` | 钳位 | 属性上下限 |
| `Lookup { table_id, index_expr }` | 查表取值（round-down 索引） | 等级缩放、分段函数 |
| `Gt { left, right }` | left > right → 1.0, else 0.0 | 比较运算 |
| `Gte { left, right }` | left >= right → 1.0, else 0.0 | 比较运算 |
| `Lt { left, right }` | left < right → 1.0, else 0.0 | 比较运算 |
| `Lte { left, right }` | left <= right → 1.0, else 0.0 | 比较运算 |
| `Eq { left, right, epsilon }` | \|left - right\| < epsilon → 1.0, else 0.0 | 浮点相等判定 |
| `And { operands }` | 所有 > 0 → 1.0, else 0.0 | 布尔与 |
| `Or { operands }` | 任一 > 0 → 1.0, else 0.0 | 布尔或 |
| `Not { operand }` | operand <= 0 → 1.0, else 0.0 | 布尔非 |
| `Random { seed_key }` | 确定性伪随机 [0, 1) | 概率判定 |
| `Floor { operand }` | 向下取整 | |
| `Ceil { operand }` | 向上取整 | |
| `Abs { operand }` | 绝对值 | |
| `Modulo { left, right }` | 取余 | 周期判定 |

保留的节点：`Constant`, `ActorAttr`, `ActorHpCurrent`, `ActorHpMax`, `DamageTakenInWindow`, `Add`, `Multiply`, `Divide`, `Negate`, `Max`, `Min`, `InputValue`

**关于 Random 节点和 RNG 契约**：

引擎内置一个确定性 PRNG（如 xoshiro256），用 `engineConfig.seed` 初始化。`Random { seed_key }` 按 seed_key 维护独立的消费序列，确保：
- 相同 seed + 相同输入 = 完全一致的输出（可回归）
- 不同 seed_key 的消费互不影响

`probabilistic` 暴击判定即通过 `Random` + `If` 节点组合实现，不需要单独的判定模式。

### 3.3 Event Queue（继承）

优先级事件调度器，保留：
- `(t_ms, priority, seq)` 三元排序
- `BinaryHeap` 最小堆
- 确定性时间推进

**变化：事件类型不再硬编码为 enum**，改为通用结构：

```rust
enum InternalEvent {
    ActorDecide { actor_id: ActorId },
    SubsystemTimer {
        subsystem_id: String,
        actor_id: ActorId,
        payload: SubsystemTimerPayload,
    },
}

/// 子系统定时器的通用载荷。
/// 每个子系统注册定时器时填写自己的 timer_type + params。
/// 引擎不解读 params 内容——只负责投递，由对应子系统的 on_timer() 解读。
/// 定时器参数值——与 FlagValue 同构，避免所有值退化为字符串
enum TimerParamValue {
    Str(String),
    Num(f64),
    Bool(bool),
}

struct SubsystemTimerPayload {
    /// 定时器类型标识，由子系统自定义。
    /// 同一子系统可以注册多种 timer_type（如 dot 子系统：
    ///   "dot_tick", "dot_expire"）。
    timer_type: String,
    /// 强类型键值参数。子系统按自己的约定读写。
    /// Str: ID / key 引用；Num: 数值（伤害、层数、剩余时间）；Bool: 开关。
    /// 示例：
    ///   dot:  { "dot_instance_id": Str("ignite_01"), "tick_damage_formula": Str("ignite_tick") }
    ///   cc:   { "cc_type": Str("stun"), "remaining_ms": Num(1500.0) }
    ///   resistance_modifier: { "modifier_id": Str("black_cleaver"), "current_stacks": Num(3.0) }
    params: HashMap<String, TimerParamValue>,
}
```

**序列化规则**：`SubsystemTimerPayload` 在 init payload JSON 中不直接出现——它是引擎运行时子系统调用 `schedule_timer()` 时构造的内部数据。但 debug/diagnostics 输出中会以 JSON 形式序列化：
```json
{ "timer_type": "dot_tick", "params": { "dot_instance_id": "ignite_01", "remaining_ms": 3000.0, "is_refreshable": true } }
```
JSON 反序列化规则（与 `FlagValue` 一致）：字符串 → `Str`，数字 → `Num`，`true/false` → `Bool`。

**校验**：`timer_type` 必须由对应 `subsystem_id` 的子系统识别。引擎在 `on_timer()` 分发时，如果子系统不认识该 `timer_type`，记录 warning（strictMode 下报错）。

所有原来的 `DotTick`, `StunExpire`, `BlackCleaverExpire` 等全部统一为 `SubsystemTimer`。

## 4. 子系统框架

### 4.1 设计原则

```
┌──────────────────────────────────────────────┐
│              SubsystemRegistry               │
│                                              │
│  for each subsystem_type:                    │
│    enabled: bool        ← 默认 false         │
│    config: SubsystemConfig  ← 前端传入       │
│    state: SubsystemState    ← 运行时         │
│                                              │
│  规则：                                       │
│    1. enabled=false → 跳过一切处理            │
│    2. 子系统之间不直接引用                     │
│    3. 子系统内的所有公式通过 config 注入       │
│    4. 子系统通过 hooks 挂载到 pipeline        │
│                                              │
└──────────────────────────────────────────────┘
```

### 4.2 子系统间通信

**子系统之间不允许直接调用或引用**。合法通信渠道有两条：

#### 渠道 A：AttributeStore（持久状态）

用于跨时间步的间接交互。子系统修改 AttributeStore 中的属性值 → 其他子系统在后续读取时自然拿到最新值。

```
resistance_modifier 子系统 → 修改 actor.attr("armor") → mitigation 子系统读取时拿到削减后的值
```

#### 渠道 B：PipelineContext（单次结算的临时状态）

用于**同一个 DamagePipeline / 同一个 EffectPipeline 执行过程中**，在阶段间传递临时数据。
PipelineContext **不写回 AttributeStore**，结算完成后丢弃。

```rust
/// 阶段间传递的标志值——支持布尔、字符串和数值三种类型
enum FlagValue {
    Bool(bool),
    Str(String),
    Num(f64),
}

struct PipelineContext {
    /// 当前 pipeline 传递的数值（如 raw_damage、heal_amount 等）
    value: f64,
    /// 当前源 actor
    source_actor: ActorId,
    /// 当前目标 actor
    target_actor: ActorId,
    /// 伤害类型 tag（对 DamagePipeline）或自定义标签
    type_tag: String,
    /// flags 集合——由 effect params 初始化，stage 可读可写
    /// 示例："triggerOnHit" → Bool(true), "critType" → Str("basic_attack")
    flags: HashMap<String, FlagValue>,
    /// 阶段间传递的临时键值对——任何 stage 可以写入，后续 stage 可以读取
    scratch: HashMap<String, f64>,
}
```

**flags 类型说明**：
- `Bool`：开关型标志，如 `triggerOnHit`、`canLifeSteal`。
- `Str`：字符串元数据，如 `critType`（暴击子系统据此匹配 rule）。
- `Num`：数值型元数据，如 `bonusMultiplier`（预留）。
- JSON 反序列化规则：`true/false` → `Bool`，字符串 → `Str`，数字 → `Num`。

- **穿透子系统**计算出 `effective_resistance` 后写入 `scratch["effective_resistance"]`。
- **减伤子系统**从 `scratch["effective_resistance"]` 读取（如果存在），而不是直接读 actor attr。
- **暴击子系统**从 `flags["critType"]`（Str）读取暴击类型，匹配 rule 表。
- 这保证了穿透的临时计算结果不污染 actor 的实际属性值，同时支持隔离、回放和 debug。

**规则：子系统只能通过上述两个渠道通信，不能持有其他子系统的引用。**

### 4.3 子系统类型目录

以下 **13 个**子系统类型预定义在引擎中。每个子系统的 `enabled` 默认为 `false`。

| # | subsystem_id | 职责 | 主要 hook 挂载点 |
|---|---|---|---|
| 1 | `mitigation` | 伤害减免（护甲减伤、魔抗减伤等） | DamagePipeline.post_raw |
| 2 | `penetration` | 穿透计算（扁平、百分比、各种模式） | DamagePipeline.pre_mitigation |
| 3 | `critical_strike` | 暴击判定与倍率 | DamagePipeline.pre_raw |
| 4 | `shield` | 伤害吸收层 | DamagePipeline.post_dealt |
| 5 | `life_steal` | 伤害回血 | DamagePipeline.post_resolve |
| 6 | `dot` | 持续伤害调度 | ActionEffect / SubsystemTimer |
| 7 | `crowd_control` | 动作打断 / 延迟 | SimLoop.pre_action_decide |
| 8 | `resistance_modifier` | 叠层式抗性修改（如黑切） | ActionEffect.post_hit |
| 9 | `cooldown` | 技能冷却计算 | ActionEffect.pre_execute / post_hit |
| 10 | `attack_speed` | 攻击间隔计算 | ActionEffect.pre_execute |
| 11 | `regen` | 周期性资源回复 | SimLoop.periodic_tick |
| 12 | `conversion` | 属性转换（如 HP→AD） | Session.post_init |
| 13 | `resource` | 通用资源管理（法力、能量等） | ActionEffect.pre_execute |

> **新增游戏初始化分区时，这 13 个 subsystem type 应作为种子数据随分区一起 INSERT，用户不需要手动创建。**

### 4.4 每个子系统的配置结构

以 `mitigation`（减伤）为例：

```jsonc
{
  "subsystemId": "mitigation",
  "enabled": true,
  "config": {
    // 减伤阶段列表——可配多个（物理、魔法、混合...）
    "stages": [
      {
        "stageId": "physical_mitigation",
        "matchCondition": {
          // 只有当伤害的 damageType tag 匹配时才执行
          "damageTypeTag": "physical"
        },
        // 有效抗性公式：接收 InputValue = 目标原始抗性
        "effectiveResistanceFormula": { /* 表达式树 */ },
        // 减伤系数公式：接收 InputValue = 有效抗性
        "mitigationFormula": { /* 表达式树 */ }
      },
      {
        "stageId": "magic_mitigation",
        "matchCondition": { "damageTypeTag": "magic" },
        "effectiveResistanceFormula": { /* ... */ },
        "mitigationFormula": { /* ... */ }
      }
    ]
  }
}
```

以 `critical_strike`（暴击）为例：

```jsonc
{
  "subsystemId": "critical_strike",
  "enabled": true,
  "config": {
    // 暴击率从哪个属性读
    "chanceAttrKey": "crit_chance",
    // 暴击判定模式
    "determination": {
      // kind: "deterministic_counter" | "probabilistic" | "always" | "formula"
      "kind": "deterministic_counter",
      // 仅 deterministic_counter 需要
      "thresholdFormula": {
        // InputValue = crit_chance
        // 默认 ceil(1 / InputValue)
        "type": "...",
        "..."
      }
    },
    // 暴击时使用哪条规则
    "rules": [
      {
        "ruleId": "basic_crit",
        "matchCritType": "basic_attack",
        "multiplierFormula": { /* ... InputValue 无意义, 引用 source actor 属性 */ },
        "enabled": true
      }
    ]
  }
}
```

> **其他 11 个子系统同理**：每个子系统声明自己需要读写的 attribute key 和公式，全部通过 `config` 注入，引擎代码中不存在任何默认值。

## 5. Damage Pipeline

伤害结算不再是一个写死的函数调用链，而是一个**可配置的阶段流水线**。

### 5.1 Pipeline 阶段定义

```
raw_damage
  │
  ▼ [crit_modify]          ← critical_strike 子系统挂载（如果 enabled）
  │
  ▼ [pre_mitigation_modify] ← penetration 子系统挂载（计算有效抗性）
  │
  ▼ [mitigation_apply]      ← mitigation 子系统挂载（减伤系数）
  │
  = dealt_damage
  │
  ▼ [absorb]                ← shield 子系统挂载（护盾吸收）
  │
  = hp_damage
  │
  ▼ [post_resolve]          ← life_steal 子系统挂载
  │                         ← resistance_modifier 子系统挂载（叠层）
  │                         ← dot 子系统挂载（触发 DoT）
  │
  done
```

### 5.2 阶段注册

Pipeline 的阶段顺序和挂载关系在 **BenchmarkBundle 配置** 中声明：

```jsonc
{
  "damagePipeline": {
    "stages": [
      { "stageId": "crit_modify",           "subsystemId": "critical_strike", "hook": "pre_raw" },
      { "stageId": "effective_resistance",   "subsystemId": "penetration",     "hook": "pre_mitigation" },
      { "stageId": "apply_mitigation",       "subsystemId": "mitigation",      "hook": "post_raw" },
      { "stageId": "shield_absorb",          "subsystemId": "shield",          "hook": "post_dealt" },
      { "stageId": "life_steal_heal",        "subsystemId": "life_steal",      "hook": "post_resolve" },
      { "stageId": "apply_armor_stacks",     "subsystemId": "resistance_modifier", "hook": "post_resolve" },
      { "stageId": "trigger_dot",            "subsystemId": "dot",             "hook": "post_resolve" }
    ]
  }
}
```

**Pipeline stage 引用的 subsystem 必须已 enabled（init 时 fail-fast 校验，见 §14.1）。**
不用的子系统不应出现在 stages 数组中——这是 **Payload 编译器的责任**（见 §16.3）：
编译器根据游戏规则决定哪些子系统 enabled，只把 enabled 的子系统编入 stages。

### 5.3 无配置时的行为

如果 `damagePipeline` 未配置或为空：
- `dealt_damage = raw_damage`（直接等于原始伤害）
- 无护盾吸收，无吸血，无 DoT 触发
- 引擎**不会报错**（pipeline 为空是合法状态，代表"裸伤害"）

**但以下情况必须 fail-fast（见 §14.1）**：
- pipeline stage 引用了不存在的 subsystemId → init 时报错
- pipeline stage 引用的 subsystem **未 enabled** → init 时报错（不做自动跳过，配置层应保证一致性）
- pipeline stage 引用的 subsystem 已 enabled 但 config 不完整 → init 时报错
- subsystemId 拼写错误 → init 时报错（已知 subsystem 类型白名单校验）

## 6. Action 系统

### 6.1 告别枚举

取消 `ActionBehavior` 枚举。一个 Action 由**效果序列**定义：

```jsonc
{
  "actionId": "q_mystic_shot",
  "label": "Mystic Shot",
  "cooldown": {
    // 冷却计算公式——由 cooldown 子系统处理
    // 如果 cooldown 子系统未启用则使用 fixedMs 兜底字段
    "formulaId": "cooldown_q",
    "fixedMs": 5000
  },
  "effects": [
    {
      "effectType": "check_resource",
      "subsystemId": "resource",
      "params": { "costAttrKey": "mana", "costFormula": { "type": "constant", "value": 50 } }
    },
    {
      "effectType": "deal_damage",
      "params": {
        "damageTypeTag": "physical",
        "formulaId": "q_damage",
        "flags": {
          "triggerOnHit": true,
          "canLifeSteal": true,
          "canApplyResistanceModifier": true,
          "countsAsAttack": true,
          "critType": "basic_attack"
        }
      }
    },
    {
      "effectType": "attach_on_hit_items",
      "params": { "itemIds": ["item_sheen"] }
    },
    {
      "effectType": "reduce_cooldowns",
      "subsystemId": "cooldown",
      "params": { "reductionFormulaId": "q_cdr_on_hit", "scope": "non_basic" }
    },
    {
      "effectType": "start_cooldown"
    }
  ]

```

### 6.2 效果类型目录

与子系统类似，引擎预定义一组效果类型（effect types）：

| effectType | 语义 | 关联子系统 |
|---|---|---|
| `deal_damage` | 产出 DamagePacket 进入 Pipeline | — |
| `attach_on_hit_items` | 触发物品 on-hit 效果 | — |
| `check_resource` | 检查并扣除资源 | `resource` |
| `start_cooldown` | 开始冷却 | `cooldown` |
| `reduce_cooldowns` | 缩减冷却 | `cooldown` |
| `apply_shield` | 施加护盾 | `shield` |
| `apply_cc` | 施加控制效果 | `crowd_control` |
| `schedule_dot` | 调度持续伤害 | `dot` |
| `modify_attribute` | 运行时修改属性 | — |
| `schedule_timer` | 注册子系统定时器 | 通用 |

**Effect 与子系统的引用规则**：

引擎默认按 effectType 提供一个基线分类，但允许 **每个 effect 实例通过 `"critical": true` 字段覆盖**：

| effectType 默认分类 | disabled 时行为 |
|---|---|
| `check_resource`、`start_cooldown`、`reduce_cooldowns`、`apply_cc` | **语义关键** → init fail-fast (`E_EFFECT_SUBSYSTEM_DISABLED`) |
| `apply_shield`、`schedule_dot`、`attach_on_hit_items`、`modify_attribute`、`schedule_timer` | **增强型** → 运行时跳过 + `EffectSkipped` 日志 |

**覆盖机制**：任何 effect 可以在 JSON 中添加 `"critical": true`，将其从增强型**提升为语义关键型**。

```jsonc
// 护盾作为此 action 的核心效果（如 Janna E）——标记为 critical
{
  "effectType": "apply_shield",
  "subsystemId": "shield",
  "critical": true,
  "params": { "shieldFormula": "janna_e_shield", "durationMs": 5000 }
}
// 护盾作为附带效果（如装备被动）——保持默认增强型
{
  "effectType": "apply_shield",
  "subsystemId": "shield",
  "params": { "shieldFormula": "item_passive_shield", "durationMs": 3000 }
}
```

- `deal_damage` 不引用子系统，始终执行。
- `"critical": true` 只能 **向上提升**（增强型 → 关键型），不能将默认关键型降级，保证安全下限。
- **Payload 编译器应保证**：如果 action 需要某个语义关键型 effect（无论默认还是显式标记），其关联子系统必须 enabled。
- Init 校验表（§14.1）的 `E_EFFECT_SUBSYSTEM_DISABLED` 规则涵盖此检查（含 `critical: true` 的 effect 也纳入）。

### 6.3 Action 决策（战斗循环）

战斗循环的 ActorDecide 事件不再根据 `ActionBehavior` 枚举分发，而是：

1. 按 `priorities` 顺序遍历 Actor 的 action 列表。
2. 对每个 action：
   a. 检查冷却是否就绪（如果 `cooldown` 子系统启用，用公式算；否则用 `fixedMs`）。
   b. 执行 action 的 effects 序列。
   c. 如果某个 `check_resource` effect 失败 → 跳过该 action，尝试下一个。
3. 如果所有 action 都不可用 → 等待最近的就绪时间。

## 8. WASM 接口

### 8.1 保留接口

| 函数 | 方向 | 说明 |
|------|------|------|
| `alloc(len) → ptr` | export | 分配内存 |
| `dealloc(ptr, len)` | export | 释放内存 |
| `engine_init(ptr, len) → i32` | export | 初始化 session |
| `engine_run(ptr, len) → i32` | export | 执行模拟 |
| `engine_response_ptr() → ptr` | export | 读取响应指针 |
| `engine_response_len() → usize` | export | 读取响应长度 |

### 8.2 新增：流式输出回调

```rust
// WASM import — 由 JS 宿主实现
extern "C" {
    fn host_emit_sample(ptr: *const u8, len: usize);
}
```

引擎在以下时机调用 `host_emit_sample`，每次发送一个 **tagged union JSON**：

| 时机 | `type` 标签 | payload 说明 |
|---|---|---|
| 每 `sampleIntervalMs` 产出一个采样点 | `"snapshot"` | 包含 `t_ms`、双方 actor 属性快照 acto |
| 每个 damage event 结算完成 | `"damage_event"` | 包含 `t_ms`、source/target、raw/dealt/mitigated、pipeline 细节 |

```jsonc
// host_emit_sample 消息示例（tagged union）
// 类型 1：定时快照
{
  "type": "snapshot",
  "t_ms": 1050,
  "actors": {
    "source": { "hp": 980.0, "mana": 250.0 },
    "target": { "hp": 720.0, "mana": 400.0 }
  }
}
// 类型 2：伤害事件
{
  "type": "damage_event",
  "t_ms": 1023,
  "source": "source",
  "target": "target",
  "damageTypeTag": "physical",
  "rawDamage": 150.0,
  "dealtDamage": 98.5,
  "mitigated": 51.5,
  "pipelineTrace": [ /* 各 stage 的中间值，仅 debug 模式 */ ]
}
```

JS 侧的 Worker 收到回调后按 `type` 字段分发推送给主线程，实现类似 channel 的增量输出。

**宿主必须始终提供 `host_emit_sample` import**（WASM 模块声明了 import 但实例化时缺失会直接失败）。
不需要流式输出时，宿主提供一个 **no-op stub**：

```js
// 非流式模式：提供空实现，满足 import 约束
const imports = {
  env: {
    host_emit_sample: (ptr, len) => { /* no-op */ }
  }
};
```

引擎侧通过 `engineConfig.streamingOutput: bool`（默认 `false`）控制行为：
- `true`：实时调用 `host_emit_sample` 发送两类增量消息（`snapshot` 和 `damage_event`，见上方 tagged union 定义）。
- `false`：引擎内部缓存到 `Vec`，`engine_run` 结束后通过 `engine_response_ptr/len` 一次性返回。`host_emit_sample` 不会被调用（但 import 仍需存在）。

#### 流式模式下的终态协议

**无论 `streamingOutput` 为何值，`engine_run` 结束后 `engine_response_ptr/len` 始终返回一个 `RunResult` JSON。**
不同之处仅在于 `samples` 字段的内容：

| streamingOutput | host_emit_sample 调用 | RunResult.samples | RunResult.summary / diagnostics |
|---|---|---|---|
| `true` | 每个采样点实时推送 | **空数组** `[]`（数据已通过回调发出） | **始终包含**（终态摘要） |
| `false` | 不调用 | 完整采样点数组 | **始终包含** |

```jsonc
// RunResult 终态结构（两种模式共用）
{
  "status": "ok",
  "samples": [ /* streamingOutput=true 时为空 */ ],
  "summary": {
    "totalDurationMs": 15230,
    "totalDamageDealt": 4821.5,
    "totalDamageTaken": 3102.0,
    "deathAtMs": null,
    "actorFinalState": { /* 两个 actor 的最终属性快照 */ }
  },
  "diagnostics": [
    { "level": "warning", "code": "W_LOOKUP_MISS", "message": "..." }
  ]
}
```

**Worker → 主线程消息协议**（流式和非流式共用同一套 tagged union）：

| Worker postMessage type | 触发时机 | payload |
|---|---|---|
| `snapshot` | `host_emit_sample` 回调（仅流式） | 定时快照（同上） |
| `damage_event` | `host_emit_sample` 回调（仅流式） | 伤害事件（同上） |
| `done` | `engine_run` 返回后 | `{ samples?, summary, diagnostics }` |
| `error` | init/run 失败 | `{ code, message, errors? }` |

- 流式模式：Worker 收到 `host_emit_sample` 回调 → 解析 JSON → 按 `type` 直接 `postMessage` 转发；`engine_run` 结束后发 `done`（不含 samples）。
- 非流式模式：`engine_run` 结束后发一次 `done`（含 samples）。

## 10. 子系统详细规格

### 10.1 mitigation（减伤）

**输入**：DamagePacket (raw_damage, damageTypeTag)
**输出**：修改后的 dealt_damage

配置字段：

```
stages[]:
  stageId: string
  matchCondition:
    damageTypeTag: string          // 匹配伤害类型标签
  resistanceAttrKey: string        // 目标抗性属性 key
  effectiveResistanceFormula: Expr  // InputValue = 原始抗性值
  mitigationFormula: Expr          // InputValue = 有效抗性值，输出 = 减伤系数 (0~1)
```

**代码行为**：
1. 遍历 stages，找到 damageTypeTag 匹配的 stage
2. 读取 target.attr(resistanceAttrKey)
3. 求值 effectiveResistanceFormula → effective_resistance
4. 求值 mitigationFormula(effective_resistance) → multiplier
5. dealt_damage = raw_damage * multiplier

**无 fallback。无默认公式。配置缺失 = 不减伤。**

### 10.2 penetration（穿透）

**输入**：PipelineContext（含 source/target actor、damageTypeTag）
**输出**：将计算结果写入 `PipelineContext.scratch["effective_resistance"]`，不修改 actor attrs

配置字段：

```
rules[]:
  ruleId: string
  damageTypeTag: string
  sourceAttrKeys: string[]           // 读取攻击方的穿透属性
  targetResistanceAttrKey: string    // 目标的抗性属性 key
  effectiveResistanceFormula: Expr   // 自由组合穿透计算，InputValue = 目标原始抗性
  outputScratchKey: string           // 写入 PipelineContext.scratch 的 key，默认 "effective_resistance"
```

支持扁平穿透、百分比穿透、或任何自定义穿透模式——全部由公式决定。

**与 mitigation 的协作**：mitigation 子系统在读取抗性时，**优先从 `PipelineContext.scratch[outputScratchKey]` 读取**（如果穿透子系统已执行并写入），fallback 到 `target.attr(resistanceAttrKey)`。这保证了穿透的临时结果不污染 actor 的实际属性。

### 10.3 critical_strike（暴击）

> **暴击不绑死 DamagePipeline**。任何通过 effect 产出数值的场景（伤害、回血、护盾量）都可以声明 `critType`，暴击子系统作为通用的"数值放大器"被调用（详见下方"通用暴击挂载"）。

配置字段：

```
chanceAttrKey: string
determination:
  kind: "deterministic_counter" | "formula"
  // deterministic_counter 模式：
  thresholdFormula?: Expr        // InputValue = crit_chance, 输出 = 触发阈值 (如 ceil(1/InputValue))
  // formula 模式：
  conditionFormula?: Expr        // 输出 > 0 = 暴击 (可组合 Random 节点实现概率暴击)
rules[]:
  ruleId: string
  matchCritType: string
  multiplierFormula: Expr
  enabled: bool
```

**暴击判定模式简化**：原草案有 4 种 kind（deterministic_counter / probabilistic / always / formula），现在简化为 2 种：
- `deterministic_counter`：沿用 MVP 的截断计数器，thresholdFormula 必配。
- `formula`：万能模式。`conditionFormula > 0` 即暴击。"概率暴击"用 `conditionFormula: If(Lt(Random("crit"), ActorAttr("crit_chance")), 1, 0)` 实现。"always"用 `conditionFormula: Constant(1)` 实现。

**代码行为**：
1. 读取 flags.critType → 匹配 rule
2. 按 determination.kind 执行判定
3. 暴击时求值 multiplierFormula → 倍率
4. 无 fallback 倍率。multiplierFormula 必须在配置中提供。

**通用暴击挂载**：除 `deal_damage` 外，以下 effect 也支持 `critType` 字段：
- `modify_attribute`（如回血暴击）
- `apply_shield`（如护盾暴击）

effect 执行时检查 `critType` 非空 + `critical_strike` 子系统 enabled → 调用暴击判定 → 放大公式输出值。


配置字段：

```
resources[]:
  resourceId: string
```

## 11. DamageTypeTag 系统

MVP 中 `DamageType` 是三值枚举（Physical / Magic / True），V2 改为**字符串 tag**：

```rust
struct DamagePacket {
    damage_type_tag: String,  // 如 "physical", "magic", "true", "pure", 游戏自定义
    // ...
}
```

配置中的 `matchCondition.damageTypeTag` 用于匹配。

**引擎不内置任何 tag 的语义。** "true 伤害不减伤"这件事由配置决定（mitigation 的 stages 里不配 true 伤害的 stage → 自然不减伤）。

## 14. Fail-Fast 校验规则

### 14.1 Init 阶段校验

引擎在 `init(payload)` 成功反序列化后、进入 SimLoop 前，执行**全量校验**。任何校验失败直接返回 `InitError`，**不会进入模拟**。

| 校验类别 | 规则 | 错误码 |
|---|---|---|
| **属性键引用** | 公式 AST 中所有 `Attr(key)` 引用的 `key` 必须存在于 `attributeDefinitions` | `E_ATTR_KEY_UNKNOWN` |
| **HP 键存在** | `engineConfig.hpAttrKey` 和 `hpMaxAttrKey` 对应的属性必须已声明 | `E_HP_KEY_MISSING` |
| **子系统 config 完整** | 每个 `enabled: true` 的子系统，其必需的 config 字段不得为空（如 `mitigation` 需要 `mitigationFormula`） | `E_SUBSYSTEM_CONFIG_INCOMPLETE` |
| **Pipeline 阶段引用** | `damagePipeline.stages[].subsystem` 必须是已注册且 **enabled** 的子系统 ID（不做运行时自动跳过，配置层应保证一致） | `E_PIPELINE_STAGE_INVALID` |
| **公式 ID 引用** | 所有 `formulaId` 引用必须在 `formulas` 表中存在 | `E_FORMULA_ID_MISSING` |
| **Lookup 表引用** | 公式 AST 中 `Lookup { table_id, index_expr }` 的 `table_id` 必须在 `lookupTables` 中存在 | `E_LOOKUP_TABLE_MISSING` |
| **Action effect 引用** | effect 序列中引用的 `formulaId`、`attr_key`、`subsystem` 必须合法 | `E_EFFECT_REF_INVALID` |
| **语义关键 effect 子系统** | 默认关键型 effect（`check_resource`、`start_cooldown`、`reduce_cooldowns`、`apply_cc`）或显式标记 `"critical": true` 的 effect，其引用的子系统必须 enabled | `E_EFFECT_SUBSYSTEM_DISABLED` |
| **循环依赖** | 公式之间不得存在循环引用（公式 A → 公式 B → 公式 A） | `E_FORMULA_CYCLE` |
| **seed 存在** | 如有任何公式使用 `Random` 节点，`engineConfig.seed` 不得为空 | `E_SEED_REQUIRED` |

### 14.2 strictMode 运行时行为

当 `engineConfig.strictMode = true` 时，运行时**额外**检查：

- 公式求值结果为 `NaN` 或 `±Infinity` → 立即中止并返回 `RuntimeError`
- `Lookup` 查找 miss → 报错（非 strict 模式下降级为 0.0 并记 warning）
- `scratch` 读取不存在的 key → 报错（非 strict 模式下返回 0.0）

非 strict 模式下，上述三种情况降级为 warning 写入 `diagnostics` 输出数组，不中止模拟。

### 14.3 校验返回格式

```json
{
  "status": "error",
  "errors": [
    {
      "code": "E_ATTR_KEY_UNKNOWN",
      "message": "Formula 'mitigation_formula' references unknown attribute key 'armor_pen_flat'",
      "path": "formulas.mitigation_formula.ast.children[1]"
    }
  ]
}
```

所有错误一次性收集返回，不因第一个错误就停止校验（"collect all, fail once"）。

## 15. RNG 契约与回放保证

### 15.1 PRNG 算法

使用 **xoshiro256++**（Rust `rand` crate 标准实现），状态 256 bit。

### 15.2 种子初始化

```
master_seed = engineConfig.seed          // u64，必须由前端提供
prng_state  = xoshiro256pp::seed_from_u64(master_seed)
```

### 15.3 seed_key 独立序列

每个 `Random` 节点声明一个 `seed_key: string`（如 `"crit_roll"`、`"dodge_roll"`）。引擎维护一个 `HashMap<String, Rng>`：

```
fn get_rng(seed_key: &str) -> &mut Rng {
    entry.or_insert_with(|| {
        let derived_seed = hash(master_seed, seed_key);  // 稳定 hash
        Rng::seed_from_u64(derived_seed)
    })
}
```

同一 `seed_key` 的第 N 次调用总是返回相同值（给定相同 master_seed），**与其他 seed_key 的调用频率无关**。

### 15.4 回放保证

**同一 `seed` + 同一 `init payload` → 逐 tick 产出完全一致的采样序列。**

- 前端保存 `seed` 即可完整复现任何一次模拟
- 测试通过固定 seed 做黄金文件 (golden file) 比对

### 15.5 无 Random 节点时

如果整份 payload 的公式中没有任何 `Random` 节点，`engineConfig.seed` 可省略，PRNG 系统完全不初始化，模拟天然确定性。

## 16. Payload 编译契约

### 16.1 问题背景

V2 的 `init payload` 是一个 ~数千行的 JSON，包含全量属性定义、公式 AST、子系统配置、action 序列等。**前端用户不手写此 JSON**。

### 16.2 编译流水线

```
                   ┌──────────────┐
  游戏配置 bundle  │  web 层编译器  │   V2 init payload JSON
  (LoL/Katarina   ──►  compile()  ──►  (传入 WASM init)
   前端 UI 选择)    │              │
                   └──────────────┘
```

- **输入**：前端已有的 "游戏配置 bundle"（包含英雄数据、装备数据、技能描述、用户选择的英雄/装备/等级等）
- **编译器位置**：`web/src/engine/` 下的 TypeScript 模块
- **输出**：符合 V2 `InitPayload` schema 的 JSON 对象

### 16.3 编译器职责

| 职责 | 说明 |
|---|---|
| 属性展开 | 从英雄 + 装备 + 等级计算初始属性值，生成 `attributeDefinitions` |
| 公式实例化 | 把 bundle 中的公式模板（如 LoL 减伤公式）翻译为 V2 AST 节点树 |
| 子系统配置 | 根据游戏规则决定哪些子系统 enabled，填充各自 config |
| Pipeline 编排 | 根据游戏规则生成 `damagePipeline.stages` 顺序 |
| Action 生成 | 从技能描述和 rotation 配置生成 action effect 序列 |
| seed 注入 | 用户选择"是否随机" → 生成 seed 或使用固定 seed |

### 16.4 编译时校验（可选）

编译器可在 TypeScript 侧做一轮前置校验（type check、key 引用检查），提前拦截配置错误。但这不替代引擎侧的 fail-fast 校验（第 14 节），二者互补。

### 16.5 与 MVP 的关系

当前 MVP 的 `web/src/engine/` 中已有 bundle → WASM payload 的编译逻辑（`formulaCompiler.ts` 等）。V2 会**复用编译器的架构**，扩展输出格式以匹配新的 `InitPayload` schema。
