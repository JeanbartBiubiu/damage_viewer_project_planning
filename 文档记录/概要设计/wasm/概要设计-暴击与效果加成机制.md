# WASM 概要设计：暴击与效果加成机制

## 1. 文档目标

本文为 T10（Wasm 暴击机制）提供概要设计，覆盖以下核心问题：

- 暴击不只是伤害倍率；它是一种**通用的效果加成判定**，可以放大伤害、治疗、护盾，甚至附加额外控制效果
- 暴击资格不能只用一个 `canCrit: boolean` 表示；不同类别的效果（普攻、技能、on-hit）可能有独立的暴击策略
- 暴击倍率不能硬编码；应通过公式驱动，支持无尽之刃等装备修正
- 暴击判定使用确定性计数器而非随机数，保证结果可复现

**MVP 范围**：T10 仅实现伤害分量的暴击判定与倍率放大。治疗/护盾/控制效果加成作为扩展方向预留接口，不在本轮实现。

**与现有文档关系**：

- 模式强化文档已规划了 `DamagePacket.tags + critPolicy + activeDamagePolicies` 的完整方案
- 本文是**该方案在 MVP 阶段的最小落地版本**，只取其中与伤害暴击直接相关的子集
- 后续治疗/护盾/控制加成可在本文架构上渐进扩展

## 2. 结论先行

### 2.1 核心设计决策

| 决策项 | 结论 | 理由 |
|--------|------|------|
| 暴击判定方式 | 确定性计数器（截断模式） | 引擎无 RNG，结果完全可复现 |
| 暴击率共享/独立 | 全局共享一个计数器 | 符合 LoL 实际暴击节奏 |

| MVP 范围 | 仅伤害暴击 | 治疗/护盾/控制留后续任务 |

## 3. 设计原则

### 3.1 暴击是"效果加成判定"，不是"伤害专用机制"

LoL 中暴击的实际实例远不止"普攻 ×1.75"：

| 场景 | 效果类别 | 来源 |
|------|----------|------|
| 普攻暴击 | 伤害 ×1.75 | 基础暴击率 |
| 亚索 Q 暴击 | 伤害 ×1.575（修正倍率）| 技能自带 critType |
| 纳维利暴击 | 治疗量 ×1.5 | 海克斯效果 |
| 某装备暴击时击飞 | 额外控制 1s | 装备 critRule |
| 无尽之刃 | 暴击倍率 +0.4 | 装备修正公式 |

因此**数据模型必须把"暴击判定"和"暴击产生的效果"分离**：

- 判定层：统一的确定性计数器 + critType 匹配
- 效果层：公式驱动的倍率/额外效果（MVP 只做伤害倍率）

### 3.2 critType 是匹配键，不是硬编码枚举

暴击类型不应做成引擎硬编码的枚举（`BasicAttack | Skill | OnHit`），而应做成**字符串标签**，与已有的 `type_ids` 体系对齐：

```
crit_type_basic_attack   → 普攻暴击
crit_type_skill          → 技能暴击
crit_type_on_hit         → 攻击特效可暴击
```

这样的好处：
- 海克斯等强化可以注入新的 critRule，给原本不能暴击的技能赋予暴击资格
- 不需要修改引擎枚举就能支持新的暴击类型
- 与 `lol_mvp_type_taxonomy.csv` 中已定义的 crit 类型体系自然对齐

### 3.3 暴击率共享，暴击倍率独立

这是你明确的决策。设计理由：

- **暴击率共享**：LoL 实际机制中，所有可暴击效果共享同一个暴击节奏。50% 暴击率时，不会出现"普攻暴了但 Q 没暴"的独立概率问题，它们共享同一个按序截断的计数器
- **暴击倍率独立**：不同 critType 的倍率可以不同。亚索 Q 的暴击倍率与普攻的暴击倍率不一样，有些装备只增加普攻暴击倍率

### 3.4 canCrit=false 则完全跳过

如果一个伤害分量没有声明 `critType`（或显式 `canCrit: false`），暴击系统完全跳过该分量：
- 不参与计数器推进
- 不做暴击判定
- 不做倍率放大

这意味着暴击机制是**纯 opt-in** 的，不会影响现有的无暴击测试。

## 4. 数据模型

### 4.1 Bundle 层：CritRule（暴击规则定义）

```jsonc
// BenchmarkBundle 新增字段
{
  "critRules": [
    {
      "ruleId": "basic_crit",
      "critType": "crit_type_basic_attack",    // 匹配哪些 critType
      "multiplierFormulaId": "crit_multiplier_formula", // 计算暴击倍率的公式
      "enabled": true
    },
    {
      "ruleId": "yasuo_q_crit",
      "critType": "crit_type_skill",
      "multiplierFormulaId": "yasuo_q_crit_formula",
      "enabled": true
    }

}
```

**设计说明**：

- `critType` 是字符串匹配键，效果分量通过 `critType` 字段声明自己的暴击类别
- `multiplierFormulaId` 指向 `BenchmarkBundle.formulas` 中的公式，该公式作为 pipeline formula 运行：

  - 公式内部自由引用 actor 属性（如 `crit_multiplier`）来计算最终倍率
- `enabled` 默认 true；海克斯系统可通过注入 `enabled: false` 的同 critType 规则来禁用暴击

## 5. 确定性暴击计数器

### 5.1 核心算法

使用**按序截断**方案，保证同一暴击率下结果完全确定：

```
状态：crit_counter: u32（每个 Actor 一个，全局共享）

对每个可暴击分量：
  1. crit_chance = actor.attr("crit_chance")  // 0.0 ~ 1.0
  2. 如果 crit_chance <= 0.0 → 不暴击，不推进计数器
  3. 如果 crit_chance >= 1.0 → 必定暴击，不推进计数器
  4. 否则：
     threshold = ceil(1.0 / crit_chance) → 例如 50% → 2，25% → 4
     crit_counter += 1
     如果 crit_counter >= threshold → 暴击，重置 crit_counter = 0
     否则 → 不暴击
```

**示例**：

| 暴击率 | threshold | 暴击序列 |
|--------|-----------|----------|
| 100% | - | ✓✓✓✓✓... |
| 50% | 2 | ✗✓✗✓✗✓... |
| 25% | 4 | ✗✗✗✓✗✗✗✓... |
| 33% | 3 | ✗✗✓✗✗✓... |
| 0% | - | ✗✗✗✗✗... |

### 5.2 计数器粒度

- 每个 `ActorRuntime` 持有一个 `crit_counter: u32`
- 所有可暴击分量共享同一个计数器推进序列
- 暴击率统一读取 `actor.attr("crit_chance")`

### 5.3 不参与暴击的分量不推进计数器

关键：只有 `crit_type.is_some()` 的分量才推进计数器。这保证了非暴击分量（荆棘甲反伤、真实伤害等）不会"消耗"暴击节奏。

### 5.4 ActorRuntime 状态扩展

```rust
// runtime.rs — ActorRuntime 新增
pub struct ActorRuntime {
    // ... 现有字段 ...
    pub crit_counter: u32,  // 确定性暴击计数器
}
```

初始化为 0，每次暴击重置为 0。

## 6. 暴击倍率计算（公式驱动）

### 6.1 为什么不硬编码 1.75

LoL 中暴击倍率不是固定值：

| 场景 | 倍率 |
|------|------|
| 默认暴击 | 1.75 |
| 无尽之刃加成后 | 2.15（+0.4） |
| 亚索 Q 暴击 | 1.575（0.9 × 1.75） |
| 某些海克斯 | 自定义倍率 |

因此暴击倍率必须通过公式计算。

### 6.2 Pipeline Formula 方案

每个 `BenchmarkCritRule` 的 `multiplierFormulaId` 指向一个公式：

```jsonc
{
  "formulaId": "crit_multiplier_formula",
  "label": "暴击伤害倍率",
  "expr": {
    "type": "actor_attr",
    "actor": "source",
    "attrKey": "crit_multiplier"  // Actor 属性中存储最终暴击倍率
  },
  "bypassValue": 1.75
}
```

**属性约定**：

| 属性 key | 含义 | 默认值 |
|----------|------|--------|
| `crit_chance` | 暴击率 (0.0~1.0) | 0.0 |
| `crit_multiplier` | 暴击伤害倍率 | 1.75 |

**装备如何修正倍率**：

无尽之刃在 Actor 初始化时通过属性叠加（或 T09 转换管道）将 `crit_multiplier` 从 1.75 提升到 2.15。公式只需要读取 `actor.attr("crit_multiplier")` 即可拿到修正后的值。

### 6.3 亚索类修正怎么处理

亚索 Q 使用独立的 `critType`（如 `crit_type_skill`），对应独立的 `BenchmarkCritRule`，其 `multiplierFormulaId` 指向一个修正公式：

```jsonc
{
  "formulaId": "yasuo_q_crit_formula",
  "label": "亚索Q暴击倍率",
  "expr": {
    "type": "multiply",
    "factors": [
      { "type": "constant", "value": 0.9 },
      { "type": "actor_attr", "actor": "source", "attrKey": "crit_multiplier" }
    ]
  }
}
```

这样不同 critType 可以有完全不同的倍率计算逻辑。

## 7. 执行流插入点

### 7.1 当前伤害结算管线

```
execute_damage_action()
  → evaluate_formula → raw_damage
  → build DamagePacket(raw_damage, flags)
  → build on-hit DamagePackets
  → apply_damage_packets_as_event()
    → for each packet:
        → resolve_component()
          → [穿透计算] effective_resistance
          → [减伤计算] mitigation
          → dealt_damage = raw_damage × mitigation
          → [护盾吸收] shield
          → [HP扣减] hp_current
          → [生命偷取] life_steal
        → apply_status_effects_after_hit()
```

### 7.2 暴击插入点：`resolve_component()` 内部

暴击放大应在 **raw_damage 之后、mitigation 之前**，这符合 LoL 实际机制（暴击放大的是减伤前的基础伤害）：

```
resolve_component():
  → [现有] raw_damage 负值检查
  → [新增] 暴击判定：resolve_crit(state, source_actor, &packet)
  → [新增] 如果暴击：raw_damage *= crit_multiplier
  → [现有] 穿透计算 effective_resistance
  → [现有] 减伤计算 mitigation
  → [现有] dealt_damage = raw_damage × mitigation
  → [现有] 护盾 → HP → 生命偷取
```

**为什么不在 `execute_damage_action()` 中插入**：

- `resolve_component()` 是所有伤害分量的统一结算入口
- on-hit 附伤、DOT、荆棘甲反伤等都经过 `resolve_component()`
- 在这里插入可以确保所有标记了 `crit_type` 的分量都能被暴击系统处理
- 每个分量独立判定，一次攻击中不同分量可以有不同的暴击结果

### 7.3 暴击判定调用伪代码

```rust
// 在 resolve_component() 中现有 raw_damage 负值检查之后插入
let (is_critical, crit_multiplier) = resolve_crit(
    state, source_actor, &packet.flags
);
let effective_raw_damage = if is_critical {
    round_number(packet.raw_damage * crit_multiplier)
} else {
    packet.raw_damage
};
// 后续使用 effective_raw_damage 代替 packet.raw_damage
```

### 7.4 normalized_flags 传递 critType

`sim/action.rs` 中的 `normalized_flags()` 需要扩展，将 SkillDef 的默认 `crit_type` 写入 `DamageFlags`：

## 8. 模块设计：`critical_strike.rs`

### 8.1 公开 API

```rust
/// 暴击判定结果
pub struct CritResult {
    /// 是否暴击
    pub is_critical: bool,
    /// 暴击倍率（非暴击时为 1.0）
    pub multiplier: f64,
}

/// 对单个伤害分量执行暴击判定
///
/// - 如果 flags.crit_type 为 None → 跳过，返回 (false, 1.0)
/// - 如果没有匹配的 CritRule → 跳过
/// - 否则推进计数器，判定是否暴击，计算倍率
pub fn resolve_crit(
    state: &mut RuntimeState,
    source_actor: ActorId,
    flags: &DamageFlags,
) -> Result<CritResult, EngineError>
```

### 8.2 内部流程

```
resolve_crit(state, source_actor, flags):
  1. crit_type = flags.crit_type  → None → return NOT_CRIT
  2. rule = state.benchmark.crit_rules.find(|r| r.crit_type == crit_type && r.enabled)
     → None → return NOT_CRIT
  3. crit_chance = state.actor(source_actor).attr("crit_chance")
     → <= 0.0 → return NOT_CRIT
     → >= 1.0 → is_critical = true（不推进计数器）
     → else:
        threshold = ceil(1.0 / crit_chance) as u32
        counter = &mut state.actor_mut(source_actor).crit_counter
        *counter += 1
        if *counter >= threshold {
            is_critical = true
            *counter = 0
        } else {
            is_critical = false
        }
  4. if !is_critical → return NOT_CRIT
  5. multiplier = state.eval_formula(rule.multiplier_formula_id, source_actor, target_actor)?
     → 如果公式缺失/求值失败 → 回退到 actor.attr("crit_multiplier") 或 1.75
  6. return CritResult { is_critical: true, multiplier }
```

### 8.3 TestProfile 交互

| Profile | 暴击行为 |
|---------|----------|
| `Full` | 正常暴击判定 |
| `FormulaBypass` | 倍率公式使用 `bypass_value`，判定照常 |
| `BucketIdentity` | 暴击正常（不影响减伤 profile） |
| `NoCrit`（新增？） | 跳过所有暴击，返回 NOT_CRIT |

**MVP 阶段**：暂不新增 `NoCrit` profile。如需禁用暴击，将 `crit_chance` 设为 0 即可。

    } else {

    };

    let source_pen_flat = ...;
    let target_resistance = ...;
    let effective_resistance = ...;

    // [现有] 减伤计算（使用 effective_raw 而非 packet.raw_damage）
    let mitigation = ...;
    let dealt_damage = round_number(effective_raw * mitigation);

    // [现有] 护盾 → HP → 生命偷取
    ...

    Ok(DamageComponentTrace {
        component: EngineDamageComponent {
            source_kind: packet.source_kind,
            source_id: packet.source_id.clone(),

### 11.2 raw_damage 语义变化

注意：暴击后，`EngineDamageComponent.raw_damage` 的含义变为"暴击放大后、减伤前的伤害"。这与 LoL 客户端的展示一致——界面上显示的"暴击伤害"是放大后的数字。

如需同时保留"暴击前原始值"，可新增 `base_raw_damage` 字段，但 **MVP 阶段不需要**。

## 12. 数据流总览

```
Bundle JSON
  ├─ critRules: [{ruleId, critType, multiplierFormulaId}]
  ├─ formulas: [{formulaId: "crit_multiplier_formula", ...}]
  ├─ skillDefs: [{critType: "crit_type_basic_attack", flags: {...}}]
  └─ selfActor.attrs: {crit_chance: 0.25, crit_multiplier: 1.75}
         │
         ▼
   compile_runtime_catalog()
         │
         ├─ compile_crit_rules() → Vec<CompiledCritRule>
         └─ BenchmarkRuntimeCatalog { crit_rules, ... }
         │
         ▼
   build_runtime()
         │
         └─ ActorRuntime { crit_counter: 0, attrs: {crit_chance, crit_multiplier, ...} }
         │
         ▼
   resolve_component(packet with crit_type = "crit_type_basic_attack")
         │
         ├─ resolve_crit() → 查找匹配的 crit_rule
         │   ├─ 推进 crit_counter
         │   ├─ 判定是否暴击
         │   └─ 求值 multiplier 公式 → 1.75
         │
         ├─ effective_raw = raw_damage × 1.75 (if critical)
         ├─ dealt_damage = effective_raw × mitigation
         └─ EngineDamageComponent { is_critical: true, raw_damage: effective_raw, dealt_damage }
```
