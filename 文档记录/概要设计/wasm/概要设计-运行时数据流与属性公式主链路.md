## 2. 先给结论

你列的 10 点方向是对的，但如果直接按这 10 点拆任务，后面会遗漏 8 个会反复返工的基础问题：

1. 缺少“静态定义层 -> 运行输入层 -> 运行时状态层 -> 输出层”的分层。
2. 缺少“模板 ID”和“运行时实例 ID”的唯一性策略。
3. 缺少 run 开始前的“编译/校验阶段”。
4. 缺少公式变量作用域、依赖关系和循环检测。
5. 缺少“公式负责算值，动作负责改状态”的强边界。
6. 缺少运行时观测日志与回放字段。
7. 缺少确定性排序、精度和舍入规则。
8. 缺少死亡、净化、控制解除后的清理顺序。

所以本轮建议不是直接从“技能伤害怎么结算”开始，而是先固定下面这条主线：

`Bundle 静态定义 -> RunInput 编译 -> RuntimeState 初始化 -> EventQueue 推进 -> 四通道结算 -> Result / Logs 输出`

## 3. 四层模型

### 3.1 静态定义层：`EngineBundle`

这一层来自版本化 bundle，只描述“有哪些规则”，不描述“这场战斗当前是多少值”。

建议最少包含：

```ts
type EngineBundle = {
  meta: EngineMeta
  attributeDefinitions: AttributeDefinition[]
  coefficientBuckets: CoefficientBucket[]
  formulaProfiles: FormulaProfile[]
  formulaBindings: FormulaBinding[]
  types: TypeDefinition[]
  typeRelations: TypeRelation[]
  statusActionControlRules: StatusActionControlRule[]

  heroes: HeroTemplate[]
  skills: SkillTemplate[]
  items: ItemTemplate[]
}
```

这一层只回答：

- 有哪些属性
- 属性属于什么值类别
- 有哪些角色模板
- 有哪些技能模板
- 有哪些装备模板
- 哪些对象挂了哪些 type/tag
- 哪个绑定点应该用哪条公式
- 哪些乘区桶存在

它不回答：

- 本场 run 的英雄等级是多少
- 本场 run 技能等级是多少
- 当前 HP/MP 是多少
- 哪个护盾实例还剩多少值

### 3.2 运行输入层：`EngineRunInput`

这一层来自浏览器，只描述“这场战斗要怎么开局”。

建议扩展理解为：

```ts
type EngineRunInput = {
  seed?: number
  stop: StopCondition
  initial: {
    self: CombatantRunInit
    enemy: CombatantRunInit
  }
  overrides?: {
    self?: CombatantOverride
    enemy?: CombatantOverride
  }
}

type CombatantRunInit = {
  heroId: string
  level: number
  skillLevels: Record<string, number>
  itemIds: string[]
}
```

关键点：

- 英雄等级、技能等级由浏览器输入，进入 Wasm 时必须是确定值。
- “因等级成长得到的值”和“战斗中因技能/装备改出来的值”必须分开。
- 输入层只给初始快照，不直接暴露运行时内部结构。

### 3.3 编译层：`CompiledRunSnapshot`

这是你原始 10 点里没有显式提到，但必须补的一层。

它负责把：

- 静态定义层
- 本次 run 输入层

编译成“可执行的确定性快照”。

```ts
type CompiledRunSnapshot = {
  self: CombatantCompiledSnapshot
  enemy: CombatantCompiledSnapshot
  triggerIndex: TriggerIndex
  formulaIndex: FormulaIndex
}
```

编译层要做的事：

1. 校验引用是否存在。
2. 把等级成长折算成确定初值。
3. 把技能等级折算成确定的等级表索引。
4. 把装备挂带的技能展开到拥有者身上。
5. 把 type relations 编译成可快速查询的标签索引。
6. 把公式绑定解析成运行时可直接执行的引用关系。
7. 为双方生成互不冲突的运行时 owner/source 标识。

### 3.4 运行时状态层：`RuntimeState`

这一层才是真正会在事件推进中不断变化的东西。

```ts
type RuntimeState = {
  nowMs: number
  combatants: Record<ActorId, CombatantRuntime>
  cooldowns: Record<RuntimeSkillId, CooldownState>
  stacks: Record<StackId, StackState>
  modifiers: ModifierInstance[]
  statuses: StatusInstance[]
  shields: ShieldInstance[]
  activeExecutions: ExecutionInstance[]
  pendingIntents: PendingIntent[]
  queue: EventMinHeap
  logs: RuntimeLogEntry[]
}
```

这一层回答：

- 当前时刻是多少
- 当前 HP/MP/护盾是多少
- 哪个技能还在 CD
- 哪个引导技能还在执行
- 哪个状态还没过期
- 下一批事件是什么

## 4. 整体数据流

```mermaid
flowchart TD
    A[Bundle 静态定义] --> B[RunInput]
    B --> C[CompileAndValidate]
    A --> C

    C --> D[CombatantCompiledSnapshot]
    C --> E[TriggerIndex / FormulaIndex / TypeIndex]

    D --> F[RuntimeState 初始化]
    E --> F

    F --> G[种入初始事件]
    G --> H[最小堆 EventQueue]
    H --> I[按 tMs / priority / seq 出队]

    I --> J[applyRatesUntil(now)]
    J --> K[校验动作合法性]
    K --> L[执行事件]
    L --> M[公式求值]
    M --> N[四通道结算]
    N --> O[更新 RuntimeState]
    O --> P[写日志 / 采样 / done 判定]
    P --> Q[派生 TriggerEvent]
    Q --> R[执行 mechanics actions]
    R --> S[生成新 InternalEvent]
    S --> H
```

核心原则：

- 公式不直接写状态。
- 动作不直接猜公式。
- 属性回复不按“每秒推一个事件”硬跑，而是按需惰性推进。
- 所有自动触发最后都回到“新事件入堆”。

## 5. 你列出的 10 点，按主链路重组后的实现要点

### 5.1 属性定义与初始化

先把属性定义清楚，后面的引用、修改、公式和乘区才有稳定落点。

建议属性定义最少包含：

```ts
type AttributeDefinition = {
  attrKey: string
  valueKind: "scalar" | "ratio" | "rate" | "flag"
  defaultValue: number
  rateTargetAttrKey?: string
  canBeCurrent?: boolean
  canBeMax?: boolean
  allowNegative?: boolean
  clampPolicy?: "none" | "min_zero" | "custom"
}
```

建议把属性再分成两类：

1. 面板属性
   例如 `attack_damage`、`ability_power`、`armor`
2. 资源属性
   例如 `hp`、`mana`、`energy`

其中资源属性还要区分：

- `base`
- `max`
- `current`
- `extra`

推荐运行时不要只保留一个 `attrs[attrKey]`，而是保留更明确的结构：

```ts
type AttributeRuntimeValue = {
  base: number
  bonusFlat: number
  bonusRatio: number
  finalValue: number
}

type ResourceRuntimeValue = {
  current: number
  max: number
  extra?: number
  lastUpdateMs: number
}
```

这样做的原因：

- 等级成长通常进入 `base`
- 装备常驻属性通常进入 `bonusFlat` 或 `bonusRatio`
- 技能临时 buff 通常进入 modifier 实例
- HP/MP 的当前值不能和攻击力这类值共用同一变更通道

### 5.2 人物初始化属性定义

这是本轮最关键的边界之一。

浏览器给 Wasm 的应该是“确定的开局值”，而不是“还没算完的成长规则”。

推荐初始化顺序：

```text
英雄模板基础值
-> 套用等级成长
-> 套用装备常驻属性
-> 套用输入覆盖值
-> 生成初始 current/max/resource/cooldown/skillLevel 快照
```

伪代码：

```ts
function compileCombatant(bundle, init, override, side): CombatantCompiledSnapshot {
  hero = mustGetHero(bundle, init.heroId)
  level = mustBeValid(init.level)
  skillLevels = normalizeSkillLevels(hero, init.skillLevels)
  items = init.itemIds.map(id => mustGetItem(bundle, id))

  baseAttrs = resolveHeroBaseAttrs(hero, level)
  itemAttrs = resolveStaticItemAttrs(items)
  mergedAttrs = mergeStaticAttrs(baseAttrs, itemAttrs)
  overriddenAttrs = applyBaseStatOverrides(mergedAttrs, override.baseStats)

  return {
    actorId: side,
    heroId: hero.heroId,
    level,
    skillLevels,
    attrs: overriddenAttrs,
    resources: buildInitialResources(overriddenAttrs),
    ownedSkills: collectOwnedSkills(hero, items, skillLevels, side)
  }
}
```

关键约束：

- 等级成长只在 compile 阶段落一次，不要在运行时反复重新算。
- 运行时的技能、装备动作造成的变化，必须和“升级带来的变化”分开。
- 如果后面支持升级过程，那也应表现为一个显式事件，而不是偷偷改 base。

### 5.3 装备和技能定义的输入

建议把技能和装备都视为“模板 + 运行时拥有关系”，而不是直接把技能复制粘贴进角色对象。

```ts
type SkillTemplate = {
  skillId: string
  ownerType: string
  ownerId: string
  skillKey?: string
  params?: SkillParams
  cooldowns?: CooldownDefinition[]
  timingProfile?: TimingProfile
  mechanicsConfig: MechanicsConfig
}

type ItemTemplate = {
  itemId: string
  skillRefs?: string[]
  statsModifier?: unknown
}
```

输入层只需要给：

- 角色模板 ID
- 装备模板 ID 列表
- 技能等级

然后由 compile 阶段做两件事：

1. 找到角色自带技能模板
2. 展开装备引用的技能模板

### 5.4 装备和技能的关联与唯一性

这是你明确提到、而且必须先拍板的点。

要严格区分三种 ID：

1. 模板 ID
   例如 `item_bork`、`skill_katarina_r`
2. 运行时拥有者 ID
   例如 `self.hero`、`enemy.item.slot_2`
3. 运行时来源 ID
   例如 `self:item:item_bork:passive_1`

推荐结构：

```ts
type RuntimeOwnedSkill = {
  runtimeSkillId: string
  sourceOwnerRuntimeId: string
  templateSkillId: string
  side: "self" | "enemy"
  slot?: string
}
```

这样即使：

- 我方和敌方都带同一件装备
- 我方和敌方都拥有同一条技能模板
- 同一单位身上有多个相同来源类型

也不会冲突，因为运行时始终按“阵营 + 拥有者实例 + 模板”唯一定位。

建议直接禁止以下错误做法：

- 只用 `skillId` 作为运行时唯一键
- 只用 `itemId` 作为运行时唯一键
- 直接把“Q/W/E/R”当唯一引用键

### 5.5 类型联动系统

类型系统不应该只服务页面筛选，它在 Wasm 内部要承担 3 个角色：

1. 稳定标签系统
2. 触发联动索引
3. 规则路由条件

建议 compile 时生成：

```ts
type TypeIndex = {
  byTarget: Record<string, Set<number>>
  byType: Record<number, string[]>
}
```

推荐约定：

- 技能、装备、角色、状态、动作都可以挂 type/tag
- 机制联动优先依赖稳定 type，不依赖中文文案或 skillKey

例如：

- A 技能挂 `type=spell.fire`
- B 被动订阅 `on_spell_cast && source has type spell.fire`
- 某控制只禁止 `abilityTag=dash`

这样比直接写：

- “如果释放的是火球术”
- “如果技能名等于某某”

更稳定，也更适合跨游戏。

### 5.6 乘区计算

这部分必须拆成两个域：

1. 属性域 `attribute`
2. HP 变更域 `hp_change`

因为：

- 攻击力、法强、移速、攻速等属性本身就可能有乘区
- 真正打到 HP 时，还会有另一套增伤/减伤/受疗/护盾顺序

建议统一使用 `coefficient_buckets`：

```ts
type CoefficientBucket = {
  bucketKey: string
  resolutionDomain: "attribute" | "hp_change"
  stageKey: string
  targetAttrKey?: string
  aggregationMode: "add" | "multiply" | "pick_max" | "set_final"
}
```

建议顺序：

#### 属性域

```text
base
-> flat_bonus
-> percent_bonus
-> multiplicative_bonus
-> final_override
-> clamp
```

#### HP 变更域

```text
formula_base
-> source_outgoing
-> target_incoming
-> mitigation
-> post_mitigation
-> shield
-> hp_apply
```

关键边界：

- 属性乘区解决“最终攻击力是多少”
- HP 乘区解决“这次伤害/治疗最后落多少”
- 不能把两层乘区揉成一层，否则调试会非常痛苦

### 5.7 公式输入与自动计算机制

公式系统推荐坚持两个原则：

1. 公式只负责算值
2. 动作只负责把值应用到目标

```ts
type FormulaProfile = {
  formulaId: string
  formulaType: "damage" | "heal" | "cooldown" | "attr" | "resource"
  formulaKind: string
  params: unknown
}

type FormulaBinding = {
  targetCategory: "skill" | "hero" | "item" | "global"
  targetId: string
  bindingKey: string
  formulaId: string
  overrideParams?: unknown
}
```

建议 bindingKey 直接表达用途，而不是模糊复用：

- `damage.main`
- `damage.tick`
- `heal.main`
- `cooldown.base`
- `resource_cost.mana`
- `panel.display`

公式变量来源建议至少支持：

```ts
type FormulaVarRef =
  | { kind: "const" }
  | { kind: "table"; by: "skillLevel" | "championLevel" }
  | { kind: "attr"; attrKey: string; target: "self" | "enemy" }
  | { kind: "resource"; resourceKey: string; target: "self" | "enemy"; field: "current" | "max" }
  | { kind: "stack"; stackId: string }
  | { kind: "cooldown"; runtimeSkillId: string; field: "remainMs" }
  | { kind: "formula_ref"; formulaId: string }
```

必须补的 3 条约束：

1. 变量作用域明确
   例如 `self.attack_damage`、`enemy.hp.current`
2. 公式依赖图可校验
   防止 `A -> B -> A` 循环
3. 公式执行默认只读
   不能在公式里直接改 CD、改 HP、改属性

真正修改状态要走 action：

- `deal_damage`
- `deal_heal`
- `apply_modifier`
- `apply_shield`
- `set_cooldown`

### 5.8 事件驱动机制

事件驱动内核建议保持最小堆：

```ts
type InternalEvent = {
  tMs: number
  priority: number
  seq: number
  type: string
  payload: unknown
}
```

排序键固定：

`(tMs, priority, seq)`

建议运行循环：

```ts
while (!queue.isEmpty() && !shouldStop(runtime)) {
  const now = queue.peek().tMs

  while (!queue.isEmpty() && queue.peek().tMs === now) {
    const event = queue.pop()

    applyRatesUntil(event, runtime, now)

    const disposition = canRun(event, runtime)
    if (disposition.kind === "drop") continue
    if (disposition.kind === "cancel") {
      emitBlockedOrInterrupted(event, runtime)
      continue
    }

    const changes = dispatch(event, runtime)
    writeLogs(changes, runtime)
    enqueue(changes.nextEvents, runtime.queue)
  }

  emitSamplesIfNeeded(runtime, now)
}
```

控制机制要在 `canRun(event, runtime)` 中统一判断：

- 是否被眩晕、沉默、缴械、压制阻断
- 是否仍在 CD
- 是否资源不足
- 是否被 directive 强制改写行为

不要做的事：

- 从堆里扫描“哪个未来事件现在唯一可执行”
- 直接跳过更早时刻事件去执行后面的事件

### 5.9 HP 变更与护盾机制

建议把所有会改 HP 的东西统一收敛成 `HpChangePacket`：

```ts
type HpChangePacket = {
  kind: "damage" | "heal"
  hpChangeType: string
  sourceId: string
  targetId: string
  baseAmount: number
  tags: string[]
  flags?: {
    ignoreShield?: boolean
    allowOverheal?: boolean
  }
}
```

伤害主链路：

```text
公式求值
-> source_outgoing 乘区
-> target_incoming 乘区
-> 抗性/减伤
-> 免伤/无敌检查
-> 护盾吸收
-> HP 扣减
-> 死亡/濒死/后置事件
```

治疗主链路：

```text
公式求值
-> source_outgoing 治疗系数
-> target_incoming 受疗系数
-> 上限截断
-> HP 增加
```

护盾必须作为实例存在，而不是普通属性：

```ts
type ShieldInstance = {
  instanceId: string
  ownerId: string
  sourceId: string
  shieldKey: string
  amount: number
  scope: "all" | "physical" | "magic" | "custom"
  priority: number
  expireAtMs: number | null
}
```

原因：

- 同时可能存在多个护盾
- 护盾有过期、打破、刷新、叠加语义
- 不同伤害类型与不同护盾 scope 交互不同

### 5.10 N 点回复/秒机制

这一类不要实现成“每秒定时触发一个事件”，而应该实现成“惰性结算”。

推荐模型：

```ts
type RateAttribute = {
  attrKey: string
  valueKind: "rate"
  rateTargetAttrKey: string
}
```

应用规则：

```ts
function applyRatesUntil(actor, nowMs) {
  dt = (nowMs - actor.lastUpdateMs) / 1000
  for (rateAttr of actor.rateAttrs) {
    delta = rateAttr.valuePerSec * dt
    actor.resources[rateAttr.rateTargetAttrKey].current += delta
  }
  actor.lastUpdateMs = nowMs
}
```

触发时机：

- 读当前 HP/MP 前
- 判定资源是否足够施法前
- 处理状态到期或回复抑制前

优点：

- 不会为每个回复源都塞大量 tick 事件
- 时间推进仍然是事件驱动，不退化成帧循环
- 更适合 HP/MP/能量等持续资源

## 6. 这 10 点之外，建议补进概要设计的缺失项

### 6.1 编译/校验阶段

在 run 真正进入事件队列前，必须先做 compile/validate。

最少校验：

- 属性 key 存在
- hero/item/skill 引用存在
- formula binding 引用存在
- type relation 引用存在
- skill level 合法
- cooldown/resource 公式可解析
- 公式依赖无环

没有这层，后面所有报错都会在运行时爆炸。

### 6.2 模板与实例分离

建议在文档里明确三套名字：

- `Template`
- `Owned`
- `RuntimeInstance`

否则“同一条技能模板被我方装备和敌方装备同时引用”这种场景一定会乱。

### 6.3 公式与动作解耦

建议直接写进文档的硬约束：

- 公式只返回值
- action 决定这个值落到哪里
- 同一公式结果可以同时服务多个 action

例如：

- 同一数值既能作为伤害
- 也能作为护盾
- 也能作为面板显示

### 6.4 运行观测日志

建议从概要阶段就预留：

```ts
type RuntimeLogEntry = {
  tMs: number
  eventType: string
  sourceId?: string
  targetId?: string
  valueBefore?: number
  valueAfter?: number
  detail?: unknown
}
```

至少能回答：

- 哪次伤害被什么护盾吸收了多少
- 哪个状态导致了哪次打断
- 哪个公式在本次事件里算出了多少

### 6.5 精度与确定性

建议在概要阶段直接固定：

- 时间统一整数毫秒
- 同刻事件稳定排序
- 小数精度统一保留策略
- 舍入规则统一

否则后面做黄金样例会不停漂移。

### 6.6 死亡、净化、状态清理顺序

建议补一条清理顺序：

```text
HP 结算
-> 死亡判定
-> 护盾/状态/执行实例清理
-> 触发死亡相关后置事件
-> done 判定
```

不先固定这个顺序，后面会出现：

- 死亡后 tick 还在跑
- 净化后旧 interrupt 还命中
- 已取消技能的旧 phase 事件还落地

## 7. 推荐的最小伪代码骨架

```ts
function init(bundle: EngineBundle) {
  validateBundle(bundle)
  indexes = buildIndexes(bundle)
  return { bundle, indexes }
}

function run(ctx, input: EngineRunInput) {
  validateRunInput(ctx.bundle, input)

  compiled = compileRunSnapshot(ctx.bundle, ctx.indexes, input)
  runtime = buildRuntimeState(compiled, input.seed)

  seedInitialEvents(runtime, compiled)

  while (!runtime.queue.isEmpty() && !shouldStop(runtime, input.stop)) {
    now = runtime.queue.peek().tMs

    for (event of popBatch(runtime.queue, now)) {
      applyRatesUntilAffectedActors(runtime, event, now)

      result = canRun(event, runtime)
      if (result.kind !== "run") {
        handleEventDisposition(runtime, event, result)
        continue
      }

      internalChanges = dispatchInternalEvent(runtime, event)
      triggerEvents = deriveTriggerEvents(internalChanges)

      for (trigger of triggerEvents) {
        actions = matchTriggerRules(compiled.triggerIndex, trigger, runtime)
        for (action of actions) {
          packets = executeActionToPackets(action, runtime, compiled.formulaIndex)
          applyPackets(runtime, packets)
        }
      }

      emitLogsAndSamples(runtime, now)
    }
  }

  return buildRunOutput(runtime)
}
```

这个骨架背后的边界是：

- `dispatchInternalEvent` 负责推进内部状态
- `matchTriggerRules` 负责找联动
- `executeActionToPackets` 负责把 action 变成 damage/heal/modifier/shield/cooldown 等标准包
- `applyPackets` 负责真正改状态

## 8. 本轮建议先拍板的结论

如果只先定本轮最重要的几个结论，建议先定这 9 条：

1. 属性必须有 `valueKind`，`rate` 必须显式指向目标属性。
2. run 输入中的英雄等级、技能等级进入 Wasm 时必须是确定值。
3. 角色升级成长与战斗中属性变化必须分层。
4. 技能和装备都只保留模板，运行时通过 owner/source 实例化。
5. 我方和敌方可引用同一模板，但运行时必须有不同实例 ID。
6. 乘区必须拆成 `attribute` 域和 `hp_change` 域。
7. 公式只算值，动作只改状态。
8. 回复/回蓝等 `N/秒` 机制采用惰性更新，不采用固定 1 秒 tick。
9. run 前必须有 compile/validate 阶段，不能把所有错误拖到运行时。

## 9. 推荐实施顺序
