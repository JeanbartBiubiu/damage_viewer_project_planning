# 通用 1v1 战斗数据模型替换方案

本文定义后端战斗数据模型的边界和模块关系。具体表、字段、DDL、接口和迁移步骤见 [通用 1v1 战斗数据模型 DDL 与接口详细设计](../../详细设计/server/game_manage/通用1v1战斗数据模型DDL与接口详细设计.md)。后端与 DDL 已切换到通用 `combat-data`；验证证据见 [通用1v1战斗数据模型验证记录-2026-07-12](../../测试记录/server/game_manage/通用1v1战斗数据模型验证记录-2026-07-12.md)。

## 1. 目标

将以 hero/item/skill、状态专用表、`mechanics_config`、Bundle snapshot 和 Wasm Catalog 为中心的数据面，替换为与具体游戏实体类别无关的通用 1v1 战斗模型。

目标模型满足：

1. 后端只保存最新的结构化战斗数据，并提供细粒度读写接口。
2. Web 可直接请求最新数据，也可缓存到 IndexedDB；Web 负责语义校验、选择两个实体、组装 source/target 和 `CompileRequest`。
3. Wasm ABI 和 TinyGo runtime 本任务不修改。
4. 数据写入后立即对 Public GET 可见，不再区分 workspace 与 published snapshot。
5. `versions:publish` 只记录本次 revision 内发生变化的数据到 `_log`，不生成 Bundle、Catalog 或其他全量 JSON 快照。
6. 所有模型只考虑 1v1；目标选择固定为 self/opponent/source/target，不设计群体、空间或随机目标查询。

## 2. 核心边界

### 2.1 后端负责

1. 保存 entity、attribute、resource、provider、ability、phase、formula、modifier、listener、effect 等最新结构化数据。
2. 维护全局 reserved type、游戏自定义 type 和 type relation。
3. 为每个游戏维护单调递增的 `change_revision`。
4. 提供普通 GET/PUT 接口。
5. 在发布时把发生变化的行写入对应 `_log`。
6. 通过数据库列类型、NOT NULL、唯一约束、FK 和一对一约束保证存储结构完整。

### 2.2 后端不负责

1. 不校验某个 operation/type/formula 是否能被当前 Wasm 执行。
2. 不校验 formula AST、机制引用闭包、数值边界或 1v1 业务语义。
3. 不组装 Catalog、Bundle、CompileRequest、initial snapshot、driver plan 或 run request。
4. 不保存用户选择、数值覆盖、模拟 session、Wasm state 或计算结果。
5. 不提供批量写入、DELETE、机制图原子保存或跨请求一致性。

### 2.3 Web 负责

1. 校验 reserved type、formula、operation detail、引用和当前 Wasm 能力。
2. 将 entity/provider/ability/effect 等表数据组装为当前 Wasm DTO。
3. 选择两个 entity 并物化为 source/target。
4. 对 provider/formula/ref 做 source/target 命名空间改写。
5. 管理 IndexedDB 缓存和 revision 失效。
6. 接受多次 PUT 期间短暂读到半成品机制图；读取前后 revision 不一致时重新加载。

## 3. 目标数据流

```text
Wiki/人工数据
  → Web 本地转换与校验
  → 后端细粒度 PUT
  → 最新结构化主表（立即可见）

Web 模拟页
  → GET 最新 entity/provider/ability/effect 数据
  → IndexedDB 可选缓存
  → Web 选择 source/target、组装 CompileRequest
  → Worker/Wasm

Admin 发布
  → 冻结当前 change_revision
  → 将本次变化行复制到各表 _log
  → 写 game_versions.change_revision
  → 不生成任何全量快照
```

## 4. 通用领域模型

### 4.1 Entity

`game_entities` 表示参与战斗配置的对象，包括角色、装备、符文、强化、召唤物和训练假人。具体类别通过 type relation 表达，不再使用 hero/item 专用主表。

本模型只保存战斗相关字段。价格、配方、称号等非战斗信息不在本任务范围。

### 4.2 Attribute 与 Resource

属性和资源严格分开：

- attribute：攻击力、护甲、移速、暴击率等可被 modifier 解析的数值。
- resource：生命、法力、能量、怒气等具有初始值和最大值、会被消耗或回复的数值。

实体的阶段数值以结构化行保存，阶段值定义为该阶段的绝对值，不继续兼容旧 `base_stats/stats_by_level` 的多种 JSON 方言。

### 4.3 Provider

每一个真实被动、状态、装备效果、符文效果或强化效果都是独立 provider。不同数值或逻辑表示不同 provider，不引入参数化 provider template 或 mount 参数覆盖。

entity 可以挂载多个 provider。多个 provider 同时监听事件、产生 modifier 或 effect，最终由 Web/Wasm 按各自规则累加和执行。

### 4.4 Ability 与 Phase

ability 私属于 provider。时间结构使用通用 phase：cast、channel、impact、tick、recovery 等 phase 由 reserved type 表示。cost、cooldown 和 effect sequence 绑定 ability/phase，不再使用 `skills.timing_profile` 大 JSON。

### 4.5 Formula

formula 私属于 provider，可被该 provider 下的 ability、modifier、listener 和 effect step 复用，不允许跨 provider 引用。formula AST 是递归异构结构，使用单独 JSONB 字段保存；不再与整份 mechanics JSON 混合。

### 4.6 Modifier

每条 modifier 自己声明目标属性、计算方式、stage、bucket、priority、value formula 和 condition formula。叠加规则不放在 attribute definition 中。

### 4.7 Listener 与 Effect

listener 使用 event type 和 any/all/none type matcher。触发后引用私有 effect sequence。effect sequence 下的 step 有稳定顺序；公共 step 与 damage/heal/resource/attribute/shield/provider/event/ability-control 等 detail 表形成一对一关系。

ability phase、listener、provider tick 分别通过明确关联表连接 sequence，不使用 `owner_kind + owner_id` 软引用。

### 4.8 State

provider/ability state 首版只支持结构化标量字段：number、boolean、string、timestamp、entity_ref 等。复杂数组/map 暂不进入首版；运行态 state 不保存到后端。

## 5. Type 体系

保留并扩展现有：

1. `reserved_type`：系统、Wasm、Web 等跨模块定义的稳定 type。
2. `reserved_type_relation`：reserved type 层级。
3. `types`：游戏自己的 type 或 reserved type 的游戏内映射。
4. `type_relations`：把 type 挂到 entity、provider、ability、phase、modifier、listener、effect step、attribute、resource 或 type。

`reserved_type` 和 `types` 增加稳定 `type_key`。operation、selector、modifier policy、phase、event、damage type 等引擎固定词表使用 reserved type。数据库中的 type 只登记已有语义，不会创造新的 Wasm handler。

1v1 selector 固定使用 reserved type：self、opponent、source、target；不建立 target selector 定义表。

## 6. Revision 与日志

每个游戏维护：

```text
current_revision
published_revision
```

一次 Admin PUT 事务只增加一次 revision，本请求修改的主表行共享该 revision。Public 始终读取最新主表。

发布时：

1. 锁定该 game 的 revision state。
2. 创建 `game_versions` 记录并保存本次 `change_revision`。
3. 查询 `(previousPublishedRevision, currentRevision]` 内变化的主表行。
4. 将行复制到对应 `_log`，以 `version_id` 作为发布边界。
5. 更新 `published_revision` 和 current version。

主表不再保存 `start_version_id/end_version_id`。`updated_at` 只用于展示，不参与差异判断。

## 7. 一致性与编辑限制

1. 数据立即可见。
2. 不提供 batch，因此跨请求写入 provider graph 不原子。
3. 前端允许短暂读到半成品，以 revision 前后复核处理。
4. 不提供 DELETE；主表不增加 tombstone。需要修改结构时使用稳定 ID PUT 覆盖。真正删除能力另立任务。
5. effect step 的公共行和 detail 由一个 PUT 在单事务写入；operation family 改变时允许服务内部清理旧 detail，但不暴露 DELETE API。

## 8. 旧模型退出范围

已废弃并删除：

- heroes/items/skills 及 log
- item stat modifiers、skill mounts、owner categories 及 log
- formula profiles/bindings 及 log
- coefficient buckets 及 log
- status definitions、modifier groups、attribute modifiers、periodic HP effects、action control、control state profiles 及 log
- published bundle snapshots
- wasm catalog source/source log/published snapshots
- 对应 Mapper、Service、Controller、缓存和 Bootstrap adapter

保留并改造：games、game_versions、game progression、images、attribute definitions、reserved type、types、type relations。

## 9. 迁移策略（历史说明）

实施顺序已完成，保留如下说明供理解切换路径：

1. 先落新表、revision 和新接口，不在旧表上继续堆新机制。
2. Wiki 原始数据作为重新转换的主要来源。
3. 只自动迁移 ID、名称、type、基础属性/资源等确定性数据；复杂 mechanics/status/formula 不做猜测转换。
4. 转换过程中按 provider/ability/effect 小步录入，并由 Web/Wasm 验证。
5. 物理删除旧表和旧接口；最终状态不保留双读或兼容 adapter。

已有库迁移顺序：generic compatibility → triggers → final drop → reserved seed。新库：schema + triggers + reserved seed。

## 10. 验收结果

当前后端满足：

1. 数据库只有最新结构化战斗数据和差异 `_log`，没有 Bundle/Catalog blob。
2. Public GET 立即反映最新 PUT。
3. Web 可仅通过新接口构造当前 1v1 `CompileRequest`（Web 侧组装仍由其负责）。
4. Wasm 无代码和 ABI 变化。
5. 新机制优先通过新增 reserved type、provider/ability/effect 配置表达，不再新增游戏专用状态表。
