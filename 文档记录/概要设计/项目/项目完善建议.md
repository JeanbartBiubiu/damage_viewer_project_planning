# 项目规划完善建议

基于现有的 `项目简介.md`，我针对各个模块进行了详细的分析，并提出了以下完善建议。这些建议旨在增强系统的可扩展性、性能和可维护性。

## 1. 总体设计与架构

### 1.1 版本管理策略 (核心增强)
- **现状**: 提到后端和数据库存储不同版本，前端轮询更新。
- **问题**: 游戏数据的版本通常与游戏补丁（Patch）挂钩（如 LoL 14.1, 14.2）。简单的“最新版本”可能不够，用户可能需要查看“历史版本”的数据来做对比。
- **建议**:
    - **显式版本号**: 引入 `GamePatch` 概念（如 `v14.1`, `v14.2`）。
    - **增量更新**: 前端本地存储当前版本号，请求接口时带上版本号。如果差异不大，后端返回 Patch Diff（增量包），否则返回全量包。
    - **对比模式**: 系统应原生支持“版本对比”功能，即同时加载两个版本的数据（如 14.1 vs 14.2）进行同一套连招的伤害计算。

### 1.2 离线能力 (PWA)
- **现状**: 提到 IndexDB 缓存。
- **建议**: 明确引入 **PWA (Progressive Web App)** 标准。
    - Service Worker 拦截请求，优先读取 Cache/IndexDB。
    - 即使在断网情况下，用户只要之前访问过，依然可以打开网页进行计算（静态资源 + 本地数据）。

## 2. 数据库设计 (PostgreSQL)

### 2.1 表结构优化
- **现状**: 单表 `attribute` + 分区。
- **问题**: 游戏数据结构复杂，单一扁平表难以表达“技能”、“装备”、“符文”、“属性加成规则”。
- **建议**: 采用 **JSONB** 配合 **关系型表**，兼顾灵活性和查询能力。

```sql
-- 游戏版本表
CREATE TABLE public.game_patches (
    game_id varchar(64) NOT NULL,
    patch_version varchar(32) NOT NULL, -- e.g., '14.23'
    release_date timestamp,
    data_hash varchar(64), -- 用于前端校验数据一致性
    CONSTRAINT pk_game_patches PRIMARY KEY (game_id, patch_version)
);

-- 基础属性/实体表 (版本化)
-- 不建议仅用 log 表，建议直接在主数据带上 version 字段，或者使用 Snapshot 设计
CREATE TABLE public.game_entities (
    game_id varchar(64) NOT NULL,
    entity_type varchar(32) NOT NULL, -- 'champion', 'item', 'rune'
    entity_id varchar(64) NOT NULL,   -- 'ahri', 'infinity_edge'
    patch_version varchar(32) NOT NULL,
    
    -- 核心数据使用 JSONB 存储，因为不同游戏的结构差异巨大
    -- LoL 英雄有 mana, energy; 云顶有 gold cost; 
    base_stats jsonb NOT NULL, 
    skills jsonb NOT NULL,
    
    CONSTRAINT pk_game_entities PRIMARY KEY (game_id, entity_id, patch_version)
) PARTITION BY LIST (game_id);
```

### 2.2 读写分离与缓存
- **建议**: 写入操作（编辑模式）更新 DB 后，触发一个异步任务，生成该版本的静态 JSON 文件推送到对象存储（或 Nginx 静态目录）。
- **优势**: 普通用户的“读”操作直接请求静态 JSON 文件，完全绕过数据库，实现极致的高并发性能（符合 10w 日活高性能要求）。

## 3. 计算核心 (Wasm/Go)

### 3.1 模拟引擎架构
- **现状**: 事件驱动，优先级队列。
- **补充**: 需要补充 **状态管理 (Status Manager)** 和 **快照 (Snapshot)** 机制。
    - **Buff/Debuff**: 很多伤害变化来自临时状态（如征服者层数、中毒）。事件队列不仅处理“主动技能”，还要处理“Buff 每一跳(Tick)”和“Buff 过期”。
    - **属性快照**: 在计算过程中，属性是动态变化的。计算伤害时需要获取“当前时刻”的属性快照（Snapshot）。

### 3.2 性能对比 (Go vs JS)
- **建议**: 定义一套标准的 Benchmark 用例（例如：攻速 2.5 的 1000 次普攻，复杂技能循环 10000 次）。
- **Wasm 通信**: 注意 Go Wasm 与 JS 的数据传输成本。频繁的小数据交互可能比 JS 直接计算更慢。
    - **策略**: “一次输入，全部执行”。前端将所有配置打包传给 Wasm，Wasm 跑完整个模拟流程，只返回结果数组（时间轴数据），减少跨语言调用次数。

## 4. 前端架构 (React)

### 4.1 模块化与扩展性
- **现状**: 需要支持多游戏。
- **建议**: 采用 **插件化/配置化 UI**。
    - 不同游戏的面板可能不同（LoL 是 6 格装备，云顶是 3 格）。
    - 抽象出 `<Inventory />`, `<StatsPanel />` 等通用组件，通过 Config 渲染。

### 4.2 数据流
- **IndexDB 封装**: 使用 `idb` 或 `Dexie.js` 等库简化 IndexDB 操作。
- **状态管理**: 推荐 `Zustand` 或 `Jotai`，适合这种高频交互、局部状态更新（如修改一个攻击力，立刻重算）的场景。

## 5. 待确认问题

1. **数据来源**: 初始数据是人工录入，还是有爬虫/API 对接？如果是人工，需要一个强大的 Admin 后台。
2. **多语言支持**: 是否考虑国际化（i18n）？
3. **协作功能**: 是否允许用户分享自己的“配置/连招”（Share Config）？这涉及到后端存储用户的配置数据。
