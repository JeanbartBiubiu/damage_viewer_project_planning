# 平台推进路线：前后端录入优先，计算后置

方案版本：0.2
方案状态：方向已由项目负责人确认；当前已进入属性与战斗资源管理详细设计，尚未编码或执行数据库操作。

1. [项目研发背景与需求说明](../../需求澄清/项目/背景说明.md)
2. [数据录入分阶段推进方案](./数据录入目标推进.md)
3. [属性与战斗资源管理重构详细设计](../../详细设计/项目/属性与战斗资源管理重构详细设计.md)

## 1. 当前结论

Damage Viewer 的长期目标仍是伤害模拟、版本对比和结论复核，但当前开发顺序调整为：

1. 先完成可实际使用的前端录入页面和后端数据管理。
2. 再完成对象关系、保存校验和发布版本。
3. 由项目负责人通过真实网页录入确认体验。
4. 最后重新设计发布配置到计算输入的转换，并决定后续 Wasm 开发。

现有 Wasm 不删除，但暂停新增机制、接口演进和由 Wasm 反推作者配置结构。当前不再把 Wasm 验证通过作为录入阶段的前置条件。

## 2. 为什么需要调整主线

当前系统已经具备大量数据表、细粒度读写接口、分表页面和 Wasm 装配链，但它们主要围绕运行时战斗图组织：

1. 用户维护一个角色或能力时，需要跨多个页面理解内部标识、类型编号和底层关系。
2. 页面数量和接口数量已经很多，但缺少围绕一个业务对象连续完成录入、校验、保存和回读的操作路径。
3. 现有数据库关系虽然较细，但表边界主要服务机制提供者、能力阶段、效果序列和效果步骤等运行时结构，不等同于易维护的作者配置模型。
4. 保存成功、发布成功和可以被 Wasm 运行是三个不同结果，当前产品表达没有充分分开。

因此本轮不是给现有分表页面继续增加控件，而是重新确定作者配置的数据边界和产品主入口。

## 3. 目标分层

```text
结构化录入页面
        ↓
可编辑的作者配置
        ↓
保存检查与关系检查
        ↓
不可随意改写的发布版本
        ↓ 录入阶段验收通过后才建设
计算输入转换层
        ↓
Wasm 计算运行时
```

各层职责必须保持独立：

1. **作者配置**回答“维护者想表达什么”，允许对象先独立存在，再逐步建立关系。
2. **发布版本**回答“哪一批配置已经冻结并通过结构与关系检查”，不承诺可计算。
3. **计算输入转换层**回答“已发布配置如何转换成稳定的计算结构”，在录入阶段结束后单独设计。
4. **Wasm 运行时**只负责确定的计算语义，不再决定录入页面和核心业务表如何组织。

## 4. 模块责任边界

### 4.1 前端

前端负责：

1. 围绕角色、属性、装备、能力内容、图片和关系提供结构化页面。
2. 管理手动保存、未保存离开提醒、字段错误定位和保存结果反馈。
3. 从业务对象两端查看关系，不要求用户复制内部标识完成挂接。
4. 在发布前展示结构与关系问题，但不展示虚构的计算结果。

前端不负责：

1. 自行扫描部分数据后宣称配置完整。
2. 在浏览器中补偿数据库缺失的核心关系约束。
3. 把当前运行时战斗图直接作为业务表单结构。

### 4.2 后端

后端负责：

1. 提供面向业务对象的列表、详情、新建、编辑和查询能力。
2. 在事务中维护稳定标识、唯一性、对象状态和明确关系。
3. 区分保存检查与发布检查，并返回可以定位到页面字段或关系的问题。
4. 保证发布版本不被后续草稿修改影响。

后端不负责：

1. 在当前阶段执行真实伤害计算。
2. 为未完成的旧数据模型提供迁移、双写或长期兼容。
3. 提前生成 Wasm 所需的最终计算输入。

### 4.3 数据库

数据库负责表达清晰的对象边界和关系方向。当前先冻结候选边界，不在概要设计中冻结全部字段：

1. 游戏根数据。
2. 角色基本资料。
3. 属性定义。
4. 装备基本资料。
5. 能力内容及可配置分类。
6. 图片资源。
7. 角色、属性、装备、能力内容、图片之间的关系记录。
8. 发布版本及其冻结内容。

已建立的核心关系必须能通过关系表和外键读懂。独立对象可以在尚未建立关系时保存；发布时再检查是否满足当前版本的完整要求。

### 4.4 Wasm

Wasm 在当前阶段仅作为冻结的既有运行时保留：

1. 不新增游戏机制。
2. 不扩展计算接口。
3. 不要求新的作者配置继续兼容现有计算输入。
4. 不把 Wasm 回归列为前后端录入阶段的默认验收。

冻结不等于删除。若以后发现现有运行时存在独立缺陷，应另行确认范围，不与本轮录入方案捆绑处理。

## 5. 产品对象与现有技术对象的关系

新的产品页面使用中文业务对象，不直接暴露现有运行时术语：

| 产品对象 | 当前可参考内容 | 当前处理原则 |
| --- | --- | --- |
| 角色 | 现有实体资料与成长曲线 | 保留可用交互经验，重新冻结角色表边界 |
| 属性 | 现有属性定义和等级值 | 先独立维护定义，具体数值放到关系阶段 |
| 装备 | 当前与角色共用的实体记录 | 改为独立业务对象，不再靠类型关系区分 |
| 能力内容 | 现有代码中的机制提供者、能力、阶段和效果图 | 当前先维护描述与分类，执行结构后置 |
| 图片 | 现有上传、预览和缓存能力 | 建立独立、稳定、可复用的图片资源 |
| 关系 | 当前挂载、类型关系和多张桥接表 | 按业务含义重新拆分，支持双向查看与移除 |
| 发布版本 | 当前修订号与发布日志基础 | 重新冻结发布前检查和不可变读取语义 |

现有 `combat-data`（战斗数据接口）和 `Provider`（机制提供者）等标识只作为现状参考，不作为新页面必须展示的产品术语。

## 6. 可保留与应替换的基础

### 6.1 可择优保留

1. React、Vite、Spring Boot 和 PostgreSQL 工程骨架。
2. 前端统一请求、错误处理、页面壳和测试基础。
3. 图片上传、预览和缓存能力。
4. 角色等级成长曲线等已证明有实际编辑价值的组件。
5. 后端事务、统一错误、稳定标识和乐观版本控制经验。
6. 现有 Wasm、计算装配代码和测试证据，作为未来转换层设计的只读参考。

### 6.2 应替换或退出主入口

1. 以约三十类底层资源表组成主导航的方式。
2. 角色、机制提供者、能力、阶段、序列和步骤分别保存的主要录入流程。
3. 让固定直伤拓扑承担通用能力录入的方式。
4. 现有以运行时表为中心的作者接口和数据库边界。
5. 缺少完整性预检与关系移除语义的现有发布模型。

旧页面和旧接口是否立即删除，由对应实施阶段决定；本概要只确认不承担长期兼容义务。

## 7. 兼容与破坏式更新边界

项目负责人已经确认当前最小可用阶段允许破坏式更新，本方案据此采用：

1. 不建设旧数据库结构到新结构的正式迁移链。
2. 不做新旧接口双写或双读。
3. 不要求新页面兼容旧页面的字段组织和路由。
4. 不要求新的作者配置继续被现有 Wasm 直接消费。

这一授权不包括：

1. 未经确认重置或删除任何具体数据库。
2. 删除未提交工作、参考分支、历史测试证据或版本库历史。
3. 在本轮方案文档中直接执行代码、脚本、配置或服务操作。

## 8. 总体阶段与恢复计算门禁

总体顺序为：作者配置基线 → 角色 → 属性 → 装备 → 能力内容 → 图片 → 关系 → 发布 → 计算输入与 Wasm。

进入计算需求澄清前必须同时满足：

1. 前述配置对象均可通过网页独立维护。
2. 核心关系可新增、查看、调整和移除，不产生失效关系。
3. 发布版本可以独立读取，后续编辑不会改写旧版本。
4. 自动检查和真实浏览器操作均通过。
5. 项目负责人亲自完成代表性录入，并明确同意进入计算阶段。

任何自动化结果都不能代替第 5 项。

## 9. 当前展开范围

当前只允许继续展开：

1. 属性定义的独立管理，包括数据库、后端接口、前端页面、保存校验和真实页面验收。
2. 将生命值、法力值、能量统一归入属性定义，新的作者配置不再建立战斗资源定义。
3. 从作者配置主入口移除旧属性/资源通用逐表页面，但不在本阶段设计角色属性值、装备加成、能力参数或计算输入。

角色、装备、能力内容、图片、关系、发布和计算阶段仍只保留范围与顺序，不提前形成可直接编码的详细设计。

属性与战斗资源详细设计必须先通过只读方案评审；编码、真实数据库重置、发布和计算阶段仍由项目负责人逐次确认。
