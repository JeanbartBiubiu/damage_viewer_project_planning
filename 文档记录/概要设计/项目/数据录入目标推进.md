# 数据录入分阶段推进方案

方案版本：0.2
方案状态：阶段顺序和总体边界已确认；项目负责人已决定当前先展开属性定义与战斗资源整合详细设计。

关联文档：

1. [项目研发背景与需求说明](../../需求澄清/项目/背景说明.md)
2. [平台推进路线：前后端录入优先，计算后置](./平台推进计划-Wasm与核心编辑后台.md)
3. [属性与战斗资源管理重构详细设计](../../详细设计/项目/属性与战斗资源管理重构详细设计.md)

## 1. 文档目的

本文只回答数据录入改造按什么顺序推进、每个阶段解决什么问题、何时允许进入下一阶段。

本文不承担以下职责：

1. 不冻结具体表名、字段类型、接口路径或页面文件。
2. 不提供可以直接交给编码代理执行的修改清单。
3. 不安排并行开发任务、预计工期或人员分工。
4. 不执行代码、脚本、配置、数据库、发布或服务启动操作。
5. 不提前设计 Wasm 机制和最终计算输入。

后续如果项目负责人决定进入某一阶段，再只为该阶段补需求细节和详细设计。

## 2. 固定推进原则

1. 一次只推进一个阶段，当前阶段未验收时不展开下一阶段。
2. 每个阶段都形成最小可用闭环：数据库保存、后端读写、前端操作、基本校验、自动检查和真实页面操作。
3. 先独立管理角色、属性、装备、能力内容和图片，再统一建立关系。
4. 核心对象和关系优先使用清晰表、关系表和外键表达，不把重要关联隐藏在大块配置内容或多态软引用中。
5. 独立对象允许先保存、后建立关系；已建立的关系必须指向真实对象。
6. 保存检查、关系检查、发布检查和未来计算检查分层处理，不把“保存成功”误说成“已经可计算”。
7. 当前按单人维护者、手动保存设计，不建设自动保存、多人冲突合并和审核流程。
8. 当前允许旧页面、旧接口和旧数据库结构不兼容，但任何具体数据库重置仍需单独确认目标。
9. Wasm 在录入阶段冻结，不与前后端录入并行扩展。
10. 自动化只能证明工程行为，是否进入下一阶段由项目负责人决定。

### 2.1 当前阶段门调整

项目负责人在 2026-08-22 查看现有页面后，决定当前先处理属性定义与战斗资源整合。该调整的边界是：

1. 只展开属性定义的独立管理和战斗资源概念退出作者配置主链。
2. 生命值、法力值、能量作为属性定义管理，不再维护平行资源定义。
3. 角色属性值、装备/能力加成、能力局部参数仍留在各自后续阶段。
4. 该决定不表示角色、装备、能力、图片、关系或发布阶段已经完成。

## 3. 阶段总览

| 阶段 | 主要目标 | 完成标志 |
| --- | --- | --- |
| 0. 作者配置基线 | 重新建立数据库、后端、前端的统一录入入口 | 空目标环境可初始化，前后端可启动，空白管理页可访问 |
| 1. 角色基本管理 | 独立维护角色基本资料 | 可新建、查询、查看、编辑并在刷新后重新读回 |
| 2. 属性管理 | 独立维护可配置属性定义 | 可维护名称、标识、数值类型、单位、范围和状态 |
| 3. 装备管理 | 独立维护装备基本资料 | 装备不依赖角色、属性或能力即可保存和重新打开 |
| 4. 能力内容管理 | 统一维护技能、天赋、被动等描述性内容 | 能力分类可配置，不要求先建立执行结构 |
| 5. 图片管理 | 建立独立、稳定、可复用的图片资源 | 可上传、预览、查询、替换和停用图片 |
| 6. 关联管理 | 建立前述对象之间的明确关系 | 可从两端查看、调整和移除关系，不产生悬空关系 |
| 7. 发布管理 | 将完整配置冻结为可追溯版本 | 后续编辑不影响旧版本，阻断问题会阻止发布 |
| 8. 计算阶段门 | 重新确认计算输入和 Wasm 需求 | 负责人完成真实录入并明确同意进入计算设计 |

阶段 1 至阶段 8 当前只冻结范围和顺序，不提前形成详细设计。

## 4. 阶段 0：作者配置基线

### 4.1 阶段目标

当前仓库已经有前端、后端、数据库和 Wasm，不需要重新创建项目。阶段 0 的含义是把“作者配置”重新确立为前后端主链，并准备后续每个业务对象都能复用的最小基础。

### 4.2 当前范围

1. 保留游戏作为数据隔离根，页面可以选择或固定当前游戏，但底层不写死英雄联盟专属规则。
2. 确定新的作者配置数据库入口和显式重置方式。
3. 建立统一的名称、稳定标识、状态、排序、备注和时间信息的基本约定；具体字段由当前阶段详细设计确认。
4. 建立统一的后端成功响应、错误响应和字段问题表达。
5. 建立前端基础布局、导航、当前游戏上下文、错误提示和空状态。
6. 建立当前阶段所需的最小自动检查入口。
7. 将现有 Wasm 验证入口移出当前产品主线；是否隐藏或保留由后续实施方案决定。

### 4.3 候选数据边界

阶段 0 只冻结边界方向，不冻结完整字段：

1. 游戏根数据独立存在。
2. 角色、属性、装备、能力内容和图片分别拥有自己的主数据边界。
3. 对象之间的关联不放入主记录的大块配置字段，统一推迟到阶段 6。
4. 发布版本与日常可编辑数据分开，具体冻结方式推迟到阶段 7。
5. 未来计算输入不进入作者配置表。

### 4.4 完成标志

1. 从明确的空目标环境开始，可以完成数据库初始化。
2. 后端可以启动并通过最小健康检查。
3. 前端可以启动并打开管理页面。
4. 前端能够展示当前游戏上下文、后端不可达和空数据状态。
5. 前后端对统一错误结构的理解一致。
6. 自动检查通过，并完成一次真实浏览器打开验证。
7. 项目负责人明确同意进入角色基本管理。

### 4.5 当前非目标

1. 不建设角色之外的完整业务页面。
2. 不一次抽象全部通用组件。
3. 不迁移旧战斗数据或旧发布版本。
4. 不恢复计算页面，不改 Wasm。
5. 不在阶段 0 决定后续所有字段。

## 5. 阶段 1：角色基本管理

### 5.1 范围标题

1. 用角色基本资料验证新的数据库、后端和前端主链是否真正适合录入者使用。
2. 支持角色列表、查询、新建、详情和编辑。
3. 候选基本资料包括稳定标识、名称、可配置分类、说明、状态和排序。
4. 不在角色主记录中加入属性值、等级成长、装备、能力或图片关系。
5. 不建设角色的计算参数和 Wasm 投影，不预置英雄联盟固定分类。

### 5.2 进入条件

只有阶段 0 完成自动检查、真实页面验证并经项目负责人确认后，才补充本阶段的需求细节和详细设计。

### 5.3 完成方向

角色可以从空数据新建、查询、查看、编辑并在刷新后重新读回；必填、重复和非法输入有清晰提示。具体测试和页面验收清单在进入本阶段后再冻结。

## 6. 阶段 2：属性管理

### 6.1 范围标题

1. 独立维护属性定义，不维护角色或装备的属性值。
2. 属性包含名称、稳定标识、数值类型、单位、范围、说明、状态和排序等候选信息。
3. 不预置攻击、防御、生命等具体属性，由当前游戏数据自行配置。

### 6.2 进入条件

项目负责人已通过当前真实页面检查确认进入本阶段。本阶段只独立管理属性定义，并同步移除作者配置中的平行战斗资源定义；不提前建设角色或装备属性值。

### 6.3 完成方向

多种属性定义可以独立保存和重新打开；重复标识、非法范围和缺少必填信息可以被发现。

## 7. 阶段 3：装备管理

### 7.1 范围标题

1. 装备作为独立业务对象，不再与角色共用一个依赖类型关系区分的主记录。
2. 当前维护稳定标识、名称和说明，以及独立保存的装备直接属性 Map。
3. `百分比护甲穿透`这类由公式直接读取的属性属于装备属性；`生命值增加 10%`这类属性乘算规则、装备技能和角色可用关系不在本阶段实现。

### 7.2 进入条件

只有属性管理通过验收并经项目负责人确认后，才补充本阶段详细设计。

### 7.3 完成方向

装备资料可以新建、查询、编辑、删除和重新打开；装备属性可以整块保存并在刷新后回读。

## 8. 阶段 4：能力内容管理

### 8.1 范围标题

1. 使用“能力内容”统一承接技能、天赋、被动和其他相似内容。
2. 能力分类由配置决定，不把技能栏位和天赋层级写死。
3. 第一轮只维护名称、分类、说明、状态、排序和必要描述。
4. 公式、效果图、复杂触发器、时间轴和计算语义不在本阶段范围。

### 8.2 进入条件

只有装备管理通过验收并经项目负责人确认后，才补充本阶段详细设计。

### 8.3 完成方向

不同分类的能力内容都能独立维护，新增分类不需要修改固定程序名单。

## 9. 阶段 5：图片管理

### 9.1 范围标题

1. 图片作为独立资源，拥有稳定标识。
2. 支持上传、预览、查询、替换和停用。
3. 保存格式、大小、尺寸、说明和状态等必要信息。
4. 业务对象与图片的用途关系推迟到阶段 6。

### 9.2 进入条件

只有能力内容管理通过验收并经项目负责人确认后，才补充本阶段详细设计。

### 9.3 完成方向

图片上传后可以重新读取和预览；替换不会错误影响其他图片；非法文件会被拒绝并说明原因。

## 10. 阶段 6：关联管理

### 10.1 候选关系

进入本阶段时再逐项确认是否需要以下关系：

1. 角色与属性：保存该角色的属性值。
2. 角色与装备：保存可用、默认或其他明确关系。
3. 角色与能力内容：保存拥有、解锁或其他明确关系。
4. 装备与属性：保存装备提供的属性变化。
5. 装备与能力内容：保存装备授予或影响的能力。
6. 角色、属性、装备、能力内容与图片：保存代表图片或其他明确用途。

### 10.2 关系原则

1. 每种核心关系使用可读的关系记录和真实外键。
2. 关系按需要保存关系类型、数值、排序、状态和备注。
3. 页面既能从源对象查看，也能从目标对象反向查看。
4. 支持移除或停用关系，不自动级联删除两端对象。
5. 被引用对象停用或删除时必须有明确阻止或处理规则。

### 10.3 进入条件

只有图片管理通过验收并经项目负责人确认后，才补充本阶段详细设计和最终关系清单。

### 10.4 完成方向

新增、调整和移除关系后两端结果一致，数据库中不留下悬空关系。

## 11. 阶段 7：发布管理

### 11.1 范围标题

1. 日常编辑内容属于当前可修改配置。
2. 发布时冻结为不可随意改写的发布版本。
3. 发布版本记录名称、说明、时间、包含范围和状态。
4. 发布前检查必填信息、重复标识、失效关系和缺失的必要数据。
5. 发布后继续编辑当前配置，不影响旧发布版本。

### 11.2 延后决策

发布版本采用复制冻结、版本化行还是其他存储方式，在进入阶段 7 时根据前述对象和关系的实际规模决定，本概要不提前冻结。

### 11.3 进入条件

只有关联管理通过验收并经项目负责人确认后，才补充本阶段详细设计。

### 11.4 完成方向

可以分别读取多个发布版本；后续编辑不改写旧版本；存在阻断问题时不能发布。发布成功不代表可以真实计算。

## 12. 阶段 8：计算输入与 Wasm 阶段门

本阶段不是自动进入的下一项任务。只有同时满足以下条件，才开始新的计算需求澄清：

1. 阶段 0 至阶段 7 均已完成各自自动检查和真实页面验收。
2. 项目负责人能够只通过网页完成一套代表性配置录入。
3. 已发布配置可以稳定、独立地读取。
4. 项目负责人明确确认录入体验可以作为后续计算设计基础。

进入后也应先设计“发布配置到计算输入”的转换层，再决定 Wasm 接口和机制；不能直接让作者配置表等同于 Wasm 输入。

## 13. 跨阶段校验分层

| 校验层 | 负责发现的问题 | 结果 |
| --- | --- | --- |
| 字段校验 | 类型、必填、范围、格式 | 阻止当前保存 |
| 对象校验 | 稳定标识、名称唯一性、对象状态 | 阻止当前保存或返回明确问题 |
| 关系校验 | 两端存在性、同游戏约束、关系重复、关系状态 | 阻止非法关系写入 |
| 发布校验 | 必要对象缺失、失效关系、当前版本不完整 | 阻止发布 |
| 计算校验 | 发布配置能否形成合法计算输入 | 仅在阶段 8 以后设计 |

保存成功只证明当前保存合同成立；发布成功只证明配置冻结和结构关系检查成立。两者都不能替代未来计算校验。

## 14. 破坏式更新与安全边界

### 14.1 当前采用

1. 不为旧数据库结构建设正式迁移。
2. 不维护新旧接口和页面长期并存。
3. 新数据模型不受当前 Wasm 输入兼容约束。
4. 实施时允许使用明确的空开发数据库验证新基线。

### 14.2 仍需单独确认

1. 具体要重置的数据库名称、主机和保留要求。
2. 旧页面和旧接口在哪个阶段删除。
3. 现有种子数据和测试证据哪些保留为只读参考。
4. 未提交分支和原型如何归档或处置。

没有单独确认时，不执行任何清库、删除、合并或发布操作。

## 15. 当前停止点

当前详细设计停止在以下边界：

1. 只为属性定义与战斗资源整合形成可实施详细设计。
2. 角色、装备、能力内容、图片、关系、发布和计算阶段仍只保留范围标题和进入条件。
3. 详细设计需先通过只读方案评审，之后才允许新建独立编码任务。
4. 真实数据库重置、迁移、发布和服务操作仍需单独确认准确目标。

当前实施完成并经过自动检查和真实页面验收后，由项目负责人决定下一阶段。
