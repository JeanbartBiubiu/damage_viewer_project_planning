# 数据录入目标推进

## 总目标
用户可以通过平台的结构化表单录入数据（英雄、装备、技能、公式、类型等），数据可以被 Wasm 引擎处理，结果可以被前端展示出来。

## 现状概述
- 前端已有 14 个资源 CRUD 页面，但所有 JSONB 复杂字段（baseStats、mechanicsConfig、params 等）均为 **JSON 文本域手填**，无结构化编辑能力。
- 后端已有完整的 Admin CRUD API + ES256 JWT 鉴权，版本发布流水线可用。
- Wasm 引擎已实现基础平A/技能释放/装备被动/双抗减伤，但公式解释器、护盾、暴击等机制尚未完成。
- Bundle 机制已跑通（后端全量打包 → 前端 bundleCompiler 编译 → Wasm 消费），但缺少读写隔离和增量能力。

## 阶段 0：基础设施层

### T01 属性选择器通用组件
**优先级**：P0（最高）  
**预计工作量**：1~2 天

#### 背景
当前所有需要引用属性的地方（英雄 baseStats、技能 scaling、公式 vars、装备 statsModifier）用户都要手写 JSON key。属性的 key 实际上全部来自 `attribute_definitions` 表，应当提供下拉选择框，从已有属性列表中选取，而不是让用户手写。

#### 目标
实现一个 `<AttributeKeySelector>` 通用组件，供后续所有结构化编辑器复用。

#### 具体要求

1. **数据源**：调用 `getAttributeDefinitions(gameId)` 获取当前游戏的全量属性定义列表，前端做本地缓存（生命周期跟随页面会话）。
2. **筛选维度**：
   - **归属方**：`self`（自身）/ `enemy`（敌方），以 tag 或 radio 形式显示。
   - **值种类**：根据 `attribute_definitions.valueKind`（scalar / ratio / rate / flag）筛选，或显示全部。
   - **值子类型**：用户可选择 `base`（基础值）、`bonus`（额外值）、`total`（总值）、`current`（当前值）、`max`（最大值）等。这些后缀最终拼接成完整的属性引用 key，形如 `{side}.{attrKey}.{subType}`。
3. **搜索**：属性数量可能达 80+，需要支持拼音首字母或名称模糊搜索。
4. **输出格式**：组件的 `onChange` 回调返回结构化对象 `{ side, attrKey, subType }` 或拼接后的字符串 key，由调用方决定。
5. **多选模式**：部分场景（如英雄 baseStats 批量赋值）需要支持多选属性。

#### 涉及文件
- 新建 `web/src/components/AttributeKeySelector.tsx`
- 需参考 `web/src/services/apiClient.ts` 中的 `getAttributeDefinitions` 接口
- 需参考 `最小验证/数据/attribute_definitions.csv` 了解现有属性列表样例

#### 验收标准
- [ ] 组件可在任意编辑器弹窗中通过 `<AttributeKeySelector gameId={...} onChange={...} />` 调用
- [ ] 支持 self/enemy 切换、subType 选择、模糊搜索
- [ ] 选择后输出结构化的属性引用
- [ ] 有独立的 Storybook 或测试页面可验证

### T02 类型系统编辑增强
**优先级**：P0（最高）  
**预计工作量**：2~3 天

#### 背景
Type 和 TypeRelation 是事件推进机制的基石。例如：「普通技能 A、终极技能 B、被动技能 C」可以属于一个叫「技能类型 M」的类型。后续给技能赋值时，可以从 type 列表中按「技能类型 M」快速筛选，最多嵌套一层（不做类型的类型的类型）。

**当前问题**：
- Types 页面和 TypeRelations 页面是两个独立的平铺表格，用户难以理解层级关系。
- 其他资源页（英雄、技能、装备）没有「类型管理」入口，无法在编辑资源时直接查看/修改其所属类型。

#### 目标

1. **Types 页面改造**：增加树形视图，展示 parent → child 的一层嵌套关系；支持拖拽或下拉框设置 parent。
2. **TypeRelation 内联管理**：在英雄/技能/装备/公式等资源的编辑弹窗中，新增「类型标签」区域，可以直接给当前实体添加/移除类型挂载（本质是新增/删除 TypeRelation 记录），无需跳转到 TypeRelations 页面。
3. **类型筛选器组件** `<TypeFilter>`：在其他资源的列表页查询卡片中，增加按类型筛选的能力（前端过滤即可，数据量不大）。

#### 具体要求

1. **Types 树形视图**：
   - 顶层显示所有 `parent_key IS NULL` 的类型，点击展开显示其 child。
   - 支持在树上直接新增/编辑/查看类型。
   - 保留原有表格视图，用 tab 切换。
2. **资源编辑弹窗中的类型标签区域**：
   - 读取 `typeRelations` 中 `targetCategory={当前资源类型} AND targetId={当前资源ID}` 的记录。
   - 以 Tag 组形式展示已挂载类型，点击 × 可移除，点击 + 可从类型列表弹出选择器添加。
   - 添加/移除时直接调用 `putTypeRelation` API。
3. **类型筛选器**：
   - 可选择一个或多个类型，资源列表按前端过滤显示匹配项。
   - 在英雄、技能、装备、公式等列表页的查询区域新增此筛选器。

#### 涉及文件
- 改造 `web/src/pages/admin/resources/types/` 全部文件
- 改造 `web/src/pages/admin/resources/type-relations/` 
- 新建 `web/src/components/TypeTagEditor.tsx`（资源编辑弹窗中的类型标签区域）
- 新建 `web/src/components/TypeFilter.tsx`（查询区域的类型筛选器）
- 修改英雄/技能/装备等资源的 `modal.tsx`，嵌入 TypeTagEditor
- 修改英雄/技能/装备等资源的 `search.tsx`，嵌入 TypeFilter
- 需参考 `最小验证/数据/lol_mvp_type_taxonomy.csv` 了解类型层级样例
- 需参考 `最小验证/数据/lol_mvp_type_taxonomy说明.md` 了解分类体系说明
- 需参考 `接口/game_manage/接口定义.md` 了解 TypeRelation API

#### 验收标准
- [ ] Types 页面有树形视图，可一目了然看到 parent-child 关系
- [ ] 英雄/技能/装备编辑弹窗中有类型标签区域，可增删类型挂载

### T03 英雄结构化编辑器
**优先级**：P1  
**预计工作量**：2 天  
**依赖**：T01

#### 背景
英雄的 `baseStats`（JSONB）和 `statsByLevel`（JSONB）当前是 JSON 文本域。用户需要手写如 `{"health": 640, "attack_damage": 58, ...}` 的 JSON，容易出错且无法校验 key 是否合法。

#### 目标
将英雄编辑弹窗中的 JSONB 字段替换为结构化表单。

#### 具体要求

1. **baseStats 编辑区**：
   - 用表格形式展示，每行一个属性：`[属性选择器(T01)] [数值输入框]`。
   - 支持动态增行/删行。
   - 属性选择器只显示 `side=self` 且排除已选属性（防重复）。
   - 初始化时解析已有 JSON 填充表格。
2. **statsByLevel 编辑区**：
   - 按等级（1~18）展示成长数据。可采用两种方案之一：
     - **方案 A**（推荐）：显示「每级成长值」表格，列 = 属性，行 = 级别差（level 1→2, 2→3, ...），如果是固定成长则只需一行。
     - **方案 B**：显示「成长公式」，如 `perLevel` + `base` 自动算出各级数值。
   - 需要和 Wasm 引擎的等级成长计算逻辑对齐（参考 `bundleCompiler.ts` 中的等级成长折算逻辑）。
3. **JSON 回退模式**：保留一个「高级 JSON 编辑」折叠面板，供高级用户直接编辑原始 JSON，与结构化表单双向同步。

#### 涉及文件
- 改造 `web/src/pages/admin/resources/heroes/modal.tsx`
- 新建 `web/src/components/BaseStatsEditor.tsx`
- 新建 `web/src/components/StatsByLevelEditor.tsx`（或合并为 `HeroStatsEditor.tsx`）
- 需参考 `web/src/engine/bundleCompiler.ts` 中等级成长折算逻辑
- 需参考 `最小验证/数据/卡特琳娜1-18数据.csv` 了解实际数据格式
- 需参考 `db/game_manage/schema.sql` 中 `heroes` 表的 JSONB 字段定义

#### 验收标准
- [ ] baseStats 可通过属性选择器 + 数值输入框录入，无需手写 JSON
- [ ] statsByLevel 有直观的等级成长编辑界面
- [ ] 结构化编辑和 JSON 文本可双向同步
- [ ] 保存到后端的数据格式与现有格式完全兼容

### T05 技能结构化编辑器
**优先级**：P1（最复杂的编辑器）  
**预计工作量**：4~5 天  
**依赖**：T01, T02, T04（skillRefs 选择器可复用经验）

#### 背景
技能是最复杂的数据实体。其中 `params`（JSONB）、`mechanicsConfig`（JSONB）、`resourceCosts`（JSONB）、`cooldowns`（JSONB）、`timingProfile`（JSONB）全部是手写 JSON，是用户出错最多的地方。技能的 `mechanicsConfig` 直接决定了 Wasm 引擎如何执行技能效果。

#### 目标
将技能编辑弹窗中的 JSONB 字段全部替换为结构化表单。这是工作量最大的编辑器。

#### 具体要求

1. **基础信息区**：
   - `ownerType`（hero/item）：下拉选择。
   - `ownerId`：根据 ownerType 不同，显示英雄选择器或装备选择器。
   - `skillKey`：文本输入。
   - `name`：文本输入。
2. **resourceCosts 编辑区**：
   - 按技能等级（1~5 或 1~3）排列，每级一行。
   - 每行：`[资源类型选择(mana/energy/health/none)] [数值输入框]`。
   - 如果所有等级相同，可用「统一值」快捷填充。
3. **cooldowns 编辑区**：
   - 同 resourceCosts 的等级排列逻辑。
   - 每行一个数值输入框（秒）。
4. **timingProfile 编辑区**：
   - 结构化表单显示 `castTime`、`channelDuration`、`windupRatio` 等字段。
   - 各字段的含义用 tooltip 或 label 说明。
5. **params 编辑区**（技能数值参数）：
   - 按技能等级排列，每级一组参数。
   - 每个参数行：`[参数名(文本输入)] [数值输入框]`。
   - 支持增删参数行。
   - 参数名建议从已有技能的常见参数名中提供自动补全（从同类型技能中收集）。
6. **mechanicsConfig 编辑区**（最核心、最复杂）：
   - 这是决定技能如何执行的配置，结构较深。
   - 需要根据 Wasm 引擎协议设计结构化编辑界面，至少支持以下层级：
     - **effects 列表**：每个 effect 是一个卡片，可增删、拖拽排序。
     - **每个 effect**：`[效果类型选择(damage/heal/shield/buff/debuff/...)] + [目标选择(self/enemy)]`。
     - **damage effect 子表单**：`[伤害类型(physical/magic/true)] + [基础值输入] + [scaling 列表]`。
     - **每个 scaling**：`[属性选择器(T01)] [比例系数输入框]`。
   - 对于 MVP 阶段，可先只支持 `damage` 类型 effect 的完整编辑，其他类型先展示 JSON。
7. **JSON 回退模式**：同 T03。

#### 涉及文件
- 改造 `web/src/pages/admin/resources/skills/modal.tsx`（会变得很大，建议拆分子组件）
- 新建 `web/src/components/skill-editor/` 目录，包含：

  - `CooldownsEditor.tsx`
  - `TimingProfileEditor.tsx`

  - `MechanicsConfigEditor.tsx`
  - `EffectEditor.tsx`
  - `ScalingEditor.tsx`

- 需参考 `最小验证/数据/技能配置固定选项.md` 了解下拉选项枚举值

### T06 公式结构化编辑器
**优先级**：P1  
**预计工作量**：2 天  
**依赖**：T01

#### 背景
公式有两个实体：`FormulaProfile`（公式模板，含 `params` JSONB）和 `FormulaBinding`（公式绑定，含 `overrideParams` JSONB）。当前全部手写 JSON。公式中的变量引用（vars）需要引用属性 key，与 T01 直接关联。

#### 目标
将公式编辑弹窗中的 JSONB 字段替换为结构化表单。

#### 具体要求

1. **FormulaProfile 编辑器**：
   - `formulaType` / `formulaKind`：下拉选择（枚举值从现有数据或协议文档中获取）。
   - `params` 编辑区：
     - **vars 定义**：每行 `[变量名(文本)] [属性选择器(T01)]`，声明此公式依赖的属性变量。
     - **expression**：公式表达式输入框，支持语法高亮或预览。
     - **constants**：键值对列表 `[常量名] [数值]`。
   - 支持「公式预览」：输入一组假设值后即时计算预览结果（前端本地用 `formulaCompiler.ts` 计算）。
2. **FormulaBinding 编辑器**：
   - `targetCategory` + `targetId`：选择绑定到哪个实体（英雄/技能/装备等）。
   - `bindingKey`：文本输入或下拉选择（常见的 binding key 如 `base_damage`, `scaling_ad` 等）。
   - `formulaId`：从 FormulaProfile 列表中搜索选择。
   - `overrideParams`：同 vars 定义格式，可覆盖公式模板中的默认参数。

#### 涉及文件
- 改造 `web/src/pages/admin/resources/formula-profiles/modal.tsx`
- 改造 `web/src/pages/admin/resources/formula-bindings/modal.tsx`

- 新建 `web/src/components/formula-editor/FormulaPreview.tsx`
- 需参考 `web/src/engine/formulaCompiler.ts` 了解公式编译逻辑
- 需参考 `最小验证/数据/公式.csv` 了解公式数据样例

**优先级**：P2

### T08 Wasm 通用公式解释器
**优先级**：P1  
**预计工作量**：3~4 天  
**依赖**：T06（弱依赖，了解公式数据格式即可开始）

#### 背景
当前 Wasm 引擎中部分公式计算是硬编码的（如破败、纳什之牙的效果公式）。需要实现一个通用的公式解释器，能根据 `FormulaProfile` 中定义的表达式 + 运行时属性值 动态计算结果。

#### 目标
在 Wasm 引擎中实现通用公式解释器模块，替换现有硬编码公式逻辑。

#### 具体要求

1. **表达式解析器**：
   - 支持 `+`, `-`, `*`, `/`, `%`, `min()`, `max()`, `if(cond, a, b)`, `floor()`, `ceil()`, `clamp()` 等基础运算和函数。
   - 支持变量引用（对应 `FormulaProfile.params.vars` 中声明的变量名）。
   - 支持常量引用（对应 `FormulaProfile.params.constants`）。
2. **运行时求值**：
   - 输入：表达式 AST + 运行时上下文（当前属性值快照）。
   - 输出：f64 数值。
   - 性能要求：单次求值 < 1μs。
3. **与现有引擎集成**：
   - `wasm/tinygo_engine_v2/internal/formula` 已有基础框架，在此基础上扩展。
   - 解析、编译和求值逻辑应按 TinyGo V2 现有包结构拆分，不恢复旧 Rust 文件布局。
   - 移除现有硬编码公式，改为从 bundle 中加载公式定义。
4. **测试**：补充单元测试，覆盖四则运算、嵌套函数、变量引用、边界值（除零、溢出等）。

#### 涉及文件
- `wasm/tinygo_engine_v2/internal/formula/**`（公式 bytecode 与求值）
- `wasm/tinygo_engine_v2/internal/compile/**`（Bundle 公式编译与引用校验）
- 需参考 `web/src/engine/formulaCompiler.ts`（前端已有类似实现，可作为参照）
- 需参考 `wasm/概要设计-运行时数据流与属性公式主链路.md`
- 需参考 `最小验证/数据/公式.csv`

- [ ] 通用公式解释器可解析和求值表达式
- [ ] 支持变量引用、常量引用、基础数学函数
- [ ] 卡特琳娜 MVP 的技能伤害回归测试全部通过

### T09 Wasm 额外转换管道
**优先级**：P2  
**预计工作量**：2~3 天  
**依赖**：T08

#### 背景
某些英雄有特殊的属性转换机制（如派克：超出一定生命值自动转为攻击力；吸血鬼：法强和生命值互转；海克斯：物理伤害转魔法伤害等）。这些转换发生在属性计算的特定阶段。

#### 目标
在属性计算管线中增加「额外转换管道」阶段，支持配置化的属性转换规则。

#### 具体要求

1. **转换规则数据结构**：
   - `sourceAttr`：源属性 key。
   - `targetAttr`：目标属性 key。
   - `formula`：转换公式（复用 T08 的公式解释器）。
   - `phase`：转换发生的计算阶段（`after_base` / `after_items` / `after_buffs` 等）。
   - `mode`：`convert`（减少源增加目标）/ `grant`（不减少源，额外增加目标）。
2. **计算管线集成**：
   - 在 TinyGo V2 的 `internal/attribute`、`internal/pipeline` 或 `internal/runtime` 中，在属性计算的指定阶段插入转换步骤。
   - 多个转换规则按优先级排序执行。
3. **防止循环**：如果 A→B 和 B→A 同时存在，需要按声明顺序执行一次，不二次迭代。

#### 涉及文件
- `wasm/tinygo_engine_v2/internal/pipeline/**`

- `wasm/tinygo_engine_v2/internal/runtime/**`

### T10 Wasm 暴击机制
**优先级**：P2  
**预计工作量**：2 天  
**依赖**：无前置，可与 T08/T09 并行

#### 背景
暴击涉及暴击率、暴击伤害倍率、暴击修正（如无尽之刃的额外暴击伤害）。当前引擎没有暴击逻辑。各种机制可能互不相关，需要各自实现而不是都写在一个 rs 文件里。

#### 目标
在 Wasm 引擎中实现暴击伤害计算模块。

#### 具体要求

1. **模块独立**：在 `wasm/tinygo_engine_v2/internal/crit` 中实现，不混入 runtime 主流程或 ABI 入口。
2. **计算规则**：
   - 暴击判定：基于 `crit_chance` 属性（0.0~1.0），确定性模式下按概率截断（如 50% 暴击每 2 次必暴 1 次）。

   - 支持暴击伤害修正（如无尽之刃加成）：通过 buff 或装备 effect 修改 `crit_damage_multiplier`。
3. **与 effects 系统对接**：在 damage effect 执行路径中插入暴击判定和伤害修正。
4. **可组合**：暴击结果标记在 `DamageEvent.components` 中，前端可识别并展示。

#### 涉及文件
- `wasm/tinygo_engine_v2/internal/crit/**`
- `wasm/tinygo_engine_v2/internal/pipeline/**`（插入暴击判定与倍率）
- `wasm/tinygo_engine_v2/internal/model/**`（输出契约增加 crit 标记时同步更新）
- 需参考 `wasm/盘点报告-引擎机制实现差距分析.md`

#### 验收标准
- [ ] 暴击率 100% 时伤害正确乘以暴击倍率
- [ ] 暴击率 0% 时不暴击

   - 隐藏所有「新增」「编辑」「删除」按钮。

   - 切换到预览时：清除写模式下的临时状态，重新加载 bundle 数据。
5. **状态管理**：
   - 引入轻量的全局状态（可用 React Context 或 zustand）管理 `{ userRole, viewMode, gameId }` 等。
   - 各资源页的数据加载逻辑需要根据 viewMode 选择不同的数据源。

## AI 执行指引

每个子任务交给 AI 执行时，需要遵循以下模板：

1. **先读上下文**：按任务中列出的「涉及文件」逐一阅读，理解现有代码结构和约定。
2. **写详细方案**：输出到 `数据录入目标推进/T{XX}_{任务名}_方案.md`，包含数据结构设计、组件接口定义、核心逻辑伪代码。
3. **实现代码**：按照方案逐步实现，每完成一个文件就运行 `get_errors` 检查编译错误。
4. **验收检查**：对照验收标准逐项确认。
5. **回归测试**：确保已有功能未被破坏（卡特琳娜 MVP 端到端跑通）。

**重要约束**：
- 不要修改 Wasm 引擎的 ABI 导出签名（`alloc`/`dealloc`/`engine_init`/`engine_run`/`engine_response_ptr`/`engine_response_len`），除非任务明确要求。
- 不要修改后端 API 的请求/响应格式，除非任务明确要求。新增字段可以，删改已有字段需要前后端联动。
- 前端组件风格遵循 Arco Design + 已有的 CRUD 页面模式（constants/types/search/columns/table/modal 六件套）。
- JSONB 字段的结构化编辑器必须保持与现有 JSON 格式的双向兼容——即结构化编辑产出的 JSON 必须能被老版 bundleCompiler 和 Wasm 正确消费。
