# 系统设计方案评估报告

基于现有文档（数据库 Schema、接口定义、后端开发方案）的深度审阅，从系统架构师与设计师的角度，对本方案的可行性评估如下：

## 1. 总体评价
**可行性等级：高 (High)**
方案采用了典型的 **"重客户端(Rich Client) + 静态化分发"** 架构。利用 IndexDB 做本地数仓，WASM 做本地计算，后端仅负责数据的“版本化管理”与“分发”。这种架构极其适合“读多写少、计算复杂、对延迟敏感”的游戏模拟器场景。

## 2. 详细评估与优化建议

### 2.1 数据库设计 (Database)
**优点：**
- **分区策略**：按 `game_id` 分区设计合理，不仅支持多游戏扩展，且能物理隔离不同游戏的数据，利于后续维护。
- **JSONB 的使用**：对于英雄属性、技能机制等高度异构的数据，使用 `jsonb` 是最佳选择，避免了 EAV (Entity-Attribute-Value) 模式的性能噩梦。

**潜在风险与建议：**
1.  **图片存储 (Images Table)**
    -   **现状**：`image_base64` 直接存入 PostgreSQL。
    -   **风险**：虽然是小图标，但大量 Base64 文本会极大地膨胀表空间和 WAL 日志，增加数据库备份恢复压力，且数据库处理大文本 IO 性能不如文件系统。
    -   **建议**：建议仅在 DB 存储图片元数据（Path/Hash/URL），图片文件存入对象存储（MinIO/S3）或本地文件系统，通过 Nginx 直接服务静态资源。若必须存 DB，建议使用 `bytea` 类型而非 `text`，并考虑独立存储，避免查询列表时拖慢 IO。

2.  **版本管理模型 (SCD Type 2)**
    -   **现状**：原始表使用 `start_version`/`end_version` 区间管理。
    -   **复杂度**：在“发布”时需要精确计算区间分裂（Split）和闭合，逻辑相当复杂且易出错。
    -   **建议**：考虑 **"草稿(Draft) + 快照(Snapshot)"** 模型。
        -   `heroes_draft`：永远只存最新编辑状态（无版本号）。
        -   `heroes_versioned`：发布时，将 Draft 数据全量（或增量）Copy 进去，带上 `version_id`。
        -   这样写接口极其简单（只改 Draft），读接口（Bundle）只需读 Draft（预览）或 Versioned（正式）。

### 2.2 接口与后端设计 (API & Backend)
**优点：**
- **强契约**：接口定义详尽，特别是错误码和 JSON 结构，利于前后端并行开发。
- **发布快照策略**：`versionCode` + 已发布 `Bundle` 快照的设计能避免 Public 侧读到编辑工作区数据。

**建议：**
1.  **Bundle 大小控制**
    -   **现状**：`GET /bundle` 返回全量数据。
    -   **风险**：随着游戏迭代（如 LoL 有 160+ 英雄），单次全量包可能过大 (>5MB)，影响首屏体验或移动端加载。
    -   **建议**：预留“分包”设计。例如 `base_bundle` (基础配置、Type), `heroes_bundle`, `items_bundle`。或者支持增量 Patch（虽然实现复杂，但对于频繁更新的游戏很有效）。当前版本判断以 `versionCode` 为主。

2.  **语义校验**
    -   **现状**：依赖后端做复杂的语义校验（如 `skillRefs` 引用存在性）。
    -   **建议**：确保校验逻辑在“发布”阶段是**强阻塞**的。脏数据进入版本库会导致所有客户端报错。

### 2.3 游戏数据模型 (Game Data Model)
**优点：**
- **机制配置 (Mechanics Config)**：设计了一套基于 JSON 的 DSL（触发器-条件-动作），这是实现通用伤害计算的核心。支持了“事件驱动”模型的落地。

**设计缺失点 (Designer's Gap)：**
1.  **状态/Buff 定义 (Status Effects)**
    -   **问题**：DSL 中有 `add_stack`，但缺乏对“状态(Buff)”本身的定义表。Buff 通常有图标、名称、描述、持续时间规则、互斥规则等。
    -   **建议**：可能需要增加 `status_definitions` 表，或者在 `skills` 中包含被动 Buff 的定义。

2.  **公共资源 (Runes/Summoner Spells)**
    -   **问题**：`owner_type` 提到了 `rune`，但没有 `runes` 表。
    -   **建议**：补充 `runes` 表设计，或将其归一化为 `items` 的一种特殊 Type。

## 3. 总结
设计方案**逻辑自洽，架构先进**，完全能够支撑“10万日活、读多写少”的目标。
核心难点不在于 CRUD，而在于：
1.  **DSL 的前端编辑器实现**：手写 JSON 配置技能极其痛苦，需要开发可视化的技能编辑器。
2.  **WASM 计算引擎的正确性**：Go 语言实现的引擎需要精确对齐游戏逻辑。

建议优先通过 **"Draft + Snapshot"** 简化版本管理逻辑，并补充 **Buff/Status** 的数据定义。
