# 项目研发背景与需求说明（扩展版）

## 1. 文档目的
本文档用于回答三个核心问题：

1. 我们到底在解决什么问题。
2. 这个问题为什么值得现在做。
3. 项目首期怎么落地，边界在哪里。

目标读者包括：项目开发者、合作测试者、后续可能参与共建的攻略作者与玩家。

## 2. 项目背景（真实场景）
我们最早做这个项目的出发点很直接：游戏版本每次改动后，很多伤害结论都要重测，但现有方式效率极低。

当前常见工作流是：

1. 先在论坛或群里看到争议结论。
2. 再进训练模式手动配符文、装备、等级、技能点。
3. 反复测试并截图记录。
4. 用 Excel 或本地笔记整理。
5. 下个版本更新后几乎从头再来。

这种方式的问题不是“不能做”，而是“长期不可持续”：

1. 复测成本高，且重复劳动非常多。
2. 测试过程依赖个人习惯，结果可复现性差。
3. 数据散落在截图、表格、聊天记录，难沉淀为可复用资产。
4. 当社区出现极端理论场景争论时，没有统一工具快速验算。
5. 版本平衡评估往往只能看胜率，难回答“机制层面到底改了多少”。

我们希望把这件事从“个人手工测试”升级成“可协作的标准化计算系统”。

## 3. 一句话定位
这是一个面向玩家与攻略者的纯 Web 数值分析平台，用于管理游戏机制数据，并快速完成伤害模拟、版本对比和结论复核。

## 4. 业务价值
### 4.1 对普通玩家的价值
1. 不需要反复进训练模式，直接在网页配置场景并得到可视化结果。
2. 能快速验证常见争议结论，避免被片面经验误导。

### 4.2 对攻略作者的价值
1. 版本更新后可以快速复用旧数据，专注分析而不是重复搭场景。
2. 输出内容更结构化，证据链更完整（参数、过程、结果可回放）。

### 4.3 对共建维护者的价值
1. 每个角色可按“认领”方式维护，职责清晰。
2. 多人协作下，数据不再碎片化，能持续迭代。

### 4.4 对项目维护方的价值
1. 在保证成本可控的前提下，建立长期可积累的数据资产。
2. 用低客单价（9.9 元永久）覆盖开发和维护成本，实现可持续运营。

## 5. 项目目标（首期）
首期目标不是做一个大而全平台，而是先跑通“数据管理 + 计算引擎 + 版本对比”的闭环：

1. 支持英雄、技能、装备、天赋等基础机制数据管理。
2. 支持伤害模拟与关键分析场景计算（斩杀线、N 秒输出、装备替换差异）。
3. 支持新旧版本对比，能够直观看到数值变化影响。
4. 支持只读与编辑权限分离，确保普通用户体验和编辑安全性。

## 6. 典型使用场景
### 场景 A：版本更新后 24 小时内复核
1. 共建维护者更新角色数据和版本号。
2. 攻略作者直接复用历史测试模板，批量跑关键场景。
3. 输出“旧版本 vs 新版本”差异结论。

### 场景 B：社区争议验证
1. 用户输入双方等级、装备、技能等级、触发条件。
2. 系统计算指定时间窗内输出与击杀阈值。
3. 用图表展示关键拐点，减少纯口水争论。

### 场景 C：出装替换决策
1. 在同等前提下只替换单件装备。
2. 比较 N 秒输出、爆发峰值和真空期表现。
3. 给出“适用场景差异”而不是单一结论。

## 7. 数据共建机制（已确认）
数据来源采用“玩家/攻略者共建”模式，核心原则如下：

1. 谁熟悉哪个角色，谁优先维护哪个角色。
2. 维护内容包括：基础属性、技能参数、装备交互、测试记录。
3. 新版本发布后由对应维护者更新，其他人可复核。
4. 数据目标是“可验证、可复用、可迭代”，而不是一次性录入。

## 8. 产品范围与边界
### 8.1 当前范围（In Scope）
1. 游戏机制数据管理（含版本字段与差异对比能力）。
2. 前端 + WASM 计算引擎（高频计算在用户侧执行）。
3. 权限体系（只读 / 编辑）与基础审核流程。
4. 图标与静态资源缓存、核心数据缓存、版本增量更新。

### 8.2 非目标（Out of Scope）
1. 完全杜绝抄袭与逆向（可提高门槛，但无法绝对阻止）。
2. 做完整社区产品（论坛关系链、内容分发、UGC 审核系统）。
3. 做多语言版本（当前明确只做中文）。
4. 做配置分享平台（当前交流方式以截图等轻量形式为主）。

## 9. 用户角色与权限
1. 普通用户：进行配置、模拟和对比分析，高级功能需付费。
2. 编辑用户：维护机制数据、提交版本更新。
3. 共建维护者：按角色认领并持续更新测试数据。
4. 管理角色（可选）：负责审核发布、权限管理和回滚决策。

## 10. 技术可行性与成本判断
本项目属于典型“读多写少”模型，具备低成本落地条件：

1. 前端使用 IndexDB 缓存图标和稳定数据，减少重复请求。
2. Nginx + 后端缓存承担大部分读取压力。
3. 计算核心放在 WASM，降低后端实时计算成本。
4. 游戏数据更新频率相对可控，系统吞吐压力主要集中在读取侧。

结论：只要架构执行到位，首期投入和长期维护成本都可控。

## 11. 商业模型与定位（已确认）
1. 定价为 9.9 元永久买断，不做订阅。
2. 收费定位是“开发与维护成本分摊”，不是高利润 SaaS。
3. 平台定位是“玩家共建数据的组织与服务系统”。
4. 当用户规模足够时，低客单价模式也可覆盖持续迭代成本。

## 12. 关键风险与应对
### 12.1 风险
1. IndexDB 中的数据可能被提取复用。
2. WASM 文件可能被逆向和二次利用。
3. 单纯 JWT 付费标识可能被绕过。
4. 共建模式下可能出现数据冲突、质量不一致问题。

### 12.2 应对思路
1. 数据分层与签名校验，关键数据加服务端授权校验。
2. 核心能力采用“本地计算 + 服务端校验”混合方案。
3. 增加支付状态校验、会话风控和异常行为检测。
4. 建立版本发布、变更审计和可回滚机制。

## 13. 高级功能建设路线
1. 斩杀线计算（生命值区间搜索/二分）。
2. 经济成长曲线与滚雪球压制量化。
3. N 秒内最大伤害组合搜索。
4. 技能真空期与有效输出窗口可视化。
5. 新旧版本伤害差异对比（Diff）。
6. 同条件装备替换收益对比（Diff）。

## 14. 成功指标（KPI）
1. 版本更新后 24 小时内完成核心角色数据同步。
2. 常见计算场景响应时间达到秒级（建议跟踪 P95）。
3. 关键结论可复现实验比例达到预设阈值。
4. 付费转化与月留存达到项目运营基线。

## 15. 实施里程碑
1. M1：单游戏 MVP（数据管理 + 基础计算 + 版本对比）。
2. M2：权限、审核、发布与回滚流程完善。
3. M3：高级分析功能上线并做性能优化。
4. M4：扩展第二款游戏，验证多游戏抽象能力。

## 16. 已确认业务决策汇总
1. 数据来源：玩家与攻略者共建，按角色认领维护。
2. 语言策略：仅中文，不做国际化。
3. 协作方式：不做配置分享平台，采用截图等轻量沟通。
4. 商业策略：9.9 元永久买断，面向长期维护与服务。
