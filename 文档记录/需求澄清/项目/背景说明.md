## 当前阶段决策（2026-08-22）

项目的长期目标仍是完成伤害模拟、版本对比和结论复核，但当前最小可用阶段尚未完成，首要阻塞是配置数据难以通过网页持续录入和维护。

当前阶段已确认按以下顺序推进：

1. 先完成可实际使用的前端录入页面、后端读写、关系化数据库和保存校验。
2. 每次只展开一个阶段，当前阶段经过自动检查和真实页面操作后，再由项目负责人决定是否进入下一阶段。
3. 在角色、属性、装备、能力内容、图片、关系和发布均形成可用闭环前，暂停新增 Wasm 机制和计算页面开发。
4. 当前允许破坏旧页面、旧接口和旧数据库结构，不为未完成的最小可用阶段建设迁移、双写或历史格式兼容。
5. 本轮只形成需求和概要方案；详细设计、编码、数据库重置、发布和服务启动均由后续独立步骤决定。

项目负责人在 2026-08-22 查看当前属性定义与资源定义页面后，进一步确认当前详细设计先处理“属性定义与战斗资源整合”：新的作者配置只保留唯一属性定义，不建立平行的战斗资源定义；生命值、法力值、能量统一按属性管理。角色、装备、能力与属性之间的数值关系仍按各自阶段处理，不在本轮同时展开。

## 2. 项目背景（真实场景）
我们最早做这个项目的出发点很直接：游戏版本每次改动后，很多伤害结论都要重测，但现有方式效率极低。

当前常见工作流是：

1. 先在论坛或群里看到争议结论。
2. 再进训练模式手动配符文、装备、等级、技能点。
3. 反复测试并截图记录。
4. 用 Excel 或本地笔记整理。
5. 下个版本更新后几乎从头再来。

这种方式的问题不是“不能做”，而是“长期不可持续”：

1. 复测成本高，且重复劳动非常多。
2. 测试过程依赖个人习惯，结果可复现性差。
3. 数据散落在截图、表格、聊天记录，难沉淀为可复用资产。
4. 当社区出现极端理论场景争论时，没有统一工具快速验算。
5. 版本平衡评估往往只能看胜率，难回答“机制层面到底改了多少”。

我们希望把这件事从“个人手工测试”升级成“可协作的标准化计算系统”。

## 3. 长期一句话定位
这是一个面向玩家与攻略者的纯 Web 数值分析平台，用于管理游戏机制数据，并快速完成伤害模拟、版本对比和结论复核。

## 4. 业务价值
### 4.1 对普通玩家的价值
1. 不需要反复进训练模式，直接在网页配置场景并得到可视化结果。
2. 能快速验证常见争议结论，避免被片面经验误导。

### 4.2 对攻略作者的价值
1. 版本更新后可以快速复用旧数据，专注分析而不是重复搭场景。
2. 输出内容更结构化，证据链更完整（参数、过程、结果可回放）。

### 4.3 对共建维护者的价值
1. 每个角色可按“认领”方式维护，职责清晰。
2. 多人协作下，数据不再碎片化，能持续迭代。

### 4.4 对项目维护方的价值
1. 在保证成本可控的前提下，建立长期可积累的数据资产。
2. 用低客单价（9.9 元永久）覆盖开发和维护成本，实现可持续运营。

## 5. 当前最小可用阶段目标

当前目标不是同时完成数据管理、计算引擎和版本对比，而是先证明配置数据可以被正常录入、保存、重新打开、建立关系并发布：

1. 角色、属性、装备、能力内容和图片都能独立维护，不依赖计算引擎才能保存。
2. 核心关系通过可读的关系表和外键表达，不把重要关联隐藏在大块配置内容或多态软引用中。
3. 前端围绕业务对象组织操作，不要求录入者理解底层运行时表、内部类型编号或 Wasm 输入结构。
4. 每个阶段都同时具备数据库、后端、前端、校验和真实页面验收，不以“接口存在”或“页面能打开”代替可用性。
5. 发布只表示配置数据被冻结并通过结构与关系检查，不表示已经能够进行真实伤害计算。

伤害模拟、斩杀线、指定时间输出、装备替换差异和版本数值对比仍是长期目标，但必须在录入阶段验收完成后重新设计计算输入，不能反向决定当前表单和数据库边界。

## 6. 长期典型使用场景
### 场景 A：版本更新后 24 小时内复核
1. 共建维护者更新角色数据和版本号。
2. 攻略作者直接复用历史测试模板，批量跑关键场景。
3. 输出“旧版本 vs 新版本”差异结论。

### 场景 B：社区争议验证
1. 用户输入双方等级、装备、技能等级、触发条件。
2. 系统计算指定时间窗内输出与击杀阈值。
3. 用图表展示关键拐点，减少纯口水争论。

### 场景 C：出装替换决策
1. 在同等前提下只替换单件装备。
2. 比较 N 秒输出、爆发峰值和真空期表现。
3. 给出“适用场景差异”而不是单一结论。

## 7. 长期数据共建机制（已确认）
数据来源采用“玩家/攻略者共建”模式，核心原则如下：

1. 谁熟悉哪个角色，谁优先维护哪个角色。
2. 维护内容包括：基础属性、技能参数、装备交互、测试记录。
3. 新版本发布后由对应维护者更新，其他人可复核。
4. 数据目标是“可验证、可复用、可迭代”，而不是一次性录入。

## 8. 当前范围与非目标

### 8.1 当前范围

1. 保留游戏作为数据隔离根，不把英雄联盟的职业、槽位、属性和伤害类型写死为平台规则。
2. 角色、属性、装备、能力内容、图片的独立录入与维护。
3. 前述对象之间的显式关系管理、双向查看、移除和失效处理。
4. 手动保存、未保存离开提醒、明确错误提示和分层校验。
5. 不可随意改写的发布版本，以及发布前结构与关系检查。
6. 单人维护场景下必要的接口保护；不扩展多人权限与协作体系。

### 8.2 当前非目标

1. 新增 Wasm 机制、计算接口、正式计算页面或测试场景。
2. 为旧数据表、旧接口、旧页面和旧计算输入提供兼容层或自动迁移。
3. 自动保存、多人冲突合并、审核工作流、历史格式升级、导入导出。
4. 完整社区产品、配置分享平台或多语言版本。
5. 支付、收费权限、防逆向和内容分发能力的新增开发。

## 9. 用户角色与权限边界

当前阶段只按单人配置维护者设计，使用手动保存，不建设角色认领、多人同时编辑、审核和复杂权限管理。

普通用户、编辑用户、共建维护者和管理角色仍属于长期产品设想。只有单人录入闭环通过真实体验验收后，才重新确认这些角色是否进入下一阶段。

## 10. 技术可行性与成本判断

当前前端、后端、PostgreSQL 和图片能力已经具备可复用工程骨架，后端也不需要调用 Wasm 才能完成配置保存。因此，暂停 Wasm 并先改造前后端在技术上没有阻塞。

当前主要成本来自数据边界和录入流程重做，而不是新建工程：

1. 把面向运行时战斗图的表和接口，改为面向角色、属性、装备、能力内容、图片及其关系的作者配置模型。
2. 把按底层资源表拆分的页面，改为围绕一个业务对象持续编辑的页面。
3. 重做发布前检查和不可变版本语义。
4. 在录入阶段完成后，新增独立的“发布配置到计算输入”转换层，再恢复 Wasm 开发。

现有缓存、图片处理、请求封装、错误处理和自动测试基础可以择优保留，不在当前方案中同时升级技术栈。

## 11. 长期商业模型与定位（已确认）
1. 定价为 9.9 元永久买断，不做订阅。
2. 收费定位是“开发与维护成本分摊”，不是高利润 SaaS。
3. 平台定位是“玩家共建数据的组织与服务系统”。
4. 当用户规模足够时，低客单价模式也可覆盖持续迭代成本。

## 12. 当前阶段关键风险与应对

### 12.1 主要风险

1. 继续沿用运行时战斗图作为录入模型，导致新页面仍然要求用户理解底层关系。
2. 一次展开全部对象和复杂机制，使字段、关系和页面互相牵制，失去阶段门。
3. 只完成自动测试，没有由项目负责人亲自录入并确认体验。
4. 破坏式更新误伤保留数据库、未提交工作或仍有参考价值的种子与测试证据。
5. 为未来计算提前设计过多字段，再次让 Wasm 决定作者配置结构。

### 12.2 应对原则

1. 一次只详细设计并实现一个阶段，后续阶段只保留范围标题。
2. 先冻结表边界、主外键和关系方向，字段允许在当前阶段内迭代。
3. 每阶段完成自动检查后，必须有一次真实页面操作；未经负责人确认不得进入下一阶段。
4. 数据库重置必须单独确认准确目标；版本库历史、未提交分支和参考证据不因“不兼容”而自动删除。
5. 作者配置、发布版本、未来计算输入和 Wasm 保持分层。

## 13. 长期高级功能建设路线
1. 斩杀线计算（生命值区间搜索/二分）。
2. 经济成长曲线与滚雪球压制量化。
3. N 秒内最大伤害组合搜索。
4. 技能真空期与有效输出窗口可视化。
5. 新旧版本伤害差异对比（Diff）。
6. 同条件装备替换收益对比（Diff）。

## 14. 当前阶段成功标准

1. 从空的目标开发数据库开始，可以启动前后端并打开管理页面。
2. 每类对象都能通过结构化页面完成新建、查询、查看、编辑和重新打开。
3. 必填、重复标识、非法范围和失效关系都有明确且可定位的提示。
4. 核心关系可以从两端查看，移除后不存在悬空关系。
5. 修改当前草稿不会改写已经发布的旧版本。
6. 项目负责人能够只通过网页完成一套代表性配置录入，并明确同意进入计算需求澄清。

版本更新速度、计算响应时间、结论复现率和运营指标保留为长期目标，不作为当前录入阶段验收条件。

## 15. 当前阶段顺序

1. 阶段 0：重新建立作者配置基线。
2. 阶段 1：角色基本管理。
3. 阶段 2：属性管理。
4. 阶段 3：装备管理。
5. 阶段 4：能力内容管理。
6. 阶段 5：图片管理。
7. 阶段 6：关联管理。
8. 阶段 7：发布管理。
9. 阶段 8：负责人验收通过后，重新进行计算输入与 Wasm 需求澄清。

当前只允许展开“属性定义与战斗资源整合”的详细设计和后续独立实施任务。该决定只调整当前切入点，不表示角色、装备、能力、图片、关系或发布阶段已经通过验收。

## 16. 已确认业务决策汇总
1. 长期数据来源：玩家与攻略者共建，按角色认领维护；当前阶段先按单人维护者设计。
2. 语言策略：仅中文，不做国际化。
3. 协作方式：不做配置分享平台，采用截图等轻量沟通。
4. 商业策略：9.9 元永久买断，面向长期维护与服务。
5. 当前优先级：先完成前端和后端录入闭环，再恢复 Wasm 开发。
6. 推进方式：一次只推进一个阶段，由负责人决定何时进入下一阶段。
7. 兼容策略：当前最小可用阶段允许破坏旧页面、旧接口和旧数据库结构，不建设历史兼容。
8. 数据建模：核心对象和关系优先使用清晰表、关系表和外键；字段可以在所属阶段逐步收敛。
9. 保存方式：当前按单人、手动保存设计，不增加自动保存和多人冲突合并。
10. 当前切入点：属性定义只保存独立面板量；固定/百分比等加成归来源关系；能力局部数值归能力参数；作者配置不再建立战斗资源定义。
