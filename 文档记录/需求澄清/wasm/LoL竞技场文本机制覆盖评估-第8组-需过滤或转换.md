# LoL竞技场文本机制覆盖评估-第8组-需过滤或转换

日期：2026-04-09
状态：已确认
数据快照：`文档记录/详细设计/最小验证/数据/lol_竞技场静态文本快照`
Data Dragon 版本：`16.7.1`
范围约束：

- 只讨论 `1v1` 数值计算
- 跳过召唤物
- 地形、位移、范围、多目标只在必要时标记为“需转换”，不作为本组主结论
- 本组目标是验证哪些静态文本应被直接过滤，哪些应被转换成独立元层能力，而不是塞进 V2 的核心战斗公式链路

## 术语约定

为避免后续讨论把“过滤”和“转换”混成同一类，本组约定如下：

1. `过滤`
   - 这类入口不进入当前 `1v1` 数值主链路。
   - 典型特征是复活、伪装、召唤对象、野区经济、地图对象等。
2. `转换`
   - 这类入口不应直接硬塞进英雄伤害/治疗/护盾公式，但可以被提炼成单独的元层模板。
   - 典型特征是 `on_death`、`on_takedown`、`summon_object`、`ally_partner`、`economy_round_meta` 之类的跨层语义。

## 本组样本

本组样本全部来自 champion 原子入口，数量足够，不需要补 item / rune / augment。

1. 英雄被动：艾尼维亚 `寒霜涅槃`
2. 英雄被动：阿兹尔 `恕瑞玛的传承`
3. 英雄被动：艾翁 `森林之友`
4. 英雄被动：妮蔻 `天生幻魅`
5. 英雄被动：崔斯特 `灌铅骰子`

## 样本 1：艾尼维亚 `寒霜涅槃`

文本摘要：

- 受到致命伤害后，艾尼维亚会进入蛋形态，并在之后复活。

抽象机制：

- 致死判定
- 死亡替代状态
- 复活结果

映射到 V2：

- 这不是普通的伤害/护盾/治疗公式问题。
- 如果未来要保留，至少需要一个 `on_death -> replace_state -> resurrect` 的独立模板。
- 当前 `1v1` 数值主链路没有必要把它当成标准 combat packet 处理。

结论：

- **当前阶段：应过滤**
- **未来如果扩展死亡替代层：可转换为复活模板**
- **不构成 V2 核心数值公式阻塞**

说明：

- 这个样本暴露的是“死亡结果如何被替换”，不是“数值如何计算”。
- 如果把它硬塞进战斗公式，会把死亡、重生、状态切换混成一层，后续维护会失控。

## 样本 2：阿兹尔 `恕瑞玛的传承`

文本摘要：

- 阿兹尔可以从防御塔废墟中召唤太阳圆盘。

抽象机制：

- 地图对象状态
- 废墟/建筑生命周期
- 召唤对象

映射到 V2：

- 这属于 `summon_object` 或 `map_object` 层，而不是英雄伤害数值层。
- 其前提依赖防御塔是否被摧毁，已经超出 `1v1` 数值计算的直接范围。

结论：

- **当前阶段：应过滤**
- **若未来要支持：必须先补地图对象层与对象生命周期模板**
- **不应进入 V2 战斗公式主链路**

说明：

- 这个样本的关键不是“圆盘有多少数值”，而是“圆盘如何被创建、挂到哪张地图、在什么对象状态下存活”。
- 这类语义更像平台对象管理，不像战斗计算。

## 样本 3：艾翁 `森林之友`

文本摘要：

- 艾翁不能攻击也不能被非史诗野怪攻击。
- 他可以在野怪营地种植小植被，成熟后获得金币和经验。

抽象机制：

- 非英雄单位的交互限制
- 野区营地与成长过程
- 结算金币/经验
- 典型的轮次/生态经济规则

映射到 V2：

- 这不是英雄对英雄的 `1v1` 伤害计算。
- 可转换成 `economy_round_meta` 与 `neutral_camp_rule` 两层，但不应并入核心战斗公式。
- 当前更适合作为过滤样本，从 duel engine 输入中剔除。

结论：

- **当前阶段：应过滤**
- **若未来扩展野区/经济层：可转换为独立元层规则**
- **对 V2 核心战斗链路无直接阻塞**

说明：

- 这个样本说明“可计算结果”并不等于“应进入战斗公式”。
- 真正要保留的是营地规则、成长触发和经济结算，不是单纯的数值面板。

## 样本 4：妮蔻 `天生幻魅`

文本摘要：

- 妮蔻可以伪装成友方英雄或其它单位。
- 被控制、施放伤害技能、攻击防御塔或伪装体受到足够伤害时，伪装会被打破。

抽象机制：

- 身份伪装
- 伪装破除条件
- 目标呈现与真实对象分离

映射到 V2：

- 这不是伤害数值本体，而是 `ally_partner` / `shapeshift_identity` 层。
- 在 `1v1` 评估里，伪装影响的是“看起来是什么对象”，不是“数值如何计算”。
- 如果未来要支持，应该作为状态包装层转换，而不是加入伤害公式。

结论：

- **当前阶段：应转换后过滤**
- **更准确的做法是把它抽成身份/伪装状态模板，而不是战斗公式**
- **不应直接进入 V2 核心数值链路**

说明：

- 这个样本最容易误判成“只是一个被动”，但它实际改变的是对象身份边界。
- 如果不先拆出身份层，后面会把视觉、交互、判定和数值混在一起。

## 样本 5：崔斯特 `灌铅骰子`

文本摘要：

- 击杀单位后，崔斯特会随机获得 1 到 6 的额外赏金。

抽象机制：

- 击杀触发
- 随机奖励
- 额外赏金结算

映射到 V2：

- 这类能力不属于伤害/治疗/护盾本体。
- 如果未来保留，应转换为 `on_takedown -> grant_random_reward` 的经济事件模板。
- 当前在 `1v1` 数值主链路里应当从战斗公式中剔除。

结论：

- **当前阶段：应转换后过滤**
- **如果未来接入经济层，随机赏金可作为独立奖励模板**
- **不应进入核心战斗公式**

说明：

- 这个样本表明“击杀后奖励”是后置结算，不是战斗数值的一部分。
- 随机性也说明它不适合直接塞到 deterministic combat formula 里。

## 本组汇总结论

### 已确认可支撑的能力

1. V2 的核心战斗数值链路不需要为了本组样本新增伤害、治疗、护盾类 AST 节点。
2. `on_death`、`on_takedown`、`summon_object`、`ally_partner`、`economy_round_meta` 这类语义可以被识别出来，但应该落到更外层的元层模板。
3. 只要明确“战斗数值层”和“对象/经济/身份层”的边界，V2 主公式不会被这些文本卡住。

### 本组暴露出的真实重点

1. 真正需要收口的是 **过滤边界**，不是公式表达能力。
2. 这类入口的共同问题是：
   - 不属于纯 `1v1` 数值
   - 需要对象生命周期、身份状态、地图对象或经济结算参与
   - 如果硬塞进战斗公式，会把核心链路污染成大杂烩
3. 其中少数能力可以“转换后保留”，但转换目标应该是独立元层模板，不是 combat packet 的补丁。

### 本组建议收口的通用模板

1. `on_death_replacement`
   - 用于复活、替死、状态替代类效果
2. `summon_object`
   - 用于塔、圆盘、召唤物、地面对象等生命周期
3. `identity_wrap`
   - 用于伪装、变形、对象身份切换
4. `on_takedown_reward`
   - 用于击杀后经济、资源、随机奖励
5. `neutral_camp_rule`
   - 用于野区/非英雄单位的交互限制与经济结算

### 本组稳定结论

1. `需过滤或转换` 不是“暂时不好实现”的委婉说法，而是明确不进入 V2 核心战斗公式。
2. 这组样本大多数应直接过滤，少数可以转换成元层模板，但都不应该伪装成普通伤害公式。
3. 当前最重要的不是再扩一层公式 AST，而是把“什么进战斗层、什么进元层”这条边界定死。

## 本组已确认的实现导向

1. 对于复活、伪装、召唤对象、击杀后奖励、野区经济这类效果，默认先做过滤，不直接进 `1v1` 数值主链路。
2. 若后续要支持这些文本，优先定义独立元层模板，再由 bundle 编译层做转换，不在英雄技能 JSON 里硬塞战斗语义。
3. 任何依赖地图对象、单位身份、营地状态、击杀后奖励的效果，都不应和伤害/治疗/护盾共用同一套核心表达。

## 当前判断

本组结论是：**这批文本不会逼 V2 推翻重来，但它们要求更严格的边界分层。**

更具体地说：

- 纯战斗数值层继续只管 `1v1` 伤害、治疗、护盾与资源公式
- `需过滤` 的内容直接排出主链路
- `需转换` 的内容只在独立元层里落模板

这比把所有机制都塞进同一套公式里更稳，也更适合后续扩展。
