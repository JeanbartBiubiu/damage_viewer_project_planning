# WASM 伤害引擎需要完成的挑战（1v1，跨游戏可适配）
纯伤害模拟，不是实时战斗引擎。

## 1. 参考基线（用于确定优先级）
当前参考数据源：`Data Dragon 16.3.1`  
当前参考样本：`172 英雄，860 条技能（被动+QWER）`

高频效果标签（出现次数）：
- 伤害：711
- 控制：314
- 自我增益：286
- 治疗/回复：228
- 二段/形态切换：153
- 位移：133
- 敌方减益：119
- 召唤/部署：118
- 资源交互：111
- 护盾：80
- 斩杀/缺失生命值联动：65

结论：必须优先保证高频标签闭环（“暂不实现但需记录”章节中的机制除外），否则后期返工概率极高。  
说明：以上统计只用于“确定实现优先级”，不是引擎绑定 LoL 的理由。

## 2. 跨游戏适配硬约束（对齐后端接口）
以下约束来自 `接口/game_manage/接口定义.md`，属于架构前提：

1. 引擎必须以 `gameId/versionId/dataHash` 作为运行上下文，不允许写死某个游戏。  
2. 引擎初始化数据只来自后端 `bundle`（`GET /api/games/{gameId}/versions/{versionId}/bundle`），前端仅透传或做轻量裁剪。  
3. 运行时能力必须由 `mechanicsConfig` + `attributeDefinitions` + `ownerCategories` + `types/typeRelations` 驱动，不能硬编码“英雄联盟专用枚举”。  
4. `ownerType` 是可扩展 key（hero/item/rune/...），引擎必须按字符串类别处理归属关系。  
5. 属性 key（如 hp/atk/armor）来自 `attributeDefinitions`，引擎不能假设固定字段集合。  
6. 同一输入可复现：`bundle + input + seed` 一致时结果必须一致。  
7. 版本漂移可追踪：任何 run 结果都能追溯到 `gameId/versionId/dataHash`。

## 3. 优先级分层（从“覆盖率”而不是“实现难度”出发）

### P0（首期必须完成，目标覆盖 >80% 常见技能行为）
1. 统一类型系统  
   主动/被动、普攻/技能、物理/魔法/真实伤害、持续/瞬发、来源归属（ownerType）统一建模。  
2. 事件驱动内核  
   时间队列、同时刻稳定排序、可取消、可中断、可复现（固定 seed）。  
3. 前端 Bundle 组装层  
   前端把后端 `GameDataBundleV1` 组装为引擎固定输入结构；引擎不依赖 LoL 专有命名（如仅认 heroId 以外留扩展位）。  
4. 伤害结算主链路  
   基础值 -> 增减伤 -> 穿透/抗性 -> 护盾 -> 生命值 -> 濒死触发，顺序固定。  
5. 高频标签能力  
   `伤害/控制/自我增益/敌方减益/治疗/护盾/位移/资源交互` 全部可表达。  
6. 常见控制能力  
   至少支持：减速、眩晕、禁锢、击飞、恐惧、击退。  
7. 技能状态机  
   前摇、后摇、读条、二段释放、形态切换、普攻重置、普攻弹道/命中时刻。  
8. 数值与叠层系统  
   固定值/百分比、分乘区、叠层、刷新时长、唯一被动互斥、内置冷却 ICD。  
9. 资源与冷却  
   法力/能量/怒气、技能急速、冷却缩减、冷却重置、充能技能。  
10. 暴击（确定性）  
    P0 至少支持期望暴击模型（可复现、可批量对比），支持普攻/技能/装备暴击开关与倍率。  
11. 数值稳定性  
    循环依赖防护（如生命与法强互转）、浮点误差控制、舍入规则统一。  
12. 工程保障  
    输入校验、错误码、战斗日志、关键事件快照、版本追踪（数据/公式/引擎）。

### P1（第二阶段，目标覆盖“高风险复杂机制”）
1. 斩杀与免死  
   缺失生命值加成、最低生命阈值、不可被击杀状态。  
2. 不可选取/无敌/金身  
   对弹道、持续伤害、目标丢失、命中时机的影响。  
3. 死亡与复活  
   死亡清理、延迟结算、复活状态恢复策略。  
4. 快照与动态取值  
   技能施法时快照 vs 命中时动态取值按技能可配置。  
5. 随机模型双轨  
   在 P0 期望暴击基础上补齐随机模拟模式（固定 seed 可复现）+ 期望模式并存。

### P2（第三阶段，低频但需要留接口）
1. 低频控制细项  
   缚地、致盲、沉默、睡眠、缴械、变形等。  
2. 隐身/伪装与视野相关  
   先在 1v1 里保留接口，后续扩展。  
3. 多目标拓展点  
   当前只做 1v1，但事件和目标选择模型不要写死。

## 4. 建议落地为“可验收挑战项”
每项都要有“完成定义（DoD）”，避免后期返工。

1. 类型系统 DoD  
   任意技能都能映射到统一枚举：`damageType/effectTags/controlTags/triggerType`。  
2. 跨游戏 DoD  
   至少两款数据结构差异明显的游戏可直接跑通（仅换 `gameId/versionId/bundle`，不改引擎代码）。  
3. 结算链路 DoD  
   同一输入重复运行 100 次结果完全一致（随机模式除外）。  
4. 事件系统 DoD  
   同时间戳事件顺序稳定且可解释（日志可追踪）。  
5. 数值系统 DoD  
   无 NaN/Infinity，无循环震荡，边界值（0 抗性/负抗性）结果可验证。  
6. 性能 DoD  
   批量 run 满足目标吞吐（需定义具体阈值，例如 N 场/秒）。  
7. 回放 DoD  
   给定 `bundle + input + seed` 可回放并复现结果。

## 5. 回归测试集（按返工风险优先）
以下场景建议作为长期固定回归：

1. 三段技能：层数、第三段强化、超时回退。  
2. 灰量/受击窗口类技能：时间窗口累计与联动结算。  
3. 叠层 + 斩杀技能：叠层、斩杀阈值、击杀重置。  
4. 属性互转被动：双向转换的收敛性。  
5. 暴击联动技能：暴击、缺失生命值联动、边界值。  
6. 充能技能：充能、独立冷却、连续施放。  
7. 免死 + 复活：免死、死亡、复活事件顺序。  
8. 无敌/不可选取：弹道命中时刻与持续伤害行为。  
9. 多被动并存：乘区、叠层、刷新规则。  
10. 普攻重置：前摇取消与 DPS 变化。  

## 6. 暂不实现但需记录（后续版本再开）
1. 技能偷取/附身类机制  
   如技能偷取、附身后技能替换。这类机制会动态替换技能池与属性来源，先不做。  
2. 多单位召唤/宠物体系  
   如炮台、宠物、召唤物群。当前 1v1 先不引入多单位战场与归属管理。  
3. 超复杂多形态武器系统  
   如多武器轮转与子弹资源联动，先不纳入首期范围。
