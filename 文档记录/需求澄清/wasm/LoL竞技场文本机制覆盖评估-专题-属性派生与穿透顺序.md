# LoL竞技场文本机制覆盖评估-专题-属性派生与穿透顺序

Data Dragon 版本：`16.7.1`
补充来源：`CommunityDragon latest/zh_cn`（Arena augments）
范围约束：

- 只讨论 `1v1` 数值计算
- 跳过召唤物
- 地形、位移、多目标、建筑物、史诗级野怪只在必要时标记为“需转换”
- 本专题只收“读多个属性后再写回一个属性 / 伤害公式内部的穿透修正 / 独立中间属性”的语义，不把纯基础属性加成当主体

## 专题定位

第 6 组已经确认：问题不在“有没有属性”，而在“属性怎么派生、穿透何时生效、适应之力怎么保留”。  
第 7 组则证明：纯面板加成和永久属性写回只是属性层基线，不该和派生属性、穿透顺序混在一起。

本专题只收下面三类语义：

- `derived_stat_from_attrs`：从多个属性读值，再写回一个派生属性
- `stack_to_stat`：从层数或计数读值，再写回一个或多个属性
- `penetration_modifier`：写进物理/魔法伤害公式内部的穿透修正

## 本专题样本

1. 拉莫斯 `锥刺甲壳`，`champion:Rammus:passive`
2. 锤石 `地狱诅咒`，`champion:Thresh:passive`
3. `最后的轻语`，`item:1031`
4. `穿针引线`，`augment:84`
5. `歌利亚巨人`，`augment:41`

说明：

- `灭世者的死亡之帽` 只作为边界说明，不纳入主样本。
- `基础属性加成` 里那种纯 flat bonus 只用于对照，不是本专题主体。

## 样本 1：拉莫斯 `锥刺甲壳`

文本摘要：

- 拉莫斯获得额外攻击力，受益于他的护甲和魔法抗性。

抽象机制：

- 一个输出属性由多个输入属性共同驱动
- 防御属性不是只服务于减伤，还可以反过来生成进攻属性

映射到 V2：

- `derived_stat_from_attrs(armor, mr) -> attack_damage`
- 这里不是 `flat_stat_bonus`
- 读多个属性，再写回一个属性，才是这个效果的本质

结论：

- **这是属性派生，不是基础属性加成**
- **核心关注点：多源输入到单一输出的口径必须统一**

说明：

- 如果只允许“某个属性 += 固定值”，这个效果就会被错误压扁。
- 它说明 V2 需要的是属性转换口径，而不是再加一类普通面板项。

## 样本 2：锤石 `地狱诅咒`

文本摘要：

- 锤石收割死亡敌人的灵魂，从而为他提供护甲和法术强度。

抽象机制：

- 层数累计后同步推动多个属性
- 输入不是多个基础属性，而是一个可累积状态
- 输出是多属性同步增长

映射到 V2：

- `stack_to_stat(stack_count) -> armor + ability_power`
- 这类效果不是 `flat_stat_bonus`
- 层数是输入状态，属性增长是输出结果

结论：

- **这是 `stack_to_stat`**
- **不是基础属性加成**
- **核心关注点：层数系统和属性写回必须分层**

说明：

- 本专题不再展开灵魂怎么掉落、怎么收集，那部分属于触发绑定专题。
- 这里只确认：一旦层数进入运行时，`护甲 + 法强` 的同步增长不构成阻塞。

## 样本 3：`最后的轻语`

文本摘要：

- 20 攻击力，18% 护甲穿透。

抽象机制：

- 一个基础属性是直接写回
- 另一个是插入伤害公式的穿透修正
- 它不是纯粹的属性派生，也不是普通数值堆叠

映射到 V2：

- `flat_stat_bonus(attack_damage, +20)`
- `penetration_modifier` 应进入 `physical_damage_formula(...)`
- 穿透位置应在物理伤害公式内部、进入目标护甲减伤之前

结论：

- **20 攻击力：属于基础属性加成**
- **18% 护甲穿透：属于公式内部修正，不是 flat bonus**
- **核心关注点：穿透必须在物理伤害公式里落位**

说明：

- 如果把穿透做成外层 buff，它会和普通攻击力加成混淆。
- 这里的关键不是数值大小，而是结算顺序。

## 样本 4：`穿针引线`

文本摘要：

- 获得 18% 护甲穿透和法术穿透。

抽象机制：

- 同一修正同时作用于物理和魔法两条伤害路径
- 本质还是公式内部修正，不是外层面板

映射到 V2：

- `penetration_modifier`
- 需要在 `physical_damage_formula(...)` 和 `magic_damage_formula(...)` 内部使用同一套穿透接口
- 不应拆成两个互相独立的边角实现

结论：

- **这是统一穿透修正，不是属性派生**
- **核心关注点：物理/魔法两条公式内部都要吃到同一套穿透口径**

说明：

- 这个样本说明穿透本身没有逼着 V2 新增 AST 节点。
- 真正要收口的是“穿透在哪个公式阶段生效”。

## 样本 5：`歌利亚巨人`

文本摘要：

- 体型变大，获得生命值和适应之力。

抽象机制：

- 生命值是基础属性写回
- 适应之力不是 AD，也不是 AP
- 这个效果更像“独立中间属性 + 面板增长”的组合

映射到 V2：

- `flat_stat_bonus(hp_max, +x)` 或 `stat_multiplier(hp_max, +y)`
- `adaptive_force` 应作为独立中间属性存在
- 不应把它提前折叠成 `attack_damage` 或 `ability_power`

结论：

- **生命值部分：基础属性加成**
- **适应之力部分：独立中间属性**
- **核心关注点：不要把 adaptive_force 直接当成 AD/AP**

说明：

- `灭世者的死亡之帽` 只适合做边界对照：它证明“基础属性加成 + 总属性放大”仍然属于属性层基线。
- 但它不属于本专题主体，因为它没有暴露多源派生或穿透顺序问题。

## 本专题汇总结论

### 已确认可支撑的能力

1. `flat_stat_bonus` 和 `derived_stat_from_attrs` 是两类不同语义，不能混成一个“属性加成”桶。
2. `stack_to_stat` 说明层数驱动的属性增长和普通面板加成也应分层。
3. `penetration_modifier` 必须进入物理/魔法伤害公式内部，作为公式阶段的一部分，而不是外层 buff。
4. `adaptive_force` 应保持独立中间属性，不提前折叠成 AD/AP。

### 本专题暴露出的真实重点

1. **属性派生不是 flat bonus。**
2. `derived_stat_from_attrs` 的关键是“读多个输入属性，再写回一个输出属性”，而不是单项加法。
3. 穿透的关键不是“有没有穿透”，而是“插在物理/魔法伤害公式的哪个阶段”。
4. `adaptive_force` 的价值在于它是一个可独立发放、独立读取的中间值，保留它能避免后续语义塌缩。

### 本专题建议收口的通用模板

1. `flat_stat_bonus`
   - 输入：固定数值
   - 输出：单属性直接加成
2. `derived_stat_from_attrs`
   - 输入：多个属性
   - 输出：一个派生属性
3. `stack_to_stat`
   - 输入：层数或可累积状态
   - 输出：一个或多个属性增益
4. `penetration_modifier`
   - 输入：护甲穿透 / 法术穿透
   - 输出：物理/魔法伤害公式内部修正
5. `adaptive_force`
   - 输入：固定值或倍率
   - 输出：独立的适应之力属性读写口径

### 本专题已确认的实现导向

1. `拉莫斯 / 锤石` 这类机制按“读多个输入后写回属性”的转换模板处理，不要按 flat bonus 处理。
2. `最后的轻语 / 穿针引线` 这类机制按“写进物理 / 魔法伤害公式内部的穿透修正”建模。
3. `歌利亚巨人` 这类机制按“生命值基础写回 + 独立 adaptive_force”建模，不把 `adaptive_force` 折叠成 AD/AP。
4. `灭世者的死亡之帽` 这类纯面板加成只作为属性层基线对照，不进入本专题主线。

## 当前判断

本专题结论是：**可行，而且把“属性派生与穿透顺序”收成了比第 6 组更精确的一层。**

更具体地说：

- 第 7 组证明了 flat bonus 和永久属性写回只是属性层基线
- 第 6 组和本专题一起证明，真正需要统一的是多源属性派生、穿透公式阶段和 adaptive_force 语义
- 这些内容不会逼着 V2 推翻重来，但必须在属性层口径上定死

因此，下一步实现收口应优先把 `derived_stat_from_attrs`、`penetration_modifier`、`adaptive_force` 三者分层，而不是继续把所有属性效果压成单一面板加法。
