# LoL竞技场文本机制覆盖评估-第1组-比例与阈值

日期：2026-04-08
数据快照：`文档记录/详细设计/最小验证/数据/lol_竞技场静态文本快照`
Data Dragon 版本：`16.7.1`
范围约束：

- 只讨论 `1v1` 数值计算
- 跳过召唤物
- 地形、位移、范围、多目标只在必要时标记为“需转换”，不作为本组主结论
- 本组目标是验证“比例与阈值”类机制是否会卡住 V2 架构

## 本组 5 个样本

1. 英雄被动：布里茨 `法力屏障`
2. 英雄技能：阿克尚 `恩怨相抵`
3. 符文：`黑暗收割`
4. 海克斯强化：`坚韧`
5. 物品：`永续意志夹心饼干`

## 样本 1：布里茨 `法力屏障`

文本摘要：

- “布里茨在血量过低时会获得一层基于它法力值的护盾。”

抽象机制：

- 自身当前生命值阈值判定
- 触发后施加护盾
- 护盾量基于另一条属性（法力值）

映射到 V2：

- 阈值条件：`Lt(ActorHpCurrent / ActorHpMax, threshold)`
- 护盾数值：`Multiply(ActorAttr("mana"), ratio)`
- 效果执行：`apply_shield`

结论：

- **公式表达：已覆盖**
- **护盾效果：已覆盖**
- **主要缺口：触发挂载点未显式定义**

## 样本 2：阿克尚 `恩怨相抵`

文本摘要：

- “每颗子弹对命中的首个敌人造成伤害，基于已损失生命值至多提升至更高伤害。”

抽象机制：

- 目标已损失生命值参与伤害计算
- 伤害存在最小值与最大值
- 同一技能内部带蓄力与多子弹阶段

映射到 V2：

- 已损失生命值：`ActorHpMax(target) - ActorHpCurrent(target)`
- 伤害区间：`Clamp(value, min, max)` 或 `Min/Max`
- 多子弹：多次 `deal_damage` 或一次 action 内派生多个 damage packet

结论：

- **比例与上限表达：已覆盖**
- **技能内部阶段：部分覆盖，但不是本组核心阻塞点**

## 样本 3：符文 `黑暗收割`

文本摘要：

- “伤害一名生命值低于50%的英雄时会造成自适应伤害并收割灵魂，并将伤害永久提升。”
- “冷却时间：35秒（参与击杀时重置到1秒）”

抽象机制：

- 目标当前生命值阈值
- 命中触发额外伤害
- 永久叠层
- takedown 重置冷却

映射到 V2：

- 阈值条件：`Lt(target.hp / target.hp_max, 0.5)`
- 额外伤害：`deal_damage`
- 永久成长：`modify_attribute`
- 冷却重置：`reduce_cooldowns` 或 cooldown subsystem

结论：

- **阈值与伤害表达：已覆盖**
- **叠层与冷却：部分覆盖**
- **主要缺口：takedown 触发源需要显式建模**

## 样本 4：海克斯强化 `坚韧`

文本摘要：

- “获得基础生命回复，在低于25%生命值时提升至更高基础生命回复。”

抽象机制：

- 自身当前生命值阈值
- 两档或多档回复倍率
- 周期性回复

映射到 V2：

- 周期回复：`regen` 子系统
- 分档逻辑：`If(Lt(hp / hp_max, 0.25), amped_regen, base_regen)`

结论：

- **已覆盖**

## 样本 5：物品 `永续意志夹心饼干`

文本摘要：

- “在5秒里持续回复生命值，基于你的已损失生命值获得提升。”
- “消耗或出售一块饼干，都会永久提供30最大生命值。”

抽象机制：

- 已损失生命值影响治疗量
- 短时持续治疗
- 永久属性成长
- 消耗品触发

映射到 V2：

- 已损失生命值：`ActorHpMax - ActorHpCurrent`
- 持续治疗：`schedule_timer + modify_attribute`，或复用 `regen` 思路
- 永久最大生命值：`modify_attribute("hp_max", +30)`

结论：

- **公式表达：已覆盖**
- **永久属性成长：已覆盖**
- **短时 HoT：部分覆盖，建议明确通用实现套路**

## 本组汇总结论

### 已确认可支撑的能力

1. `当前生命值 / 最大生命值 / 已损失生命值` 这三类量，V2 现有公式层足以表达。
2. 阈值判断、上下限钳位、分档倍率，都可由 `If / Lt / Lte / Clamp / Min / Max` 表达。
3. 基于生命值比例派生的护盾、回复、额外伤害、永久成长，不构成 V2 的公式层阻塞。

### 本组暴露出的真实重点

1. **最大缺口不是公式，而是触发绑定层。**
2. 被动、符文、海克斯、装备被动这类机制，经常依赖：
   - `on_damage_dealt`
   - `on_damage_taken`
   - `on_takedown`
   - `on_consume`
   - `on_threshold_crossed`
3. 如果这些触发源不在配置层被显式建模，后续会重新回到 MVP 那种“到处补 if”的风险。

### 本组稳定结论

1. `生命值比例类公式` 不需要新增 AST 节点，现有节点足够。
2. `触发源/触发时机` 必须成为实现阶段的重点收口对象。
3. `短时持续治疗` 可以先不单独建子系统，但要定义标准实现套路。

## 需要你确认的点

1. 对于布里茨这类“低血量触发一次护盾”的机制，已确认后续统一抽象成：
   - `受伤后检测是否跨阈值`
   - 不采用“满足阈值即可触发（带冷却）”作为默认语义
2. 对于饼干这类效果，已确认：
   - 可以接受统一的 `短时 HoT 模板`
   - 不再默认每次都临时拼 `schedule_timer + modify_attribute`

## 当前判断

本组结论是：**可行，而且不会逼着 V2 推翻重来。**

真正需要提前加固的不是“比例类公式”，而是“被动/符文/海克斯/装备被动的触发绑定模型”。

## 本组已确认的实现导向

1. 低血量触发类护盾，默认按“受伤后跨阈值触发”建模。
2. 短时持续治疗类效果，允许引入统一 HoT 模板，避免在配置层重复手工拼装。
