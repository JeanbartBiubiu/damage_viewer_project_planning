## 样本 1：拉莫斯 `锥刺甲壳`

文本摘要：

- “拉莫斯获得额外攻击力，受益于他的护甲和魔法抗性。”

抽象机制：

- 护甲与魔抗共同驱动一个派生攻击力
- 防御属性不是只影响生存，还会被转成进攻属性

映射到 V2：

- 这不是普通的 `offense_stat` 直给，而是一个 `stat_conversion`
- 可表达为 `derived_ad = f(armor, mr)`
- 如果实现层只有单属性读取，就需要先补一个“多源派生值”再写回攻击力

结论：

- **抗性本体：已覆盖**
- **防御转进攻：已覆盖**
- **主要关注点：多源属性派生的表达方式要统一**

说明：

- 这个样本的重点不是 `拉莫斯` 本身，而是“护甲 / 魔抗可以共同作为一个公式输入”。
- 它说明 V2 不需要为“抗性转攻击力”单独加新机制，只需要把属性引用和转换公式收口好。

## 样本 2：锤石 `地狱诅咒`

文本摘要：

- “锤石可以收割那些死在他身边的敌人们的灵魂，从而为他提供护甲和法术强度。”

抽象机制：

- 灵魂是可累积资源
- 每层资源同时推动护甲与法术强度
- 这类效果本质上是“栈层 -> 双属性增益”

映射到 V2：

- 灵魂数量：`stack`
- 属性增益：`modify_attribute("armor", ...)` + `modify_attribute("ability_power", ...)`
- 如果后续要统一收口，建议把它抽成 `stack_to_stat` 模板，而不是每个英雄被动单写一套

结论：

- **堆叠式属性增长：已覆盖**
- **双属性同步加成：已覆盖**
- **主要缺口不在数值层，而在灵魂来源事件如何挂到层数系统**

说明：

- 本组不再展开“灵魂怎么掉落、怎么收集”的触发层细节，那部分属于前面几组已经反复确认的触发绑定问题。
- 这里只确认：一旦层数进来，`护甲 + 法强` 的同步增长不构成 V2 阻塞。

## 样本 3：物品 `最后的轻语`

文本摘要：

- “20 攻击力，18% 护甲穿透。”

抽象机制：

- 直给攻击力
- 按百分比削减目标护甲后再参与伤害结算
- 本体不复杂，但它要求伤害流水线有明确的防御计算顺序

映射到 V2：

- 攻击力：普通属性加成
- 护甲穿透：`armor_penetration`
- 物理伤害公式读取：`physical_damage_formula(..., armor_penetration, target_armor, ...)`
- 伤害结算顺序应明确为：先在物理伤害公式里应用攻击方穿透，再进入目标防御减伤

结论：

- **攻击力加成：已覆盖**
- **百分比护甲穿透：已覆盖**
- **主要关注点：穿透必须进入统一的防御结算顺序**

说明：

- 这个样本的价值在于“顺序”，不是“数值大小”。
- 如果穿透只被当成普通攻击力 buff，结果会完全偏掉；它必须在目标护甲应用前生效。

## 样本 4：海克斯强化 `穿针引线`

文本摘要：

- “获得 18% 护甲穿透和法术穿透。”

抽象机制：

- 同一增益同时作用于物理和魔法两类伤害
- 不是单一属性，而是双通道穿透修正

映射到 V2：

- `armor_penetration`
- `magic_penetration`
- 最好在物理 / 魔法两套伤害公式内部走同一套防御修正接口，不要拆成两条互不相干的实现路径

结论：

- **双穿透表达：已覆盖**
- **主要缺口：需要统一物理 / 魔法两条路径的穿透应用顺序**

说明：

- 这个样本说明“穿透”本身没有逼着 V2 新增 AST 节点。
- 但如果物理和魔法减伤各自散写，后面很容易出现一边更新了、一边漏掉的实现偏差。

## 样本 5：海克斯强化 `歌利亚巨人`

文本摘要：

- “体型变大，获得生命值和适应之力。”

抽象机制：

- 体型变化是视觉/表现层，不是本组主结论
- 关键数值是 `生命值` 与 `适应之力`
- 适应之力不是单纯的 AP 或 AD，而是一个独立的中间属性

映射到 V2：

- 生命值：普通属性加成
- 适应之力：建议作为独立属性 `adaptive_force`
- 如果当前实现只保留 AD / AP 两个终值，那么这里就需要先落一个中间层，不要硬把它塞成某个固定进攻属性

结论：

- **生命值加成：已覆盖**
- **适应之力：已覆盖**
- **主要关注点：适应之力应保持为独立语义，不要过早折叠成 AD 或 AP**

说明：

- 这个样本的核心不是“变大”，而是“适应之力是可独立发放和读取的数值”。
- 这会直接影响后续能否稳定支持一切“按适应之力加成”的 Arena 强化效果。

## 本组汇总结论

### 已确认可支撑的能力

1. `护甲 / 魔抗 / 攻击力 / 法术强度 / 适应之力` 这些基础属性，都可以继续按 V2 的属性层表达。
2. `防御 -> 进攻` 的转换语义已经有明确落点，不需要为“抗性转攻击力”单独扩新子系统。
3. `护甲穿透 / 法术穿透` 可以继续作为伤害结算前的统一修正项处理。
4. `stack -> stat`、`derived_stat = f(attrs)`、`dual penetration buff` 这些模式都能被同一套公式外置路线承接。

### 本组暴露出的真实重点

1. **真正要收口的是数值顺序，不是数值字面。**
2. 穿透必须明确插入到防御结算顺序里，否则会变成普通属性加成。
3. 多源属性转化要支持“一个效果读多个属性，再写回另一个属性”的表达，不要只允许单输入单输出。
4. 适应之力最好保留为独立中间属性，不要过早折叠到攻击力或法强，否则后续强化会越来越难复用。

### 本组建议收口的通用模板

1. `derived_stat_from_attrs`
   - 输入：多个属性
   - 输出：一个派生属性
2. `stack_to_stat`
   - 输入：层数
   - 输出：一个或多个属性增益
3. `penetration_modifier`
   - 输入：护甲穿透 / 法术穿透
   - 输出：参与防御结算的统一修正
4. `adaptive_force_buff`
   - 输入：固定值或倍率
   - 输出：独立的适应之力属性

### 本组稳定结论

1. `抗性、穿透、转化、适应之力` 不会逼着 V2 推翻重来。
2. 这个组的核心不是新增公式节点，而是把 **属性派生、穿透顺序、适应之力语义** 固化成统一约定。
3. 只要防御结算顺序和派生属性口径统一，后续英雄被动、装备和 Arena 强化都能继续复用同一套表达。

## 本组已确认的实现导向

1. `拉莫斯 / 锤石` 这类机制，按“层数或防御属性驱动的派生统计”建模。
2. `最后的轻语 / 穿针引线` 这类机制，按“写进物理 / 魔法伤害公式内部的统一穿透修正”建模。
3. `歌利亚巨人` 这类机制，按“独立适应之力属性”建模，不直接折叠成 AD / AP。

## 当前判断

本组结论是：**可行，而且更像是把数值口径收紧，而不是补新能力。**

第 1、2 组暴露的是触发与结果载荷问题；第 6 组进一步说明：

- 触发之外，V2 还要把 **派生属性** 和 **防御结算顺序** 固化
- 但这仍然是同一条公式外置路线上的收口，不是重做引擎

换句话说，`抗性、穿透、转化、适应之力` 这一组的风险点在“实现约定”，不在“机制能力缺失”。
