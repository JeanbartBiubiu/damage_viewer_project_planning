# 查漏补缺：前端 Bundle 直通 & 引擎未实现机制差距分析

## 一、问题 1：前端直接使用 Bundle 数据输入需要多大工作量

### 1.1 当前数据流

```
后端 buildBundle → GameDataBundle（heroes/skills/items/formulas/…）
     ↓
前端 MvpEngineClient.init(meta, bundle)
     ↓
Worker → KatarinaWasmBridge → JSON.stringify → Wasm engine_init(ptr, len)
     ↓
Rust: init_session(EngineInitPayload) → compile_benchmark_catalog(bundle, config)
                                                  ↑
                                          要求 bundle.benchmark 存在！
```

### 1.2 核心矛盾

前端当前拥有的 `GameDataBundle` 包含：`heroes / skills / items / attributeDefinitions / formulaProfiles / formulaBindings / types / typeRelations …`

Wasm 引擎实际消费的是 `bundle.benchmark: BenchmarkBundle`，这是一套**完全不同的数据结构**：

| 维度 | 前端 Bundle | 引擎 BenchmarkBundle | 差距 |
|------|------------|---------------------|------|
| 英雄属性 | `hero.baseStats`（基础面板） | `actor.attrs`（已合并 hero+item+override 的最终属性） | 引擎要预计算结果 |
| 技能 | `skill.params`（松散 JSON：adRatio, baseDamage…） | `skillDefs[]`（结构化：formulaId, flags, dot, stun, on-hit 关联） | **表达方式完全不同** |
| 装备 | `item.statsModifier`（数值加成 map） | `itemDefs[]`（on-hit 公式、dot、反甲、黑切叠层机制） | 前端只有数值；引擎要**机制定义** |
| 公式 | `formulaProfiles[].params`（松散 JSON） | `formulas[]`（可执行 AST 树：Add/Multiply/ActorAttr/Constant） | 需要编译步骤 |
| 行为系统 | **不存在** | `actions[]`（behavior 枚举、cooldown、priority、manaCost） | **完全缺失** |
| 规则系统 | **不存在** | `rules`（scheduler 优先级、count_to_three 联动） | **完全缺失** |
| 场景配置 | **不存在** | `selfActor / enemyActor` 的完整定义 | **完全缺失** |

当前的 `benchmark_m1_init_payload.json`（648 行）是**手工编写的测试夹具**，不由任何自动化流程产出。

### 1.3 工作量拆解

#### 路径 A：最短路径 — 后端编译 BenchmarkBundle 嵌入 Bundle

> 核心思路：后端 `buildBundle` 增加编译阶段，从 DB 管理数据自动产出 `benchmark` 子结构。前端零改动。

| # | 工作项 | 复杂度 | 预估人天 | 说明 |
|---|--------|--------|---------|------|
| A1 | 后端增加"场景模板配置"（哪个 hero 做 self/enemy、带哪些装备） | 低 | 1 | 产品+后端 |
| A2 | 合并 `hero.baseStats + item.statsModifier` → `actor.attrs` | 低 | 0.5 | 纯数值聚合 |
| A3 | `Skill.params` → `BenchmarkSkillDefinition` 映射 | **高** | 5-8 | 需定义技能机制正式 schema |
| A4 | `Item` → `BenchmarkItemDefinition` 映射（on-hit/dot/反甲/黑切） | **高** | 3-5 | 需装备机制 schema |
| A5 | `FormulaProfile.params` → `BenchmarkFormulaExpr` AST 编译 | **高** | 3-5 | 公式表达式树编译器 |
| A6 | 生成 `BenchmarkActionDefinition`（behavior/cooldown/priority） | 中 | 2-3 | 行为枚举映射 |
| A7 | 生成 `BenchmarkRules`（scheduler 优先级、联动规则） | 中 | 1-2 | 规则编排 |
| A8 | 前端 TS 类型对齐（`GameDataBundle` 增加 `benchmark?`） | 低 | 0.5 | 纯类型定义 |
| A9 | 集成测试：bundle 端到端跑通 | 中 | 1-2 | |
| **合计** | | | **17-27 人天** | |

#### 路径 B：前端编译层 — 在前端做 Bundle → BenchmarkBundle 转换

> 与路径 A 的区别：编译逻辑放在前端 TypeScript 而非后端 Java。

工作项基本相同，区别在于：
- A3-A7 的实现语言变为 TypeScript
- 不需要后端改动
- 但前端会多一个"编译器"模块（~2000-3000 行 TS）

**总量与路径 A 相当：~17-27 人天。**

#### 路径 C：分阶段混合 — 先静态嵌入，后自动编译

| 阶段 | 做什么 | 预估人天 |
|------|--------|---------|
| C1 | 后端为每个已有场景手工维护 `benchmark` JSON，嵌入 bundle 返回 | 2-3 |
| C2 | 前端类型对齐 + WasmBridge 透传验证 | 1 |
| C3 | 自动编译器逐步替换手工 JSON（按 A3→A5→A4→A6→A7 顺序） | 15-24 |

**推荐路径 C**：最快 **3-4 天**可以让前端直接用 bundle 驱动 Wasm（手工 JSON 阶段），完整自动化需 **~20 人天**。

### 1.4 关键决策点

1. **编译层放前端还是后端？** — 推荐后端：保证 bundle 在 CDN 缓存即可用，前端无需二次计算
2. **Skill 机制如何从松散 `params` JSON 走向结构化？** — 这是最大工作量项，因为当前 `params` 没有正式 schema
3. **公式 AST 如何从 `FormulaProfile.params` 编译？** — 需要在数据管理层引入公式编辑能力（或先用约定格式的 JSON）
