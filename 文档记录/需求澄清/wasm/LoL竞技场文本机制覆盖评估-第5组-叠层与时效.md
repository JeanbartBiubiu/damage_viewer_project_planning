## 样本 1：铸星龙王 `星海焕然`

文本摘要：

- 奥瑞利安·索尔的伤害型技能会将敌人转化为【星尘】，星尘会永久增强他的技能。

抽象机制：

- 技能命中后累积层数
- 层数不是临时 buff，而是长期成长资源
- 后续技能强度由累计层数决定

映射到 V2：

- 命中触发：`on_damage_skill_hit`
- 叠层写入：`add_stack("stardust", +1)`
- 层数驱动效果：`modify_attribute` 或公式读取 `stack_count`

结论：

- **叠层本体：已覆盖**
- **永久成长：已覆盖**
- **主要缺口：需要稳定的“技能命中 -> 增层”通用挂载点**

说明：

- 这个样本说明 V2 不缺“按层数改公式”的能力，缺的是把层数增长统一挂到正确事件上的约定。

## 样本 2：荣耀行刑官 `德莱文联盟`

文本摘要：

- 接住旋转飞斧，或击杀小兵、野怪、防御塔后，会获得崇拜层数。
- 击杀敌方英雄时，会按崇拜层数获得额外赏金。

抽象机制：

- 多来源叠层
- 层数影响后续经济收益
- 部分来源来自 1v1 以外的局内对象

映射到 V2：

- 叠层：`add_stack("adulation", +1)`
- 结算奖励：`grant_currency` 或 `modify_attribute("gold", +x)`
- 触发源：`on_catch_proc / on_last_hit / on_takedown`

结论：

- **层数与层数驱动奖励：已覆盖**
- **经济型回报：已覆盖**
- **主要缺口：触发源需要过滤或转换，不能把小兵/野怪/防御塔语义原样塞进 1v1 核心链路**

说明：

- 这个样本本身不逼着新增公式节点。
- 真正需要提前收口的是“叠层来源集合”，尤其是带经济回报的局内 meta 机制。

## 样本 3：海洋之灾 `烈火审讯`

文本摘要：

- 普朗克每过几秒，近战攻击就会让目标着火。

抽象机制：

- 固定间隔刷新
- 条件触发型普攻附加效果
- 着火属于持续状态，而不是一次性瞬发结果

映射到 V2：

- 时间驱动：`schedule_timer` 或周期检查
- 命中附加：`on_melee_attack`
- 持续效果：`apply_status("burn")` 或周期 `deal_damage`

结论：

- **周期触发：已覆盖**
- **持续状态：已覆盖**
- **主要缺口：需要统一的 timer/proc 模板，避免每个被动各自手写“每 N 秒判定一次”**

说明：

- 这个样本说明“时效”不是新公式问题，而是标准化的时间驱动效果模板问题。

## 样本 4：深渊巨口 `来自艾卡西亚的惊喜`

文本摘要：

- 克格莫死亡后 4 秒会爆炸，对周围敌人造成真实伤害。

抽象机制：

- 死亡后仍保留一个延迟结算
- 结算对象来自自身尸体状态
- 结果是延迟的伤害事件，不是立刻清算

映射到 V2：

- 死亡事件：`on_death`
- 延迟执行：`schedule_timer(delay=4s)`
- 结算输出：`deal_damage`

结论：

- **当前阶段：不纳入实现收口**
- **死亡/复活相关钩子：先不处理，默认过滤出当前主路径**
- **这类样本可保留为后续扩范围时再讨论的生命周期条目**

说明：

- 这个样本的难点不是真实伤害本身，而是“主体已经死亡，效果仍然要延后触发”。
- 但按当前范围约束，这类死亡后语义先不进入当前实现收口，避免把注意力从计数器/叠层主线拉偏。

## 样本 5：黑暗之女 `嗜火`

文本摘要：

- 施放 4 个技能后，下一个伤害类技能会晕眩目标。
- 游戏开始和重生时，安妮会带着满层【嗜火】。

抽象机制：

- 计数型叠层
- 达到阈值后消费层数并触发控制效果
- 需要 spawn / respawn 初始化状态

映射到 V2：

- 叠层：`stack_count`
- 阈值触发：`threshold_crossed` 或 `on_stack_full`
- 消耗：`consume_stack`
- 初始化：`counter_seed`

结论：

- **计数叠层与阈值消费：已覆盖**
- **出生/重生满层：通过 `counter_seed` 即可表达，不需要单独生命周期钩子**

说明：

- 这个样本说明“层数”本身没问题，问题在于层数什么时候初始化、什么时候消费。
- 当前更直接的做法是允许配置层给计数器一个初始值或种子，而不是先扩复杂的 `spawn / respawn` 生命周期钩子。

## 本组汇总结论

### 已确认可支撑的能力

1. `stack`、`duration`、`timer` 和 `counter_seed` 这些基础运行时能力，已经足以覆盖本组当前主样本的机制形态。
2. 计数叠层、永久成长、周期触发、延迟爆发、阈值消费，都可以继续走 V2 现有公式与事件组合，不需要新增 AST 节点。
3. 本组真正展示的是生命周期编排问题，而不是数值表达能力不够。

### 本组暴露出的真实重点

1. **需要标准化触发契约，而不是继续堆局部 if。**
2. 后续最常见的触发源会是：
   - `on_damage_skill_hit`
   - `on_last_hit`
   - `on_melee_attack`
   - `on_takedown`
3. 后续最常见的结果载荷会是：
   - `stack_count`
   - `duration_remaining`
   - `stack_consumed`
4. `德莱文` 这类条目说明：只要触发源依赖局外或非 1v1 语义，就要先做转换/过滤，不要直接塞进核心链路。
5. `克格莫` 这类条目说明：死亡后语义会迅速把讨论带出当前实现范围，因此这一轮应先过滤，而不是提前扩生命周期系统。

### 本组建议收口的通用模板

1. `stack_accumulate_proc`
   - 输入：命中/击杀/接住/其他可配置来源
   - 输出：层数累积与层数驱动效果
2. `periodic_proc`
   - 输入：固定间隔或条件轮询
   - 输出：持续伤害、持续增益、持续减益
3. `counter_seed`
   - 输入：计数器初始值或预置层数
   - 输出：角色开场即带有正确层数、属性或待消费效果
4. `stack_threshold_proc`
   - 输入：当前层数、阈值、消费规则
   - 输出：额外属性、控制或其他阈值效果

### 本组稳定结论

1. `叠层与时效` 本体不会逼着 V2 推翻重来。
2. 当前阶段优先收口的是 **触发绑定、计数器、周期模板和计数器初始值**，不是再扩公式节点。
3. 复活、死亡后延迟结算这类生命周期语义，当前阶段先过滤，不进入这一轮实现讨论。
4. 含 `ally_partner`、`economy_round_meta`、`death_delay` 这类语义的条目，应该优先进入转换/过滤层，而不是直接当作 1v1 核心样本。

## 本组已确认的实现导向

1. 层数型效果统一按“可持久化 stack state + 阈值消费”建模。
2. 周期型效果统一按“timer 模板 + 持续状态”建模。
3. 计数器应支持显式 `seed / initial_value`，让角色开场就能带着正确层数、额外属性或待消费效果。
4. 死亡/复活相关条目当前阶段先过滤，不为了它们先引入 `post-death scheduler` 或复杂生命周期钩子。
5. 如果条目依赖 1v1 之外的单位或 round meta，先标记为 `needs_conversion` 或 `out_of_scope`，不要硬塞进 V2 核心路径。

## 当前判断

本组结论是：**可行，而且不会逼着 V2 改写核心数值层。**

真正要提前收口的不是“层数怎么加、时效怎么减”这些公式问题，而是：

- 触发从哪里来
- 计数器初始值怎么给
- 阈值效果怎么稳定消费

这几件事如果先标准化，后面的叠层、持续、开场满层、阈值触发都还是同一套抽象里追加，不需要为每个英雄单点补洞。
