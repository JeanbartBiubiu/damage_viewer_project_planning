# LoL竞技场文本机制覆盖评估-第2组-护盾治疗吸血

日期：2026-04-08
状态：已确认
数据快照：`文档记录/详细设计/最小验证/数据/lol_竞技场静态文本快照`
Data Dragon 版本：`16.7.1`
范围约束：

- 只讨论 `1v1` 数值计算
- 跳过召唤物
- 地形、位移、范围、多目标只在必要时标记为“需转换”，不作为本组主结论
- 本组目标是验证“护盾、治疗、吸血”类机制是否会卡住 V2 架构

## 本组 5 个样本

1. 英雄被动：阿克尚 `无所不用`
2. 英雄技能：卡西奥佩娅 `双生毒牙`
3. 物品：`饮血剑`
4. 符文：`护盾猛击`
5. 海克斯强化：`溢流`

## 术语约定

为避免后续讨论时对英文语义理解不一致，本组开始对关键运行时载荷采用“中文主名 + 英文别名”的写法。

1. `actual_damage_dealt`：**实际生效伤害**
   - 默认指一个伤害包在减伤、护盾结算完成后，最终真正生效的伤害量。
   - 如果后续发现“打到护盾也算造成伤害”的机制需要单独区分，再继续拆更细字段。
2. `heal_attempted`：**尝试治疗量**
   - 指按公式算出来、准备施加的治疗量。
3. `heal_applied`：**实际生效治疗量**
   - 指真正加到生命值上的治疗量，不含超过生命上限的部分。
4. `overheal_amount`：**过量治疗量**
   - 指 `尝试治疗量 - 实际生效治疗量`。
5. `new_shield_amount`：**新生成护盾量**
   - 指这次护盾施加动作新产生的护盾量，不含已有旧护盾存量。

后续文档讨论默认优先使用中文名，括号保留英文别名。

## 样本 1：阿克尚 `无所不用`

文本摘要：

- “来自阿克尚攻击或技能的每第三次命中会造成额外伤害，并且如果目标是英雄还会为他提供一层护盾。”

抽象机制：

- 统一命中计数
- 到达阈值后同时触发额外伤害与自护盾
- 条件分支里包含“目标是英雄”

映射到 V2：

- 额外伤害：`deal_damage`
- 护盾：`apply_shield`
- 计数触发：需要命中计数器或“每 N 次命中”触发模板

结论：

- **护盾数值本身：已覆盖**
- **第 N 次命中触发：部分覆盖**
- **在 `1v1` 对英雄前提下，“目标是英雄”不是阻塞点**

说明：

- 这个样本暴露的重点不是护盾公式，而是“计数类触发”如何挂到被动。
- V2 目前已有 `deterministic_counter` 的思路，但它被写在暴击判定语境里，还没有明确提升为通用触发能力。

## 样本 2：卡西奥佩娅 `双生毒牙`

文本摘要：

- “可对中毒的目标造成额外伤害并且基于实际伤害值为她提供治疗效果。”
- “如果目标死于这次攻击，卡西奥佩娅会回复法力值。”

抽象机制：

- 条件额外伤害
- 治疗量基于实际伤害值，而不是原始面板伤害
- 击杀后资源返还

映射到 V2：

- 额外伤害：`deal_damage`
- 资源返还：`modify_attribute("mana", +x)`
- 治疗：可复用 `modify_attribute("hp", heal)`，但其输入应来自 **伤害结算后的实际结果**

结论：

- **治疗效果本身：已覆盖**
- **“基于实际伤害值治疗”语义：部分覆盖**
- **主要缺口：伤害流水线需要向后续效果暴露标准结果值**

说明：

- 如果这里只能拿到 raw damage 或 pre-mitigation damage，语义就会偏掉。
- 本组建议把 `实际生效伤害（actual_damage_dealt）` 视为后续治疗、返还、吸血等效果的标准输入之一。

## 样本 3：物品 `饮血剑`

文本摘要：

- “将来自你的生命偷取的溢出治疗效果转化为护盾值。”

抽象机制：

- 吸血先尝试治疗
- 超过当前可回复生命值上限的部分，不丢弃，改填充到“饮血剑护盾”这一具名被动护盾
- 这是“治疗结算结果”驱动“具名护盾被动状态”的二段串联

映射到 V2：

- 吸血：`life_steal` 子系统
- 护盾：`shield` 子系统中的具名护盾实例或具名护盾槽位
- 关键中间量：
  - `尝试治疗量（heal_attempted）`
  - `实际生效治疗量（heal_applied）`
  - `过量治疗量（overheal_amount）`

结论：

- **吸血与护盾分别存在：已覆盖**
- **“溢出治疗转护盾”串联：未明确覆盖**
- **这是本组最需要提前收口的能力之一**

说明：

- 仅有 `life_steal.healFormula` 还不够，因为它只定义“应治疗多少”，没有定义“实际生效多少”和“溢出了多少”。
- 从你的视角看，`饮血剑` 更像“装备自己携带一个护盾被动状态”，过量治疗不是直接临时生成匿名护盾，而是去填充这个被动状态。
- 这个理解更精确，也更适合引擎实现：治疗结算层产出 `过量治疗量（overheal_amount）`，而 `饮血剑` 被动自己决定如何把它写入对应的护盾实例。
- 如果没有统一的溢出结果载荷，后面凡是“过量治疗转 X”或“过量治疗填充某个被动槽位”的机制都只能走特判。

## 样本 4：符文 `护盾猛击`

文本摘要：

- “在你获得一个新的护盾时，你的下一次对英雄发起的普攻造成额外自适应伤害。”
- “额外伤害的一部分基于新护盾值。”
- “在护盾消散后，你最多有2秒的时间来使用这个效果。”

抽象机制：

- `on_new_shield` 触发
- `护盾猛击` 主动订阅护盾生成事件
- 触发时由 `护盾猛击` 自己读取并捕获 `新生成护盾量（new_shield_amount）`
- 生成一个可消耗的短时攻击增益
- 增益在护盾结束后还可短暂残留

映射到 V2：

- 额外伤害：命中时派生 `deal_damage`
- 临时状态：`modify_attribute` + `schedule_timer` 或统一 proc 模板
- 事件源：护盾子系统发出的“新增护盾”事件
- 关键输入：`护盾猛击` 从事件载荷里提取 `新生成护盾量（new_shield_amount）`

结论：

- **伤害表达：已覆盖**
- **短时窗口状态：部分覆盖**
- **主要缺口：shield 子系统需要显式产出 “新护盾生成” 事件和事件载荷**

说明：

- 这个样本不是在要求新护盾公式，而是在要求“护盾结果也能反过来驱动下一个命中效果”。
- 从配置视角看，更准确的说法不是“护盾把变量传给护盾猛击”，而是“护盾猛击关联护盾类事件，并从事件载荷中取值”。
- 它和饮血剑一起说明：本组的核心不是 heal/shield 子系统本身，而是 **结果值能否继续被后续效果消费**。

## 样本 5：海克斯强化 `溢流`

文本摘要：

- “你的法力值消耗翻倍。”
- “你的技能的治疗效果、护盾效果和伤害获得提升，提升幅度基于你的最大法力值。”

抽象机制：

- 资源消耗倍率修正
- 基于最大法力值的统一增幅
- 同一增幅同时作用于：
  - 技能伤害
  - 技能治疗
  - 技能护盾

映射到 V2：

- 资源消耗：`check_resource.params.costFormula`
- 伤害：`deal_damage` 公式外包一层倍率
- 治疗：`modify_attribute` 公式外包一层倍率
- 护盾：`apply_shield` 公式外包一层倍率

结论：

- **能力上可覆盖**
- **不需要为它单独新增子系统**
- **但应定义统一的“技能输出增幅”实现套路，避免伤害/治疗/护盾各写一套**

说明：

- 这个样本说明 V2 现有“公式外置”的方向是对的。
- 真正要补的不是新节点，而是一个稳定约定：
  - 同一来源的增幅，如何一致地包到多个 effect 上
  - 不让 bundle 编译层把同一种语义重复散落到多处

## 本组汇总结论

### 已确认可支撑的能力

1. `apply_shield`、`modify_attribute`、`life_steal`、`check_resource.costFormula` 这些基础能力，足以覆盖本组里的护盾、治疗、吸血、资源倍率本体。
2. 本组没有暴露出必须新增 AST 节点的新公式需求。
3. `技能伤害 / 技能治疗 / 技能护盾` 这三类数值都可以继续走“公式外置”的 V2 主路线。

### 本组暴露出的真实重点

1. **需要标准化“结果值载荷”，而不只是输入公式。**
2. 后续效果至少会依赖这些结果值：
   - `实际生效伤害（actual_damage_dealt）`
   - `尝试治疗量（heal_attempted）`
   - `实际生效治疗量（heal_applied）`
   - `过量治疗量（overheal_amount）`
   - `新生成护盾量（new_shield_amount）`
3. 如果这些结果值不在运行时被显式建模，`饮血剑`、`护盾猛击`、`双生毒牙` 这类机制会迫使实现层回退到大量特判。

### 本组建议收口的通用模板

1. `damage_based_heal`
   - 输入：`实际生效伤害（actual_damage_dealt）`
   - 输出：治疗量
2. `overheal_to_shield`
   - 输入：`过量治疗量（overheal_amount）`
   - 输出：填充某个具名护盾实例或具名护盾槽位
3. `shield_granted_proc`
   - 输入：`新生成护盾量（new_shield_amount）`
   - 触发方式：由消费方订阅“新增护盾”事件并自行取值
   - 输出：短时可消耗增益
4. `skill_output_amp`
   - 对 `deal_damage / modify_attribute(heal) / apply_shield` 统一包倍率

### 本组稳定结论

1. `护盾 / 治疗 / 吸血` 本体不会逼着 V2 推翻重来。
2. V2 下一步要补强的是 **结果值建模与跨效果串联模板**，不是再扩公式节点。
3. `溢出治疗转护盾` 更适合抽象成“结果值驱动具名被动状态”的通用模式，不应只为 `饮血剑` 单点特判。
4. `新护盾生成` 应被视为正式触发源，而消费方应自己订阅并读取载荷，而不是让 shield 子系统替消费方持有语义。

## 本组已确认的收口方向

1. `饮血剑` 这类机制，不按“临时匿名护盾”理解，而按“装备自己持有一个具名护盾被动状态”理解。
   - 过量治疗量（`overheal_amount`）是这个具名被动状态的填充值。
   - 更通用的抽象不是“直接转护盾”，而是“治疗结算结果可被具名被动状态消费”。
2. `护盾猛击` 这类机制，不让 shield 子系统替消费方持有业务语义。
   - shield 子系统负责发出“新增护盾”事件及事件载荷。
   - 消费方主动关联该事件，并自行读取 `新生成护盾量（new_shield_amount）` 后保存为后续效果输入。
3. `双生毒牙` 这类机制继续沿用同一原则。
   - 伤害流水线负责产出 `实际生效伤害（actual_damage_dealt）`。
   - 消费方自己决定如何使用这个结果值做治疗、返还或其他派生效果。

## 当前判断

本组结论是：**可行，而且结论与第 1 组一致，不会推翻前面的方向。**

第 1 组说“真正的风险在触发绑定层”；第 2 组进一步把这个判断收紧成：

- 不只要有触发源
- 还要有 **可复用的结果值载荷**
- 以及 **跨效果串联模板**

这样后面的装备、符文、海克斯、英雄技能即使继续变复杂，也还是在同一套抽象里追加，而不是重写语义。
