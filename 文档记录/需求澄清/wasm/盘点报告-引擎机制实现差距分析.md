## C. 用户指定机制的专项分析

### C1. 乘区机制（Multiplicative Damage Zones）

**设计范围**：
- 概要设计-护盾 §3.7/3.10：定义 `coefficient_buckets` 注册表，`combineGroup` 内加法、组间乘法
- 运行时数据流 §5.6：属性域（base → final）和 HP 变更域（formula_base → hp_apply）双域乘区
- 示例公式：`(1 + source_outgoing) × (1 + target_vulnerability) × (1 - target_reduction)`

**实现状态**：
- **完全未实现**
- 当前计算路径：`raw_damage × mitigation_multiplier(resistance - flat_pen)` → 无任何增减伤叠加层
- `coefficient_buckets` 概念在 DB schema `coefficient_bucket_schema.sql` 有设计但未接入引擎
- 公式系统无 `source_outgoing` / `target_incoming` 阶段

**差距**：
1. 缺 `CoefficientBucket` 数据结构
2. 缺聚合引擎（组内求和 → 组间求积）
3. 缺 `DamagePacket` 上的 bucket 引用
4. 缺属性域乘区（当前属性直接从 HashMap 读取，无 base/bonus/final 管线）

---

### C2. 控制状态定义（Crowd Control States）

**设计范围**：
- 概要设计-控制 §3–5：22 种 LoL 控制状态完整分类
- DB Seed：`lol_status_types_seed.sql`（22 种）+ `lol_status_action_control_rules_seed.sql`（32 条 forbid/interrupt 规则）
- `status_control_schema.sql`：`status_action_control_rules` 表已建
- 运行时模型：`StatusInstance` / `ControlDirectiveInstance` / `ExecutionInstance`

**实现状态**：
- **仅 Stun 基础版**
- 实现内容：`StunState { until_ms }` + `apply_stun()` + `expire_stun()` + 决策时检查 `is_stunned_at()`
- `TestProfile::NoControl` 可跳过控制检查

**差距**：
1. 缺 21/22 控制类型（除 stun）
2. 缺 `StatusInstance` 通用容器（tags、duration、stacking、cleanse mode）
3. 缺 `ActionBlockRule` 矩阵——当前 stun 直接 hardcode "阻止一切"
4. 缺强制行为（fear/taunt/charm/berserk）
5. 缺技能执行阶段追踪（`ExecutionInstance`），因此无法实现打断
6. 缺免控、净化、韧性
7. 缺 `PendingIntent`（控制结束后自动重试动作）
8. 缺金身（invulnerable + untargetable）
9. 缺睡眠特殊机制（受伤即醒）
10. 缺致盲（攻击 miss 而非禁止攻击）

---

### C3. 派生属性强化（Derived Attribute Enhancement）

**设计范围**：
- 概要设计-模式强化 §7-8：七阶段派生属性流水线（base → raw → pre_cap → cap → overflow → final → formula_read → packet）
- 五种派生原语：`derived_stat` / `full_convert` / `overflow_convert` / `set_final` / `clamp_final`
- 概要设计-移动速度 §5：移速分桶 + 软上限 + 最高减速选取
- 示例：固定攻速 + 溢出转 AD、法强 ↔ 攻击力互转、暴击率溢出转属性

**实现状态**：
- **完全未实现**
- 当前属性：`HashMap<String, f64>` 单层读写
- `base_attrs` 和 `attrs` 仅在 `ActorRuntime` 中分开存储（用于黑切护甲恢复）
- 无 raw/bonus/final 分层、无 overflow 计算、无派生规则执行器
- 无 `DerivedRuleSpec` 数据结构

**差距**：
1. 缺属性四口径（base/bonusFlat/bonusRatio/finalValue）
2. 缺七阶段流水线
3. 缺五种派生原语引擎
4. 缺循环依赖检测
5. 缺属性刷新时机管理
6. 移动速度派生完全缺失

---

### C4. 暴击机制（Critical Strike）

**设计范围**：
- 需要可以完成的挑战 P0-10：至少支持期望暴击模型
- 概要设计-模式强化 §9：三层暴击模型（packet tags → critPolicy → activeDamagePolicies）
- 测试基准.md：我方 `暴击率 = 0`、`暴击倍率 = 1.75`（虽然当前测试基准不触发暴击，但属性已声明）
- 技能配置说明：普攻 `是否可进行暴击判定: 可以`

**实现状态**：
- **完全未实现**
- `ATTR_CRIT_CHANCE` / `ATTR_CRIT_MULTIPLIER` 在 `benchmark_fixture.rs` 中定义为常量
- 伤害计算（`resolve_component`）中无暴击判定逻辑
- 无 `CritPolicy` 数据结构
- 无 `DamagePolicySpec`
- 无期望模式（`raw × (1 + crit_chance × (crit_multiplier - 1))`）
- 无随机模式

**差距**：
1. 缺基础暴击判定（至少需期望模式）
2. 缺暴击倍率计算
3. 缺 `DamagePacket.critPolicy` 标记
4. 缺可配置暴击资格（普攻/技能/DoT 分别控制）
5. 缺随机 + 期望双轨模式
