## 样本 1：亚托克斯 `暗裔利刃`

文本摘要：

- “亚托克斯可以挥击三次，每次都有一个不同的范围效果。”
- “这个技能可以再次施放两段，每段都会改变形状并比上一段多造成 25% 伤害。”

抽象机制：

- 多段施法窗口
- 每段施放都有独立形状和伤害系数
- 节奏上不是单次瞬发，而是一个可继续接续的阶段序列

映射到 V2：

- 阶段索引：`cast_stage`
- 阶段窗口：`next_cast_window`
- 分段伤害：`deal_damage(stage_damage)`
- 形状变化：必要时标记为 `需转换`

结论：

- **多段节奏：已覆盖**
- **分段倍率：已覆盖**
- **边缘命中 / 形状变化：需转换，不是本组阻塞点**

说明：

- 这个样本暴露的是“技能不是一个点，而是一条阶段链”。
- 只要 V2 能把阶段索引和下一段窗口显式化，就不需要为这类技能单独补硬编码分支。

## 样本 2：安妮 `碎裂之火`

文本摘要：

- “对目标造成伤害。”
- “如果目标死于碎裂之火，则返还法力值，且冷却时间减半。”

抽象机制：

- 基础施放消耗资源
- 击杀后返还资源
- 击杀后缩短冷却
- 同一技能同时含有命中结果和资源回收

映射到 V2：

- 资源检查：`check_resource.costFormula`
- 法力返还：`modify_attribute("mana", +x)`
- 冷却缩短：`reduce_cooldowns`
- 触发源：`on_kill` / `on_takedown`

结论：

- **基础资源消耗：已覆盖**
- **击杀后返还：已覆盖**
- **击杀后冷却减半：已覆盖**
- **主要缺口：触发源必须统一建模，不能散写成局部特判**

说明：

- 这类效果最容易把“资源消耗”和“结果回收”混成一个特判分支。
- 更稳妥的做法是把施放消耗、击杀返还、冷却回收拆成独立运行时结果，再由效果层消费。

## 样本 3：阿木木 `绷带牵引`

文本摘要：

- “这个技能拥有 2 层充能。”
- “命中的第一个敌人会被拉向目标，并造成眩晕和伤害。”

抽象机制：

- 充能次数是显式资源
- 每次施放会消耗一层充能
- 充能按时间回补
- 节奏控制来自“剩余充能”而不是单一冷却

映射到 V2：

- 充能状态：`remaining_charges`
- 回补时钟：`recharge_timer`
- 充能消耗：`consume_charge`
- 冷却表达：由充能状态派生，而不是只看一个静态冷却值

结论：

- **多充能资源：已覆盖**
- **回补节奏：已覆盖**
- **主要缺口：V2 需要把 charge/recharge 作为标准状态，而不是只当作冷却的别名**

说明：

- 这个样本不是在挑战伤害或控制，而是在确认“资源也可以是次数型资源”。
- 只要充能状态能被统一表达，后续同类技能就能复用同一套模板。

## 样本 4：伊泽瑞尔 `秘术射击`

文本摘要：

- “命中敌方单位后，会略微减少所有技能的冷却时间。”

抽象机制：

- 命中驱动的冷却返还
- 返还对象不是自己这一招，而是整组技能冷却池
- 体现的是节奏加速，而不是直接伤害数值变化

映射到 V2：

- 命中结果：`actual_hit`
- 冷却返还：`reduce_cooldowns(all_skills, cdrefund)`
- 触发源：`on_damage_dealt` / `on_hit`

结论：

- **命中后冷却返还：已覆盖**
- **全技能池联动：已覆盖**
- **主要缺口：需要统一“命中结果 -> 冷却返还”的标准链路**

说明：

- 这类机制说明节奏加速可以挂在命中结果上，而不是只挂在击杀结果上。
- 如果运行时没有统一的命中结果载荷，后续会被迫在很多技能里重复写冷却回收逻辑。

## 样本 5：金克丝 `罪恶快感`

文本摘要：

- “参与击杀或摧毁一名英雄、史诗级野怪或建筑物后，移动速度和攻击速度都会显著提升。”

抽象机制：

- takedown 触发节奏爆发
- 同时提升位移节奏和输出节奏
- 属于典型的“击杀后推进窗口”

映射到 V2：

- 触发源：`on_takedown`
- 移速增益：`modify_attribute("move_speed", +x)`
- 攻速增益：`modify_attribute("attack_speed", +x)`
- 持续时间：`schedule_timer`

结论：

- **击杀后节奏爆发：已覆盖**
- **移动速度 / 攻击速度增益：已覆盖**
- **主要缺口：需要把 takedown 后的短时加速模板标准化**

说明：

- 这个样本说明“节奏”不只是冷却，也包括战斗结束后的推进窗口。
- 只要加速效果能复用统一的短时 buff 模板，后续同类被动不需要各自重写。

## 本组汇总结论

### 已确认可支撑的能力

1. 基础资源消耗通过 `check_resource` 和成本公式即可表达。
2. `mana refund`、`cooldown refund`、`cooldown reduction` 这类回收语义，V2 现有方向可以覆盖。
3. `attack speed`、`move speed` 这类节奏型属性加成，属于标准属性修改，不构成公式层阻塞。
4. 多段施法、充能回补、命中返还、击杀爆发这些语义本身都不是新 AST 节点需求。

### 本组暴露出的真实重点

1. **阻塞点不在数值表达，而在节奏状态的标准化。**
2. 需要统一显式建模的状态主要有：
   - `cast_stage`
   - `remaining_charges`
   - `recharge_timer`
   - `cooldown_refund`
   - `takedown_refresh`
3. 如果这些状态不标准化，后续就会把“资源与节奏”拆成一堆独立特判。

### 本组建议收口的通用模板

1. `stage_cast`
   - 输入：当前阶段、下一阶段窗口
   - 输出：下一段伤害或形态变化
2. `consume_charge`
   - 输入：剩余充能
   - 输出：充能消耗和回补排队
3. `refund_cooldown`
   - 输入：命中或击杀结果
   - 输出：对一个或多个技能池的冷却返还
4. `grant_temporary_haste`
   - 输入：takedown 或其他节奏触发源
   - 输出：短时移动速度 / 攻击速度增益

### 本组稳定结论

1. `资源与节奏` 本体不会逼着 V2 推翻重来。
2. V2 下一步要补的不是新的数值节点，而是 **充能、阶段、返还、节奏爆发** 的统一状态模型。
3. `技能节奏` 应该被视为可组合的运行时状态，而不是零散地写进每个 champion 技能里。

## 本组已确认的实现导向

1. 基础资源消耗继续统一走 `check_resource`。
2. 多充能技能统一显式暴露 `remaining_charges` 和 `recharge_timer`。
3. 命中或击杀后的冷却回收统一走 `refund_cooldown` / `reduce_cooldowns`。
4. 击杀后的移动速度和攻击速度爆发统一走短时 `haste` 模板。
5. 多段施法统一用 `cast_stage` 和下一段窗口表达，不再散写成特判。

## 当前判断

本组结论是：**可行，而且不会卡死 V2。**

真正需要提前收口的是“资源与节奏状态”的统一表达，而不是再补新的公式节点。  
如果后续要继续扩展到更复杂的武器队列、弹药序列或更长的阶段链，最好在这一组的基础上继续往前收敛，而不是重新发明一套新的节奏语义。
