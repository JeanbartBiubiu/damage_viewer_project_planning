## 1. 记录范围

本记录补录 M1 / M2 开发完成后的验收结论，验收口径按 `集成测试报告与OCR基线方案.md` 对齐。

本次只判断当前 Web -> Wasm 开发侧能力是否已经具备，不把尚未落地的自动化集成测试 runner、golden fixture 或 OCR 基线误记为已完成。

结论分两层：

1. 开发侧闭环：页面、发布 bundle 读取、bundle adapter、TinyGo V2 bridge 和字段级人工基线对照是否可用。
2. 正式集成测试 gate：是否已经有可复跑 runner、固化 golden case、Markdown/JSON 报告和 OCR/人工 expected baseline 归档。

## 3. M1 验收结果

| 验收项 | 方案要求 | 当前证据 | 结论 |
| --- | --- | --- | --- |
| 发布 bundle 输入 | 使用同一份发布 bundle 或 fixture 构造 Wasm 输入 | 页面通过 `loadPublishedBundleSnapshot(...)` 读取发布 bundle，并通过 `compileTinyGoV2ValidationInput(...)` 生成输入 | 通过 |
| M1 专用 ABI | 使用 `engine_snapshot_initial(ptr, size)` 输出初始化后快照 | bridge 暴露 `snapshotInitial(...)`，M1 页面运行 `bridge.snapshotInitial(inputPreview.value.runInput)` | 通过 |
| HUD actor 字段展示 | 展示 actor 初始属性快照，可逐字段核对 | M1 页面展示 actor / attribute 行，并支持复制 snapshot | 通过 |
| expected baseline 对照 | 比较 expected baseline 和 Wasm 实际输出 | 当前通过人工粘贴 baseline JSON 计算 `diffRows` | 开发侧通过 |
| 自动化报告 | runner 输出 Markdown/JSON 报告 | 当前没有 `test:validation`、`web/scripts/` 或 `web/tests/` runner | 阻塞 |
| OCR 基线 | OCR 只作为离线 expected baseline 来源，人工确认后进入 fixture | 当前未发现 M1 golden fixture 或 OCR JSON 归档 | 阻塞 |

M1 结论：M1 开发侧 actor 初始化快照闭环可验收；但按新方案定义的正式集成测试 gate 尚未完成，不能标记为“自动化集成测试通过”。

## 4. M2 验收结果

| 验收项 | 方案要求 | 当前证据 | 结论 |
| --- | --- | --- | --- |
| Action 输入来源 | 使用发布 bundle 中的技能、等级、资源和冷却配置 | M2 页面复用 bundle adapter，并通过 `listWasmValidationSkills(...)` 构造可选 action | 通过 |
| M2 专用 ABI | 输出 action 初始状态快照，不跑完整战斗 | bridge 暴露 `snapshotActionsInitial(...)`，M2 页面运行 `bridge.snapshotActionsInitial(inputPreview.value.runInput)` | 通过 |
| 面板字段展示 | 对齐技能等级、消耗、冷却、面板输入和效果行 | M2 页面展示 `skillLevel`、`cooldownMs`、`readyAtMs`、`resourceCosts`、`effectRows`、`panelInputs` | 开发侧通过 |
| 字段级 diff | M2 diff 按 action 字段展开，而不是只给总状态 | M2 页面维护 `actionBaselineText`、`matchedActionRows` 和 `diffActionRows` | 开发侧通过 |
| 自动化报告 | runner 输出 M2 case 的 Markdown/JSON 报告 | 当前没有 `test:validation`、固化 M2 golden case 或报告输出目录 | 阻塞 |
| 游戏侧 baseline | 每个 case 最多验证 1 个技能，expected baseline 来自人工或 OCR 确认 | 当前页面支持人工 action baseline，但未发现已归档的游戏侧 golden baseline | 阻塞 |

M2 结论：M2 开发侧 action 初始状态快照和字段级人工对照能力可验收；但正式 gate 仍缺 runner、golden case 和游戏侧 expected baseline。

## 5. OCR 与 baseline 状态

当前 OCR 只停留在方案约束和 M1 HUD ROI 映射层，没有进入 Web 运行时代码，也没有作为 `test:validation` 的依赖。这符合“离线 OCR 证据接入”的边界。

本次补录不把 OCR 结果作为通过证据，原因：

1. 未发现已归档的 `golden` case fixture。
2. 未发现人工确认后的 `ocr_confirmed` baseline 文件。
3. 当前页面验收依赖人工粘贴 baseline JSON，不生成方案要求的 Markdown/JSON 报告。

## 8. 后续最小补齐项

1. 新增 `web/src/validation-report/` 或等价目录，落地报告类型、fixture 读取、diff 和 Markdown/JSON 输出。
2. 新增 `web/scripts/` 或测试目录中的最小 runner，并在 `web/package.json` 增加 `test:validation`。
3. 固化首批 `golden` case：M1 至少 3 个 HUD actor case，M2 至少 2 个 action case，M2 每个 case 最多验证 1 个技能。
4. 将 OCR 输出只作为候选 baseline 来源，人工确认后再写入 fixture，并标记来源为 `ocr_confirmed`。
5. runner 输出目录优先使用 `web/test-results/validation/` 或其他 ignored 目录，避免把临时测试产物提交为源码。
