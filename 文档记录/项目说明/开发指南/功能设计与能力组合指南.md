# 功能设计与能力组合指南

新增功能、增加变体或发现现有接口无法表达需求时，先用本页确定行为、契约、对象和组合方式，再进入三端编码指南。现有目录、类型和调用链提供调查依据；合适的边界可以复用，不合适的契约可以在授权范围内修改，缺少的能力可以新建。设计不要求把新功能塞进某个相似旧文件。

对象封装需要共同维护的状态与行为，组合能力通过明确契约连接这些行为。接口表示调用双方的行为约定，可以用函数、类型和说明表达；是否使用抽象类或运行时接口另行决定。

下文的条件编辑、批量校验和数值修正均为设计方法示例，不声明已有对应功能，也不冻结新的生产协议。实际产品语义仍需从当前任务确认。

## 从用户行为推导最小能力

先给出本次要发生的行为，包括一个正常例子、一个拒绝或失败例子，以及会改变结果的边界。将用户输入、读取的事实、计算或判断、状态变化和展示结果区分清楚，再寻找能承担这些行为的能力。

对每个缺口按下表选择，不把“当前没有相同类名”直接等同于“需要新子系统”。

| 当前证据 | 应选择的改法 | 实施前应能说明 |
| --- | --- | --- |
| 现有能力的完整契约已覆盖需求 | 直接复用，补本次接线和验收 | 输入怎样映射，输出怎样满足用户行为 |
| 多个现有能力已覆盖各部分，缺少连接规则 | 在明确的组合者中定义顺序、选择或聚合 | 组合者独占什么规则，子项仍保持什么契约 |
| 原契约有效，缺少一种相同语义的新实现 | 新增最小叶能力或策略 | 新实现如何在同一调用位置替换现有实现 |
| 原有顺序、失败、上下文或结果形状不能表达需求 | 修改所属契约，或新增语义明确的组合规则 | 为什么只加叶子无效，哪些生产者和消费者需一起调整 |
| 原能力承担了不属于它的责任，持续迫使下游绕行 | 修正职责与接口，在授权范围内迁移调用方 | 哪些事实由谁拥有，哪些产品策略留在调用方 |
| 业务含义或允许的副作用仍不明确 | 先用具体例子收敛关键语义 | 哪项选择会改变用户结果，缺少什么决定 |

例如需求是“收集全部字段问题”，现有入口却在第一个问题抛出异常，不能只把同一入口循环调用。先判断异常是否其实是可累积的业务结果，再决定调整检查契约或新增符合该语义的检查入口；不能用空列表掩盖失败。

## 对象按责任和必须共同成立的条件形成

对象适合封装一组需要一起维护的状态和行为。先写清“哪些变化必须由同一个拥有者保证正确”，再确定类型与方法；不要为每个名词建类，也不要把所有业务行为放进一个只因方便访问数据而膨胀的服务。

| 需要表达的东西 | 起步结构 | 何时需要再拆分 |
| --- | --- | --- |
| 没有独立生命周期的数据 | 明确的数据类型或值 | 字段之间出现需由行为持续维护的约束时 |
| 无状态的转换或计算 | 函数及明确的输入输出 | 存在独立变化的策略或资源边界时 |
| 有状态且需维护不变量的行为 | 由一个具体对象或模块持有状态并提供受控方法 | 另一组状态具有不同生命周期或独立责任时 |
| 稳定算法依赖可变化的行为 | 有限函数参数、小接口或明确策略值 | 当前需求确实要求新的行为变体时 |
| 能由相同契约的子项继续构成的行为 | 叶能力与组合能力 | 子项或组合规则出现新的真实语义时 |

例：一个编辑任务可以拥有服务端基线、草稿和保存状态，纯格式化函数不需要因此变成有生命周期的对象。多个请求或计算实例也不应因为数据类型相同，就共享一份可变任务状态。

## 先定义契约，再选择接口形式

新增公开能力时，至少说明调用方实际依赖的以下内容；只写本次有意义的项目，不要求固定模板或额外长文档。

| 契约方面 | 要回答的问题 |
| --- | --- |
| 输入前提 | 接受哪些值和状态？缺失、空集合、有效0分别怎样处理？ |
| 结果保证 | 返回值、单位、身份、路径、顺序和完整性保证是什么？ |
| 失败 | 哪些属于正常拒绝，哪些属于执行失败？调用方能否继续、重试或合并结果？ |
| 副作用与时间 | 读取的是哪个时点的事实？何时允许发布状态？失败时已提交什么？ |
| 所有权与生命周期 | 谁创建、修改和释放资源？传入内容是借用还是转交，能保留多久？ |
| 组合与成本 | 是否允许嵌套？怎样限制规模、深度或执行次数？哪些次序必须稳定？ |

类型能表达的约束优先由类型表达；涉及借用、提交、错误或时序的约束写在真实声明旁。名称相同、方法签名相同，都不足以说明两个实现能互换。

## 继承、组合与可替换性

继承适合“新类型是一种原能力，原调用方可以直接使用它”。如果只是“对象使用或持有另一个能力”，采用组合并明确委派关系。两者都以当前责任和契约判断，不为复用几段实现强行继承，也不为了形式统一增加转发壳。

可替换性具体要求如下：

- 原契约允许的输入，新实现也必须接受；不得增加调用方原本无需满足的前提。
- 原契约保证的输出、错误、状态、身份与生命周期，新实现不得削弱；可以接受更多合法输入或提供更强保证。
- 调用方不能先检查具体类型，再绕开某个实现的“不支持”或额外初始化步骤，才能使用原本承诺的能力。

例：契约允许非负值，某个实现改为只接受正值，就不能在原位置替换它；“校验更严格”不能成为拒绝有效0的理由。新增实现通过返回默认成功绕过不支持的操作，同样破坏契约。

遇到实现只支持一部分能力时，先检查输入是否应更精确，或原接口是否混合了不同责任。可以拆成实际需要的能力，或者改变共享契约及所有调用方；不要宣称完整实现后在常规路径返回“不支持”。

验证时分别核对输入前提与结果保证，方法见[测试指南](测试编写与运行指南.md)。

## 所有权与整组生命周期

每份可变事实有一个明确拥有者；持有引用不等于拥有。先决定谁负责创建、修改、取消和结束，再选择语言中的实现方式：前端按组件或操作生命周期，Java按业务及框架资源边界，Go按显式状态拥有者和借用期限。

多个协作对象相互引用、却没有自然父对象时，可以由一个装配对象共同持有，使初始化、部分失败及结束都有责任位置。这个对象负责共同生命周期，不因能访问全部对象就接管它们的业务规则。

例：一次对比任务拥有多个独立运行实例。取消任务时由任务释放它创建的实例；某个展示组件只借用结果，不负责关闭其他消费者仍在使用的资源。无独立生命周期的计算结果仍可作为值返回。

释放必须与实际契约对应。失败后进程仍运行、会话还会复用或事务仍待结束时，不能照搬“反正崩溃就不清理”的假设；也不能释放其他任务拥有的资源。状态回滚和资源释放是不同的承诺。

## 让组合结果仍然是一项可使用的能力

可递归组合的关键是：叶子和组合体遵守同一能力契约，组合后的整体还能作为下一层的子项。调用方使用这项能力时，不需要知道内部有一个叶子还是多层组合。

例如一个只读检查能力可以采用以下示意契约：

```text
检查(只读上下文) → 完成(有序问题列表) | 执行失败(明确原因)

全部检查([检查甲, 全部检查([检查乙, 检查丙])])
```

若本次需求选择“收集全部业务问题”，则空问题列表表示通过；普通问题是可合并的结果，不能当成异常提前终止。组合者按声明顺序调用子项，合并其字段路径和问题；遇到不能继续的执行失败则明确失败，不能把已收集前缀报告成完整结果。空组是否允许及其含义也要明确，例如允许时返回完成的空列表。

叶子只负责一项检查，组合者负责遍历与合并。新增叶检查时，消费方仍调用同一契约；新增短路选择、并行聚合等规则时，需要另行定义组合语义，不能悄悄改变“全部检查”的行为。

设计组合能力时逐项确定：

| 组合问题 | 设计决定 |
| --- | --- |
| 同一形状 | 子项和整体怎样被同一调用方使用，是否要求特殊类型判断？ |
| 上下文 | 共享只读事实、传递逐步结果，还是显式建立子作用域？是否保留来源和路径？ |
| 顺序 | 顺序执行、满足条件才执行还是并行？是否短路？结果如何稳定排列？ |
| 失败与状态 | 子项失败后是否继续？谁拥有暂存值，谁发布结果？已经提交的事实怎样处理？ |
| 空与单项 | 空组合是合法单位值还是输入错误？单项包装是否改变观察到的语义？ |
| 边界 | 输入是否有环？深度、节点数、执行次数与取消由谁限制？ |

递归形状不要求运行时使用无限递归调用。可在编译阶段校验并转成有界计划、显式栈或顺序表；已经有公式或过程组合入口时，优先扩展其适用契约，不新造平行解释器。

组合也不自动具有交换、结合或整体回滚性质。例如“先加10再乘2”与“先乘2再加10”不同；只有契约明确等价的变换，才能通过展开或重排优化。

## 把变化交给能力，把稳定流程留给调用方

稳定算法需要根据具体类型到处增加分支时，先找真正变化的行为。将该行为作为函数、策略或小接口传入，在装配处选具体实现，让算法只依赖契约；这就是控制反转（IoC），即算法声明需要什么行为，外层提供该行为。

设计时分别确定三项责任：稳定流程承诺什么顺序与结果，变化的能力承诺什么输入输出，以及谁根据本次场景选择并提供实现。装配可以是现有调用处或构造函数，不要求另建容器、注册中心或工厂层。

例如批量处理器只负责遍历、预算和聚合，具体检查由输入的能力提供。新增一种检查不应要求每个批量消费者知道其类型；共享层接收通用事实，不反向依赖页面、英雄名称或产品专属状态。若算法内部仍按实现类型分支，或者调用方必须给出一组互相牵制的开关才能切换行为，变化还没有被隔离。

再如本次需要对已经得到的计算结果按不同指标排序，排序流程可以接受明确的比较规则，由场景选择规则。若只需要一个固定次序，直接实现即可；只有当前出现了不同规则，才需要分离这一变化。不能因为采用控制反转，就为每种指标创建一整套服务层。

封闭且有限的种类可以用带种类标记的数据结构和集中分支。解析、编译或组件渲染处需要区分形状，本身不是错误；问题是同一种语义分散在许多消费者中，或每增加叶能力就修改不相关算法。不为消除所有分支而建立全局注册、插件或反射框架。

检验依赖方向时，把本次新增实现代入：稳定流程应仍只理解约定的能力，具体选择留在装配处。如果新增一种行为需要改所有消费者，先修正共同契约或职责分工，而不是继续增加类型特判。

## 新抽象层必须承担一项真实责任

抽象的价值在于隐藏调用方无需了解的变化、集中同一规则，或维护一组必须共同成立的条件。新增一层前应能说明这一责任；只是改名转发、搬走代码或包住几个参数，不能自动算作设计改善。

| 判断 | 支持增加抽象的证据 | 应保持直接实现的情况 |
| --- | --- | --- |
| 变化原因 | 当前已有不同实现或独立变化的业务规则 | 只有假设中的后续扩展 |
| 调用方知识 | 调用方可只依赖稳定契约，不再理解内部步骤 | 参数与细节原样穿过每一层 |
| 内聚与依赖 | 同一原因变化的行为聚合，独立变化的行为分离 | 为共享几行代码把无关场景绑在一起 |
| 正确性 | 一处可以维护必要不变量或共享语义 | 新层不增加任何保证，却增加分支和状态 |
| 成本 | 阅读跳转、参数、测试与运行成本有明确收益支撑 | 复杂度由实现转移给每个调用方，甚至还要绕过新层 |

不要按文件长度或重复达到几次机械决定。一个小函数可能隔离重要的业务规则，一大段单次且连贯的流程也可能适合保留在所属模块。只有一个实现也可能有真实依赖边界；多个实现看似相似也未必共享同一语义。

抽象也应允许退出。若不断增加互斥开关、调用方反复绕过公共入口、修改一个场景总影响无关场景，或层间只剩机械转发，应缩小契约、拆开错误聚合，或移除没有责任的层。MVP可以直接调整调用方，不为保留一次失败的抽象再增加兼容适配层。

## 按问题选择设计模式

设计模式提供对重复问题的职责安排，不是新增功能的必选清单。先说明当前变化及期望依赖方向，再选择最小结构；函数、具体类型或已有模块能清楚表达时，不必先创建带模式名称的类。

| 已出现的问题 | 可考虑的职责安排 | 不应据此扩大的范围 |
| --- | --- | --- |
| 同一稳定流程需要不同规则 | 用策略或有限能力隔离规则，由外层装配 | 不把每个参数差异都变成新服务 |
| 两端模型或契约不同，需要明确转换 | 由适配边界拥有转换，领域规则留在原拥有者 | 不复制两套业务判断，或用适配器掩盖错误的共享契约 |
| 多个对象需要协调次序或共同生命周期 | 用明确的协调者组织协作，子对象保持自己的责任 | 不让协调者通过访问全部状态吞并所有业务 |
| 行为确实需要递归嵌套 | 用同契约的叶能力和组合能力 | 不为平铺的固定流程建立通用解释框架 |

评审应能指出采用后哪类变化被限制在何处、调用方少知道了什么，以及哪些保证由谁维护。若答案只有“更通用”“以后好扩展”或模式名称，应回到实际需求重新选结构。

## 具体实现、静态组合与动态接口怎样选择

| 当前需要 | 合适的选择 | 必须证明的收益或边界 |
| --- | --- | --- |
| 只有一个具体行为，调用关系清楚 | 直接函数或具体类型 | 契约清楚，调用方不依赖内部状态 |
| 小范围无状态行为变化 | 函数参数或有限策略值 | 改变的是行为，非额外共享状态 |
| 有真实独立依赖边界或运行时实现替换 | 小接口及明确装配 | 调用方只需要该能力，生命周期与错误可替换 |
| 组合结构在编译阶段已知 | 编译计划、编号或具体结构组合 | 运行时保持同一契约、顺序与预算 |
| 只是需要列出公开能力 | 声明或接口目录加说明 | 不因此强制把所有字段改为接口类型 |

不要求先制造第二个实现才承认真实依赖边界，也不因未来可能扩展就预建接口层。Wasm尤其应区分契约目录与实际动态分派；动态调用、分配或热路径结构变化按正式产物验证成本。

## DRY：同一知识由一个来源负责

DRY（避免重复表达同一知识）关注规则、事实和契约的重复，不要求消除所有相似语句。判断方法是：同一业务决定改变时，哪些位置必须同步改变才能继续正确？如果多个地方各自解释同一条规则，就应找出其真实拥有者。

| 表面相似的情况 | 应怎样判断 |
| --- | --- |
| 多个功能各写一套相同分组或匹配规则 | 属于同一语义时集中规则及其契约，调用方保留各自的上下文准备 |
| 两处都把几个字段写入对象 | 若不包含共同业务决定，可以保留直观构造，不为行数减少增加转发 |
| 前端提示、后端拒绝、引擎编译都检查同一约束 | 这些边界各有职责；统一共享定义及样例，不删除必要的独立校验 |
| 测试有独立手算期望，与生产计算涉及相同公式 | 独立期望用于发现实现错误，不能为“复用”调用被测实现得到期望 |
| 两种玩法当前公式碰巧相同，但变化原因不同 | 先保留语义边界，不能只凭当前表达式相等绑定两者的演进 |

提取共享部分时只移动同一知识。某些结果检查可以共用“已准备标签如何匹配”的规则，但各自准备哪些标签、怎样证明来源的责任不一定相同。若抽取后需要传入整套上下文或大量模式开关，说明边界可能过大。

共享规则的名字、输入和测试应表达其领域含义。修改一条规则时应有明确的定义入口和可追踪消费者，而不是靠搜索所有相似代码保证没有漏改。

## 修正错误契约，而不是层层绕行

新增功能被旧接口卡住时，先判断旧接口是否错误地混合责任或缺少必要事实。在本次授权范围内修正所属模块及调用方，保持仍有效的行为，不在下游复制另一套实现来绕过问题。共享模块暴露领域事实与能力，具体产品选择留给消费者；MVP不增加旧设计兼容层。

如果问题来自共同定义，就修正共同定义并核对所有受影响调用方；如果差异本来属于某个场景，就在该场景明确表达，不把它反向塞入共享内核。不要把“尽量复用”理解为必须保留已不成立的接口，也不要借修复根因扩大到无关模块。

正确性优先体现为显式契约和可验证结果：类型、签名及说明能表达的前提先表达出来，预期拒绝作为正常结果处理；内部不变量失效应暴露原因，不能靠默认成功或不断叠加兜底分支维持表象。

## 实施前短说明与设计验收

普通任务在现有说明或交付中回答下列问题即可，重要共享语义按根规则独立评审：

1. 用户新增的可观察行为及正常、拒绝和边界例子是什么？
2. 哪些能力复用、组合、增加或修改，为什么该选择能表达本次语义？
3. 每项新责任的输入、结果、失败、副作用和拥有者是什么？
4. 若存在变体或嵌套，调用方如何统一使用，组合者独占哪些顺序与生命周期规则？
5. 新增本次要求的变体时，哪些稳定部分应保持不变；通过什么场景发现契约被破坏？

无需为第五项实现未请求的变体。用本次实际变化和一个有依据的对照，检验抽象是否减少重复知识和调用方细节即可。验收既看实际功能是否成立，也看新增行为是否有清楚落点；仅列出当前目录或为每个名词起类名仍不足以指导实施。
