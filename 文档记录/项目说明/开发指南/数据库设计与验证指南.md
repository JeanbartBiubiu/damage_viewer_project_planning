# 数据库设计与验证指南

本指南用于设计新增表、字段、约束、索引、查询和迁移，不表示当前所有表已按本文重新验收。权限与最低检查见[数据库规则](../../../db/AGENTS.md)，目录及安装入口见[数据库导览](../../../db/README.md)。本文解释设计方法，不复制完整字段定义或另存数据库状态。

业务服务如何组织事务、返回错误及管理资源，复用[后端编码指南](后端编码指南.md)；用例构造与运行证据见[测试指南](测试编写与运行指南.md)。访问实库时使用项目的数据库访问技能；仅做静态设计不需要连接配置或凭据。

## 先确定持久化什么事实

设计前写清一行代表什么、谁创建和更新、哪些查询需要它、保存多久、删除后谁仍需要历史事实。新增表必须有当前独立事实或关系；不能只因页面多了一个区块就复制原表，也不为可能的未来查询预建冗余数据。

| 要决定的事 | 应能回答的问题 | 定义位置 |
| --- | --- | --- |
| 业务事实与用途 | 是作者配置、身份、关系、累计还是可重算派生值？ | 需求与共享定义 |
| 当前结构 | 列、键、约束、索引和触发器实际应是什么？ | 所属建表脚本及约束脚本 |
| 结构变更 | 哪一种已有结构怎样到达新结构？ | 明确前置的迁移脚本 |
| 写入与校验 | 谁保证跨对象一致性、事务和权限？ | 所属服务、守卫及存储代码 |
| 现场状态 | 目标库实际存在什么，哪些数据已提交？ | 已授权目标的实库读回证据 |

同一事实确定一个拥有者。数据库保存作者配置，不因为引擎能计算就同时持久化每场运行过程；确需存派生结果时明确输入身份、更新条件和失效规则，不能把旧结果当作当前配置事实。

## 身份、关系和删除行为

主键标识一行，业务唯一键表达不允许重复的业务事实；使用独立编号也不能代替真正的唯一约束。先确定标识在哪个作用域唯一，再决定键的组成。

- 游戏内标识带所属游戏；技能内效果标识还带所属技能。外键沿用被引用对象的完整键，不仅凭显示名称或局部标识关联。
- 一对一、一对多及多对多分别明确哪一端拥有关系；中间关系表的唯一约束应阻止同一关系重复落地，不靠服务先查后插。
- 删除行为逐关系决定：随拥有者消失的从属事实可以级联；被其他对象引用的配置通常先拒绝或显式处理；需要保留审计事实时可置空引用并保留必要身份快照。不要统一套用级联删除。
- 外键只证明被引用行存在，不自动证明它已启用、类型正确、可用于当前场景或整个引用图无环；这些语义仍由真实业务拥有者维护。

### 设计例一：游戏内唯一的属性与跨游戏隔离

当前属性键由 `(game_id, attribute_key)` 标识，名称另按同游戏的去空白、忽略大小写规则唯一。设计同类新对象时，先判断是否具有相同的身份和命名语义，再采用对应模式；不是所有名称都必须忽略大小写。

| 输入 | 设计应表达的结果 |
| --- | --- |
| 两个不同游戏各有 `attack_damage` | 允许，所属游戏不同 |
| 同一游戏重复 `attack_damage` | 拒绝，同一业务身份重复 |
| 同一游戏名称为 `Attack` 与 ` attack ` | 按当前属性命名契约拒绝重复 |
| 子表只写 `attribute_key`，忽略 `game_id` | 不能证明关联到正确游戏，不应作为完整引用 |

当前模式见[游戏结构脚本](../../../db/game_manage/schema.sql)中的属性主键、名称唯一索引及吸血规则复合外键。新增关系要检查相同局部键在不同作用域的正反场景，而不仅验证一条合法插入。

## 空值、类型、单位与时间

先定义未提供、未知、不适用、有效0、空文本和空集合的不同含义。必填用明确的非空约束；业务不允许空文本时另作值约束，不把所有缺失都补成0或空字符串。

- `CHECK`（检查约束）表达允许条件；条件得到空值并不等同于拒绝。因此 `CHECK (amount >= 0)` 不能代替 `NOT NULL`。默认值也只负责生成缺省值，不会把已有空值自动改正。
- 普通可空唯一约束允许多条空值。若“未设置”也有唯一性含义，先确定业务规则，再选择目标数据库支持且能被测试证实的约束，不用应用层预查猜测唯一性。
- 多列合成一个可选引用时，明确是否必须同时为空或同时出现；默认外键的空值处理不能代替这项规则。下面仅示意字段成对出现的约束，不是待执行迁移：

```sql
CHECK ((target_skill_key IS NULL) = (target_effect_key IS NULL))
```

若上述引用属于当前游戏，其外键还须包含 `game_id`，并匹配目标的完整技能、效果键。只填技能或只填效果都应被拒绝，两者均空表示契约允许的“没有目标”。

| 数据 | 设计时必须明确 |
| --- | --- |
| 整数计数、等级、容量 | 合法范围、是否可为0、增长上界及Java与前端能否精确表示 |
| 作者小数、倍率、百分数 | 精度、有限性、取整位置；`1`表示整体倍率还是百分比数值，单位随字段契约明确 |
| 绝对发生或到期时刻 | 时区语义、来源时钟及比较规则；新设计通常用 `timestamptz` 表达绝对时刻，不能直接重解释旧无时区列 |
| 业务自然日 | 使用哪个时区划日；`date`只表示日期，本身不保存划日时区 |
| 时长、运行相对时刻 | 单位、起点、允许范围；不能把毫秒时长当作数据库绝对时间 |
| JSONB（数据库内的结构化JSON） | 键的稳定性、类型、缺失语义、查询与引用需求；结构化值不等于免校验 |

选择可表达实际范围的类型。需要精确小数时定义十进制语义，需要近似数值时明确允许误差；不要只为省一次转换而让数据库、Java和前端对同一列使用不同含义。

## 数据库约束与业务校验各自保证什么

| 不变量 | 主要落点 | 同时需要注意 |
| --- | --- | --- |
| 行身份、稳定唯一性、存在关系、行内值域 | 主键、唯一、外键、非空及检查约束 | 数据库约束覆盖所有写入入口，服务返回可理解的业务拒绝 |
| 跨对象用途、启用状态、引用循环、最终组合合法性 | 所属服务与现有事务守卫 | 必须覆盖正式写路径；直接SQL不会自动运行这些服务校验 |
| 需要持久化维护的引用索引或派生关系 | 真实拥有者及对应写入边界 | 明确何时更新、失败是否回滚、怎样与源事实对账 |
| 权限、账号状态及操作来源 | 已有鉴权和业务入口 | 数据库连接可写不等于业务上允许该操作 |

关系列需要独立检索、约束及生命周期时，优先评估真实关系结构；结构随作者配置变化、主要整体读取时，可以沿用已有结构化载荷。不能把原本可以约束的关系全部藏入JSON，也不因追求规范化把完整作者配置机械拆成大量表。

例如当前共同计算配置的数据库约束检查基本形状，启用目录、类型用途及完整共同公式授权还由游戏写锁内的最终态校验负责。新增字段时同时更新所属校验和消费者，不能只扩充JSON允许键就认为功能已经成立。

## 索引从实际查询和写入成本出发

先列出具体过滤、连接、排序、分页与删除条件，再考虑索引；记录预期数据量、返回比例和更新频率。索引提高某些读取效率，也增加空间、插入、更新及清理成本。

- 主键和唯一约束已有支撑索引，新增前检查是否重复；复合索引的列顺序结合实际谓词与排序选择，不能把列清单当作无序集合。
- 外键的引用端不会仅因声明外键就自动得到适用的查询索引；根据连接、父项删除检查和实际数据量判断是否需要补充，不能给每列机械建索引。
- 少量活跃行才需要访问时，可评估与真实谓词一致的部分索引；表达式索引须匹配实际查询和唯一性含义。排序索引还要核对稳定分页所需的完整顺序。
- 查询只取需要的列，明确空结果、排序及聚合口径；修改查询同时核对参数绑定、结果别名、Java返回类型和调用方，不通过拼接外部文本决定列名或排序。
- 性能判断依据代表数据量、参数、执行计划及同口径测量，不能由存在索引、模拟测试或小表快速返回推出容量结论。`EXPLAIN ANALYZE`会实际执行语句，写语句不能被当作只读诊断。

### 设计例二：每日访问累计与近三十天查询

一行代表“某业务自然日的某匿名浏览器累计”，完整身份是 `(visit_date, visitor_id)`，次数是正整数；同一天同编号再次上报应增加次数，不新增另一条每日独立访客事实。

| 场景 | 应验证的结果 |
| --- | --- |
| 同日同编号当前次数为1，两个并发上报均成功 | 最终次数为3，仅一条身份记录 |
| 同日两个不同编号各上报一次 | 两条身份记录，每日独立访客为2 |
| 同编号跨业务自然日上报 | 分属两条每日事实，不能跨日相加当作当天独立访客 |
| 查询近三十天且存在窗口外数据 | 只返回约定窗口；空日补零由当前查询契约决定 |

当前实现用唯一键冲突时原子递增，避免两个请求分别读1再都写2。日期在服务按北京时间确定；表列为 `date` 不会自动完成时区转换。精确定义见[统计说明](../../../db/visit_statistics/README.md)和[统计表](../../../db/visit_statistics/schema.sql)。

该主键的日期前导列可作为日期范围查询的候选访问路径；是否另建索引应由查询计划与数据量决定。当前若没有按访客编号查历史的需求，就不为假设中的查询预建访客索引。每日独立访客来自每日记录数，不能把每日独立访客相加当作整个窗口去重人数。

## 并发与事务必须保护同一不变量

在设计说明中给出必须一起成立的事实、事务起止、需要锁定的拥有者及加锁顺序。唯一约束解决重复身份，原子更新解决读改写丢失；跨表最终组合仍须在正确的业务事务中复核。

具体事务入口、基线摘要检查、游戏锁及账号锁顺序复用[后端事务方法](后端编码指南.md#事务拥有完整业务变更)与[并发方法](后端编码指南.md#并发由共享事实的拥有者约束)。数据库设计改变隔离级别、锁范围或提交边界时，核对真实调用链及正反交错场景，不只检查最终总数。

事务外预查可以给提示，不能代替写入边界的权威复核；进程内锁不能代替多个应用实例共享的数据库事实。超时或连接中断可能留下未知提交状态，重试按真实幂等规则判断，不自动补写或重复扣减。

## 新库与已有库分别设计执行路径

结构变更同时维护当前目标结构与需要的已有库变更说明。当前处于MVP，允许明确的破坏式升级；只为本次真实存量决定数据处置，不预建双写、兼容表或未来版本桥接。

| 环节 | 新库路径 | 已有库路径 |
| --- | --- | --- |
| 开始前 | 确认需要哪些模块及前置扩展、模式、角色 | 核对目标、实际源结构、约束、数据及依赖，不把未知结构当作空库 |
| 脚本选择 | 使用当前所属建表与约束脚本，按模块说明初始化 | 只选匹配源结构的迁移，不批跑目录或重放已执行历史脚本 |
| 执行边界 | 核对脚本是否自带事务及失败处理 | 写清事务由脚本还是调用方持有、锁与预计影响；需要的数据映射和拒绝条件显式列出 |
| 数据处置 | 不凭空补业务配置或种子 | 在已有授权内核对备份、保留、转换或删除范围及恢复方法 |
| 完成读回 | 检查目标结构及代表性合法、拒绝输入 | 独立检查新结构、转换前后身份及数量、不应受影响的数据和失败原子性 |

不要把 `CREATE TABLE IF NOT EXISTS` 当作升级器：同名表存在不证明列、约束及索引与目标一致。已执行迁移保留历史语义，新变化通过明确的新迁移或当前授权的替换路径实现。

迁移脚本的事务归属逐份核对：当前访问统计安装脚本自己开始并提交事务，构筑替换脚本由调用方持有事务；不能对整个目录统一套用一种执行方式。需要事务外执行的操作也必须单独明确其失败和恢复边界。

游戏配置、账号和统计是不同安装范围；图片还依赖父表、分区函数与实际子分区。变更后检查真实目标依赖是否齐全，不能由建表语句或创建函数成功推断所有分区已存在。

## 分层验证与交付

| 证据 | 能证明 | 不能替代 |
| --- | --- | --- |
| 静态DDL、迁移和消费代码核对 | 设计意图、脚本内容及已识别依赖一致 | 目标库真实结构、执行成功和性能 |
| 模拟单测或参数断言 | 服务分支、调用参数和错误约定 | 数据库约束、锁、隔离、真实SQL及回滚 |
| 已授权隔离实库执行与独立读回 | 对应目标上的结构、拒绝、提交或回滚及具体并发结果 | 未执行版本、其他数据库或生产容量 |
| 最终服务接口与实际调用方验证 | 新结构经正式写读链正确使用 | 所有游戏对象均能运行或其他接口未受影响 |

实库完成检查应包含约束和索引的实际定义及有效状态，而不只确认表名存在；数据读回从已提交事实出发，最好使用独立连接或重新发起的读取，避免把当前未提交事务视图当作结果。

合法样例须伴随本次改变对应的拒绝或冲突样例；并发和回滚只验证真实变化的不变量。检查目标、参数、角色或时区与原证据不同，不能直接复用原结论。

交付写明改了哪些定义、哪些迁移尚未执行、实际目标及证据层次。纯文档或静态脚本任务如实报告为静态核对；未授权或未访问的实库状态保留未知，不宣称已经迁移、备份或通过运行验证。
