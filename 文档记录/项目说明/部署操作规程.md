# 部署与公网体验交接

开发仓库负责业务实现、数据库结构及验证；同级的本地部署仓库 `damage_deploy` 负责冻结制包、服务器交接、数据库执行和公网验收。具体参数、命令及当前发布状态仅由[部署入口](../../../damage_deploy/README.md)维护，本文不复制服务器配置或第二套操作命令。部署仓库不添加远端，不存业务源码真源。

## 从开发交付到公网体验

1. 开发完成本轮目标，按模块规则验证并合入主干，交付明确提交和代表体验场景。其他任务的工作区与未提交重构不作为发布输入。
2. 部署从指定提交导出完整源码，在独立目录重新检查与构建；发布清单绑定源码、前后端、计算模块及显式数据库计划。正式对象证明仍遵循[开发流程](开发与独立评审流程说明.md)，合成机制通过不代表任意英雄已准入。
3. 数据库计划逐个列出本次实际需要的文件、摘要、顺序、事务拥有者、前置及后置核对。不批跑迁移目录，不整体复制测试库或账号数据到云端，不重放已完成安装。
4. 有数据库变化时先在已确认测试实例的隔离库演练同一组文件。测试库若已是新结构，不能以跳过成功代替旧结构升级；演练记录基线、保留数据及清理结果。没有数据库变化的发布使用空计划，只读核对目标身份，不制造新迁移。
5. 云端核对实际应用与部署使用同一主机、端口、库、账号和实例标识，再维护停写、形成可完整读取的备份，按脚本真实事务边界执行并独立读回。失败保留维护及已提交事实，不盲目重放或声称跨文件自动回滚。
6. 两机程序及静态文件均核对同一发布身份，依次切换后端与前端，再运行公网浏览器的代表场景。最终检查失败恢复维护。网站必须由普通浏览器正常验证证书，不把跳过证书、服务器本机成功或固定健康页当作公网可用。
7. 交付公网地址、发布编号、简短改动与已验证场景。用户反馈玩家目标、取舍及使用感受；代理据此复现、调查、修复并重新发布。未验证部分保留明确限制。

## 数据与恢复边界

数据库结构定义继续属于 `db/**`，执行记录属于发布证据。新库与已有库分别处理，账号、统计和游戏配置按各自说明选择入口。应用回退同时核对结构与真实数据格式：例如新版生成的密码格式可能不被旧程序接受，即使表结构兼容也不能自动回退。

需要恢复数据库时，在新的空库恢复并读回后再切换显式连接，不覆盖故障库。正式密钥、私密环境、真实账号和游戏数据不随日常制包重新生成或清空。原始备份、日志、截图与执行记录放入忽略目录或服务器私有目录，交付只保留非敏感摘要。

## B 验证后进入 C 清理

遵循[全项目清理规则](../../AGENTS.md#2-工作流)：B 在公网完成程序、数据库和关键场景验收后，C 必须移除本轮过渡入口、旧配置路径、兼容分支及失效说明。删除迁移前确认所有已登记目标都已应用；恢复备份按实际恢复需要保留。历史从 Git 与发布证据追溯，不把一次性操作留作下一轮默认命令。
