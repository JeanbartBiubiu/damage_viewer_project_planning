## 从请求到验证

1. **查依据与已有实现。** 从[知识手册](项目知识手册/README.md)进入相关概念，再查其指向的唯一来源、定义、调用方及测试。核对哪些行为已实现、哪些是已确认取舍、哪些仍是草案。按模块 README 选择现有工具和构建入口。
2. **先确认问题和验收。** 故障修复先记录触发输入、实际现象、期望行为及成功标准，复用已有有效失败证据；需要补回归时，先运行最小用例，确认失败来自目标问题。无法稳定复现时说明限制，通过实际日志、调用链或调试缩小原因。新增功能先确定可观察行为及边界，文档和引用修正直接核对相应内容。
3. **形成可验证的改法。** 故障说明根因或待验证假设；新增功能说明能力为何复用、组合、增加或改变，以及输入、结果、失败、副作用和拥有者。存在变体或嵌套时明确可替换性、次序、上下文及组合边界，再确定实现位置与验证。按根规则选择直接实现、短说明或独立评审；普通小任务可在当前说明中写清，不为内部步骤另建任务或长方案。重要假设改变时更新当前方案，再验证受影响部分。
4. **修改并取证。** 先用类型、明确返回值及现有静态检查表达约束，再修改实际拥有该行为的模块。遇到崩溃或一次猜测性修补仍失败时，检查实际运行产物、调用链和错误信息，必要时调试；不继续无证据地叠加兜底分支。按模块规则运行受影响检查及收尾检查，失败时判断是实现、假设还是环境问题。
5. **复核最终文件。** 核对需求、共享定义、实现、测试及必要文档是否一致。评审后又修改的代码按影响重跑检查；合入引入执行代码变化或解决代码冲突时复查并验证受影响部分。交付时说明实际改动、执行结果、证据层次及仍未解决的限制。

## 开发与评审责任

- 主负责人收敛目标、范围、共享契约和验收，直接实现或委派写入范围明确的执行代理，并负责最终集成与验收。
- 需要独立评审的任务，由未承担相应实现的只读代理评审当前方案，完成后独立检查关键改动。沿用成熟模式的局部改动按根规则直接实现并做针对性验证。
- 成熟同类数据录入按批次抽查，不逐对象安排独审；共享运行语义、权限及数据安全变更仍按根规则独审。代理只完成指定范围，整体集成与后续选批由主负责人负责。
- 评审记录对应方案版本或最终差异、所依据的证据、结论及有证据的阻塞项。只处理影响正确性、数据安全或验收的问题；新事实改变重要决定时才复审相关部分。
- 实现者可以调整内部实现。共享语义、权限、数据处置或任务范围发生变化时，返回主负责人决策；原本只授权方案或评审的任务仍须取得开发授权。

## 证据与异常处理

评审必须保持只读，所用资料与实际待实施方案或最终文件一致。运行未完成、关键证据缺失或评审对象被后续改动影响时，保留已有记录，补齐证据或对受影响部分复审。无关文件变化不自动使评审失效；按实际审阅对象及授权写入范围判断。

实现失败、取消或超时后，先检查已经落地的文件、工作树差异、实际写入和产物，再决定接手或重试。切换执行方式仍遵守原授权，不盲目重放已经发生的业务写入，不自动回滚他人修改。

## 共用测试原则

独立期望、行为断言、三端用例写法、依赖替身、隔离、发现规则与结果读取统一见[测试编写与运行指南](开发指南/测试编写与运行指南.md)。开始运行及失败定位见[构建运行与排错指南](开发指南/构建运行与排错指南.md)。低影响、可逆改动及复用既有证据仍按根规则判断。

## 回归与验收证据

- 普通录入采用正常触发、关键等级或属性变化、条件不成立及必要边界的代表场景；分段曲线覆盖实际转折，不默认穷举每个等级或场景组合。配置声明的全部可选等级不等于每级均已实际执行，证明必须如实区分可选范围与已验证样本。
- 完整对象的 `requiredCoverage` 返回合法选择范围，验证要求为 `representative-cases`。新代表证明另用 `validationCases` 记录实际病例、证据引用、对象位置、双方等级、参与技能等级及完成和释放事实；成功样本须覆盖必要技能和双方位置。不支持的对象继续记录明确问题，不要求成功样本。确切字段与有界校验由后端 `SimulationAvailabilityResources` 维护，数值、分段及条件边界仍须独立对照，字段合法不等于运行通过。
- 现存 `each-declared-level` 证明保留原声明及证据；其完整范围与当前配置仍匹配时，继续作为更充分的证据。不要只改标签或把合法等级列表抄成新病例，也不为本次流程精简重跑旧矩阵。
- 新机制先用一个生产适配与真实 Wasm 场景打通编译、运行、结果准入及释放，再扩大边界用例。候选与保存后复用同一场景和独立预期，只重新读取实际配置；重复执行不重新整理资料或另写接线。
- 引擎或前端适配层变化后的回归，以 `web/tests/mechanisms/` 的固定机制用例为准：合成游戏数据加事先手算的期望，经生产适配链路和真实 Wasm 比对（`npm run test:mechanisms`）。新增或修改机制时，同一改动里带上对应用例；编写规则见该目录 README。
- 已准入对象不再逐个重跑。稳定批次收尾时，机制回归通过、且各对象声明的配置摘要仍匹配、依赖机制都有用例后，用 `web/scripts/refresh-verification-identity.mjs` 刷新正式证明的引擎身份；覆盖不全时补用例或对缺口对象单独复核。中间候选不反复刷新正式证明，新对象首次准入仍按其真实配置验收。
- 源码身份以提交号加相关路径无未提交改动为准，不再复制源码或逐文件记录摘要。完整证明刷新必须用固定工具链按正式参数重建当前Go源码和目标配置，逐字节确认分发Wasm一致，再执行机制回归，避免用旧二进制证明新源码。
- 浏览器验收只保留少量代表对象的完整页面冒烟，不做每轮全量回放。
- 原始响应、日志、压缩包和截图写入被忽略目录（`web/output/`、`wasm/tinygo_engine_v2/target/`、`output/`）或外部归档，只在失败排查需要时保留；仓库长期维护测试用例、正式证明及必要的持续约束。实际检查结果和限制在任务交付中报告，不再要求单独累积验收过程文档。
- 证据归档合并到稳定批次或工作树移除前；不为每个小检查点重打包。普通录入不开展性能专项，必要机制修复通过现有基准后，优化研究按明确风险另行处理。

## 验收与共享发布

主负责人复核最终差异并按目标模块规则验证，分别报告静态、单测、实库、最终 Wasm、运行时及浏览器证据。代理的文字结论不能代替实际验证结果，未执行的验证如实说明。

各模块在同一检出的 `master` 主干上协作：任务从最新 `master` 开短期分支，按改动范围完成本地验证后合入 `master` 并按任务授权推送。分支与路径约定见根 AGENTS.md 第 4 节。

需要用户体验的改动继续进入[部署与公网体验交接](部署操作规程.md)。开发交付明确源码提交、已执行验证、数据库变更文件及验收场景；部署仓库从该提交导出源码，不能复制其他任务正在修改的工作区。公网发布编号、程序及计算模块摘要、数据库变更和代表场景证据一致后，再请用户反馈目标是否达成、操作是否清楚及结果是否有用。可自动获取的错误、日志、复现与回归由代理处理，不让用户重复承担技术验收。

## 所有变更的后续清理

根规则中的 A→B→C 适用于整个项目。B 完成功能或模型变更并通过目标环境验收后，C 作为下一轮必做工作，删除只为 A→B 过渡的旧代码、兼容分支、双重配置、临时入口及说明，验证清理后仍满足 B 的当前契约。不要把旧说明改成长期并列方案，也不要为了这一步重新建立兼容层。

B 交付附简短清理清单：对象、触发条件、当前证据和仍被哪个已确认目标依赖。涉及发布与数据库时，条件包括实际发布版本及已执行变更；仅本地测试通过不触发线上依赖删除。仍在使用的当前行为测试、尚被实际旧数据需要的读取能力、未升级目标所需迁移，以及恢复点不按名称或日期机械删除。依赖消失后在 C 删除有效入口中的旧内容，历史过程从 Git 和忽略目录中的发布证据追溯。

按问题选择验证层次可从[知识手册的验证导航](项目知识手册/07-当前能力与阅读导航.md)进入。历史落地过程与当时结果从Git追溯。
