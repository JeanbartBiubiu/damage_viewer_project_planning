# 剩余表格页面前端方案

## 1. 背景与目标

当前后台前端已经围绕 4 张核心表展开设计和开发：

- `formulaProfiles`
- `formulaBindings`
- `coefficientBuckets`
- `statusActionControlRules`

本次需要补齐其余可编辑表的前端页面，重点是页面设计与实现，不扩展后端接口。

本轮补齐范围：

- `attributeDefinitions`
- `types`
- `typeRelations`
- `heroes`
- `skills`
- `items`

不在本轮范围：

- 图片编辑页重做
- 新增后端 `GET list/detail` 管理接口
- 新增前端自动化测试框架
- 调整发布链路的后端行为

## 2. 视觉与交互基调

### Visual Thesis

把后台做成“数据工位”而不是“卡片拼盘”：浅色雾面底、强层级标题、细颗粒状态标签，重点突出资源切换、表格扫描和当前编辑上下文。

### Content Plan

- 顶部：资源状态与当前工作上下文
- 中部左侧：资源列表 / 搜索 / 行状态
- 中部主区：创建、PUT、PATCH 编辑器
- 中部右侧：结构提示、依赖关系、当前记录摘要
- 底部：版本创建 / 发布 / bundle 刷新结果

### Interaction Thesis

- 资源切换时突出“当前资源”与“数据来源”，弱化无关面板
- 列表行通过 `bundle` / `session-draft` / `new` 状态标识让用户知道当前看到的是哪一层数据
- 成功保存后立即更新本地草稿覆盖层，让新增和修改结果不需要等发布也能继续编辑

## 3. 页面范围

保留现有 `#/admin/{resource}` 路由模式，补齐以下 6 个资源页面：

| 资源 | 路由 | 读取来源 | 写入接口 |
| --- | --- | --- | --- |
| 属性定义 | `#/admin/attribute-definitions` | current bundle + session overlay | `PUT/PATCH /attribute-definitions/{attrKey}` |
| 类型 | `#/admin/types` | current bundle + session overlay | `PUT/PATCH /types/{typeId}` |
| 类型关系 | `#/admin/type-relations` | current bundle + session overlay | `PUT/PATCH /type-relations/{typeId}/{targetCategory}/{targetId}` |
| 英雄 | `#/admin/heroes` | current bundle + session overlay | `PUT/PATCH /heroes/{heroId}` |
| 技能 | `#/admin/skills` | current bundle + session overlay | `PUT/PATCH /skills/{skillId}` |
| 装备 | `#/admin/items` | current bundle + session overlay | `PUT/PATCH /items/{itemId}` |

同时保留现有 4 张核心表页面，不改路由语义。

## 4. 关键约束与应对

### 4.1 后端约束

剩余 6 张表只有 `PUT/PATCH`，没有后台管理端的 `GET list/detail`。

同时后端当前明确不会在“非发布写入”后刷新 `currentVersion/bundle` 缓存，因此：

- 写入成功后，公共 bundle 不会立刻看到最新草稿
- 新建记录如果只依赖 bundle，会在列表里消失

### 4.2 前端应对策略

前端读取模型拆成两层：

1. `bundle baseline`
   - 来自 `GET /versions/current`
   - 再拉 `GET /versions/{versionId}/bundle`
   - 作为每个页面的初始列表和详情基线

2. `session overlay`
   - 仅存在前端内存
   - 在 `PUT/PATCH` 成功后用返回体覆盖对应记录
   - 新建记录直接插入 overlay
   - 页面渲染时以 overlay 覆盖 bundle 同 key 记录

这样可以满足：

- 保存后列表立即可见
- 新建后可继续编辑
- 发布前仍能基于当前会话持续操作

限制也要明确保留：

- overlay 不是跨浏览器持久草稿
- 刷新页面后会回到 bundle 基线
- 真正发布结果仍以版本创建 / 发布后的 bundle 为准

## 5. 信息架构

### 5.1 侧边导航

后台资源导航拆成两组：

- 核心规则表
  - 公式档案
  - 公式绑定
  - 乘区档
  - 状态动作规则
- 基础内容表
  - 属性定义
  - 类型
  - 类型关系
  - 英雄
  - 技能
  - 装备

每个资源都保持独立 hash，可直接深链进入。

### 5.2 页面骨架

每个资源页面统一为三段式：

1. 资源顶部条
   - 当前资源名称
   - 当前 gameId
   - 数据来源状态
   - bundle 版本信息
   - overlay 记录数

2. 工作区
   - 左侧：搜索、计数、资源列表
   - 中间：创建 / PUT / PATCH 编辑器
   - 右侧：字段提示、关联约束、当前记录摘要

3. 底部控制区
   - 版本创建
   - 发布
   - 发布后的 current version / bundle 刷新反馈

移动端顺序改为：顶部条 -> 列表 -> 编辑器 -> 右侧提示。

## 6. 页面行为设计

### 6.1 列表区

列表区提供：

- 关键字搜索
- 资源计数
- 行来源标签
  - `bundle`
  - `session-draft`
  - `new`
- 打开当前记录按钮

不同资源采用配置化列定义，不为每张表单独手写整页。

### 6.2 编辑区

编辑区保留现有三种模式：

- `新增`
- `编辑 (PUT)`
- `修改 (PATCH)`

新增模式规则：

- 用户先填写资源主键
- 前端根据资源类型生成默认 JSON 草稿
- 点击 `使用 PUT 新增` 后直接走对应 `PUT`

PUT 模式规则：

- 主文本区显示完整 JSON
- 保存成功后更新 overlay

PATCH 模式规则：

- 单独维护局部 JSON
- 成功后用服务端返回体回填完整草稿区

### 6.3 右侧提示区

右侧不是装饰区，必须承担操作辅助：

- 当前资源主键说明
- 服务端强约束字段提示
- 关联关系提示
- 当前选中记录摘要

示例：

- `skills` 需要 `ownerType / ownerId / mechanicsConfig`
- `heroes` 需要 `name / baseStats`
- `typeRelations` 需要目标类别合法且目标存在
- `attributeDefinitions` 的 `valueKind=rate` 时必须带 `rateTargetAttrKey`

## 7. 组件与代码方案

### 7.1 前端实现原则

采用“配置驱动 + 共享工作台”，避免为 6 张表复制页面。

### 7.2 新增或调整的核心前端能力

- 扩展导航配置，加入 6 个资源入口
- 扩展 `App.tsx` 的 hash 解析与资源映射
- 在 `api.ts` 中补齐剩余资源类型与可复用响应结构
- 在 `apiClient.ts` 中补齐 6 张表的 `PUT/PATCH` 写接口
- 在后台页面中补一层 bundle 读取与 overlay 合并能力
- 抽离资源配置对象
  - 标签
  - 路由 segment
  - 主键生成 / 解析
  - 列表列定义
  - 默认创建 payload
  - 字段提示
  - 写接口映射

### 7.3 建议代码结构

- `web/src/config/navigation.ts`
  - 扩展 admin 资源导航定义
- `web/src/services/apiClient.ts`
  - 增加剩余资源写接口
- `web/src/types/api.ts`
  - 增加剩余资源响应与工作台类型
- `web/src/pages/AdminPage.tsx`
  - 升级为统一资源工作台
- 可新增 `web/src/pages/admin/*` 或 `web/src/pages/adminResourceConfig.ts`
  - 存放资源配置与辅助函数

## 9. 状态与异常

必须覆盖以下页面状态：

- 未选择 gameId
- 未填写 JWT
- current version 不存在
- bundle 拉取中
- bundle 拉取失败
- overlay 为空
- 保存成功
- 服务端校验失败
- 语义错误返回

在 bundle 读取失败但已有 overlay 时，页面仍保留本次会话可见草稿，并明确标出“基线失效，仅显示本地草稿”。

## 10. 实施顺序

1. 扩展导航与资源定义
2. 补齐 `apiClient` 写接口
3. 在后台页面接入 bundle baseline
4. 加入 session overlay 合并逻辑
5. 完成 6 个资源页面配置与交互
6. 联通版本创建 / 发布后的刷新反馈
7. 执行 `npm run build`

## 11. Review 关注点

前端子代理 review 时重点检查：

- 是否真的覆盖了 6 张剩余表
- 路由是否可深链
- overlay 方案是否足以应对“无 GET 管理接口”的后端限制
- 页面是否保持统一但不混乱
- 移动端是否仍能完成新增 / 编辑 / PATCH
- 是否避免把后台页面做成纯卡片堆砌
