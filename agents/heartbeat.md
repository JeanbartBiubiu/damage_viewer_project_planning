# 角色协作定时唤醒流程

本流程供当前开发环境的原生定时自动化及人工触发使用，环境编号为 `codex-local`。其他环境先按共享入口建立自己的登记与自动化，不跨环境派送。用户授权了本角色协作机制内必要的会话创建、接续和定向通信；每条消息的业务工作仍受原始用户任务及模块规则约束。

## 检查与有界派送

1. 在主检出读取当前 [共享入口](README.md) 与本流程，然后执行 `node agents/coordination.mjs tick --environment codex-local`。它先补偿已申报的完成事件到各角色待办，不向会话发送这些通知；`completionRepair` 若存在则单独报告通知补偿的失败或积压，不能忽略，也不阻断有效的详细派工。没有详细任务派送计划、未知结果或通知故障就结束，不扫描全部仓库、不新建会话、不重复汇报。完成通知只存文件，等待角色自然接手或检查点读取，禁止为了提醒其查看待办而发送新输入，即使刚才查询为空闲也不发送。普通进度变化和近况陈旧不构成唤醒理由。
2. 存在 `sending` 或 `uncertain` 时，先用当前环境的会话读取工具核对目标中的消息编号。`runtime` 只显示投递元数据，可取得派送编号和目标。确认已接受、确认未接受、仍无法确定分别用 `settle` 记录 `sent`、`not_sent`、`uncertain`，回执写实际工具回执或核对依据。不能把超时当成未发送；无法确定就保留并报告一次需要输入的原因，不重放。
3. 按计划顺序检查候选，实际派送最多两个目标（`dispatchBudget`），每个目标的消息编号合并为一批。先重新 `resolve` 查询目标角色，不缓存会话编号。已有会话用当前环境的真实会话状态工具核对，例如 Codex 的 `wait_threads`，使用零等待快照。正在运行、需要用户操作或状态未知时延后，并继续检查后面的候选；跳过者不占实际派送预算，不让队首忙碌角色长期挡住空闲角色。不打断，也不改写其业务近况。
4. 缺少会话时，使用当前环境的会话创建工具新建对应角色，项目指向本仓库的本地项目。新会话的首条输入只要求读取角色规则和接续资料并返回初始化就绪，明确禁止业务写入、主动派工和自行绑定。取得真实会话、宿主编号，等待其初始化结束后，按 `resolve` 的代次运行 `bind`。工具若返回临时客户端编号，先等待真实会话编号，不能用临时值绑定。绑定冲突时重新查询，额外创建的会话不承接业务。
5. `rotationDue` 为真时，只在旧会话确认空闲、进行中的写入已得到处置、角色笔记足够交接时按共享入口换代；资料不足时先保留原会话，请它在当前授权任务内补齐交接，不能假定摘要完整。存在正在投递或未知结果会阻止换代。没有原任务就不能借换代让角色自行选业务开发。
6. 发前再次查询会话身份，确认空闲，再用下述 `claim` 领取。领取会核对当前会话代次并将目标锁定为本次投递身份；从此到明确回执期间不能切换该目标的登记。仅本次成功领取后，才可以发送正文。

```text
node agents/coordination.mjs claim <目标角色> <消息编号...> --environment codex-local --thread-id <实际会话编号> --generation <当前代次> --idle-confirmed
```

7. 使用实际会话发送工具将这一批详细正文投递到 `claim` 返回的目标。输入必须包含消息编号、原任务及授权、正文、有效角色与代次，并要求接收方先核对登记，重复任务先回读，完成后自写短近况。不能让角色根据一句摘要推断未授权范围；不把其他角色的笔记或全部历史注入。不会自行收到原生发送工具的代理只能将需要沟通的内容排入请求，不能伪造已发送。
8. 工具明确接受后记录 `sent`；明确拒绝且未投递记录 `not_sent`；超时、取消或不确定记录 `uncertain`。每次领取返回的 `dispatchToken` 是派送编号，只能用于该批实际结果。三次明确未投递后以 `failed`（已知失败）结束并解除目标锁定，向用户报告该次失败，不冒充未知结果继续锁住角色。仍不明确的投递始终保留 `uncertain`。状态记录失败时先查询已落地记录，不重发正文。

```text
node agents/coordination.mjs settle --environment codex-local --token <派送编号> --outcome sent --receipt <真实工具回执编号或已核对依据>
```

9. 回执只证明工具接受，不证明业务完成。角色若需要对方进一步行动，另登记有明确原任务阶段的详细请求。任务阶段真实完成时使用 `complete` 写关联角色待办；处理通知不调用 `complete`，普通确认与结束回复不自动触发下一轮消息。一次检查完成便结束，后续由下一次定时检查或明确人工触发接续，不在一个自动化轮次内无限追跑。

## 首次验收

首次接入时允许为验证本机制创建最少的角色会话，跑通“创建→绑定→本人发布短近况→他方主动查看→详细任务投递→实际回执”。这仅验证协作基础，不授权英雄录入、业务开发、推送或部署。原生钩子信任、脚本回调验证、实际会话通信和自动化激活分别记录，不用其中一项替代另一项。
