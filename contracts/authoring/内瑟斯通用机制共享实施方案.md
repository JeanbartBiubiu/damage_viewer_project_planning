### 1. Q：一个附加伤害量，使用开始冻结累计值

继续使用现行技能计数 `SCENE_INITIAL_PARAMETER` 场景初值绑定、启动动作 `INTERNAL_STATE` 输入和 `PROCESS_START` 计数 SET。累计伤害点数必须由用户明确提供，0 合法，缺值拒绝；不生成击杀成长。两个状态仍分别是入战初值和本次冻结值，不共享不同拥有者、挂载或使用的可变槽。

把旧草案的两条伤害结果改为**一条**普通附加物理伤害：

`Q附加量 = 基础额外伤害 × [1 + clamp(当前暴击率,0,1) × (max(游戏倍率下限,基础倍率+额外暴击伤害)-1)] + 本次冻结累计伤害`

本次固定资料基础倍率为 2；真实游戏配置绑定 `critical_strike_chance`，倍率下限 1；额外倍率读 `critical_strike_damage_bonus_percent`。通过新增完整作者公式表达上述运算，原等级参数和原 `bonus_damage` 表达式保留。新伤害 `critical.mode=DISALLOWED`、`multiplierValue=null`，避免整段再次暴击；`deliveryKind=BASIC_ATTACK`、`originKind=DIRECT`、`vampQualification=RESOLVED`，不声明 `attackDamageRole`。普通主体继续结算一次，Q 只产生一个额外伤害实例，累计项不暴击、不重复加总攻击力。

宿主在 `adaptProcessProgram` 中根据真实 START 绑定及本过程 START 的 SET，机械建立“运行参数 → 冻结状态”映射，传给 `adaptEmpoweredProcessPayload` 的数值编译上下文。新增**编译协议**的具名公式参数来源：

```json
{"parameterKey":"q_stack_damage","valueMode":"RUNTIME_INPUT","valueType":"INTEGER","runtimeSource":{"kind":"process_start_state","stateKey":"frozen_stack_damage"}}
```

这里只示例真实数据键，通用实现不得按它分支。该来源不得带 `value`、`resourceKey`、默认值或其它字段，显式 null、未知字段、非整数参数均拒绝。只有本技能自己的技能范围 COUNTER、由同一真实过程 START 的唯一 SET 生产，且在同过程的真实待击负载中读取才合法。首版不放开任意供值器状态读取，也不改共同公式表达式协议；只是给既有参数目录增加一种供值来源。

### 3. R 上限与同批提交

新增 resource_max 的严格模型字段/准入和编译计划；普通 attribute resolver 不得把该修正写进 Resolved 后冒充 Max。先版只收第一章的静态有限 hp 加算及唯一当前值策略，编译绑定实际生命槽位。

运行时为每个实际拥有者保留**未含本类动态修正的生命上限锚点**；初态锚点取传入 hp.max，已经包含场景等级和静态装备贡献，不取 hp.Base再丢掉装备、不把装备 HP 供值器重复计入。动态贡献按实际 provider 实例记录，新的上限等于锚点加本类所有有效贡献。不会在每次属性重算时继续累加；首版拒绝本类百分比/动态生命派生，不能声称同时支持尚未接入的其它上限层。

资源批次定义为**同一 executionFrame 内连续的供值器变更段**。在首次任何数值读取、伤害、治疗、采样或提交之前，必须先结算当前待处理批次；该批次取其最终有效贡献集合，以旧→新总上限的**净差值**处理。跨过该可见边界后又有供值器变更，则开启下一批，按实际操作顺序继续，不能把整个帧都合成一次净差：

- 上限增加 Δ 且当前生命 >0、对象未死亡：当前值加 Δ，再夹取至新上限；不是治疗，不触发治疗事件、吸血、重伤、治疗统计或溢出治疗。
- 上限下降、移除或到期：只将当前值夹取到新上限；不减同 Δ、不按比例换算。当前为 0 或已死亡始终不复活。
- 同值刷新净差为 0，不回血。旧贡献 300 换成 450 只给 150；同一个 provider 的刷新/替换是一次不可见中态的原子操作，不能拆成先移除再施加的两个批次。R 三结果仍是一次 provider 挂载。
- 同一连续变更段的多个移除/替换一起算最终净结果；若两次操作之间有可见数值读取，则如实结算两个批次，允许产生两个真实资源变化，不能在帧末回溯改写已经结算的伤害或读取结果。

全过程处于现有 executionFrame 的预检/暂存/提交边界，每个批次在上述结算点生成暂存生命变化，后续读取、护盾/伤害/公式、快照与采样看到当前批次之后的同一套 Max/Current/Resolved；`hp.Resolved` 仍同步 Current，MAX 读取 Max。provider commit 不能再次结算已经处理的增量。即使帧内已有多个结算点，后续出错仍回滚**整个帧**，丢弃全部暂存资源事实和累计。惰性过期与清理事件共享幂等的贡献移除，重复清理无效果；同刻不同事务继续遵守现行事件次序，不擅自合并事务。

首版只允许 apply_provider 在运行期建立本类动态贡献；新场景初态不得已挂载本类动态 provider。把含活动资源上限实例的最终快照直接作为新初态，应明确拒绝，避免把已增加的 Max 当新锚点、重复给当前值；本轮不新增任意战斗存档恢复协议。同一会话的新运行仍从各自明确场景初态开始，互不继承动态贡献。

例：生命 500/1000，加装备 500 时场景上限已为 1500；R+300 后为 800/1800。受到 200 伤害后为 600/1800，同值刷新不变，到期为 600/1500。未受伤、满血 1500/1500 开 R 为 1800/1800，到期为 1500/1500。0/1500 开效果仍是 0/1800。双抗各增加 40 后与生命在同一挂载生效，刷新不重复增加。

批次例：锚点1000、已有贡献300、当前1200/1300。连续移除300并施加300，中间无可见读取，净差0，仍1200/1300且不造资源记录。若移除后先读取，第一批得到1000/1000（currentDelta=-200、maxDelta=-300）；再施加300并读取，第二批得到1300/1300（+300、+300）。若两个批次之间实际受伤100，则中间为900/1000，第二批后1200/1300，伤害仍按当时1000生命结算；不能拿最终相同上限抹掉中途的夹取、伤害或增益。

**独立生命事实与累计（新增输出协议）。** 现有 provider evidence 会截断，且不含足够的 Max/Current 前后值；不能拿它替代生命账。新增 `DoneResult.resourceChangeRecords`、`DoneResult.resourceChangeSummary`。启用边界明确为编译会话具有 resource_max 授权：具有授权但未触发时输出零累计/空明细；旧会话完全无新字段且输出逐字节保持，包括 resourceChangeRecords/Summary、healthOrder 和 recording 新字段均省略。每个实际拥有者/每个有变化批次在结算点生成一条暂存事实：`healthOrder`（本运行统一严格递增顺序）、`timeMs`（沿现行记录命名，毫秒）、`target`、`resourceKey=hp`、`currentBefore/currentAfter/currentDelta`、`maxBefore/maxAfter/maxDelta`、`contributors`。contributors 每项明确 `source/providerRef/definitionRef/modifierKey/reason`，已知使用归属另有 useRef；modifierKey须对应真实编译resource_max修正并由宿主覆盖表回到作者结果。reason为apply/refresh/remove/expire，同批有多项逐项列明，不能任意归属给最后一个技能。施加时保留实际来源供到期使用，不能伪造到期时又施法。净Current/Max均0不造事实；currentDelta=0但maxDelta非0仍须有独立可核上限事实。

所有 delta 均为有符号的 after−before，出现增益为正、到期夹取可为负。同刻伤害、直接治疗、资源变更共用 healthOrder；新机制场景的伤害和直接治疗记录同步加该可选字段，吸血继续包含在伤害记录已有来源生命前后值内，不能再重复加一条治疗。healthOrder在批次结算点按实际数值可见顺序生成，不能留到帧末重排；失败帧的事实和累计全部丢弃，允许全局顺序值有回滚造成的空号但不能重复或逆序。不把同刻仅按时间碰巧接得上的记录当作归属证明。

`resourceChangeSummary` 固定包含 changeCount 及 source/target 的 `currentIncrease/currentDecrease/maxIncrease/maxDecrease`（分别累计正量/负量绝对值）、finalMax；累计不依赖记录保留。recordBudget 新增 `maxResourceChangeRecords`，范围0—10000，缺省1000、显式null拒绝；缺省只在引擎内部解释，宿主不得向旧运行请求补写缺省字段而改变旧字节。recording 增加对应 count/returned/dropped/truncated，并仅在上述授权会话出现。预算0、截断与仅汇总模式保持完整累计和最终Max，明细前缀照实标截断；不填造被丢弃事实。记录缓存、summary编码/严格解析、冻结导出和生命账同时接线，新增 schema 字段必须成套验收。

### 4. 有期冷却时长倍率

ModifierDefinition 新增 `affectedAbilityRefs`，仅 kind=cooldown_duration 允许并必须为去重字符串数组，其它 kind带该字段拒绝；target=self、valuePolicy=multiply、静态有限正值、无条件、有限自身单层生命周期。编译第二阶段把完整 INITIAL 引用校验、绑定为实际拥有者/挂载/能力短编号；禁止按 public skillKey 或名字前缀进行运行匹配。空范围为确定的无匹配，不生成任何冷却修改。

在 `runtime/generic_process.go` 既有冷却提交处：先按原公式求出当前时长，读取本次真实 INITIAL 的有效倍率乘积，再统一执行原正毫秒取整和安全时间戳检查，最后写原共同账本并唤醒原等待。倍率只改变**这次新提交**的时长，不重写之前的 readyAt，也不改变后续剩余冷却操作的含义；撤销效果不再修正已经提交的值。没有匹配时走原路径，不全量扫描所有英雄或新建组合字符串热 map。

有效区间为 `[appliedAt,expireAt)`。同刻先已提交 R 再提交 Q则生效；Q先提交则不追溯。恰在 R 到期提交 Q，惰性到期检查必须使倍率无效，无论清理事件是否已执行。新挂载、刷新和移除修改该拥有者的受影响能力集合，不能误命中另一个 actor 的同名 skill/provider。多个独立有效倍率按确定性顺序连乘。

原 Q 7500ms、倍率 .5 为 3750ms；已有公式本身算出 5000ms 时为 2500ms，不伪造 +100 技能急速。原值 3ms×.5 最终一次取整为 2ms。已在 R 前提交到 7500 的 Q 不变；R 内新提交 3750 后，即使 R 中途到期也不改其 readyAt。急速本身沿原作者公式/现行支持范围，本轮不额外引入通用急速系统。
