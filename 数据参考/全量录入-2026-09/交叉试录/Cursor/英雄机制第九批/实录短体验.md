# 英雄第九批实录体验

本次实际创建 161 项，全部 POST 201 且随后 GET 一致。默认只读预检先发现 76 个已有组成，其中 19 个公共参数与候选只有说明/排序差异；执行沿原始快照保护完整原值，只比较确定数值并补缺，没有请求用户逐项确认或更新旧数据。

每次写前持久记录精确请求，成功后独立 GET，整批后又另开一次只读运行核对六类组成、主体、代表图与关系。该流程对已经稳定的管理 API 足够直接；未新增主体、图片或关系，因此没有借用其他录入任务的写权限。全部 161 个请求只有一次创建，没有因后续核算失败而重新执行。

写后首次核算误报五个特朗德尔差异，原因是旧脚本用 JSON 字符串比较：响应对象字段顺序与源文件不同，顶层组成列表顺序也可能不同。修复仅将同类组成按稳定键配对并逐字段比较；对象内部 sortOrder、公式运算元次序和其他实际字段继续严格核对。原错误报告及逐项同值证据已保存，独立重读与 1,252 项实际数据检查随后通过。

单位与资格的纠错保持到了实库：易 Q 的秒公式由效果乘 1000 变为毫秒，显式倍率 0.5/1/1.25 分别得到 500/1000/1250 毫秒；三项比例冷却效果没有落库，比例参数保留。五条未证等级曲线均为无默认输入，无法仅因缺值就计算成零；潘森 E 当前持续总伤害不被命名成每次戳刺伤害。

后续标准流程应保留三点：实际写入固定完整候选散列；公共原值与新增请求采用明确各自的比较依据；未知响应或下游核算报错先查已保存对象和流水，不能直接重跑 apply。最终 405 GET、237 组成详情、2,927 业务叶字段、333 公式算例通过，只证明管理保存与算术，不替代来源资格、运行时接线和页面验收。
