# 三项装备主动分支录入体验报告

## 本批结果

救赎、水银弯刀和中娅沙漏三个独立分支已经按冻结请求保存。救赎新增实际英雄命中规则，并把伤害公式改为直接读取目标生命值总值；水银弯刀和中娅沙漏各新增一个主动过程和一条主动使用规则。独立回读为 1062 个技能、171 条规则、73 个过程，其中来源初始化规则 29 条。

真实页面重新打开后，三个技能的代表图均为 64×64；救赎公式显示目标生命值最终值与比例相乘；水银弯刀和中娅沙漏的过程均显示主动启动、冷却参数和效果挂接；三条规则的事件、来源、英雄条件或启动过程动作均与冻结请求一致。浏览器阶段 198 次请求全部为 GET，后续全量回读 2125 次也全部为 GET，没有控制台错误、警告、页面错误、失败请求或错误响应。

## 错误恢复

原始请求在首个救赎规则写入时被后端拒绝。原因是公式仍要求技能命中事件绑定目标最大生命运行值，而该事件没有这个输入。即时定点回读确认零落地，后续六项请求没有执行。修订一把公式改为读取目标生命属性，但公式更新体误带不可变稳定标识，再次在首个请求停止，仍为零落地。

修订二仅修正更新体，使用新的冻结散列重新准备和评审。九次业务请求全部成功并即时回读。写入完成后，执行脚本因局部变量与同名函数遮蔽而在汇总阶段报错；恢复脚本只执行 GET，根据写入流水和当前对象重建即时回读证据，没有重放业务请求。该执行脚本作为已执行证据保持原样，后续复用同类执行器时必须避免使用 `const requestAudit = requestAudit(api)` 这种同名声明。

## 操作效率

本批的稳定冻结和白名单保护有效，但读取量偏大：准备、独立评审、独立回读和浏览器后回读都重新遍历了全量技能、规则和过程。它能够证明历史基线没有变化，却不适合作为每个三对象批次的默认方式。后续批次应共享一次写前全量基线，准备阶段只做目标 GET；写后保留一次独立全量回读，真实页面只检查冻结目标，不再为同一批重复多轮全量读取。

管理页面能够清楚展示图片、公式、过程和规则。页面用“最终值”展示属性模型中的总值，过程详情用“冷却时长取值”展示冷却参数；验收脚本第一次沿用旧页面文案断言时停止，改为当前页面实际中文后完整通过。数据没有因此修改。

流程稳定后，通过受保护 API 录入明显快于逐项页面保存。页面更适合作为首次试录和写后代表性验收；固定请求、来源散列、现值校验、白名单写入、即时回读及失败后的按键回查应继续由脚本执行。

## 系统结论

救赎暴露的问题不是缺表，而是公式取值方式不合适。现有公式模型已经能够读取目标生命值总值，因此无需扩展命中事件或新增表。水银弯刀的解控与浮空例外、中娅沙漏的不可选取与行动限制仍缺少通用状态或运行时语义；本批只保存来源明确且现有系统能正确表达的移动速度和伤害免疫分支。

当前证据只证明管理配置持久化和页面展示正确。宿主是否生产实际命中或主动使用事件、过程冷却是否在战斗中执行、Wasm 是否组装这些配置以及真实对局结果均未验证。

本次恢复服务时，当前 Windows 与 Java 的本地域套接字连接异常导致 Tomcat 首次启动失败；使用只作用于当前进程的套接字临时目录回退后启动成功，没有修改项目配置或业务数据。该环境问题与三项配置结论无关。
