Chapter 01

先建立正确心智模型

把它看成“规则编译器 + 离散事件模拟器”，而不是一个接收技能 ID、返回伤害数字的函数。

Damage Viewer 的 Wasm 核心不联网、不读数据库、不认识“某个英雄应该特殊处理”。宿主先把英雄、装备、符文、状态等材料整理成 canonical JSON；Wasm 再把规则编译成只读 session，基于一次初始快照完成一次确定性 1v1 模拟。

因此你要用三层问题来阅读源码：

  1. 规则是什么？——由 model 描述，由 compile 验证和预处理。
  2. 这一刻发生什么？——由 scheduler 排序，由 runtime 推进。
  3. 数值怎样合法落地？——由 operation → command → pipeline 统一结算。
一句话版本 Compile 把人类可编辑的规则变成机器易执行的只读索引；Run 把一次战斗快照变成有序事件；Pipeline 保证所有数值变化遵守同一套语义。
图 1 · 系统边界左边准备数据，中间计算，右边消费结果
设计意图：把网络、缓存、版本协商、UI 编排留在 JS/Worker，把 Wasm 保持成纯计算内核。这样相同输入与相同 Wasm 版本可以复现相同结果，也能在 Node smoke 中复用同一 ABI。
先别误会正式宿主是浏览器 Worker；scripts/*.mjs 只是本地/CI 验证。当前 run 是同步完成的单次计算，不是可以暂停、逐帧继续的 step-loop。

  • Node 脚本是否被误当成正式宿主？正式超时、取消与重建边界属于浏览器 Worker。

Chapter 04

ABI：frame、memory、outbox

ABI 是两种运行时之间最小、最稳定的边界。这里传的是 bytes，不是 Go 对象。

internal/abi/frame.go

16-byte header

主链frame 固定为 Magic(4) + SchemaVersion(2) + Kind(2) + Flags(4) + PayloadLen(4)，后接 UTF-8 JSON payload。坏 magic、版本不匹配、长度越界都会在进入业务层前失败。

internal/abi/memory.go

unsafe bridge

主链用 TinyGo 线性内存指针在 []byte 与 uint32 之间转换。它只处理内存视图，不解析业务 payload。

internal/abi/memory.go

internal/abi/outbox.go

1 MiB fixed capacity

主链返回 frame 写进固定容量 outbox。终态 compile_result/done/error/snapshot/release_result 是 priority frame：空间冲突时可清掉旧内容，优先保证关键结果可被宿主读到；非优先帧允许丢弃并计数。

设计意图：Provider 负责“能力从哪里来、活多久、共享什么状态、监听什么事件”；Ability 负责“一次可以尝试和执行的行为”；Operation 负责“最小可结算动作”。把三者分开后，英雄、装备、符文和临时状态都可以复用同一执行内核。

设计意图：把字符串解析、引用校验、公式编译和 matcher 构建的成本放在 compile，一份只读 session 可以被多次 run 复用。错误也能一次返回多条路径，而不是用户修完一个字段再遇到下一个。

  • 新的引用是否在 compile 期被解析并 intern，而不是每个事件里用字符串搜索？
  • 有错误时是否绝不产生可运行的 CompiledSession？
  • compile 是否保持纯规则转换，不创建 event queue 或 mutable runtime state？
  • 新增公式 read path、type domain 或 operation 是否有明确 compile-time 拒绝条件？

Chapter 08

Run 与 Scheduler：跳到下一件事

引擎不逐毫秒扫描。它把“未来会发生的事”放进稳定最小堆，每次直接跳到下一个事件时间。

RunGeneric 只有三步：创建 genericRunState、执行 runLoop、构建 DoneResult。初始化时从 initial snapshot 物化双方战斗状态，合并 compile/run 安全预算，然后播种 driver attempt、sample、expire cleanup 与 provider tick。

图 5 · 同一 timeMs 的固定顺序category order 是战斗语义，不允许配置覆盖
1. Anchored tick目标状态到期点仍可见
2. Expire cleanup清理过期实例
3. Provider tick普通周期能力
4. Ability attemptdriver 尝试施法
5. Continuation延迟 repeat 回放
6. Sample记录结算后状态

排序键是 timeMs + category + priority + seq。seq 是单调递增的最终稳定键，所以相同输入不会因 Go map 遍历或插入偶然性改变事件顺序。源码：internal/scheduler/generic_heap.go。

两个 Schedulerinternal/scheduler 是业务事件堆；构建参数 -scheduler=none 是关闭 TinyGo 的并发调度器。两者同名但完全不是一件事。

设计意图：离散事件模型只为“真的会发生的点”付费；稳定排序把并发式的游戏语义压成单线程可复现顺序。预算则为触发环和异常配置提供有界停止。
队列边界的当前缺口GenericHeap 有 100,000 的硬上限，但 DTO 中的 maxQueueEvents 尚未接入运行时；continuation push 会检查错误并 fail-closed，部分 driver/sample/provider/expiry 播种路径仍忽略 Push 返回码。因此不能笼统宣称“所有 heap overflow 都严格 fail-closed”。
当前实现与优化目标设计边界偏好短 ID、bitset、arena/索引；但当前 runtime 为了正确性仍大量使用 map 与深拷贝。不要把“目标约束”误写成“已经完全无 map 分配”。性能优化必须以现有 benchmark 和等价行为为前提。

Chapter 09

Gate 与 Execution Frame：先判断，再原子结算

一次 ability attempt 不等于一次成功 cast。Gate 只回答“现在能不能施放”，Execution Frame 才负责“施放后发生什么”。

图 6 · 一次技能的 staged 边界commit 前失败不写 staged combatant；这不是完整 ACID rollback

Gate 的顺序

generic_gate.go 集中检查 target 是否存在、cooldown 是否 ready、资源是否足够、driver/ability condition 是否为真。失败不是 fatal，而是带原因的 attempt_skipped；while-ready 或 dynamic repeat 可以据此安排下一次尝试。

Frame 为什么像事务

executionFrame 为涉及的 combatant 创建 staged copy。cost、cooldown、damage、resource 与 provider mutation intent 先进入 frame；在 commit() 之前遇到公式非 finite、target 不合法或预算超限，不会把 staged combatant 写回 live state。

准确边界不是完整数据库事务：commit() 先复制 staged combatant，再执行 deferred provider mutation；provider mutation 在 commit 内失败时，本次 run-local state 可能已有部分写入。随后 listener/child frame 也可能失败。但宿主只会收到 done 或 error 二选一，失败 run 不输出可复用 finalSnapshot，下一次 run 仍从新的 InitialSnapshot 开始。

设计意图：先 staging 能阻止大多数 operation 在校验失败时把半成品直接写入 live combatant；run 的对外结果仍保持 success/error 二选一。把 gate 单独集中也避免不同技能各自发明 cooldown/resource 条件。

Chapter 10

Provider、Ability、Listener：能力从哪里来

这是扩展英雄、装备、符文、状态机制的主落点。引擎扩展的目标不是多写 switch，而是组合已有对象。

Provider

ownership + lifecycle

表示一组能力的来源和共享生命周期：可以是 champion、item、rune、status 或 system。它拥有 abilities、modifiers、listeners、lifecycle 和 provider state；combatant 挂载的是 provider instance。

Ability

attempt + execution

表示一次可尝试的行为或被动行为：active、passive listener、aura modifier、tick、stateful。它拥有 params、cost、cooldown、condition、operations 和可选 TickSpec。

Listener

event → child behavior

用 TypeSet matcher 订阅事件，命中后执行自己的 operations，或按 abilityRef 启动完整 child ability。它不直接改 live store，仍然进入 execution frame。

Provider state

shared mutable state

保存层数、计数、目标绑定、过期时间等跨 ability 的共享状态。结构化 schema 在 compile 期规范化；runtime 通过 state bag、作用域与 policy 读写。

两种 tick

模式何时启动适用场景源码
普通 provider tickmount/run 初始化后按 startDelay + interval持续光环、固定 DoT、周期资源变化generic_provider_tick.go
target-state anchored tick第一次合格 provider_target state 写入后启动；刷新重启 cadence依赖目标上临时状态窗口的周期效果generic_anchored_tick.go

Anchored tick 同一时刻排在 expire cleanup 前，是为了实现“到期时刻仍可在本次公式/管道窗口可见”的 inclusive-at-expiry 语义，而不修改全局过期规则。

当前 tick 限制findTickAbility 只返回一个 Provider 中遇到的第一个 kind="tick" Ability。不要把文档写成“同一 Provider 的多个 tick ability 会自动全部运行”。

Cast identity 与延迟 repeat

每次成功的顶层 cast 会获得单调 castInstanceId 和可选 castOrigin；同一 frame 内多 operation 继承身份。listener 的 perCastThrottleMs 用这份身份限制同一 cast 的触发频率，而不把重叠 cast 混在一起。

copyable-on-hit 的 repeat 不重新跑原公式：真实命中时冻结 raw、crit、entry attrs 和 provenance。repeatDelayMs=0 在事件局部 flush；正延迟则排入 GenericCategoryTriggeredContinuation，到时应用冻结的 phantom damage，不再次收集或 repeat。

相关源码：generic_provider.go、generic_provider_state.go、generic_cast_context.go、generic_execution.go。

设计意图：所有机制差异尽量落在数据与组合关系里：Provider 决定所有权和生命周期，Ability 决定执行入口，Listener 负责因果连接，Operation 负责最小动作。这样新增机制通常是新增规则数据与小型通用语义，而不是新增英雄专用 runtime。

Chapter 11

Formula 与 TypeSet：让规则可计算、可匹配

公式回答“值是多少”，TypeSet 回答“这是什么、是否匹配”。两者都在 compile 期收敛，run 期只消费紧凑结果。

Formula

formula/generic.go 把 JSON AST 编译成简单指令序列；generic_eval.go 用显式 context 求值。支持常量、read、ref、算术、min/max/clamp、round/floor/ceil/trunc 与比较。

read path 是能力边界：source/target attr/resource、ability params、provider state、event entry/emit snapshot、damage context 等必须显式允许。没有 event context 却读取 event.* 会结构化失败，不偷偷返回 0。

TypeSet

typeset.go 用 4 个 uint64 组成 256-bit 精确集合；matcher 支持 any/all/none。typeset/generic.go 校验 key 的 domain 与有限 relation。

这不是 Bloom filter。战斗触发不能接受假阳性；一次错误命中会真正多打一段伤害。

公式 JSON AST                  Compile                   Run
{ op: "mul", ... }  ───────→  []GenericInstr  ───────→  float64 / structured error

type keys                      Compile                   Run
["event/damage_instance"] ─→  256-bit TypeSet  ──────→  matcher.Match(types)
设计意图：把规则作者需要的表达力限制在一个可验证、确定性、无反射的 DSL 中；把字符串 type 变成精确 bitset，既减少运行期开销，也避免“字符串拼错但静默不生效”。
新手常见错误不要把 formula 当成任意脚本语言，也不要把 type relation 当成运行期自动继承。实体真正拥有的 canonical type 必须显式列在 payload 中。

Chapter 12

Operation 与 Pipeline：数值只能走正门

Operation 是规则世界的“动词”，Command 是结算层的规范化请求，Pipeline 是统一数值语义。任何 raw set HP 都会绕过护盾、抗性、证据与统计，因此被禁止。

一次 damage 的实际顺序

图 7 · Damage pipeline每一步都有明确输入与证据语义
Formulabase raw
Expected crit仅 critEligible
Outgoing modssource/provider
Resistance含 penetration
Incoming modstarget/provider
Shieldspriority absorb
HP clipping落地 + evidence

物理伤害读取 target armor.resolved，魔法伤害读取 magic_resist.resolved，真实伤害跳过抗性与穿透。正抗性使用 100/(100+R)，负抗性使用 2-100/(100-R)；source 侧 percent penetration 先于 flat penetration。

command.Result.Amount 与 summary damage 记录的是抗性后、护盾前的伤害；护盾吸收和 HP clipping 之后，目标实际掉血可能更少。Review 图表时不要把这三个数混成一个含义。

如果 operation 显式 critEligible=true，当前策略是确定性的 expected crit，而不是 RNG：base × ((1-p) + p×multiplier)。缺失或非 finite 的 crit 属性会失败，不静默造默认值。

职责切分

模块职责不应该做
runtime execution解释 compiled operation、求公式、维护 staged frame、发事件绕开 pipeline 直接改 live HP
command把 damage/heal 等规范化为最小请求与 result持有完整战斗状态
pipeline resolver抗性、穿透、护盾、HP clipping、heal/execute 结算产生新的额外伤害 command
damage modifiers按 stage/channel/priority 收集并修改当前 command 数值偷偷触发另一条 ability
attribute resolver挂载 provider modifier，按 policy 解析 resolved 属性把 bucket 当 slot 存储
设计意图：“额外效果”通过 listener/ability/operation 显式表达；pipeline modifier 只改变当前 command。这样事件数量、预算、evidence 与触发链始终可观察，不会在 resolver 深处凭空多出伤害。
禁止项不要直接写 HP，不要让 listener 直接写 runtime store，不要让 pipeline modifier 产生新 command。三者都会绕过统一结算和事务边界。

Chapter 14

输出、证据与采样

前端拿到的不是一串调试日志，而是可以直接画图、对比和解释的结构化 DoneResult。

DoneResult
├─ ok
├─ summary
│  ├─ stopReason / durationMs / final HP
│  ├─ 双方 damage dealt / taken / overheal
│  └─ attempt / cast / skip + abilityStats[]
├─ finalSnapshot
├─ series[]                  // chart-ready 时间序列
├─ warnings[]                // 面向用户的摘要
├─ evidence                  // 机器可追踪事实
└─ seriesSamplingEvidence    // 是否降采样、采用何种口径

三种输出不要混用

输出用途不能替代
summary / series图表、对比、最终结论；shape 稳定且 chart-ready不能解释每个跳过或截断原因
warnings向用户提示 budget、downsample、truncation 等降级不是每个机制事件的完整日志
evidenceattempt skipped、damage、provider tick、listener 等可追踪事实不能被倒推成唯一 runtime state 来源

“快照”其实有五种语义

快照时间点用途
CompiledSessioncompile 结束只读规则快照，不含战斗现场。
InitialSnapshotrun 开始宿主显式提供的本次战斗起点。
FinalSnapshot成功 run 结束从 live run state 组装的结果，不携带队列与 driver 进度。
entry_* / event.*frame 创建 / emit 当点公式在 cost/CD 前与 emit 当点读取稳定上下文。
frozen damage/replay真实命中当点延迟 repeat 复用 raw、crit、entry resistance 与 provenance，不重跑原公式。

sample 本身是 scheduler event，同一时刻默认最后执行，所以 series 记录的是该时刻所有战斗变化完成后的状态。超出 MaxSeriesPoints 会稳定降采样，并在 warning 与 sampling evidence 中公开；evidence 超限则截断并记录计数，而不是无限占用内存。

预算不是同一种失败

情况结果
MaxEvents 达到优雅收口为 DoneResult.OK=true，stopReason=budget_exceeded，带 warning/evidence。
evidence / series 超限截断或降采样，正常 done，并公开降级证据。
commands per event / chain depth 超限runtime_invariant_failed，返回 error，不生成 DoneResult。
session/hash 错配入口处拒绝，结构化可恢复错误。

源码：model/generic_run_output.go、runtime/generic_run.go · buildDoneResult。

设计意图：把“用户需要的结论”“系统需要的降级提示”“工程师需要的事实证据”拆开。UI 不必扫描底层日志重新拼主时间线，runtime 也不依赖日志恢复状态。
Error 通道run fatal 返回单个结构化 EngineError，不会同时假装给一个正常 done，也不会把半成品 finalSnapshot 当作可续跑状态。

架构 Review 的 12 个问题

  1. Wasm 是否仍只消费准备好的 canonical payload，没有越界联网、查库或承担 UI 编排？
  2. 导出层是否仍然薄，业务逻辑是否都在 internal 层？
  3. 新增公共字段是否完整贯穿 model → compile → runtime → output / validation？
  4. 进入已知 schema 后，compile 是否 collect-all，并且失败不注册 session？
  5. run 是否同时校验 sessionId 与 expectedRulesHash？
  6. 每次 run 的 mutable state 是否隔离，没有跨 run 泄漏？
  7. 事件排序是否仍是固定 category + priority + seq，新增类别是否明确同刻语义？
  8. ability gate 是否集中处理 target/cooldown/resource/condition？
  9. 所有状态改变是否先 stage，fatal 时是否不会半提交？
  10. 所有 HP/资源/属性变化是否经 operation/pipeline，而不是 raw write？
  11. listener/repeat 是否有 chain/command/event 预算以及稳定 provenance？
  12. Go test、native bench、build、Node smoke 是否按变更风险覆盖到真实边界？

当前值得记住的结构性风险

风险为什么Review 态度
generic_execution.go 过度集中2,764 行，汇合 operation、damage、event、listener、repeat；修改影响面大。先补调用链与测试证据，再考虑行为保持的职责拆分。
runtime map / clone 成本当前正确性优先，和“热路径短 ID/arena”目标仍有距离。只用 benchmark 识别真实热点，不做审美式微优化。
队列设置未完全接线maxQueueEvents 未实际控制 heap，且部分 push 错误码未消费。新增事件来源时显式审计 Push 结果；不要过度宣称 fail-closed。
Provider 只自动选择首个 tick abilityfindTickAbility first-match 返回。规则数据避免同一 Provider 声明多个期待自动调度的 tick，除非先扩展通用语义。
同步 run 的取消边界单次 run 内没有逐事件宿主 cancel。Worker 做墙钟超时与 terminate/recreate；不要伪装成可中断 step-loop。
孤岛 package 的完成错觉augment/control/mark/trigger 存在，但未接主链。文档必须写“独立/预留”，直到 production call chain 可证。
256 MiB 内存基线换稳定延迟，但不是低配兼容方案。任何下探都要同时给同口径包体、延迟与行为证据。
